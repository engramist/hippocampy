# B255 - Plugin Installation Path (`campy install --plugin`)

State: complete -- re-verified 2026-08-03: functionality is real and tested (14/14 tests pass: tests/cli/test_plugin_installer.py, test_doctor_plugin.py, test_install_plugin.py, test_install_plugin_integration.py, tests/test_installer_idempotency.py), but AC1/AC3's literal `campy install --plugin` flag never shipped -- see Verification Findings below for the corrected design and AC4 caveat
Priority: P0

Plan: backlog/plans/B-255-plugin-installation-path.md

### Problem

The Campy daemon is running and collecting data from 4 agents (Claude Code, Codex, Gemini CLI, VS Code), but no agent ever recalls from memory. The plugin at `plugin/` was built but never wired into `campy install`. The CLI install path starts the daemon but doesn't install the plugin into any agent. Agents don't see the memory tools.

### What This Card Does

Extends `campy install` to detect installed agents and install the Campy plugin (MCP server config + skills) into each. Adds a `--plugin` flag and updates `campy doctor` to check plugin installation status.

### Dependencies

- None (foundation card)

### Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Plugin install mechanism | Per-agent detection + config injection | Each agent has different config paths; reuse existing `detect.py` and `register.py` |
| Idempotency | Re-run updates but doesn't duplicate | Same pattern as existing `campy install` |
| Claude Code plugin install | `claude plugins add <path>` CLI or copy to `~/.claude/plugins/` | Uses Claude Code's native plugin system |
| Doctor integration | Add plugin status checks | Operator can verify plugin is connected |

### Acceptance Criteria

- [x] `campy install --plugin` detects Claude Code, Codex, Gemini CLI, VS Code and installs plugin for each detected agent (~~AC text stale~~ — see finding below: shipped as automatic Step 9 of `campy install`, not a `--plugin` flag)
- [x] `campy doctor` reports plugin installation status per agent
- [x] Running `campy install --plugin` twice is safe (idempotent) (~~AC text stale~~ — verified idempotent via the actual shipped mechanism)
- [~] Plugin's `.mcp.json` connection to `http://127.0.0.1:7799/sse` is verified working (config exists and is correct in spirit, but points at `/mcp` not `/sse`, and live connectivity was NOT verified — daemon not running in this environment)

### Verification Findings (2026-08-03)

**AC1 and AC3 text is stale relative to the shipped design, but the underlying capability is real:**
- There is no `--plugin` flag on `campy install` (`campy/cli/main.py:179` — `install()` takes only `plugin_dir`, no boolean `--plugin`).
- Plugin installation for all 4 agents is instead wired in automatically as **Step 9/10 "Plugin Skill Distribution"** of the main `campy install` flow (`campy/cli/install.py:1282-1288`), which calls `install_plugin_for_agents()` unconditionally — so every `campy install` run already does what AC1 describes, without needing a flag.
- A separate `campy install-plugin` command also exists (`campy/cli/main.py:193-204`) as an explicitly `[DEPRECATED]` standalone entry point to the same `install_plugin_for_agents()` function, kept for compatibility. `campy/cli/plugin_installer.py` itself emits a `DeprecationWarning` on import pointing at `campy setup`.
- Ran the real (non-mocked) test suites covering this: `PYTHONPATH=<worktree> .venv/bin/python -m pytest tests/cli/test_plugin_installer.py tests/cli/test_doctor_plugin.py tests/cli/test_install_plugin.py tests/cli/test_install_plugin_integration.py tests/test_installer_idempotency.py -v` → **14/14 passed**, including `test_install_is_idempotent` and `test_bootstrap_dry_run_twice` which directly cover AC3's idempotency claim.
- `campy doctor` confirmed to have a real `_check_plugin_status()` check (`campy/cli/doctor.py:44,296-341`) that reports per-agent plugin status (AC2, unambiguously met).
- Recommendation: reword AC1/AC3 in a future pass to describe the actual shipped surface (`campy install` Step 9, or deprecated `campy install-plugin`) rather than a `--plugin` flag that was never built. Not treating this as "needs work" because the described *capability* (detect 4 agents, install plugin per agent, idempotent) is genuinely implemented and tested — only the invocation syntax in the AC text is wrong.

**AC4 caveat:** `plugin/.mcp.json` exists and configures `"type": "http", "url": "http://127.0.0.1:7799/mcp"` — functionally the same connection intent as the AC (daemon's MCP endpoint), but the literal path is `/mcp` (streamable HTTP), not `/sse`, reflecting a transport change since the card/plan was written. Could not live-verify "working" — the daemon is not running in this environment (`curl http://127.0.0.1:7799/mcp` → connection refused). Config correctness confirmed by static read only.
