# B325 - Remote MCP Server Surface with Pluggable Auth

State: todo
Priority: P0

Plan: (inline — self-contained, sized for a Sonnet-level implementer)

Depends on: **B315** (`PrincipalResolver` protocol — this card adds an implementation and is
the first real consumer of that seam). Composes with **B316** (workspace routing) and
**B318** (fail-open).

### Why

B315/B316/B324 make Campy *deployable* into a customer's AWS account. **Nothing makes it
reachable.** That is currently a hole in the cloud plan: a container running Campy that no
remote agent can call is not a service.

The immediate consumer is an external platform whose Layer-3 agents run on AWS Bedrock
AgentCore, reached through their own governed tool plane —
`ecosystem/shared-infra/agentcore-gateway/`, described in their standards as a *"shared,
IAM-authenticated MCP tool plane between AgentCore agents and governed tools/adapters."*
Campy registers there as a target rather than integrating with each agent.

**Build the generic surface, not an AgentCore adapter.** Every serious agent framework speaks
MCP now, so one remote transport serves AgentCore, Strands, LangGraph, CrewAI and the six
existing local harnesses. An AWS-specific integration would also directly contradict the
project's stated positioning (`docs/marketing-positioning.md`: works across harnesses, across
providers, local or cloud). AgentCore Gateway is this card's first consumer, not its API.

### Current State (verified in code)

Campy has **no remote surface at all**, and the locality is deliberate rather than accidental:

- `campy/adapters/mcp_server.py` — **stdio only**. A local process bridging to the daemon over
  a unix socket (`_call_brain`, `_socket_path`).
- `campy/brain_daemon.py:303` `_start_web_server` — FastAPI Memory Control Panel, bound
  `host="127.0.0.1"` with the comment `# NEVER 0.0.0.0 — local-only by design`.
- `web/server.py:4` — *"FastAPI server bound strictly to 127.0.0.1 — never 0.0.0.0."*
- Clients (`brain_transport.py:17`, `cli/recall.py:29`, `cli/smoke_test.py:107`,
  `cli/install.py:947`) all expect `http://127.0.0.1:7799/mcp`, but **no route serving `/mcp`
  could be located under `campy/`**. It may live in `extensions/` or `mcpb/`, or be stale.
- **Nothing on any transport is authenticated.** The unix socket relies on filesystem
  permissions; the HTTP surfaces rely on being unreachable.

`_dispatch` (`brain_daemon.py:217`) advertises `"protocolVersion": "2024-11-05"`. Streamable
HTTP was introduced in the **2025-03-26** MCP revision, so this card implies a protocol version
bump — call it out explicitly rather than changing the string quietly.

### The safety property this card must not get wrong

Campy stores a customer's accumulated memory. Exposing it on a non-loopback interface without
authentication would be a serious breach, and it is a one-environment-variable mistake.

**Binding to any non-loopback address while no auth resolver is configured must be a hard
startup failure.** Not a warning, not a log line — refuse to start, with an error naming both
the bind address and the missing auth configuration. This is the single most important
requirement in the card; everything else is plumbing.

### What This Card Does

**Task 0 — Find or bury `/mcp`.**

Locate whatever serves `127.0.0.1:7799/mcp`. Search `extensions/`, `mcpb/`, `adapters/`,
`web/`, and `packaging/`. Three possible outcomes, all acceptable — report which in the PR:

1. It exists → this card extends it rather than adding a parallel endpoint.
2. It does not exist and clients are broken → say so; that is a separate bug worth its own card.
3. It exists outside `campy/` → decide whether to absorb or keep it, and state the reason.

Do not build a second `/mcp` next to an existing one.

**Task 1 — Streamable HTTP MCP transport.**

Serve MCP over HTTP per the 2025-03-26 streamable-HTTP transport: a single endpoint accepting
`POST` for JSON-RPC and supporting SSE for server→client streaming, with session handling per
the spec.

- **Reuse `TOOL_HANDLERS` unchanged.** The tool surface must be identical to stdio and socket —
  same names, same signatures, same results. Do not fork the tool list per transport; a
  divergence here is how the two deployments start drifting.
- Route through the same `_dispatch` path so principal derivation, the forbidden-key guard
  (B315) and workspace routing (B316) all apply identically.
- Bump the advertised `protocolVersion` and confirm the existing local adapters still negotiate.
  If any pinned client breaks, keep the old version for stdio and advertise the new one only on
  HTTP, and say so in the PR.

**Task 2 — Bind address as explicit, guarded configuration.**

```
[server]
bind_host = "127.0.0.1"    # default unchanged
bind_port = 7799
auth      = "none"          # "none" | "iam" | "oidc"
```

Rules, enforced at startup:

- `bind_host` defaults to `127.0.0.1`. **A local install must behave exactly as it does today.**
- `bind_host` not in `{127.0.0.1, ::1, localhost}` **and** `auth = "none"` → refuse to start.
- `auth != "none"` with a loopback bind is fine (useful for testing the auth path locally).
- Log the effective bind address and auth mode at startup, every time. An operator should never
  have to guess whether the thing is exposed.

**Task 3 — IAM/SigV4 resolver.**

Implement `IAMPrincipalResolver` against B315's `PrincipalResolver` protocol:

- Verify the SigV4 signature on the inbound request and extract the calling IAM identity.
- Map the caller ARN to `Principal` fields — `subject_id` from the ARN, `tenant_id` and
  `workspace_id` from a configured mapping or a session tag.
- **Workspace still never comes from request params** (B315's rule). If the Gateway passes
  workspace as a session attribute, that is a transport-level credential and acceptable; if it
  would arrive in the JSON-RPC body, it is not.
- Construct `TransportContext` in the HTTP handler *before* the body is parsed, exactly as
  B315 does for the socket path.

Keep `boto3`/signature verification an optional import, as B324 does — a local user must not be
made to install AWS libraries.

**Task 4 — Document AgentCore Gateway registration.**

A short `docs/deployment-agentcore.md`: how Campy is registered as a Gateway target, what IAM
policy the Gateway role needs, how workspace maps to the caller, and how to verify end to end.

**Open question — the Gateway target type is not yet known.** It may be an MCP target, an
OpenAPI target (Gateway converts a spec into tools), or a Lambda target (a shim invokes Campy).
The streamable-HTTP surface is required in all three cases, so this card is not blocked, but
the registration doc cannot be finished until the platform team answers. Write what is known,
mark the target-type section explicitly as pending, and do not guess.

**Task 4b — The AWS deployment path is Lambda-fronted, not a direct MCP target.**

The customer's architecture review (2026-08-15) established that Task 4's assumption is wrong
for their platform, and the constraint is policy-enforced by a machine check:

- **ADR-0031 decision #3**: *"Targets are Lambdas wrapping ecosystem adapters — Layer 6/5
  adapter code is reused server-side as the Lambda implementation. Adapters are never
  reimplemented per-gateway."* Their single registered Gateway target is
  `target_configuration.mcp.lambda` (`targetType: LAMBDA`). No MCP-server target is registered
  anywhere, though the provider supports one.
- **Gate check #8** (`agent_harness_schema.py:35`, `_ADR_REQUIRED_TYPES`): a `harness.json`
  wiring a `remote_mcp` tool **without a cited ADR is a HIGH finding**, and their Layer-3
  review lens flags *"a custom MCP server without review"* as an ADR-0031 violation regardless
  of whether the gate caught it.

So an ecosystem agent cannot point at Campy's HTTP surface directly. Note this is a **policy**
constraint rather than a technical one — the AWS provider supports `mcp.mcp_server` targets and
their own rule names the escape hatch (cite an ADR). Both paths are legitimate; the platform
picks.

**This does not change the work in Tasks 1–3.** The transport, the bind guard, and the IAM
resolver are needed for every non-AWS consumer and for the Lambda to talk to. What changes is
the deployment topology documented in Task 4:

```
AgentCore agent → Gateway (AWS_IAM) → Lambda (thin adapter) → Campy HTTP MCP surface
```

The Lambda is a thin proxy: it receives tool arguments plus the tool name in
`context.client_context.custom["bedrockAgentCoreToolName"]`, and forwards to Campy. **Do not
reimplement tool logic in the Lambda** — that is precisely what ADR-0031 forbids.

Two unresolved items to record in the doc rather than guess at:

1. **Identity does not propagate through their Gateway today.** It invokes with its own service
   role (`gateway_iam_role {}`), and `metadata_configuration` is never set, so neither caller
   identity nor session attributes reach the target. Their ADR-0031 accepts this as a known
   risk. The provider supports `caller_iam_credentials` and `metadata_configuration`; both are
   unused. Until one is enabled, **B315's rule that workspace derives from the transport
   credential cannot hold behind their Gateway** — the only channel is the request body.
   Document the fallback: a short-lived signed token minted by the platform backend, scoped to
   one workspace, is categorically different from a plaintext `workspace_id` and preserves the
   rule's intent. Do not implement the fallback in this card; record it as the open decision.
2. **Kùzu is single-process-writer**, so a Lambda cannot open the database file directly —
   several concurrent invocations would contend for exclusive access. The Lambda must proxy to
   a long-running Campy process, which is why the HTTP surface is the prerequisite rather than
   an alternative to it.

Write both into `docs/deployment-agentcore.md` alongside the target-type answer. The doc stays
marked pending until the platform answers on `caller_iam_credentials`.

**Task 5 — Do not regress local.**

The existing stdio adapter and unix socket path stay exactly as they are. A local install
upgrading through this card must see no behavioral change: same default bind, same absence of
auth on loopback, same tool results.

### Acceptance Criteria

- [ ] **Bind guard**: non-loopback `bind_host` with `auth="none"` raises at startup and the
      process does not listen — assert nothing is bound, not merely that a message was logged
- [ ] Bind guard covers `0.0.0.0`, `::`, and a concrete LAN address, not just `0.0.0.0`
- [ ] Loopback + `auth="none"` starts normally (today's behavior, unchanged)
- [ ] Non-loopback + `auth="iam"` starts
- [ ] Effective bind address and auth mode appear in startup output in every configuration
- [ ] A tool call over streamable HTTP returns **byte-identical** results to the same call over
      the unix socket — assert equality across at least three tools, not just one
- [ ] `tools/list` over HTTP matches `tools/list` over stdio exactly
- [ ] With `auth="iam"`, an unsigned request is rejected before any handler runs
- [ ] With `auth="iam"`, a signed request yields a `Principal` whose `subject_id` derives from
      the caller ARN
- [ ] B315's forbidden-key guard fires on the HTTP path: a request with `workspace_id` in
      `params` is rejected with `-32602`
- [ ] `TransportContext` on the HTTP path carries no request-body-derived field
- [ ] Missing optional AWS dependencies leave every non-IAM mode fully working — assert the
      module imports and loopback mode starts with `boto3` absent
- [ ] Existing stdio adapter tests pass **unmodified**
- [ ] `pytest tests/ -q` failure set identical to pre-change baseline

### What This Card Does NOT Do

- Does not build an AgentCore-specific adapter — generic MCP, Gateway is one consumer
- Does not build the Lambda proxy itself. Task 4b documents the topology and its two open
  items; the Lambda is a separate, small card once the platform answers on identity
  propagation.
- Does not implement the signed-token workspace fallback — recorded as an open decision only
- Does not implement OIDC (the config accepts the value; the resolver is a follow-up)
- Does not add TLS termination — that belongs to the ALB or the platform's ingress
- Does not add rate limiting, quotas, or per-tenant throttling
- Does not change the default bind address or local behavior in any way
- Does not finish the Gateway registration doc — blocked on the platform team's answer about
  target type

### Outcome

Campy becomes reachable by a remote agent over an authenticated transport, with the same tool
surface it already exposes locally, and it becomes structurally impossible to expose that
surface without auth by accident. This is the missing piece between "Campy can be deployed in
your AWS account" and "your agents can actually use it."
