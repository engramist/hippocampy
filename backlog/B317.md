# B317 - Named-Query Eval Pack: Bounded Multi-Hop Conformance Suite

State: done
Priority: P1

Plan: (inline — self-contained, sized for a Sonnet-level implementer)

Depends on: **B312** (provenance), **B313** (authority), **B314** (GraphGateway).
Land those first — this card composes all three and is the proof they work together.

### Why

An external platform evaluating Campy as its graph engine has a published entry criterion:

> *"Define and regression-test bounded multi-hop questions before selecting a graph
> engine."* … *"A graph-database seam becomes real when a second adapter is introduced for
> proven multi-hop workloads."*

They have already written the questions. This card turns them into an executable
conformance suite. It serves three purposes at once, which is why it is worth building
even if that specific evaluation goes nowhere:

1. **Acceptance test** for the external evaluation — written by the customer, so passing
   it is not a matter of opinion.
2. **Backend-conformance suite** for Campy itself. Any future storage adapter must pass
   the identical suite. This is the artifact that makes engine choice reversible, which is
   the thing B314's seam is *for*.
3. **Regression coverage** for graph traversal generally, which Campy currently tests
   thinly compared to recall.

### The Five Questions (verbatim from the customer)

1. Given this user, intent, trust tier and policy set, what capability path is allowed?
2. Why was this path selected or blocked?
3. If this adapter changes, which agents, workflows, apps and policies are affected?
4. Which skills, tools, data, approvals and infrastructure produced this artifact?
5. Can an existing chain of capabilities satisfy the request without building something
   new?

Their starter relationship set: `INVOKES`, `REQUIRES`, `IMPLEMENTS`, `READS`, `WRITES`,
`CONSTRAINED_BY`, `DEPLOYED_ON`, `PRODUCED`, `APPROVED_BY`, `REUSES`.

They have chosen a **labeled-property-graph** model specifically because *"the edges need
operational properties such as version, access mode, confidence, run ID and evidence."*
That requirement drives the schema below — properties live on edges, not only nodes.

### What This Card Does

**Task 1 — A generic projected-fact schema.**

Do **not** add ten domain-specific node tables. Their ontology will change; Campy's schema
should not churn with it. Add one generic entity table plus one rel table per predicate.

In `campy/brain/hippocampus/schema.py` `NODE_TABLES`:

```
"FactEntity": """
    entity_id     STRING,     -- stable DOMAIN identifier, from the source system
    entity_type   STRING,     -- "capability" | "agent" | "workflow" | "policy" | ...
    label         STRING,
    properties    STRING,     -- JSON blob for source-specific attributes
    embedding     FLOAT[384], -- for question 5 (reuse candidates)
    embedding_model STRING,
    embedding_dim INT64,
    source        STRING,     -- B312 provenance
    source_version STRING,
    observed_at   TIMESTAMP,
    evidence_ref  STRING,
    authority     STRING,     -- B313 — always 'projected' for harvested facts
    superseded_by STRING,
    superseded_at TIMESTAMP,
    supersession_reason STRING,
    created_at    TIMESTAMP,
    PRIMARY KEY (entity_id)
"""
```

`entity_id` is the **source system's stable domain identifier**, not a Campy-minted one.
That is the join key that makes cross-system traversal possible at all; minting our own
would defeat the entire exercise.

Then ten rel tables, all `FROM FactEntity TO FactEntity`, each carrying the LPG edge
properties they asked for:

```
version STRING, access_mode STRING, confidence DOUBLE, run_id STRING,
evidence_ref STRING, source STRING, source_version STRING,
observed_at TIMESTAMP, authority STRING,
superseded_by STRING, superseded_at TIMESTAMP, supersession_reason STRING
```

One table per predicate: `FACT_INVOKES`, `FACT_REQUIRES`, `FACT_IMPLEMENTS`, `FACT_READS`,
`FACT_WRITES`, `FACT_CONSTRAINED_BY`, `FACT_DEPLOYED_ON`, `FACT_PRODUCED`,
`FACT_APPROVED_BY`, `FACT_REUSES`. Prefix with `FACT_` so they never collide with Campy's
memory rel tables.

Note: Kùzu 0.11.3 has no `ALTER REL TABLE` — see the `_REL_MIGRATIONS` block in
`schema.py` (~line 1258) and follow its drop+recreate pattern if you need to change these
later. Get the property set right the first time.

**Task 2 — Fact-envelope ingest.**

New module `campy/brain/hippocampus/facts.py`:

```python
@dataclass(frozen=True)
class FactEnvelope:
    subject_id: str
    predicate: str          # must be in the ten-predicate vocabulary
    object_id: str
    properties: dict        # edge properties
    source: str
    source_version: str
    observed_at: datetime
    evidence_ref: str | None

async def ingest_facts(gateway: GraphGateway, facts: list[FactEnvelope]) -> dict:
    """Upsert entities and edges. Always writes authority='projected'.
    Returns {"entities": N, "edges": M, "rejected": [...]}"""
```

Rules:
- Everything ingested here is `projected` — it has an external owner by definition. Reuse
  B313's `validate_authority()`, which will reject a missing `source_version`. That is the
  intended behavior: an unversioned projected fact is not rebuildable and must not be
  accepted.
- Unknown predicate → reject that fact, do not raise; return it in `rejected` so a
  harvester can report partial success.
- Ingest is **idempotent** — re-running the same envelope set produces no duplicates.
  Match on `(subject_id, predicate, object_id)`.
- Re-ingest with a newer `source_version` supersedes the prior edge via B312's
  `mark_superseded(reason="replaced")` rather than overwriting it. Lineage is the point.

**Task 3 — The five queries, as named queries.**

Register in `campy/brain/hippocampus/graph/queries/capability.py` (B314's registry).
Every one **must be bounded** — an explicit hop limit, never an open `*` traversal. Their
standard says so and it is also just correct: an unbounded traversal on a real capability
graph is an outage.

| Name | Question | Shape |
|---|---|---|
| `capability.permitted_paths` | Q1 | bounded path `INVOKES`/`REQUIRES` from an entry capability, filtered by `CONSTRAINED_BY` policies matching the caller's trust tier. Max 5 hops. |
| `capability.explain_path` | Q2 | for a given path, return each edge's `CONSTRAINED_BY` policies with their `confidence`, `source`, `evidence_ref` — the "why" is the provenance |
| `capability.impact_of` | Q3 | **reverse** traversal from the changed entity over `REQUIRES`/`INVOKES`/`READS`/`WRITES`/`DEPLOYED_ON`. Max 4 hops, returns entities grouped by `entity_type`. |
| `capability.lineage_of` | Q4 | reverse `PRODUCED` from an artifact, collecting `APPROVED_BY`, `READS`, `DEPLOYED_ON` along the way. Max 6 hops. |
| `capability.reuse_candidates` | Q5 | vector similarity over `FactEntity.embedding` filtered to `entity_type='capability'`, then verify each candidate's `REQUIRES` are satisfiable. Similarity floor `0.70` — the convention already used in `bundle_compiler.py`. |

Every query must exclude superseded rows (`superseded_by IS NULL`) unless a
`as_of`/`include_superseded` parameter is passed. Getting this wrong makes every answer
silently wrong, so test it explicitly per query.

Q5 is the one that genuinely needs Campy rather than a JSON catalog — semantic reuse
detection is not answerable by descriptor inspection. Make sure it actually uses
embeddings and is not reduced to a string match.

**Task 4 — Fixture graph and regression tests.**

Follow the existing pattern in `benchmarks/ask_eval/` (`fixtures.py`, `questions.py`) —
read it first and mirror its structure rather than inventing a parallel harness.

New `benchmarks/capability_eval/`:
- `fixtures.py` — a synthetic capability graph of roughly 40–60 entities spanning all ten
  predicates and all the entity types in the customer's ingest list (capability catalog
  entries, agent cards, MCP contracts, workflow definitions, policies, Terraform outputs,
  App/Iteration records, build-run evidence). Include deliberate difficulty: a blocked
  path, a superseded edge, two near-duplicate capabilities (for Q5), and a diamond
  dependency (so Q3 must deduplicate).
- `questions.py` — the five questions with expected result sets against the fixture.
- `README.md` — states plainly that this doubles as the backend-conformance suite: *any
  storage adapter claiming to back Campy must pass it unmodified.*

Tests in `tests/test_capability_queries.py` run the five queries against the fixture and
assert exact expected sets — not "returns something."

### Acceptance Criteria

- [ ] All five queries registered and callable through `GraphGateway.run()` — none of them
      use `execute_raw()`
- [ ] Each of the five returns the exact expected set against the fixture
- [ ] **Every query is bounded** — assert by inspecting the registered Cypher for an
      explicit hop limit and the absence of an unbounded `*` quantifier
- [ ] Superseded edges are excluded by default; each of the five has a test proving it
- [ ] Q3 (`impact_of`) deduplicates across the diamond dependency
- [ ] Q5 (`reuse_candidates`) finds the near-duplicate pair and respects the `0.70` floor
      (a below-floor entity is excluded)
- [ ] Q5 uses vector similarity, not string matching — assert by giving the near-duplicate
      a lexically dissimilar label
- [ ] `ingest_facts` is idempotent: ingesting the same list twice yields identical entity
      and edge counts
- [ ] Re-ingest with a newer `source_version` supersedes rather than overwrites — the old
      edge is still retrievable with `include_superseded=True`
- [ ] Unknown predicate lands in `rejected`, does not raise, and does not abort the batch
- [ ] Ingest without `source_version` raises (B313's `validate_authority`)
- [ ] All ingested entities and edges carry `authority='projected'`
- [ ] `drop_projections(source=...)` (B313) removes the whole fixture graph and leaves
      earned memory in the same DB untouched — the round-trip proof that the two subgraphs
      coexist safely
- [ ] `pytest tests/ -q` failure set identical to pre-change baseline

### What This Card Does NOT Do

- Does not build harvesters for any real source (git, Terraform, Temporal) — the ingest
  API is fed by fixtures here; real harvesters belong to whoever owns those sources
- Does not implement RDF/ontology representation — LPG only, per the customer's stated
  choice for the first pilot
- Does not implement a second storage adapter — it defines the suite that adapter would
  have to pass
- Does not make the capability graph authoritative for anything. It is `projected`, always,
  and every entry point enforces that.

### Outcome

The five multi-hop questions become executable, bounded, regression-tested queries with
verifiable answers. Campy gains a conformance suite that makes any future engine swap a
measurable exercise rather than a rewrite — and gains the specific artifact an external
platform's governance process asks for before a graph database is allowed anywhere near
its critical path.
