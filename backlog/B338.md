# B338 - No Encryption at Rest, No Content-Level Secret Scrubbing on Stored `text_raw`

State: complete — merged via PR #62 (2026-08-20)
Priority: P2

Plan: none yet — this card is scoped to produce a design decision plus a first concrete mitigation
(secret scrubbing at ingest), not necessarily full at-rest encryption in one pass. See scope below.

### Problem

An external security audit found that Campy persists captured text verbatim in KuzuDB's `text_raw`
fields (confirmed widely used across the codebase — `campy/brain/basal_ganglia/frustration_clusters.py`,
`campy/brain/thalamus/working_memory.py`, `campy/brain/temporal_lobe/loop/anomaly_detection.py`, and
many other read/write sites reference `text_raw`). The only redaction that exists today is
**key-name-based** (`campy/brain/brainstem/observability.py`, `campy/brain/brainstem/activity_log.py`
— confirm exact mechanism by reading these files) and applies to OTel spans / the activity log, not to
the actual stored `text_raw` content in the graph.

For a system explicitly designed to durably remember everything an agent sees across sessions, this
means: (a) there is no encryption at rest for the KuzuDB database file itself — anyone with filesystem
access to the DB reads everything in plaintext; (b) if a credential, API key, or other secret is ever
pasted into a captured conversation, it is stored forever in cleartext in the graph, with no
content-level scrubbing pass at ingest time to catch it.

### What it does (scope)

This is a two-part card; do both, but they're independently valuable and can land separately if needed:

**Part A — content-level secret scrubbing at ingest (the higher-value, more tractable fix).**
1. Identify the ingest chokepoint(s) where raw text becomes `text_raw` on a node (grep for where
   `text_raw` is first set on write, likely in capture/ingest handlers under
   `campy/brain/thalamus/` or `campy/brain/brainstem/`).
2. Add a secret-detection pass at that chokepoint using pattern-based detection for common credential
   shapes (AWS access keys `AKIA[0-9A-Z]{16}`, generic API-key-shaped high-entropy tokens, private key
   PEM headers `-----BEGIN...PRIVATE KEY-----`, bearer tokens, etc. — a small, maintainable regex set is
   fine; don't try to build a general secret-scanning engine from scratch, consider whether a
   lightweight existing library like `detect-secrets`'s plugin patterns can be vendored/referenced for
   the regex list instead of hand-rolling all of them).
3. When a likely secret is detected, redact it in place before the text is persisted (e.g. replace with
   `[REDACTED:aws_access_key]`) rather than rejecting the whole capture — the goal is "don't store the
   secret," not "block the write."
4. Add tests proving common secret shapes are redacted before reaching storage, and that normal text
   (including text that merely mentions the word "password" or "API key" without an actual credential
   shape) passes through unmodified.

**Part B — encryption at rest (design decision + doc, minimum bar for this card).**
1. Investigate whether KuzuDB 0.11.3 supports any native at-rest encryption option (check the `kuzu`
   package's own docs/API for anything like an encryption-key parameter on `kuzu.Database(...)`).
2. If native support exists, wire it up behind an opt-in config flag (default off, to avoid breaking
   existing installs without a migration path) and document the tradeoffs (key management burden,
   performance cost).
3. If no native support exists, document that clearly (in `docs/ARCHITECTURE.md` or a new
   `docs/security-model.md`) as a known limitation, and note the practical mitigation available today —
   e.g. relying on filesystem/disk-level encryption (FileVault, LUKS, EBS encryption) rather than
   application-level encryption — rather than leaving the gap silently undocumented. Do not attempt to
   build a custom encryption-at-rest layer on top of KuzuDB from scratch in this card if no native
   support exists — that's a much larger effort than this card's scope; documenting the honest current
   state is an acceptable outcome for Part B.

### Dependencies

None.

### Files to create/modify

- The ingest chokepoint file(s) where `text_raw` is first written (locate via grep before editing).
- A new small module for secret-pattern detection (e.g.
  `campy/brain/brainstem/secret_scrub.py`), with its own unit tests.
- `docs/ARCHITECTURE.md` or a new `docs/security-model.md` — document both the scrubbing behavior and
  the at-rest-encryption decision from Part B.

### Acceptance Criteria

- [ ] A pattern-based secret scrubber runs at the ingest chokepoint before text reaches `text_raw`,
      with tests proving at least AWS-key-shaped and PEM-private-key-shaped strings are redacted.
- [ ] Normal conversational text (including text that discusses secrets abstractly, without containing
      one) is verified unmodified by the scrubber via a test.
- [ ] A documented decision exists for at-rest encryption — either it's implemented behind an opt-in
      flag with tests, or its absence is explicitly documented with the recommended filesystem-level
      mitigation.
- [ ] Existing capture/ingest tests still pass after the scrubber is wired in (no unrelated regression
      in normal text capture).
