# B282 - Batch Sweep Writes with UNWIND

State: ready
Priority: P2

Plan: backlog/plans/B-282-batch-sweep-writes.md

### Problem

The background sweep performs per-row writes, each acquiring the global asyncio write lock and dispatching a separate Cypher statement. In `campy/brain/brainstem/sweep.py::_decay_and_archive` (~line 553), nodes below the archive threshold are archived one `execute_write` per node. The same one-row-per-query pattern appears in `_resurrect_archived`, `_hebbian_promote` edge writes, and the per-table `count(n)` full scans run every sweep. On a graph with thousands of decayed nodes, a single sweep serializes thousands of lock acquisitions and blocks the GCL loop's writes.

### What This Card Does

Converts per-row sweep writes to batched `UNWIND` statements (chunked), and removes the redundant per-sweep `count(n)` scans by computing counts from data the sweep already has.

### Acceptance Criteria

- [ ] `_decay_and_archive` archives all below-threshold nodes for a table in ≤ ceil(n/500) write statements via `UNWIND $ids AS id MATCH (n:{table} {pk: id}) SET n.archived = true`
- [ ] The decayed-count no longer requires a separate `count(n)` scan per table (read the count from the archive-candidate query + one cheap count, or RETURN count from the bulk decay if Kuzu supports it — otherwise keep a single count query but document why)
- [ ] `_resurrect_archived` batch-updates resurrection candidates the same way
- [ ] A test with a mock DB asserts: 1,200 archive candidates → ≤ 3 write calls (chunk 500)
- [ ] Existing sweep tests pass: `pytest tests/ -q -k "sweep or dreaming or basal"`
- [ ] Sweep stats dict shape unchanged (callers/tests depend on keys)

### Outcome

Sweeps hold the write lock for a bounded number of statements instead of O(nodes), eliminating lock contention between background maintenance and live message processing.
