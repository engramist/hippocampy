# B418 - Gateway `sparql=` Create Path Bypasses Vector Indexing: All Semantic Recall Over Runtime-Written Nodes Returns Empty Post-Cutover

State: ready
Priority: P0
Branch: fix/b418-gateway-sparql-skips-vector-index

### Problem

After the Kùzu→Oxigraph / GraphGateway cutover (B386/B397), **embeddings for nodes
written at runtime are never indexed into the sqlite-vec vector store**, so every
embedding-similarity recall returns empty for anything written after the cutover. Core
memory retrieval is silently broken.

Found live on 2026-09-09 during a paired smoke test with the ARC_AGI client (arc-agi-31).
ARC's pre-flight `require_roundtrip_persistence` readiness gate
(`sidequest_mcp_client/readiness.py`) did: `upsert_lesson(probe)` → got a real
`lesson_id` back → `recall_relevant_lessons(query=probe_token)` ×3 → `{'lessons': []}`
every time → `RuntimeError: HippoCampy MCP write-read roundtrip failed`. The entire smoke
test aborted before any `arc_*` tool ran.

### Root cause (confirmed at code + data level)

1. `upsert_lesson` (`campy/brain/thalamus/tools/lessons.py:606,667`) computes
   `vector = emb.embed(text)` then writes the node via
   `gw.run("lessons.create_lesson", emb=vector, ...)`.
2. `lessons.create_lesson` (`campy/brain/hippocampus/graph/queries/lessons.py:673`) is a
   `NamedQuery` **carrying a `sparql=` template**. Per the gateway dispatch (the same
   mechanism B413 documented), any query with `sparql is not None` routes straight to
   `OxigraphClient.execute_write()` → `store.update()` and **never calls `write_node()`**.
3. `write_node()` (`campy/brain/hippocampus/graph/oxigraph_client.py:863-868`) is the
   **only** place that populates the vector store:
   ```python
   emb_cols = [c for c, t in cols.items() if t == "FLOAT[384]"]
   for ec in emb_cols:
       if props.get(ec) is not None and self.vector_store is not None:
           self.vector_store.upsert_vector(v_uri, props[ec])
   if props.get("text_raw") and self.vector_store is not None:
       self.vector_store.index_text(uri, str(props["text_raw"]))
   ```
   The `sparql=` path skips all of it — no `upsert_vector`, no `index_text`.
4. Worse, the SPARQL template's `campy:embedding ?emb` cannot serialize a 384-float Python
   list as a single RDF term, so the vector is **also dropped from the graph node**.

### Verified (2026-09-09, read-only against the live store)

- Probe Lesson persisted fine as scalars: `lesson_id 0a5356ea-…`,
  `text_raw arc_readiness_probe_75d89a93fbb2`, `embedding_dim 384`,
  `embedding_model all-MiniLM-L6-v2`, `content_hash …` — but **no `embedding` property**.
- `~/.campy/vectors.db`: `vectors` table holds **7 rows, all `GistClass/*`** centroids
  (the ontology bootstrap, inserted via the Python-handler branches at
  `gateway.py:521/594` and `schema.py:1669`). Zero Lesson/Message/Plan vectors. The
  `lexical` FTS5 table is empty.
- `recall_relevant_lessons(query="arc_readiness_probe_75d89a93fbb2")` → `[]` (exact-token
  query — not a semantic miss; the vector simply isn't indexed).
- `current_truth` likewise returned `[]` for a written fact.

### Blast radius

Every read path that ranks by embedding similarity is affected for runtime-written data:
`recall_relevant_lessons`, `current_truth` (vector branch), `recall_scene_graph_priors`,
`recall_mechanic_priors`, `ask` (retrieval stage), and the whole
`gateway.py:735-888` `search_vectors(...)` family (Concept/Lesson/Rule/entity recall used
by the ARC world-model tools). Exact-id lookups, BGP/property filters, edge traversals,
and all writes are unaffected. Only bootstrap ontology vectors survive.

This is the same structural class as B413 (`sparql=` queries bypass the Python write
path), but where B413's cases were *inert*, this one is *broken* — silent, and it guts a
core feature.

### Fix options (decide one; needs care — this is the write-path seam)

1. **Index in the gateway's `sparql=` dispatch.** After `execute_write()` for a mutating
   query, if params carry an embedding (`emb`/`embedding`) and/or `text`/`text_raw` for a
   node with a known PK, call `vector_store.upsert_vector()` / `index_text()` with the
   minted URI. Centralizes indexing for all `sparql=` creates. Must resolve the URI the
   same way the template does (`https://campy.dev/data/{table}/{ENCODE_FOR_URI(pk)}`).
2. **Route embedding-bearing node creates through `write_node()`** instead of a `sparql=`
   template, so indexing happens as designed. Cleaner conceptually but touches every such
   create query and the dedupe/upsert flow.
3. **Explicit index step per create handler** (`upsert_lesson`, plan/step, concept,
   message, ARC entity writers). Most localized, most duplication, easiest to drift again.

Option 1 is the likely right call (single chokepoint, mirrors how `write_node` already
does it). Whichever is chosen, add a **regression test**: write a node with an embedding
via the tool path, then assert `vector_search`/`recall_relevant_lessons` returns it — the
exact round-trip ARC's readiness gate performs. A conformance-style guard that fails when a
`FLOAT[384]`-bearing create query is `sparql=`-dispatched without a corresponding index
step would prevent recurrence (ties into B413's measurement-gap note).

### Severity

P0. Semantic memory is a core capability and it is silently non-functional for all
post-cutover writes on the Oxigraph backend. It also blocks any client (ARC included)
whose readiness gate asserts write-read persistence.
