# B301 - Fix Outcome-Sense Polarity: Stop Mislabeling Success Reports as Failures

State: ready
Priority: P1

Plan: (inline — this card is self-contained and sized for a Sonnet-level implementer)

### Problem (observed 2026-07-13, real graph)

Two durable Lessons in the graph read:

> "Plan outcome (**failure**): ✅ B290 Continuous Work State — COMPLETE & CERTIFIED …
> 192 passed, daemon healthy, all 9 B290 commits in place…"

A *success* report, permanently labeled a failure at 0.85 confidence. These surfaced in
the top `current_truth` results during a real review session. Durable memory with the
wrong polarity is worse than no memory: it feeds `_plan_feedback_from_similarity`'s
warnings ("similar plans failed!") and poisons future plan feedback.

### Root Causes (verified in code)

1. **The failure signal list matches count-reporting, not judgments.**
   `campy/brain/temporal_lobe/loop/step4_pattern.py` `_FAILURE_SIGNALS` includes bare
   `r"\bfailed\b"`. Assistant work summaries routinely contain "17 failed + 12 errors in
   the sampled set" or "the only failures (4) are fixed" — *mentions* of test counts, not
   outcome judgments. One "failed" outweighs zero success-list hits (the actual success
   markers in the message — "✅", "COMPLETE", "192 passed" — aren't in `_SUCCESS_SIGNALS`),
   so `infer_outcome_valence` returns -0.8.
2. **Outcome sense runs on every role.** `campy/brain/thalamus/tools/capture.py` (the
   "B69: outcome sense" block in `notify_turn`, ~line 310) calls
   `infer_outcome_valence(content)` for user AND assistant turns. The design intent (B69)
   is that outcome valence is a *reward signal from the user/environment* — "perfect",
   "that broke", "revert it". An assistant grading its own work defeats that, and the
   codebase already recognizes this class of problem: ISSUE-024 caps assistant-role
   artifact confidence at `ASSISTANT_CAP` in `classify_artifact` for exactly the
   "self-report poisoning" reason. Both observed mislabels came from assistant messages.
3. Downstream, `_store_plan_outcome_lesson` (`campy/brain/thalamus/tools/lessons.py`)
   bakes the polarity into the Lesson text prefix (`"Plan outcome (failure): …"`) with no
   record of WHICH signal triggered it — unauditable after the fact.

### What This Card Does

**Task 1 — restrict auto outcome-sense to user turns.**
In `capture.py`'s B69 outcome-sense block: only run `infer_outcome_valence` when
`role == "user"`. Explicit `report_outcome` MCP calls are unaffected (agents can still
self-report deliberately — that path carries `valence_source` and is intentional).
Comment the change with the B69 rationale and the ISSUE-024 precedent.

**Task 2 — make the failure list judgment-shaped.**
In `_FAILURE_SIGNALS` (`step4_pattern.py`), replace `r"\bfailed\b"` with patterns that
match judgments and not counts/reports:
- `r"\b(?:it|this|that|build|test|tests|deploy|deployment) (?:has )?failed\b"`
- `r"\bfailed to\b"`
Keep the rest of the list as-is. Do NOT add a lookbehind for digits as the only fix —
"the 3 tests failed because of my change" is a legitimate judgment; the subject-anchored
patterns above handle both directions better than digit exclusion.
Note: `campy/brain/thalamus/tools/_shared.py` contains a fallback copy of these signal
lists (the `except ModuleNotFoundError` shim for benchmark consumers) — apply the same
edit there so the two lists stay identical.

**Task 3 — require a margin, not a plurality of one.**
In `infer_outcome_valence` (both copies, per Task 2 note): return a valence only when
`abs(success_hits - failure_hits) >= 2` OR one side has hits and the other has zero.
A 3-vs-2 mixed message is ambiguous → `None`. Preserve the exact return values
(+0.8 / -0.8 / None) — downstream thresholds depend on them.

**Task 4 — auditability: record what triggered the polarity.**
`infer_outcome_valence` currently returns `float | None`. Add a sibling function
`infer_outcome_valence_detail(text) -> tuple[float | None, list[str]]` returning the
matched pattern strings; implement `infer_outcome_valence` as a thin wrapper over it (so
every existing caller and the `_shared.py` fallback keep their signature). In
`capture.py`, use the detail variant and pass the matched signals through to
`report_outcome` params as `trigger_signals`; in `_store_plan_outcome_lesson`, append a
final line to the lesson text: `\n[valence_trigger: <comma-joined signals>]`. That makes
every system-labeled outcome auditable from the Lesson node itself.

**Task 5 — regression tests.**
New test file `tests/test_outcome_valence.py`:
- The actual observed failure case: a success-summary string containing "✅ … COMPLETE",
  "192 passed", "17 failed + 12 errors in the sampled set", "failures (4) are fixed" →
  `infer_outcome_valence` returns `None` or `+0.8`, NEVER `-0.8`
- `"that broke the build, revert it"` → `-0.8` (judgment still detected)
- `"the deploy failed"` → `-0.8`; `"17 failed"` alone → `None`
- Margin rule: text with exactly one success and one failure hit → `None`
- Role gate: `notify_turn` with `role="assistant"` and content `"revert it, that broke"`
  issues NO `report_outcome`/outcome-lesson write; same content with `role="user"` does
  (use the fake-db pattern from `tests/adapters/test_claude_memory_capture.py` —
  `_EmptyResult`/`_make_capture_db` — and monkeypatch `capture_mod.emb.embed`)
- Trigger audit: a system-labeled lesson's text contains `[valence_trigger:`

### What This Card Does NOT Do

- No retroactive relabeling of existing mislabeled Lessons (graph cleanup is a separate
  decision — flag any you find in the card's PR description instead)
- No LLM-based sentiment classification — keep it regex + margin (System 1); if this
  proves insufficient later, escalation to a System 2 check is a new card
- No change to explicit `report_outcome` semantics or its schema

### Outcome

Outcome valence means what it says: a user-side judgment with an auditable trigger.
Assistant self-summaries can no longer mint "failure" Lessons out of passing test counts,
and plan-similarity warnings stop being poisoned by wrong-signed history.
