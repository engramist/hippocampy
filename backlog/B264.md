### Problem

Hermes Agent is an external agent framework that supports "Session Recall" — loading context at the start of each agent session. Hermes can spawn background agents. Campy should be the ambient memory layer for Hermes-spawned agents, providing compiled context bundles so each spawned agent starts with full project context instead of working blind.

### What This Card Does

Creates a Hermes Agent adapter that:
1. Provides session recall via Campy's `compile_context` tool
2. Captures turns from Hermes agent sessions
3. Supports Hermes's background agent spawning with per-agent context bundles

### Dependencies

- B252 (bundle compiler must work)
- B262 recommended (REST API is the simplest integration path)

### Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Integration method | REST API client + MCP SSE fallback | REST is simplest; MCP SSE for full tool access |
| Session recall | Call `compile_context` with agent's task description | Bundle compiler handles heterogeneous assembly |
| Spawned agent context | Thin context bundle scoped to the spawned task | Spawned agents get focused context, not full project dump |
| Adapter location | `adapters/hermes/adapter.py` | Follows existing adapter pattern |

### Implementation (2026-08-04)

**New methods on `HermesAdapter` (`adapters/hermes/adapter.py`):**
- `session_recall(task_description, token_budget=32000, agent_type="generic")` — POSTs `{query, token_budget, agent_type}` to `/api/v1/bundle`, which server-side routes to `compile_context` (confirmed by reading `bundle_endpoint` in `campy/brain/brainstem/rest_api.py`). Returns the response envelope's `data` field, same unwrap convention `recall()`/`decide()` already use.
- `spawn_context(parent_session_id, task_description, token_budget=8000)` — thin wrapper over `session_recall()` with `agent_type="spawned"` and a smaller default budget, matching the card's stated purpose (task-scoped slices for Hermes-spawned sub-agents, not a full project dump). `parent_session_id` is accepted for interface parity with the plan's signature but isn't forwarded in the request body — `bundle_endpoint` only reads `query`/`token_budget`/`agent_type` and has no session concept to attribute it to.
- `capture_turn(role, content, session_id=None)` — thin wrapper over the existing `notify()`, with a per-call `session_id` override that's restored (not left mutated) after the call when provided; defaults to the adapter's already-configured session when omitted.

**Real bug found and fixed while implementing (not in the original audit):** `recall()`, `decide()`, and `notify()` all did `import aiohttp` inside the method body. `aiohttp` is not listed anywhere in `pyproject.toml`'s dependencies and is not installed in this repo's `.venv` — every call to these three methods was silently raising `ModuleNotFoundError`, caught by each method's broad `except Exception`, always returning `None`/`False`. Confirmed live: `await adapter.notify(...)` returned `False` before the fix even with the real Campy daemon running and reachable on `127.0.0.1:7799`. Fixed by switching all HTTP calls (existing three plus the two new ones) to `httpx.AsyncClient` — `httpx` is already a declared, installed dependency (used elsewhere for sync/async HTTP), so no new dependency was added. Re-verified live against the running local daemon after the fix: `notify()` now returns `True`.

**Verification:** TDD. `tests/adapters/test_hermes_adapter.py` gained 9 new async tests (using a hand-rolled `_FakeAsyncClient`/`_FakeResponse` pair patched over `httpx.AsyncClient`, since real end-to-end coverage of the target `/api/v1/bundle` route already exists via `tests/test_rest_api.py`'s `TestClient` pattern) — written first, watched all 9 fail (`AttributeError: no attribute 'session_recall'` etc., plus the two aiohttp-regression tests failing with the pre-fix behavior), then implemented. Covers: correct URL/payload shape and defaults for `session_recall`/`spawn_context`, failure-status handling (both return `None` on non-200), `capture_turn`'s session-id override not leaking past the call, and regression coverage proving `notify()`/`recall()` genuinely succeed now. `tests/adapters/test_hermes_adapter.py`: 18/18 passed. Full suite: no regressions (see command output below).

### Verification Findings (2026-08-03, historical — the two unmet ACs below are now implemented, see Implementation above)

Read `adapters/hermes/adapter.py` in full (158 lines). The shipped `HermesAdapter` has 5 methods: `configure()`, `recall()` (async, hits `GET /api/v1/recall`), `decide()` (async, hits `POST /api/v1/decide`), `notify()` (async, hits `POST /api/v1/notify`), `health_check()` (sync, hits `GET /health`). Plus a module-level `get_adapter()` factory.

None of these are `session_recall`, `capture_turn`, or `spawn_context`. `grep -rn "session_recall\|capture_turn\|spawn_context" adapters/ campy/ tests/` returns **zero matches** anywhere in the codebase (the only unrelated hit, `_capture_turn` in `campy/brain/thalamus/ask.py`, is a private helper in the B289 `ask` tool, unconnected to Hermes).

`notify()` is a reasonable functional analog to `capture_turn` (same underlying REST call, `/api/v1/notify`) — that part is just a naming difference I would treat as stale-AC-text. But **`spawn_context` is not a renaming issue — the capability itself does not exist.** Grepped for any call to `/api/v1/bundle` or `compile_context` anywhere under `adapters/hermes/` — none. The adapter has no way to request a task-scoped, reduced-token-budget context bundle for a spawned background agent, which was this card's stated core purpose, not an incidental detail.

Ran the real test suite: `PYTHONPATH=<worktree> .venv/bin/python -m pytest tests/adapters/test_hermes_adapter.py -v` → **9/9 passed** — but the test file itself only covers `configure`, `health_check`, `get_adapter`, `detect_hermes`, `register_hermes`, and README existence; it never references `session_recall`/`capture_turn`/`spawn_context` either, confirming the divergence from the AC is the accepted, intentional current state, not an accidental regression introduced later.

Read `adapters/hermes/README.md` — it documents exactly the real API (`recall`/`decide`/`notify`/`health_check`) and never mentions `session_recall`/`spawn_context`, so the code and docs are internally consistent; the drift is specifically between the shipped design and this card's AC/plan.

**Not attempting a fix:** adding `spawn_context` (a real, non-trivial feature — needs to call `/api/v1/bundle` with a task description and a smaller token budget, per the plan's own `spawn_context(parent_session_id, task_description, token_budget=8000)` signature) is implementation work, not a safe one-line correction, so per this audit's constraints I'm leaving it as a documented gap rather than building it. A fix would need to: add a `spawn_context()` async method to `HermesAdapter` that POSTs to `/api/v1/bundle` (now confirmed working, see B262) with a reduced `token_budget`; likely rename/alias `recall()`→`session_recall()` or add a new `session_recall()` that calls `/api/v1/bundle` instead of `/api/v1/recall`; update the README and add corresponding tests.
