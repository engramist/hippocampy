# B451 - CO_OCCURS_WITH Upsert Minted a Fresh Reifier Per Solution and Doubled on Every Re-Write — the Daemon Memory Blowup

State: fixed (2026-09-23, see completion notes; live-store cleanup pending)
Priority: P0
Branch: fix/b451-co-occurs-reifier-explosion

### Finding

`pathways.unwind_co_occurs_with` (called from `write_co_occurs_with`, Step 7 of
the Gated Consolidation Loop) was a pure-SPARQL upsert:

```sparql
INSERT { << ?a CO_OCCURS_WITH ?b >> campy:count ?new_count ; ... }
WHERE  { ... OPTIONAL { << ?a CO_OCCURS_WITH ?b >> campy:count ?old_count } ... }
```

`oxigraph_client.py`'s own module docstring (points 2-4) documents that
pyoxigraph 0.5 desugars `<< s p o >> pred obj` into a **fresh blank-node
reifier per occurrence**, that SPARQL cannot delete them, and that `star`
edges (which `CO_OCCURS_WITH` is classified as) must be written through
`write_edge` (native remove-then-insert). This query bypassed that (the
recurring "`sparql=` bypasses `write_node`/`write_edge`" class: B413/B418/B420).
Worse, the `OPTIONAL` matches **every** existing reifier of the edge, and the
`INSERT` runs once per solution, so re-writing the same pair took k reifiers to
2k. Doubling per write is unbounded.

### Evidence (2026-09-23)

- macOS unified log: `memorystatus: killing largest compressed process Python
  [9037] 120429 MB` — the daemon (`ai.hippocampy.brain`) was killed by jetsam
  mid-benchmark; the ~4 min restart is what turned the rest of B446's v3 run
  into instant fake "offline" answers.
- Reproduced under a 3-scenario LoCoMo slice: daemon `footprint` 0.9 GB →
  43 GB in ~10 min while RSS stayed ~4.5 GB (memory sat in the compressor, so
  RSS-based checks were blind). `pathways.unwind_co_occurs_with` was the first
  `WRITE_TIMEOUT_TRIPPED` (16:56:40), then repeated in a fixed ~63s trio with
  `capture.set_session_token_limit` / `sweep.flag_orphan_lesson` (the writes
  queued behind it).
- Cloned store: 26.9M quads, **6,529,054 `campy:count` triples on blank-node
  subjects** against only 270 plain `CO_OCCURS_WITH` edges (~24k reifiers per
  edge); `brain.db` had grown 1.9 GB → 7.7 GB during that one run. Opening the
  store took 149s.
- This also explains B447's "slow `create_gist_example` / `touch_main_quest`"
  (they were waiting behind the runaway write, not slow themselves) and the
  earlier unexplained daemon restarts.

### Fix

- `OxigraphClient.upsert_co_occurrence()` — both endpoints must be existing
  Concepts (parity with the old `MATCH`), reads existing reifiers' count/strength
  natively, then `write_edge("CO_OCCURS_WITH", ...)` which removes all existing
  reifiers and asserts exactly one. Polluted edges self-heal on their next write
  (largest count wins).
- `unwind_co_occurs_with` no longer has `sparql=`; `GraphGateway._handle_oxigraph_handler`
  dispatches it to the new method.
- `scripts/collapse_star_reifiers.py` — one-time, idempotent cleanup
  (`--report`, `--collapse CO_OCCURS_WITH`) for data already polluted.
- `tests/test_b451_co_occurs_reifier_explosion.py` (6 tests, real
  `OxigraphClient`): 10 re-writes leave 1 reifier with count 10 (old code: 512);
  store size constant across 15 re-writes; missing concept writes nothing;
  polluted edge collapses; multi-pair call; cleanup script. Confirmed
  load-bearing by stashing the fix (first test fails).
