# B457 - HTTP REST and Dashboard Routes Ignore the Caller's Workspace (Cross-Tenant Access in Multi-Tenant Mode)

State: fixed (2026-09-29 — see completion notes)
Priority: P1 (P0 before any multi-tenant / `auth = "iam"` deployment)

### Problem Statement

Found during the B385 audit (2026-09-29). In HTTP mode only `/mcp` is
workspace-isolated. `_dispatch_mcp` resolves the database per request from
`principal.workspace_id` via `WorkspaceRouter` (B316/B325). Every other HTTP
route runs against the daemon's single fixed database, whatever the
authenticated caller's workspace:

- `web/server.py::create_app` builds the REST routes with
  `create_router(db=db, config=_config)`, where `db` is the daemon's
  `self.db` (`brain_daemon.py`, `create_app(self.db, ...)`).
  `rest_api.py` passes that same `db` to every handler; there is no router or
  principal lookup.
- The dashboard's own `/api/*` routes use `gw = get_gateway(db)`, the same
  fixed database.
- The auth middleware only establishes that the caller is *some* valid
  principal; it does not scope what they can reach.

With `auth = "iam"` and the default `dashboard_enabled = true`, an
authenticated tenant can read and write the fixed ("local") workspace through
these routes, bypassing the per-workspace isolation that `/mcp` enforces.
Routes affected (from the live route table):

- **Reads:** `GET /api/v1/{recall,timeline,diff,status,tools,heartbeat,activity/stream}`, `POST /api/v1/bundle`, `POST /api/v1/decide`, `GET /api/{node/{id},stats,token-metrics,graph,open-loops,merge-events,quests,thinking}`, `GET /api/export/constraint-ledger[.json]`, `GET /memory/node/{id}`
- **Writes:** `POST /api/v1/notify`, `POST /api/confirm/{id}`, `POST /api/reject/{id}`, `DELETE /api/merge-events/{id}`

Not affected: the default local single-user install (`auth = "none"`,
loopback, one workspace). The bind guard prevents exposing it
unauthenticated. `dashboard_enabled = false` currently removes all of these
routes (see B385), which incidentally avoids the problem but also drops the
REST API.

The README's cloud section says auth and workspace routing "apply
identically regardless of which transport a request came in on". That is
true for the socket and `/mcp`, but not for these routes.

### What It Does (Scope)

1. Resolve the database per request for every non-`/mcp` HTTP route, the
   same way `_dispatch_mcp` does: `request.state.principal.workspace_id` →
   `WorkspaceRouter.get()` / `release()`. Fall back to the fixed `db` only
   when no router is configured (local single-user, current behaviour).
2. Or, as a smaller first step, refuse to register these routes when auth
   is on and a `WorkspaceRouter` is present, so a multi-tenant deploy can't
   reach the shared database, until (1) lands.
3. A regression test with two principals in different workspaces: a write
   through `/api/v1/notify` by one must not be readable by the other through
   `/api/v1/recall` or the dashboard `/api/*` routes. Mirror the existing
   `/mcp` tests in `tests/test_workspace_router.py`
   (`test_http_dispatch_mcp_resolves_db_from_router`,
   `test_isolation_fact_written_to_one_workspace_not_readable_from_another`).
4. Correct the README cloud section's claim once the behaviour matches, or
   now if (2) is chosen.

### Outcome

Workspace isolation holds on every HTTP route, not just `/mcp`, so a
multi-tenant deployment can't reach another tenant's memory through REST or
the dashboard.

### Completion notes (2026-09-29)

**REST (`/api/v1/*`): scope item 1, the proper fix.** `rest_api.create_router`
takes `router` and `principal_resolver`. Each tool call now:
- resolves the principal per request (from the auth middleware, or the local
  single-user principal when auth is off);
- borrows that principal's workspace from `WorkspaceRouter`, releasing it
  afterwards;
- dispatches through `campy.brain_daemon.route_tool_call`.

So REST now gets the same workspace routing, B424 scope checks and B315
forbidden-key guard as the socket and `/mcp`; it had bypassed all three by
calling `TOOL_HANDLERS` directly. Errors map to HTTP status: scope → 403,
unknown tool → 404, forbidden key or invalid workspace → 400, handler
failure → 500, as before. `web/server.py` passes the daemon's router and
resolver in.

**Dashboard: a guard, not per-workspace routing.** The dashboard (UI, `/api/*`,
`/memory/*`, `/static`, token metrics) is an operator view of the local
workspace. Routing its ~15 routes per tenant would build a multi-tenant
dashboard nobody has designed. Instead, when auth is on, the auth middleware
serves it only to principals whose `workspace_id` is `local`: GET/HEAD need
`memory.read`, anything else needs `memory.write`, and everyone else gets 403.
The guard is an allowlist, so every path except `/health`, `/mcp`, `/sse` and
`/api/v1/*` is guarded; a route added later is protected by default. With
auth off (the default local install) nothing changes.

**Left as is:** `/api/v1/tools` (static list) and `/api/v1/heartbeat` /
`/api/v1/activity/stream`, which carry only the daemon-wide phase name and
timestamps, no memory content. Any authenticated principal can still read them.

**Tests:** `tests/test_http_workspace_isolation.py` (12 tests). They drive the
real app with auth on, a real `WorkspaceRouter` with the local database
registered as `"local"` (as the daemon does), and a header-to-principal
resolver:
- a REST write by tenant A lands in A's workspace, not the shared database;
- tenant B's REST read doesn't see it;
- REST enforces scopes and rejects unauthenticated callers;
- the dashboard refuses other workspaces (reads and writes), serves the local
  workspace, and requires the write scope for writes;
- `/health` stays public.

9 of the 12 fail on the pre-fix code; the other 3 (the 401, `/health`, and
the local dashboard) pass either way, as they should.
`tests/adapters/test_hermes_adapter.py` now stubs
`campy.brain_daemon.TOOL_HANDLERS` (where `route_tool_call` looks) instead of
swapping the tools module; its assertions are unchanged.

Also fixed B385's criterion that `/api/v1/*` resolves through
`WorkspaceRouter`, and the README's transport claim.
