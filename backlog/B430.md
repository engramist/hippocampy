# B430 - `arc_get_causal_path` Was Structurally Incapable of Ever Returning `path_exists: True` — `DERIVED_FROM_FACT` + `REQUIRES_ENTITY` Never Had a Writer

State: fixed (this PR)
Priority: P1
Branch: fix/b430-derived-from-fact-requires-entity

### Correction to this card's original framing

Filed as "15 pre-cutover edge types never classified in `EDGE_REIFICATION`," implying
unexamined drift. Investigation found that framing was wrong: **12 of the 15 are already
correctly, deliberately documented** in `UNCLASSIFIED_ESCALATED_TABLES` with per-table
reasons naming their original (now-superseded) feature cards — `ADJACENT_TO`, `BLOCKS`,
`CAUSES_CHANGE_IN`, `CONFIRMS`, `CONTAINS_ENTITY`, `CORRELATES_WITH`, `CO_MOVES_WITH`,
`EXECUTED_AS`, `OBSERVED_IN`, `RESPONDS_TO`, `STRUCTURALLY_SIMILAR`,
`SUPPORTS_HYPOTHESIS` (B168's ARC exploration graph, B88's hypothesis engine, B66/B69's
active planning — no writer exists today, nothing reads them). **No action needed on
these 12.**

`INFERRED_FROM` (the 13th) is real but already tracked cross-repo — the ARC_AGI client
session's own card A247: `arc_confirm_hypothesis`/`arc_contradict_hypothesis` only ever
link `ENTITY_HYPOTHESIS`, never `INFERRED_FROM` from a `VictoryCondition`. Noted in
`UNCLASSIFIED_ESCALATED_TABLES`'s reason string; left to that side, not duplicated here.

### The real finding: 2 of the 15 back a live, currently-broken tool

`DERIVED_FROM_FACT` and `REQUIRES_ENTITY` are **mandatory (non-optional) hops** in
`arc_get_causal_path`'s Cypher/SPARQL (`arc.query_causal_chain`/
`arc.query_causal_chain_with_goal`) — a **live, registered MCP tool**
(`TOOL_HANDLERS["arc_get_causal_path"]`). Since neither edge had a writer anywhere in the
repo, verified live against the real production store (even after migrating in 44,427
real historical edges from B417's migration, run on this same day): **zero triples of
either type existed, anywhere.** `arc_get_causal_path` has been structurally incapable of
returning `path_exists: True` for any input, ever, since it was built.

### Fix

- **`DERIVED_FROM_FACT`** (ActionFact→ActionEffect, `step INT32` per `schema.py`'s DDL):
  `arc_record_action_effect` already computes both `fact_id`
  (`f"{task_id}_{action_id}"`) and `effect_id` (`f"{task_id}_{action_id}_step{step}"`)
  deterministically in the same call that creates both nodes — every effect observation
  IS, by definition, one of the observations the fact aggregates. New query
  `arc.link_action_fact_derived_from_effect`, wired into `arc_record_action_effect`
  immediately after both nodes are created. Zero new parameters, zero guessing.
- **`REQUIRES_ENTITY`** (`schema.py`: **FROM VictoryCondition TO GridEntity**,
  `requirement STRING`): no existing call site carries entity awareness at all
  (`arc_update_goal_confidence` never has). Rather than invent a heuristic (e.g. a
  GridEntity/VictoryCondition color-id match), extended `arc_update_goal_confidence` with
  an **optional** `entity_ref` parameter (+ optional `requirement`) — the same additive
  pattern `record_rule`/`arc_confirm_hypothesis` already use for exactly this purpose.
  Existing callers (none supply it today) are byte-identical in behavior; a caller that
  knows which entity a goal update is about can now say so. New query
  `arc.link_entity_requires_victory_condition`.

**Correction found mid-implementation:** an early draft classified both edges `"plain"`
based on how the pre-existing read query happened to access them (no property access,
undirected match). That was the wrong signal — `schema.py`'s own Kùzu DDL is authoritative
for `REL_COLUMNS`, and it declares real columns (`step`, `requirement`) on both. Corrected
to `"star"` before shipping; caught immediately by two real Kùzu-backed tests failing
(`Table DERIVED_FROM_FACT does not exist` for the plain-vs-star mismatch surfacing via
`_edge_property_lines`' validation, plus a hand-rolled test fixture needing the new rel
table added to its minimal schema).

Both new handler branches route through `GraphGateway`'s Python dispatch (no `sparql=` on
either `NamedQuery`), matching the established B420/B421 pattern: `ActionFact`/
`ActionEffect`/`VictoryCondition` are addressed directly via `mint_uri` (the caller already
holds their real primary keys); `GridEntity` is resolved via `find_node_uri(task_id,
region_index)`, identical to B420's resolution.

### Proof

`tests/test_b430_causal_path_edges.py` (6 cases): both edges classified `star`;
`arc_record_action_effect` writes `DERIVED_FROM_FACT` with the correct `step`; multiple
effects across steps all derive the same fact (star-shaped, one fact to many effects);
`arc_update_goal_confidence` without `entity_ref` is a byte-identical no-op (regression
safety for every existing caller); with `entity_ref` it writes `REQUIRES_ENTITY` in the
correct direction with the `requirement` property; **and the actual target regression**:
`arc_get_causal_path` now returns `path_exists: True` for a fully-wired chain — the exact
thing it could never do before.

**Verified live against the real running daemon** (not just unit tests): called
`arc_record_action_effect` through the real MCP surface, then queried the live Oxigraph
store directly — `DERIVED_FROM_FACT` landed with `step=1` correctly reified.

Regression: 162 passed across the focused sweep (b430/arc_queries/arc_world_model/
arc_mechanic/oxigraph/gateway/b420/b421/b422/rdf-mapping/b412) + 138 passed across the
full `-k arc` sweep (incl. real Kùzu-backed tests — one hand-rolled minimal-schema fixture
needed the new rel table added). Both static guards clean: schema-conformance ratchet
unchanged (32), Cypher ratchet unchanged (0) — `kuzu_migrate.py`'s unrelated 3 lines from
B417 allowlisted (same category as `export.py`: standalone legacy-engine plumbing, not an
application query).
