# B412 - The 24 Read-Path Schema Violations: Queries That Silently Return Nothing

State: ready
Priority: P0
Branch: feat/b412-read-path-violations

### Problem

B406's schema conformance guard ratchets a baseline of **56 violations** — queries
referencing properties that do not exist in `schema.py`. Splitting them by the
`mutating` flag on their `NamedQuery` shows two very different risk profiles:

| Path | Count | Exposure |
|---|---|---|
| **WRITE** | 32 | ~~Guarded.~~ **Correction (2026-09-08, second pass): this claim doesn't hold either.** All 32 write violations carry their own literal `sparql=` DELETE/INSERT template and dispatch straight to `OxigraphClient.execute_write()`/`execute()`, which does zero property validation. `write_node()`'s `schema.NODE_TABLES` check only runs for NamedQueries with `sparql=None` (the Python-handler path) — none of the 32 use it. Verified live: writing an `ActionFact` then calling `provenance.touch_last_accessed_actionfact` through a real `GraphGateway` silently persists an undeclared `campy:last_accessed_at` triple, no exception. Still out of scope for **this** card (see below) — filed as follow-on work. |
| **READ** | 24 | **Silent.** Returns nothing. No error, no failing test. **7 resolved by deletion — see cluster 1. Remaining 17 resolved in the second pass: 16 fixed/deleted, 1 escalated (see "Open decision" below, now answered).** |

The 32 writes are a documented caller-discipline contract, not bugs (see
`provenance.py`'s `touch_last_accessed` docstring) and remain guarded at runtime.
**This card is about the 24 reads.**

Every previous instance of this exact pattern turned out to be a live production bug:
B404 (decay silently dead for three node types), B405 (concept dedup aborting
mid-merge, alt-label gazetteer never populating), and `Message.content` /
`Concept.prefLabel`, found during the B392–B394 translation batches.

### The clusters

**1. ~~`provenance.find_live_*` on 7 `Arc*` tables~~ — RESOLVED, and my framing was wrong**

> **Correction (2026-09-08).** This card originally called these "the most consequential
> cluster", claiming *"if it cannot match, dedup never finds the existing node and the
> graph accumulates duplicates silently."* **That was false.** All 7 have **zero
> callers**. `provenance.py:525` dispatches dynamically via
> `f"provenance.find_live_{t_lower}"`, and the only tables ever passed to
> `find_live_by_dedupe_key()` are `Lesson`, `Plan`, and `FactEntity`. **No `Arc*` table
> is ever passed.** Nothing was failing, because nothing called them.
>
> The error was reasoning from *"this query is broken"* to *"therefore this path is
> broken"* without checking the path was live. Recorded because it is the third time
> that inference misfired in this migration.

`CONTENT_HASH_TABLES = tuple(t for t in PROVENANCE_TABLES if not t.startswith("Arc"))` —
29 provenance tables, 22 with `content_hash`, 7 `Arc*` deliberately excluded. But
`find_live_*` was generated uniformly for all 29, producing 7 unreachable queries
filtering on a column that by design does not exist.

**Resolved by deletion**, not repair. Fixing them would have required adding
`content_hash` to 7 tables that deliberately exclude it, to serve queries nothing calls.
This card's own rule permits deletion once a query is established unused, and it is.
Baseline **56 → 49**.

If Arc dedup is wanted later it should be designed against the real Arc ingestion path,
not inherited from a generator loop.

**2. `Message.content` (7 violations)** — **RESOLVED.** `Message` has `text_raw`, not
`content`. A straight rename, in both `cypher` and `sparql`, across all 7
`retrieval.get_originating_message_*` queries (5 generated by the `_DIFF_TABLES` loop
plus the standalone `documentextract`/`message` variants). The SPARQL variable name
(`?content`) was kept even though the predicate changed to `campy:text_raw`, because the
one live caller (`current_truth`'s rationale lookup in `thalamus/tools/retrieval.py:527`)
reads `row.get("m.content")`, and `RowDict` resolves a `"m.content"` lookup against a
bare `"content"` key by stripping the `m.` prefix — so the caller needed no change.
Proven with a parametrized test (`tests/test_b412_read_path_fixes.py`) against a real
`OxigraphClient`, with a teeth check confirming the pre-fix SPARQL shape returns nothing
against the same fixture.

**3. `Concept.prefLabel` / `Concept.altLabel` (4 violations)** — **RESOLVED.** These are
not `Concept`/`Decision` columns; they are separate `Label` nodes reached via
`HAS_PREF_LABEL` / `HAS_ALT_LABEL` (both "plain" in `EDGE_REIFICATION`, SKOS pattern).
Fixed `thalamus.file_bridge_concepts`, `file_bridge_concept_relationships`, and
`file_bridge_decisions` (the 4th violation — `Decision.prefLabel` — wasn't called out by
name in the original framing but is the same bug on `Decision`, which is also one of
`HAS_PREF_LABEL`'s declared `FROM` tables) to traverse the real edges, using the same
`GROUP_CONCAT`-over-`OPTIONAL` pattern already established in
`quests.get_concept_with_alt_labels`. Confirmed live and reachable: `campy context regen`
→ `file_bridge.regen_all` → `generate_context_md`/`generate_adrs`. Alt-label results are
expected to stay sparse in production, per B405 (gazetteer write path never populated) —
this is a traversal-shape fix, proven correct against real fixture data with tests, not a
data-population fix.

**4. `ActionFact` (4)** — **RESOLVED by deletion.** `arc.get_action_fact_detail` had
**zero callers**: grepped `campy/`, `tests/`, `scripts/`, and every non-`.venv` file in
the repo for the string, and checked every known dynamic-dispatch pattern
(`gw.run(f"...{key}")`-shaped call sites across the codebase) — none target this query
name. Its 4 missing fields (`evidence_summary`, `sample_count`, `last_tested_step`,
`recommended_next`) don't exist anywhere else in the codebase either — no caller under
any name expects them. The live equivalent, `arc.get_action_evidence` (already
schema-conformant, called from `arc_get_action_evidence` in `arc_queries.py`), already
serves this need. Deleted rather than repaired, same resolution as cluster 1. A
regression-guard test greps the whole tree for the deleted name.

**Singles (2):**
- `capture.get_last_proactive_push_count` — **RESOLVED, schema was wrong.**
  `Session.last_proactive_push_msg_count` is real, live data (B195's Active Context
  Push, `thalamus/tools/capture.py`) — the query was already correct, `schema.py` was
  just missing the declaration. Added to `SCHEMA_MIGRATIONS`. (As a side effect, this
  also resolves the paired write violation, `capture.set_last_proactive_push_count`,
  since both reference the same now-declared column — not something separately "fixed"
  out of scope, just a natural consequence of correcting the shared schema.)
- `quests.get_session_onboarding_status` (`MainQuest.git_branch`) — **escalated, left
  unfixed.** See "Open decision", now answered below.

### Scope

For **each** of the 24: determine whether the query or the schema is wrong, fix the
correct side, and prove the fix with a test asserting the query now returns data —
**not merely that it runs without error.** A query returning `[]` passes today.

Decrement `scripts/schema_conformance_baseline.json` as each is resolved.

### Explicitly NOT in scope

- The 32 write-path violations. They are guarded and documented; leave them ratcheted.
- Do not "fix" a violation by deleting the query without establishing it is unused.

### One correction to make while here

`provenance.py`'s `touch_last_accessed` docstring justifies its caller-discipline
contract with *"would raise from Kùzu."* Kùzu is gone (B397). The guarantee still holds
— `OxigraphClient.write_node()` reimplements the check — but the stated reason is
obsolete. Update it to cite the current mechanism.

### Outcome

The read-path half of the conformance baseline is resolved: 16 of 17 remaining
violations fixed or deleted (with tests proving real, non-empty, correct results against
a live Oxigraph store), 1 escalated with a documented answer. Baseline 49 → 32.

The one violation still open, `quests.get_session_onboarding_status`
(`MainQuest.git_branch`), surfaced a second instance of this card's own trap: the
"more correct" fix (join through `Workspace.branch_name`) turned out to route through a
node type nothing in the codebase ever creates — investigated and rejected rather than
implemented on the strength of being schema-correct. See the NamedQuery's own comment in
`campy/brain/hippocampus/graph/queries/quests.py` for the full reasoning.

Also surfaced, out of this card's scope but recorded for follow-on work: the WRITE-path
"guarded, safe to ratchet" premise that justified excluding 32 violations from this card
does not hold on the current Oxigraph backend — none of the 32 write queries go through
the validated `write_node()`/`write_edge()` path, so they can silently persist
undeclared properties exactly like the read violations this card fixes. Not fixed here
(explicitly out of scope); flagged as a follow-on investigation.

## Open decision for the remaining work

**`MainQuest.git_branch`** (cluster 4, `quests.get_session_onboarding_status`):
`MainQuest` has `git_repo_root` (a filesystem path), not `git_branch`. Two options:

- **Return `git_repo_root`** and let the caller keep its existing `"main"` fallback for
  branch display. Simple, no extra traversal.
- **Join through `Workspace.branch_name`** (B323 added that column). More correct, more
  query complexity.

This turns on whether onboarding status actually needs the *branch* or just the *repo*.
**Escalate rather than choosing** — check what the caller does with the value first, and
report the finding.

> **Answered (2026-09-08, second pass) — left unfixed, escalated to the user.** The
> caller (`get_openclaw_prompt` in `thalamus/tools/quests.py`) does
> `branch = row.get("q.git_branch"); quest_info = {"name": name, "branch": branch or
> "main"}` — it unambiguously wants a branch-name string, which rules out returning
> `git_repo_root` (a path would display as nonsense where a branch name is expected).
> That much is unambiguous from the call site. But the "more correct" option isn't
> actually available: grepping `campy/` for any `write_node("Workspace", ...)` or
> `CREATE`/`MERGE (w:Workspace)` in any `NamedQuery` turns up **zero** — nothing in the
> current codebase ever creates a `Workspace` node, so joining through
> `Workspace.branch_name` would always resolve to nothing, not merely sparse like the
> alt-label gazetteer. Implementing it would pass a fixture-only test while providing zero
> real improvement over today's silent NULL. That's a new fact the original framing
> didn't have, and it isn't resolvable from the call site alone — it's a product decision
> (build real Workspace population first, or accept a repo-path-labeled-as-branch
> string). Left unfixed; full reasoning recorded as a comment on the NamedQuery itself in
> `campy/brain/hippocampus/graph/queries/quests.py`.
