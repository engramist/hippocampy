# B420 - ARC Entity↔Rule/Hypothesis Link Handlers Write the Wrong Edge (`ANCHORED_TO` plain) With Wrong Endpoints — Entity Mapping Is Structurally Impossible

State: ready
Priority: P1
Branch: fix/b420-entity-rule-hypothesis-link-handlers

### Problem

The Python handler branches for `arc.link_entity_rule` and `arc.link_entity_hypothesis`
(`campy/brain/hippocampus/graph/gateway.py:522-527`) write the **wrong edge to the wrong
nodes**, so an ARC entity is never linked to the rules/hypotheses that constitute its
evidence. Result: `arc_get_entity_neighborhood` always returns
`{hypotheses:[], rules:[], mechanics:[]}`, and the client's `entities_mapped` counter can
never move off `0` — regardless of run length. Found live on 2026-09-09 during a paired
ARC_AGI smoke test (task `wa30-ee6fef47`): `entities_mapped` stayed `0/12` every cycle.

```python
if name == "arc.link_entity_hypothesis":
    self._client.write_edge("ANCHORED_TO",
        mint_uri("InvestigationThread", params["tid"]),
        mint_uri("Hypothesis", params["hid"]),
        {"weight": params.get("weight"), "step": params.get("step")})
    return []
if name == "arc.link_entity_rule":
    self._client.write_edge("ANCHORED_TO",
        mint_uri("InvestigationThread", params["tid"]),
        mint_uri("Rule", params["rid"]),
        {"weight": params.get("weight"), "step": params.get("step")})
    return []
```

Three defects:

1. **Wrong edge label.** Writes `ANCHORED_TO`, which is classified `"plain"` — no
   properties — in `oxigraph_client.py:278`, but passes `{weight, step}`. This **raises**:
   `RuntimeError: ANCHORED_TO is classified 'plain' (no properties) but properties were
   passed: ['step', 'weight']` (observed under `method=record_rule`, `status=error`/
   `degraded`, 2026-09-09 22:21–22:22Z). The queries' own cypher templates declare the
   correct edges — `MERGE (ge)-[er:ENTITY_RULE]->(r)` (`queries/arc.py:1092`) and
   `MERGE (ge)-[eh:ENTITY_HYPOTHESIS]->(h)` (`queries/arc.py:762`) — both classified
   `"star"` (properties allowed, `oxigraph_client.py:389-390`). The handler contradicts
   the query it implements.
2. **Wrong source node.** Mints `InvestigationThread` from `params["tid"]`, but in these
   queries `tid` is the **task_id**, not a thread id. The cypher matches
   `(ge:GridEntity {task_id: $tid, region_index: $eref})` — the source must be the
   GridEntity, not a thread.
3. **`eref` ignored entirely.** The entity the rule/hypothesis is about
   (`region_index = $eref`) is never used, so even the intended endpoint is lost.

### Impact

- `record_rule(..., entity_ref=…)` and the hypothesis-confirm/contradict path both call
  these links; the write raises and the entity evidence edge is never created.
- `arc_get_entity_neighborhood` (which reads `ENTITY_RULE`/`ENTITY_HYPOTHESIS` via
  `arc.get_entity_rules`/`arc.get_entity_hypotheses`) therefore returns empty for every
  entity. Verified: graph has 14 Rule + 14 GridEntity nodes but **0 rule↔entity edges**,
  0 hypothesis↔entity edges.
- Cynefin "mapping" (moving an entity off DISORDER) depends on that neighborhood evidence,
  so `entities_mapped` is pinned at 0. This is a silent capability failure, not cold-start.

Same family as B413's `HAS_ALT_LABEL`/`dict_link_*` plain-edge mismatch, but **breaking
(raises)** rather than inert — and here the endpoints are wrong too, so it is not a pure
classification issue.

### Fix

Rewrite both handler branches to match their cypher templates:

- Resolve the GridEntity subject URI by `(task_id = tid, region_index = eref)` — a
  two-property lookup (extend the B418 `find_subject_uri` helper to accept multiple
  `(pred, value)` pairs, or add a small `find_grid_entity_uri(task_id, region_index)`).
- `write_edge("ENTITY_RULE", entity_uri, mint_uri("Rule", rid), {"weight": …, "step": …})`
  and likewise `ENTITY_HYPOTHESIS` → `mint_uri("Hypothesis", hid)`. Both are `"star"`
  edges, so `write_edge` carries the props.
- Confirm the round-trip: after `record_rule(entity_ref=e)`,
  `arc_get_entity_neighborhood(entity_ref=e)` returns the rule; likewise for a confirmed
  hypothesis. A test asserting NON-EMPTY neighborhood after a link (the same shape as
  B412/B418 proof tests) prevents regression.

Consider a guard: a handler `write_edge(rel, …, props)` where `rel` is classified `"plain"`
but `props` is non-empty should fail at registration/test time, not only at runtime — this
class of bug (B413, B420) keeps recurring.

### Provenance

Found by hippocampy-75 pairing with the ARC_AGI client session (arc-agi-31) on a live
smoke test of the recent rework. The client correctly flagged `entities_mapped=0` as
suspicious rather than assuming cold-start; root-caused server-side here. Relates to B309
