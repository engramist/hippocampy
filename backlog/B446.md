### Note on origin

Filed in response to a direct question during this session's B434-B440
backlog-cleanup thread: "where are the cards for getting benchmarks
with the external benchmarks." Checked the whole backlog by grep for
`campy-benchmarks`/"re-run"/"corrected baseline" and confirmed: **no
card exists for this.** B381 built the harness, B415/B416 fixed its
measurement integrity, B436/B438/B439 fixed three real bugs the
harness's own use surfaced — but nothing tracks the obvious next step:
actually running it again now that the bugs are fixed, to get a real
"After" number.

### The gap

`docs/benchmarks/kuzu-baseline-kpis.md` (committed via
[PR #229](https://github.com/engramist/hippocampy/pull/229) — itself
an orphaned document recovered from the working tree, never
purpose-committed) is the **only** external-benchmark data point that
exists anywhere in this repo, and it's the **"Before" snapshot**:
dated 2026-09-04/06, git anchor `d35b28b`, running against the legacy
**Kùzu** engine, before B389/B397's cutover to Oxigraph, and before
B434/B436/B438/B439's fixes. There is no "After" run anywhere —
`~/.campy/eval_results/` and the sibling repo's own output files are
gitignored/runtime-only by design, so nothing durable exists past that
one committed snapshot.

### Why this run should look very different now — the B434 connection

The orphaned baseline doc's own root-cause section documented very low
external scores at the time: **MemoryGym 0.0% episode success**,
**MemBench 0.0 persona fact precision / 0.0% token savings**, LoCoMo
F1 0.0407. Its root-cause analysis blamed an "asynchronous ingestion
race condition" — probe queries running before the background
consolidation loop had processed queued turns.

**This session found something worse, later, independently**: B434
(merged via [PR #230](https://github.com/engramist/hippocampy/pull/230))
found the Gated Consolidation Loop worker had an **unconditional queue
tuple-arity crash** — not a timing race, a hard crash on the very
first `.get()`, permanently crash-looping the entire background
consolidation pipeline. Git blame showed this bug had been live since
at least 2026-07-13, predating the original benchmark run by nearly
two months. **The original run's near-zero MemoryGym/MemBench scores
were very plausibly caused by B434's bug, not (or not only) the timing
race the original report blamed** — if the consolidation loop was
permanently dead the whole time, no amount of waiting for it would
have helped, which the original report's own "wait and it eventually
gets there" framing didn't anticipate.

With B434 now fixed, there is a real, concrete, testable hypothesis
that a fresh run will show dramatically different — likely much
better — MemoryGym/MemBench numbers, not just marginal improvement.
This is worth confirming rather than assuming.

### What else has changed since the orphaned baseline

- **B389/B397**: full engine cutover, Kùzu → Oxigraph. The "Before"
  numbers are for a since-retired engine.
- **B434**: the loop-worker crash above.
- **B436**: MemBench's `token_count` key bug — the original 0.0% token
  savings figure was **partly a harness bug**, not real. Now fixed;
  a fresh run should show a real, non-artifact number for the first
  time.
- **B438**: mock-client state leak — only matters in `--smoke` mode,
  not a real daemon run, but affects `run_all.py --smoke --suite all`
  specifically, which the old reproduction command used.
- **B439**: unrelated (internal CI timing test), doesn't affect
  external benchmark numbers.
- **B435/B437**: `bundle_compiler.py` fixes (lexical fallback,
  flagged/archived exclusion) — could shift Ask-Eval-adjacent and
  `ask()`/`compile_context()`-backed suite behavior, if any of the
  external suites route through those paths.

### Scope

   confirm health (`campy status` / the `/health` endpoint).
2. Run the external harness for real (not `--smoke`, which uses the
   mock client and wouldn't exercise any of B434/B436's real fixes) —
   the old reproduction command in
   `docs/benchmarks/kuzu-baseline-kpis.md` §7 is the starting point:
   ```bash
   cd /Users/djshelton/Desktop/GitProjects/campy-benchmarks
   CAMPY_SOCKET_PATH=<path> CAMPY_MCP_CMD="<python_exec> -m campy.adapters.mcp_server" python run_all.py --baseline --out post_cutover_live.json
   ```
   Verify `campy.adapters.mcp_server` still resolves as a valid module
   path first (spot-checked during this card's filing — it does,
   confirm again at implementation time since more has landed since).
3. Write a new, dated report analogous in structure to
   `docs/benchmarks/kuzu-baseline-kpis.md` (e.g.
   `docs/benchmarks/post-cutover-kpis.md`), explicitly comparing
   against the committed "Before" numbers section-by-section, with
   particular attention to whether the MemoryGym/MemBench hypothesis
   above holds up against real data rather than assumption.
4. If MemBench/LoCoMo/MemoryGym scores are still low after all four
   fixes, root-cause that too rather than assuming success — this
   card's job is to get a real number, not a good-looking one.
