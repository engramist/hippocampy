### Why this run should look very different now — the B434 connection

The orphaned baseline doc's own root-cause section documented very low
external scores at the time: **MemoryGym 0.0% episode success**,
**MemBench 0.0 persona fact precision / 0.0% token savings**, LoCoMo
F1 0.0407. Its root-cause analysis blamed an "asynchronous ingestion
race condition" — probe queries running before the background
consolidation loop had processed queued turns.

**This session found something worse, later, independently**: B434
(merged via [PR #230](https://github.com/engramist/hippocampy/pull/230))
found the Gated Consolidation Loop worker had an **unconditional queue
tuple-arity crash** — not a timing race, a hard crash on the very
first `.get()`, permanently crash-looping the entire background
consolidation pipeline. Git blame showed this bug had been live since
at least 2026-07-13, predating the original benchmark run by nearly
two months. **The original run's near-zero MemoryGym/MemBench scores
were very plausibly caused by B434's bug, not (or not only) the timing
race the original report blamed** — if the consolidation loop was
permanently dead the whole time, no amount of waiting for it would
have helped, which the original report's own "wait and it eventually
gets there" framing didn't anticipate.

With B434 now fixed, there is a real, concrete, testable hypothesis
that a fresh run will show dramatically different — likely much
better — MemoryGym/MemBench numbers, not just marginal improvement.
This is worth confirming rather than assuming.

### Completion notes (2026-09-22)

The real run was executed exactly per this card's scope: daemon
restarted clean on current `main`, `run_all.py --baseline` (not
`--smoke`) run against it over real MCP/STDIO transport. Full writeup:
[`docs/benchmarks/post-cutover-kpis.md`](../docs/benchmarks/post-cutover-kpis.md).

**Result: scores are still near-zero, but the B434-crash hypothesis
this card was built on turned out to be incomplete.** The run caught a
new, live, currently-reproducing P0 bug — [B447](B447.md): the Gated
Consolidation Loop worker takes roughly **96 minutes** to process the
very first real message after a daemon restart, silently, with every
other `notify_turn` queued behind it (confirmed live during this run
via daemon.log timestamps; it does eventually clear and then catches up
normally — B447 originally described this as a permanent stall and was
corrected the same day after continuing to observe the live process).
B434 fixed a *crash* in this worker; it did not fix this separate
first-item latency problem. Every probe in this benchmark run finished
well before that 96-minute window closed, so a 0% score is exactly what
that predicts. A secondary, always-broken issue was also found and
filed as [B448](B448.md) (the harness's `run_sweep()` calls target an
MCP tool that has never existed, silently no-op'ing since the harness's
first commit — predates B434 entirely).

This card is marked `blocked` rather than `fixed` — the actual
deliverable (a real, meaningful "after" comparison) doesn't exist yet,
because B447 alone would have zeroed out these suites' scores
regardless of anything else. Re-run this same reproduction once B447
(and ideally B448) land; see `post-cutover-kpis.md` §4/§5 for the exact
steps. This card's own acceptance criteria (a real run executed, root
cause investigated rather than assumed, new bugs filed) are otherwise
satisfied.

### Completion notes, round 2 (2026-09-23)

Re-ran per the plan above, once [B447](B447.md)'s per-write timeout fix
merged ([PR #246](https://github.com/engramist/hippocampy/pull/246)).
Full writeup: `docs/benchmarks/post-cutover-kpis.md` §2b.

**Scores are still 0.0% across LoCoMo/MemoryGym/MemBench, identical to
before, even though B447's fix is confirmed genuinely working** — the
daemon logged 400+ real consolidation completions during this run
(versus zero, frozen, during the first attempt). Investigating why the
numbers didn't move despite that found a third, distinct, unrelated
bug: [B449](B449.md) — `campy.adapters.mcp_server` (the MCP server the
benchmark harness talks to) silently gives up on every tool call after
~6-12 seconds, using a timeout budget meant for implicit background
paths, not the explicit external tool-call traffic this adapter
actually handles. The daemon is real and slower than that under load
(directly observed: 30-45s per real `ask()` call earlier in this same
investigation), so the harness has never once, in any run across this
entire investigation (including the original pre-cutover "Before"
baseline), waited long enough to see a real answer. Every "latency"
number ever reported by this harness has been measuring that timeout
firing, not the daemon.

Remains `blocked` — B449 is believed to be the last blocker. Re-run
this same reproduction a third time once it lands.

### Completion notes, round 3 (2026-09-23) -- DONE

Root cause of the chain's final blocker (and of the mid-run daemon deaths and
slow writes seen in rounds 1-2): [B451](B451.md) — an exponential reifier
blowup in the CO_OCCURS_WITH / semantic-relation upserts, killed by macOS
jetsam at ~120 GB. With B448 (settle), B449 (adapter timeout), B450 (strict
harness), B451 fixed and the live store cleaned, a full run is valid for the
first time: `post_cutover_live_v4.json`, 648 calls / 0 failures, ~26 min.
Numbers and analysis: `docs/benchmarks/post-cutover-kpis.md` §2c. The scores
are low (LoCoMo F1 0.011, others 0) for real retrieval/consolidation reasons,
tracked in [B454](B454.md). This card's deliverable (a real After measurement)
is met.
