# B364 - `campy start`/`stop` Have No Fallback When the Daemon Isn't Launchd-Managed (macOS)

State: ready
Priority: P2

Plan: none yet.

### Problem

Found live 2026-08-25 while restarting the brain daemon to pick up B363's fix (a long-running
daemon process only loads new code on its own restart — restarting a client/adapter subprocess
doesn't help). `campy stop` reported `"Failed to stop Brain Daemon via launchd."` and the
subsequent `campy start` reported `"Failed to start Brain Daemon via launchd."`, leaving the
daemon fully offline (`~/.campy/brain.sock` gone) until it was started manually.

Root cause: `campy/cli/main.py`'s `start()`/`stop()` commands (lines 225-260), on Darwin, call
*only* `campy/cli/launchd.py`'s `load_plist()`/`unload_plist()` — there is no fallback path on
macOS (the raw-subprocess fallback in both functions is gated to the `else` branch, i.e.
non-Darwin only). `load_plist()` immediately returns `False` if the plist file doesn't exist at
`get_launchd_plist_path()` (`~/Library/LaunchAgents/ai.hippocampy.brain.plist` by default) —
it never attempts `generate_plist()` first. In this environment, only
`dev.hippocampy.indicator.plist` was present; no plist existed for the daemon itself, even though
a daemon process (PID 97163, uptime tracked back to 21:51:01) had clearly been running for hours —
meaning it was started some other way (manually, or via a mechanism that predates/bypasses
`campy start`), not via `campy start`/launchd at all.

Secondarily: `unload_plist()` reported failure (`stop` printed the red failure message) but the
daemon process was, in fact, killed cleanly (`daemon.log` shows a normal `"Brain Daemon stopped."`
shutdown sequence) — likely `unload_plist()`'s `is_loaded()` post-check raced launchd's own state
update and returned a false negative. Not chased further here since the practical failure (no
fallback + no plist) is the actionable part; this is secondary noise on top of it.

Not urgent in the sense that a manual `nohup .venv/bin/python brain_daemon.py &` immediately
recovered the daemon, but the *lack of any macOS fallback* meant `campy start`'s own documented
purpose ("Start the HippoCampy memory daemon") does not do that reliably in the exact common case
where no plist has ever been generated for this checkout/install — a realistic first-run and
recovery-from-incident scenario.

### What it does (scope)

1. Give `campy start`'s Darwin branch a fallback: if `load_plist()` fails because the plist
   doesn't exist, call `generate_plist()` (already implemented in `launchd.py`) to create it, then
   retry `load_plist()` — and only fall back to a raw `subprocess.Popen` (matching the existing
   non-Darwin path) if that still fails.
2. Consider whether `campy start` should attempt plist generation unconditionally on first run,
   rather than only reactively after a failure — needs a decision, not assumed here.
3. Investigate the `unload_plist()` false-negative (`is_loaded()` racing launchd's own state after
   `launchctl remove`/`unload`) — likely a short retry/poll before returning, rather than checking
   immediately.

### Dependencies

None.

### Files to create/modify

- `campy/cli/main.py` — `start()`/`stop()` (lines 225-260).
- `campy/cli/launchd.py` — `load_plist()`, `unload_plist()`, possibly wiring in `generate_plist()`.

### Acceptance Criteria

- [ ] `campy start` on macOS succeeds even when no plist has ever been generated for this install.
- [ ] `campy stop`'s reported success/failure accurately reflects whether the daemon process
      actually stopped.
- [ ] Regression test covering the no-plist-yet `campy start` case.
