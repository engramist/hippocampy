# B280 - Server-Side Traversal for explore_graph

State: complete — 2026-08-03. Fixed the real bug: `explore_graph`'s frontier expansion now uses one unlabeled-node query per direction per depth level, filtered by Kuzu internal id (`id(a) IN [INTERNAL_ID(table, offset), ...]`) instead of a `UNION ALL` across one MATCH branch per node table. The old query shape hit `RuntimeError: Binder exception: a has data type NODE but NODE was expected.` on every real call once enough differently-typed node tables were unioned — confirmed by reproducing the exact error against a real temp KuzuDB built with the full production schema (`init_schema`, 12 node tables, 92 relationship types), then confirming the fixed query returns correct results against that same real schema. See Implementation section below for the full root-cause and fix writeup, and the original Audit Findings (preserved for history) further down.
Priority: P1

Plan: backlog/plans/B-280-server-side-traversal.md

### Problem

`campy/brain/thalamus/tools/explore_graph.py` walks the graph in Python. `_get_neighbors()` issues one Cypher query per (node table × relationship type × direction) combination — 12 node tables × ~90 rel types × 2 directions ≈ up to 2,000+ queries per node expansion — and `_get_node_data()` adds another query per visited node. A depth-3 BFS over a modest graph can issue tens of thousands of round-trips. This is the classic "traversal in application code" anti-pattern; Kuzu supports multi-label patterns and bounded variable-length relationships server-side.

The same N+1 pattern appears in `_add_temporal_context()` (same file) and in `step5_retrieval.py`'s `_get_neighbor_set()`.

### What This Card Does

1. Rewrites `explore_graph`'s neighbor expansion to use a small number of server-side Cypher queries with variable-length bounded paths and multi-relationship patterns.
2. Keeps the existing tool contract (params and response shape) byte-compatible — callers and tests must not notice.
3. Applies the same batching to `_get_neighbor_set()` in step5.

### Dependencies

- B279 recommended first (P0) but not technically required — no shared files except minor step5 overlap.

### Files to Modify

- `campy/brain/thalamus/tools/explore_graph.py` — replace `_get_neighbors`/`_get_node_data` per-row loops
- `campy/brain/temporal_lobe/loop/step5_retrieval.py` — batch `_get_neighbor_set`
- `tests/test_explore_graph.py` (or wherever explore_graph tests live — find with `rg -l "explore_graph" tests/`) — add a query-count regression test

### Acceptance Criteria

- [x] A single `explore_graph` call at depth 3 issues ≤ 30 Cypher queries (measured by a counting wrapper in the test), down from potentially thousands
- [x] Response shape unchanged: `{paths: [{nodes, edges, path_depth, path_strength}], total_nodes_visited, exploration_complete, exploration_truncated, context_window}`
- [x] Cycle prevention, depth clamp (≤5), MAX_NODES=1000 bound, and edge-type allowlist all preserved

- [x] `_get_neighbor_set` in step5 issues 1 query per direction instead of 1 per (table × rel) — already true before this card; see Audit Findings below. No change needed.

### Outcome

`explore_graph` becomes usable on graphs beyond toy size; the flagship multi-hop tool does its traversal where traversal belongs — in the database engine.

### Audit Findings (2026-08-03 re-verification, historical — issue is now fixed, see Implementation below)

Severe real bug, the worst found in this audit batch: `explore_graph`'s server-side neighbor expansion is completely non-functional against the real database — it silently visits ONLY the start node and returns zero neighbors, at any depth, for any graph, in production. Root cause in `campy/brain/thalamus/tools/explore_graph.py::_build_frontier_query` (~L60-76): it builds a single query as `UNION ALL` across one branch per node table in `_NODE_TABLES` (~12+ tables), e.g. `MATCH (a:Concept)-[r:...]->(b) ... RETURN a, b, ... \nUNION ALL\n MATCH (a:Decision)-[r:...]->(b) ... RETURN a, b, ...` etc. Reproduced directly against a real temp KuzuDB (`init_schema`, no mocks): a 2-branch version of exactly this UNION ALL pattern (Concept branch + Decision branch, both from the real schema) raises `RuntimeError: Binder exception: a has data type NODE but NODE was expected.` on kuzu==0.11.3 — Kuzu's binder requires UNION ALL branches to return the *same concrete node table type* per column, not just any NODE; unioning different node tables' typed columns is rejected. The exact same single-table query (no UNION) with the FULL multi-relationship-type OR-pattern (`[r:TYPE1|TYPE2|...]`) works fine in isolation — the multi-rel-type pattern is not the problem, the cross-table UNION ALL is. This exception is caught by a bare `except Exception: _logger.exception(...)` in `_execute_frontier_query` (L111-112) and silently converted to an empty result list, so every real `explore_graph()` call returns `{"paths": [], "total_nodes_visited": 1, "exploration_complete": True}` — it reports SUCCESS while doing nothing. Confirmed end-to-end: built a real 6-node chain graph (`n0→n1→n2→n3→n4`, `n1→n5`) via REQUIRES edges, called the real `explore_graph({"start_node_id": "n0", "depth": 3, ...})` against it — result was `total_nodes_visited: 1`, `paths: []`, `exploration_complete: True` (should have visited n1/n2/n3/n5). `pytest tests/test_explore_graph.py -q` → 14 passed, fully green, because `MockDB.execute()` (test file L126-167) pattern-matches on query substrings and returns preprogrammed rows regardless of whether the query is valid Kuzu Cypher — it never actually validates the query against real schema/type rules, so it cannot catch a Kuzu binder-level rejection. Same MockDB-blind-spot class as B278/B283/B284. The query-budget acceptance criterion (`≤30 queries at depth 3`) is technically "met" (4 real queries observed) but only because traversal does nothing — a vacuous pass, not evidence of correctness. By contrast, `step5_retrieval.py::_get_neighbor_set` (also in this card's scope) is NOT affected: it queries only `(c:Concept)-[r]->(n:Concept)` (single node table on both ends, no cross-table UNION), confirmed working correctly against the same real DB (`_get_neighbor_set(db, ['n0'])` correctly returned `{'n1'}`). `_add_temporal_context` (same file) uses the identical `_expand_frontier`/`_build_frontier_query` path and was equally broken for the same reason.

### Implementation (2026-08-03)

**Fix:** replaced the per-node-table `UNION ALL` in `_build_frontier_query` with a single unlabeled-node query per direction per depth level, filtered by Kuzu's internal id: `MATCH (a)-[r:TYPE1|TYPE2|...]->(b) WHERE id(a) IN [INTERNAL_ID(table, offset), ...] RETURN a, b, label(r), coalesce(r.confidence, 1.0)`. Leaving `a`/`b` unlabeled makes Kuzu scan every node table in one query — no union, so no cross-table type mismatch.

**Why internal ids, not primary keys:** an unlabeled node pattern can't filter on a primary-key property (`a.concept_id = ...`) because different node tables use different pk column names (`concept_id`, `decision_id`, `quest_id`, ...) — Kuzu can't resolve `a.concept_id` for an unlabeled `a` that might be a `Decision` row. `id(a)` (Kuzu's internal row id) works uniformly across every table, but there's no working *parameterized* form: passing the `{"table": int, "offset": int}` struct Kuzu's Python client returns from `id(a)` back as a query parameter fails to bind (`Cannot compare types INTERNAL_ID and STRUCT(offset INT8, table INT8)` — confirmed empirically). `INTERNAL_ID(table, offset)` is a real Kuzu constructor function, so the fix builds the id list as a literal directly in the query text (`_internal_id_literal`) instead of a parameter. table/offset are small non-negative ints minted by Kuzu itself via a prior `id(n)` call — never user-controlled strings — so this isn't a string-injection risk.

**Verification methodology:** every claim above was checked empirically against a real Kuzu 0.11.3 database, not just plausible-sounding Cypher:
1. Reproduced the exact reported binder error against a real temp DB built with the *full* production schema (`init_schema` — 12 node tables, 92 relationship types), matching the audit's own repro methodology.
2. Probed the internal-id-literal approach against a toy 2-table fixture first, then against that same full 12-table/92-rel-type schema, confirming it returns correct results where the old query threw.
3. Ran the exact end-to-end scenario from the audit (`n0→n1→n2→n3→n4`, `n1→n5` via REQUIRES, depth 3) through the real `explore_graph()` — result: `total_nodes_visited: 5`, 4 paths, all reaching n1/n2/n3/n5 and correctly excluding n4 (4 hops away, beyond the depth cap). This is the exact case the audit found broken.

**Other changes in the same file:**
- The start-node resolution query now does `RETURN n, id(n) LIMIT 1` instead of a bare existence check, so the node's own properties and its internal id both come back in one query — this eliminates the separate `_get_node_data()` round-trip entirely (now dead code, removed).
- `_get_neighbors()` was unused (no internal or external callers) and is also removed.
- `_add_temporal_context()` now takes an `internal_id_cache` (built once during `_traverse()`) instead of re-deriving frontier ids from primary keys, since primary keys alone can no longer seed a frontier query.
- `_get_neighbor_set()` in `step5_retrieval.py` was left unchanged — the audit already confirmed it queries only `(c:Concept)-[r]->(n:Concept)` (single node table both ends, no cross-table UNION, already just 2 queries total regardless of graph size), so it was never affected by this bug and needs no batching work.

**Tests:**
- `tests/test_explore_graph.py`: existing 14 mocked tests kept exactly as-is at the assertion level. `MockDB` was updated to simulate the new query shape (assigns each known node a fake internal id, parses `INTERNAL_ID(table, offset)` literals back out of the query text via regex instead of reading an `ids` param) — this is the AC's "existing tests pass unchanged" satisfied at the behavioral-spec level, since a mock that pattern-matches query substrings can't stay byte-identical to a genuinely different (and now correct) query shape.
- `tests/test_explore_graph_real_kuzu.py` (new, TDD — written and confirmed RED against the pre-fix code, reproducing the literal reported binder error, before implementing): 8 tests against a real Kuzu DB built with the full production schema — multi-hop traversal correctness (including the exact audit repro scenario), depth-1 truncation, edge metadata correctness, the full 92-rel-type default pattern (not just a filtered one), cycle prevention, incoming/outgoing direction filtering, and the ≤30-query budget AC, all against real data.
- Full suite: `.venv/bin/python -m pytest -q` → 1657 passed, 31 skipped, 2 xfailed (was 1649 before this card; +8 for the new real-Kuzu tests, no regressions).
