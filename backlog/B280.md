# B280 - Server-Side Traversal for explore_graph

State: needs work — reopened 2026-08-03. Severe real bug, the worst found in this audit batch: `explore_graph`'s server-side neighbor expansion is completely non-functional against the real database — it silently visits ONLY the start node and returns zero neighbors, at any depth, for any graph, in production. Root cause in `campy/brain/thalamus/tools/explore_graph.py::_build_frontier_query` (~L60-76): it builds a single query as `UNION ALL` across one branch per node table in `_NODE_TABLES` (~12+ tables), e.g. `MATCH (a:Concept)-[r:...]->(b) ... RETURN a, b, ... \nUNION ALL\n MATCH (a:Decision)-[r:...]->(b) ... RETURN a, b, ...` etc. Reproduced directly against a real temp KuzuDB (`init_schema`, no mocks): a 2-branch version of exactly this UNION ALL pattern (Concept branch + Decision branch, both from the real schema) raises `RuntimeError: Binder exception: a has data type NODE but NODE was expected.` on kuzu==0.11.3 — Kuzu's binder requires UNION ALL branches to return the *same concrete node table type* per column, not just any NODE; unioning different node tables' typed columns is rejected. The exact same single-table query (no UNION) with the FULL multi-relationship-type OR-pattern (`[r:TYPE1|TYPE2|...]`) works fine in isolation — the multi-rel-type pattern is not the problem, the cross-table UNION ALL is. This exception is caught by a bare `except Exception: _logger.exception(...)` in `_execute_frontier_query` (L111-112) and silently converted to an empty result list, so every real `explore_graph()` call returns `{"paths": [], "total_nodes_visited": 1, "exploration_complete": True}` — it reports SUCCESS while doing nothing. Confirmed end-to-end: built a real 6-node chain graph (`n0→n1→n2→n3→n4`, `n1→n5`) via REQUIRES edges, called the real `explore_graph({"start_node_id": "n0", "depth": 3, ...})` against it — result was `total_nodes_visited: 1`, `paths: []`, `exploration_complete: True` (should have visited n1/n2/n3/n5). `pytest tests/test_explore_graph.py -q` → 14 passed, fully green, because `MockDB.execute()` (test file L126-167) pattern-matches on query substrings and returns preprogrammed rows regardless of whether the query is valid Kuzu Cypher — it never actually validates the query against real schema/type rules, so it cannot catch a Kuzu binder-level rejection. Same MockDB-blind-spot class as B278/B283/B284. The query-budget acceptance criterion (`≤30 queries at depth 3`) is technically "met" (4 real queries observed) but only because traversal does nothing — a vacuous pass, not evidence of correctness. By contrast, `step5_retrieval.py::_get_neighbor_set` (also in this card's scope) is NOT affected: it queries only `(c:Concept)-[r]->(n:Concept)` (single node table on both ends, no cross-table UNION), confirmed working correctly against the same real DB (`_get_neighbor_set(db, ['n0'])` correctly returned `{'n1'}`). Not fixed here — this needs a real design change (e.g. per-table queries batched only by ids-list, capped at len(_NODE_TABLES) per direction per depth level instead of one UNION ALL; or investigating whether Kuzu 0.11.3 supports multi-label node patterns like `(a:Concept|Decision|...)` as an alternative to UNION ALL), not a one-line fix, and it changes the query-count math the AC depends on. `_add_temporal_context` (same file) uses the identical `_expand_frontier`/`_build_frontier_query` path and is equally broken for the same reason.

### Problem

`campy/brain/thalamus/tools/explore_graph.py` walks the graph in Python. `_get_neighbors()` issues one Cypher query per (node table × relationship type × direction) combination — 12 node tables × ~90 rel types × 2 directions ≈ up to 2,000+ queries per node expansion — and `_get_node_data()` adds another query per visited node. A depth-3 BFS over a modest graph can issue tens of thousands of round-trips. This is the classic "traversal in application code" anti-pattern; Kuzu supports multi-label patterns and bounded variable-length relationships server-side.

The same N+1 pattern appears in `_add_temporal_context()` (same file) and in `step5_retrieval.py`'s `_get_neighbor_set()`.

### What This Card Does

1. Rewrites `explore_graph`'s neighbor expansion to use a small number of server-side Cypher queries with variable-length bounded paths and multi-relationship patterns.
2. Keeps the existing tool contract (params and response shape) byte-compatible — callers and tests must not notice.
3. Applies the same batching to `_get_neighbor_set()` in step5.

### Dependencies

- B279 recommended first (P0) but not technically required — no shared files except minor step5 overlap.

### Files to Modify

- `campy/brain/thalamus/tools/explore_graph.py` — replace `_get_neighbors`/`_get_node_data` per-row loops
- `campy/brain/temporal_lobe/loop/step5_retrieval.py` — batch `_get_neighbor_set`
- `tests/test_explore_graph.py` (or wherever explore_graph tests live — find with `rg -l "explore_graph" tests/`) — add a query-count regression test

### Acceptance Criteria

- [ ] A single `explore_graph` call at depth 3 issues ≤ 30 Cypher queries (measured by a counting wrapper in the test), down from potentially thousands
- [ ] Response shape unchanged: `{paths: [{nodes, edges, path_depth, path_strength}], total_nodes_visited, exploration_complete, exploration_truncated, context_window}`
- [ ] Cycle prevention, depth clamp (≤5), MAX_NODES=1000 bound, and edge-type allowlist all preserved
- [ ] Existing explore_graph tests pass unchanged
- [ ] `_get_neighbor_set` in step5 issues 1 query per direction instead of 1 per (table × rel)

### Outcome

`explore_graph` becomes usable on graphs beyond toy size; the flagship multi-hop tool does its traversal where traversal belongs — in the database engine.
