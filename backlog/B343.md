# B343 - Root-Cause B342's Leak: Real Heap Profiling on a Grown brain_daemon.py Process

State: complete — superseded by B342's actual resolution, not this card's proposed method
Priority: P0

Plan: none yet — this is an investigation card. A fix plan should be written once the actual leaking
object type is identified.

### Problem

`backlog/B342.md` documents a live `brain_daemon.py` process observed at a **99.0GB physical
footprint** (`vmmap -summary <pid>`; `ps -o rss=` badly undercounts it — it only showed 1.8-5.4GB,
since it doesn't count the ~94.5GB that was swapped/compressed out of a 95.4GB `MALLOC_SMALL` zone,
24,433 individual regions) on a process holding only 5 concepts and 8 messages in its graph. The
`ask` MCP tool (retrieval + thalamic compression + LLM synthesis) was non-functional on that exact
process ("Brain: OFFLINE - memory unavailable") while lighter endpoints (`/health`, `current_truth`)
still worked — this is a real, severe problem degrading a core feature, not just a large but harmless
number.

B342's own diagnostic pass (2026-08-21) read `campy/brain/brainstem/sweep.py`'s error-counting logic
and found nothing obviously wrong (the repeating `[Sweep] ... errors=21` line comes from a fresh local
counter per call, not an accumulating list) — but that was a code-reading check, not a heap profile.
`py-spy` was not available in that environment. **This card is that missing profiling step.**

### What it does (scope)

1. Install `py-spy` (`pip install py-spy` or `brew install py-spy` on macOS — it's a standalone
   sampling profiler that attaches to a running process without needing debug hooks compiled in;
   confirm it can actually attach on this machine — macOS SIP sometimes requires `sudo` or a specific
   entitlement for `py-spy` to attach to another user's process; if it can't attach at all, fall back
   to option 3 below).
2. Reproduce the growth under controlled conditions: start a fresh `brain_daemon.py` (use
   `launchctl kickstart -k ai.hippocampy.brain` if it's launchd-managed, per B342's diagnostic notes —
   confirm the exact service name via `launchctl print` first, or start it manually per
   `docs/` install instructions if not launchd-managed in this environment) and drive it with
   sustained realistic traffic for long enough to see meaningful growth — either: (a) coordinate with
   the ARC_AGI-side Claude Code session (message it via cross-session messaging, name `arc-agi-4d` or
   whatever the current live peer is named — check `ListAgents` first) to run several consecutive
   `make smoke` episodes back to back against it, or (b) if the ARC agent isn't available, write a
   longer-running synthetic driver reusing the pattern from B311's isolated-repro harness (real
   `arc_perceive_state`/`record_transition`/`record_rule` calls against the real daemon over MCP, not
   the standalone scratch-DB harness — this needs to go through the real daemon process to reproduce
   the real leak, not a fresh in-process `KuzuClient`).
3. Once the process has grown to at least several hundred MB above its fresh-start baseline, take a
   `py-spy dump --pid <pid>` (stack sample) and, if `py-spy`'s memory/dump features don't give enough
   detail, also try `tracemalloc`: since you can't retroactively enable `tracemalloc` on an already-running
   process without restarting it, this means starting the *next* test run with `tracemalloc.start()`
   added near the top of `brain_daemon.py`'s `main()` (temporarily, for this investigation — revert
   before merging anything, or gate it behind an env var like `CAMPY_TRACEMALLOC=1` if you want to keep
   it as a permanent opt-in debug flag, coordinate with B344 below if so) and periodically logging
   `tracemalloc.take_snapshot().statistics('lineno')[:20]` to see which allocation sites dominate.
4. Identify the actual leaking structure: a growing list/dict/cache that's never cleared, retained
   exception tracebacks, an accumulating set of coroutines/tasks never garbage collected, embedding
   tensors not released, or something in KuzuDB's own buffer pool (in which case this may turn out to
   be the same root cause as B311, or a related-but-distinct KuzuDB memory-management issue — don't
   assume either way, follow the evidence).
5. Document findings in `backlog/B342.md` under a new "Root Cause Identified" (or "Root Cause Still Not
   Found, Here's What We Ruled Out" — an honest negative result is a valid outcome, matching this
   project's B311 investigation-card discipline) section, following the same rigor as B311's rounds:
   raw data, what was and wasn't established, no unsupported leaps.

### Outcome

Closed 2026-08-26 as part of an audit of B342-era cards left in "ready" state despite the underlying
work concluding. Root cause was found, but not via this card's proposed method (a py-spy/tracemalloc
heap-allocation profile) — and for a good reason discovered along the way: the actual cause (macOS's
memory compressor acting on already-resident pages under real system-wide memory pressure) lives
entirely outside the Python heap. A heap profiler would never have found it, because there was
nothing wrong with what Python was allocating — see `backlog/B342.md`'s final entries for the full
investigation (direct correlation of compression events against system memory pressure, confirmed
live, not inferred). Acceptance criteria as literally written were not met (no heap profile was ever
taken); the card's actual goal — know why the daemon grows — was met by a different, better-fitted
method. Not scope-creeping a fix here: B342 itself found no code fix applies (it isn't a bug), and
the one real lever (reducing resident footprint) is already being pulled via B355.
