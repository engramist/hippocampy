# B262 - REST API Endpoints for External Integration

State: complete -- re-verified 2026-08-03: found and FIXED a real, severe bug -- every tool-calling REST endpoint (recall/bundle/timeline/diff/decide/status/notify) was returning HTTP 500 for 100% of real requests due to a keyword-argument mismatch (`arguments=` vs the real handler signature's `params=`), confirmed live via FastAPI TestClient + the real tool registry (not mocks), fixed with a 2-line change in campy/brain/brainstem/rest_api.py, added 2 regression tests, re-verified all endpoints now return 200 -- see Verification Findings for full repro
Priority: P1

Plan: backlog/plans/B-262-rest-api-endpoints.md

### Problem

The MCP daemon at `http://127.0.0.1:7799` only speaks MCP protocol (JSON-RPC over SSE). External tools, scripts, CI pipelines, and non-MCP agents need a simpler REST interface to query Campy memory. The CLI commands (B261) use the MCP protocol internally, but external integrations need standard REST.

### What This Card Does

Adds REST API routes to the existing FastAPI/Starlette daemon alongside the MCP SSE endpoint. These are thin wrappers that call the same tool handlers as MCP but return standard JSON responses.

### Dependencies

- None (can be built independently, uses existing tool handlers)

### Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Framework | Extend existing daemon's ASGI app | No new process — same daemon, same port |
| Path prefix | `/api/v1/` | Standard REST versioning, avoids collision with `/sse` |
| Auth | None initially (localhost only) | Same trust model as existing MCP endpoint |
| Response format | Standard JSON with consistent envelope | `{"ok": true, "data": {...}}` or `{"ok": false, "error": "..."}` |

### Endpoints

| Method | Path | MCP Tool | Purpose |
|---|---|---|---|
| GET | `/api/v1/recall?q=<query>` | `current_truth` | Quick recall |
| POST | `/api/v1/bundle` | `compile_context` | Full bundle (body: `{query, token_budget, agent_type}`) |
| GET | `/api/v1/timeline?since=<ISO>` | `reconstruct_timeline` | Timeline |
| GET | `/api/v1/diff?since=<ISO>` | `diff_since` | Diff since |
| POST | `/api/v1/decide` | `memory_decision` | Memory routing |
| GET | `/api/v1/status` | `context_status` | Health check |
| POST | `/api/v1/notify` | `notify_turn` | Ingest a turn |
| GET | `/api/v1/tools` | `tools/list` | List available tools |

**Modified `brain_daemon.py` (or `mcp_engine/server.py`):**

### Verification Findings (2026-08-03) — REAL BUG FOUND AND FIXED

**The bug:** `campy/brain/brainstem/rest_api.py`'s internal `_call_tool()` helper (used by every endpoint except `/tools`) called tool handlers as `handler(arguments=arguments, db=db, config=config or {})`. But every entry in `TOOL_HANDLERS` (`campy/brain/thalamus/tools/__init__.py`) is wrapped by `_with_phase()` (`campy/brain/thalamus/tools/_shared.py:33`), whose signature is `async def wrapper(params=None, db=None, config=None, **kw)`, forwarding to the real tool function as `fn(params=params, db=db, config=config, **kw)`. Since `_call_tool` passed `arguments=` instead of `params=`, the real `params` argument was always `None` and `arguments` silently landed in `**kw`, which the underlying tool functions (e.g. `notify_turn(params: dict, db, config)`) do not accept — raising `TypeError: <tool>() got an unexpected keyword argument 'arguments'` for literally every real tool call.

**How I confirmed it (before any fix):**
```
$ PYTHONPATH=<worktree> .venv/bin/python -c "
import asyncio
from campy.brain.thalamus.tools import TOOL_HANDLERS
async def main():
    handler = TOOL_HANDLERS['notify_turn']
    await handler(arguments={'role':'user','content':'hello world','session_id':'test'}, db=None, config={})
asyncio.run(main())
"
TypeError: notify_turn() got an unexpected keyword argument 'arguments'
```
Same `TypeError` reproduced for `current_truth`, `context_status`, `compile_context`, `memory_decision`. Then confirmed end-to-end over real HTTP via `fastapi.testclient.TestClient` + the actual `create_app()` from `web/server.py` (a stub DB standing in for Kùzu, matching this repo's own `tests/test_web.py` pattern):
```
GET  /api/v1/recall  -> 500 {'ok': False, 'error': "current_truth() got an unexpected keyword argument 'arguments'"}
POST /api/v1/notify  -> 500 {'ok': False, 'error': "notify_turn() got an unexpected keyword argument 'arguments'"}
GET  /api/v1/status  -> 500 {'ok': False, 'error': "context_status() got an unexpected keyword argument 'arguments'"}
```
Every endpoint that calls a real tool handler was 100% broken. Only `/api/v1/tools` (doesn't call `_call_tool`) and 404-for-unknown-routes worked.

**Why the existing tests never caught this:** `tests/test_rest_api.py` only tested `_ok`/`_err` (pure formatting helpers) and that the router object has the right route *paths* — it never actually invoked an endpoint against the real tool registry. This is the same failure mode flagged elsewhere in this audit batch (B278/B283): tests exercised the shape of the code, not its real execution path.

**The fix (2 lines, `campy/brain/brainstem/rest_api.py`):**
1. Line 37: `handler(arguments=arguments, ...)` → `handler(params=arguments, ...)` — matches the real wrapper signature.
2. `status_endpoint` (was `_call_tool("context_status", {})`) never supplied `session_id`, but `context_status` (`campy/brain/thalamus/tools/retrieval.py:761-763`) hard-requires one (`if not session_id: return {"error": "session_id is required"}`) — a second, independent bug making `/api/v1/status` unconditionally fail even after fix #1. Changed to `_call_tool("context_status", {"session_id": request.query_params.get("session_id", "rest-api")})`, matching the `session_id` default pattern already used by `recall_endpoint` elsewhere in the same file.

**Verified the fix for real** (same TestClient harness, after the fix):
```
GET  /api/v1/recall  -> 200 {'ok': True, 'data': {'results': [], ...}}
POST /api/v1/notify  -> 200 {'ok': True, 'data': {'status': 'ingested', 'message_id': 'd8b8c0c9-...', ...}}
GET  /api/v1/status  -> 200 {'ok': True, 'data': {'token_estimate': 0, ...}}
POST /api/v1/decide  -> 200 {'ok': True, 'data': {'should_recall': False, 'recommended_tool': 'none', ...}}
POST /api/v1/bundle  -> 200 {'ok': True, 'data': {'bundle': {...}}}
```
Added 2 regression tests to `tests/test_rest_api.py` (`test_notify_endpoint_calls_real_handler_without_typeerror`, `test_status_endpoint_passes_session_id`) that call through the real `create_app()` + `TOOL_HANDLERS`, not just the formatting helpers — these would have caught this bug and now guard against it recurring. Full suite re-run: `PYTHONPATH=<worktree> .venv/bin/python -m pytest tests/test_rest_api.py -v` → **7/7 passed**.

**Caveat — real Kùzu persistence not independently re-verified:** the stub DB used above accepts writes silently (`execute_write` is a no-op), so `notify_turn` returning a `message_id` shows the code path executes correctly through to a DB-write call, but does not independently confirm the write survives against a real Kùzu instance. Did not start the operator's real `brain_daemon.py` or bootstrap a full real Kùzu schema for this card, for the same reason noted on B255/B256/B259/B261 (risk of colliding with the operator's live production graph DB / heavy embeddings prewarm). Real-Kùzu persistence correctness for `notify_turn` itself is being tracked separately (see B278, which found and is tracking a related real persistence bug in a different write path).
