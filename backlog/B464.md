# B464 - Stated Values Never Become Concepts, So No Supersession Edge Can Link Them

State: fixed in the sandbox (2026-10-04); real-model confirmation pending
Priority: P1

### Problem Statement

Found by campy-benchmarks after B460 (2026-10-04). On a real-model
(`llama3.1:8b`, all-MiniLM-L6-v2) `--isolated` LoCoMo store,
`diag_supersession_edges.py` finds a right REPLACES edge for 15 deprecation
probes, but 8 have no Concept at all for one side, so no edge can exist:

- no Concept for the **current** value: `p_7_active` (Python 3.12),
  `p_11_active` (eu-central-1), `p_16_active` (Tailwind CSS v3),
  `p_18_active` (Cloudflare DNS), `p_22_active` (pytest), `p_25_active`
  (Debian 12 Bookworm slim);
- no Concept for the **retired** value: `p_13_active` (autopep8 / yapf),
  `p_23_active` (AngularJS / Vue 2).

`p_5_active` and `p_19_active` have both sides but no edge between them.

### Root cause

Every one of these scenarios states its supersession in its last user
message, "Final decision: {v2} has been replaced by {v3}. Constraint: strictly
use {v3} ...", and B460's Step 1b extracts it with the right direction and
the full names for all 23 (offline, real spaCy): "Python 3.12 REPLACES Python
3.11", "pytest REPLACES nose2", "eu-central-1 REPLACES us-west-2", ...
`_store_relation` then creates both endpoints as Concepts. So whenever the
relation is stored, both values exist -- in the real store it was not stored.

Tracing the value through the loop (`orchestrator.run_loop`):

1. **Step 1 NER** often does not produce the value itself. It produces
   "Python" for "Python 3.12" (and nothing for 3.9/3.11), "west-2" /
   "east-1" for the regions, no entity at all for "pytest" or "yapf" in the
   final message (NER found other entities, so the noun-chunk fallback did
   not run), "Vue 2" as a DATE. For "Python 3.12" and "pytest" the Step 1b
   relation endpoint is the *only* place the value is named.
2. **Step 1b** gets the value right (B460).
3. **Step 2 gist** classifies each NER span. An entity it calls noise is
   gone; with real models this is the embedding's centroid score (computed on
   the whole message) or llama's System-2 answer.
4. **The Step 1b filter** (`orchestrator`, O4/B80/B460) kept a relation only
   if an endpoint names an entity that **survived Step 2**. When Step 2
   dropped the endpoint-naming entities, the user's own statement of which
   value replaced which was discarded -- and with it the only path to a
   Concept for the values NER did not produce. Steps 4-7 gating does not
   touch relations (the filter runs on the post-Step-2 list, and deferred
   relations are flushed after Step 7.5).

This is LLM-independent in its mechanism: the relation's fate depends on a
classifier verdict about *other spans* (the truncated NER entities), not on
the relation. Which messages hit it depends on the models: the sandbox's
hashed embeddings put every entity of these messages below the noise floor
(B460's sandbox store: `[Loop] ... entities=5 concepts=0 relations=0
noise=5` for the Python final decision), and the real store lost the
relation for these 8 (plus `p_5`/`p_19`, where both values exist through
other messages but the edge is missing -- same cause). The 23 final messages
are structurally alike (offline trace: every one has a Step 1b REPLACES and
1-3 entities naming its endpoints), so nothing in NER or Step 1b separates
the 8 from the 15 -- the difference is Step 2's verdict.

Per probe (offline trace with real spaCy; "endpoint entities" are the Step 1
entities that name an endpoint and whose Step 2 survival kept the relation):

| Probe | Missing | Step 1b relation (final msg) | Endpoint entities (NER) | Value's own NER entity anywhere? | Cause |
|---|---|---|---|---|---|
| p_7 | current | Python 3.12 REPLACES Python 3.11 | "Python" | no (only "Python") | Step 2 dropped "Python" -> relation filtered |
| p_11 | current | eu-central-1 REPLACES us-west-2 | "eu-central-1", "west-2" | "eu-central-1" (final msg only) | Step 2 dropped both -> relation filtered |
| p_13 | retired | Ruff REPLACES yapf | "Ruff" | "yapf": noun chunk in the "Update" message and its reply only; "autopep8": ORG | final msg's "Ruff" dropped -> relation filtered; Ruff exists via the assistant turn |
| p_16 | current | Tailwind CSS v3 REPLACES Bulma | "Tailwind CSS", "Bulma" | "Tailwind CSS" (final msg + assistant) | Step 2 dropped them -> relation filtered |
| p_18 | current | Cloudflare DNS REPLACES Route53 | "Cloudflare", "DNS", "Route53" | "Cloudflare" | Step 2 dropped them -> relation filtered |
| p_22 | current | pytest REPLACES nose2 | "nose2" | no ("Confirmed pytest" chunk in assistant turn) | Step 2 dropped "nose2" -> relation filtered |

The Step 2 verdicts themselves are inferred, not observed: the real store's
daemon log was not available here. Two other explanations were checked and
excluded: the harness drains consolidation before probing (B448 settle), so
no message goes unprocessed; and duplicate merging only happens on a human's
`resolve_disambiguation`, and archived Concepts still count in the audit. The
one remaining alternative -- an exception in Steps 4-7.5 aborting `run_loop`
before the relation flush -- would log `[Loop] Error processing message`;
the real-model check below greps for it.

The audit's regexes are not the cause: each missing value's regex matches the
text the relation would store ("Python 3.12" ~ `\b3\.12\b`, "pytest" ~
`\bpytest\b`, ...), and in the fixed sandbox store every one of them is found.

### What It Does (Scope)

- `step1b_relations`: each relation records `names`: both endpoint spans are
  names -- a proper noun, a noun capitalized mid-sentence ("Graphite",
  "REST"), a token with a digit ("Python 3.12", "eu-central-1", "Route53"),
  or a word the model's vocabulary does not know ("pytest", "yapf"; only
  when the model has vectors). Common-noun spans ("the new version", "the old
  one", "the team", "this approach") are not.
- `orchestrator`: a Step 1b relation is also kept when it is a **stated
  supersession** (`_stated_supersession`): REPLACES, both endpoints names,
  head != tail, neither endpoint junk by Step 1's `_is_junk_entity`. Its
  endpoints become (confidence_low, minimal) Concepts through the existing
  `_store_relation` path, whatever Step 2 made of the message's entities.

Generic words stay out: "Final decision", "Constraint", "Update" are never
REPLACES endpoints and still go through Step 2 like any entity. Measured on
7004 texts (LoCoMo, LoCoMo10's conversations, 80 backlog cards as technical
prose): 39 Step 1b REPLACES relations, 24 count as stated supersessions --
all 23 LoCoMo final decisions but "gRPC <- REST", plus the B460 card's quoted
examples -- and 15 do not (pronoun, title-case and markdown fragments such as
"That <- One", "card <- framing", "B <- Constraint A").

Not changed:

- **Step 2 itself, and other relation types.** Only REPLACES between two
  names bypasses the Step 2 survival check; REQUIRES / ENABLES / ... still need
  a surviving entity. Whether Step 2 should drop these entities at all (the
  System-1 score is computed on the whole message, so one message's entities
  live or die together) is a separate question.
- **Step 1 NER spans.** NER still produces "Python", "west-2", "east-1" for
  the v1 values; widening Step 1 spans to whole written words (as Step 1b does
  for endpoints) would give the *retired* v1 values their own Concepts, but
  no probe needs it once the v3/v2 relation is stored. Follow-up if wanted.
- **"Update: V1 is deprecated; migrate X to V2"** still yields no relation
  (B460: a move with only "to" names no retired value).
- Existing stores are not repaired.
