# B330 - CRITICAL: Client-Supplied Header Outranks Operator's Workspace Map; No Scope Tiering

State: complete — merged via PR #55 (2026-08-20)
Priority: P0

Plan: none yet.

### Problem

An external security audit found two related authorization problems in `campy/brain/auth.py`,
verified again against current HEAD (same lines):

**1. Header-over-map precedence (`campy/brain/auth.py:327-331`):**

```python
header_workspace = headers.get("x-campy-workspace-id") or headers.get("X-Campy-Workspace-Id")
workspace_id = (
    header_workspace                        # client-supplied — wins
    or self._workspace_map.get(caller_arn)  # operator config — loses to the header
    or self._default_workspace_id
)
```

Nothing cryptographically binds the client-supplied `x-campy-workspace-id` header to the
SigV4-verified `caller_arn`, and the header is checked **before** the operator-configured
ARN→workspace map. A Gateway session attribute forwarded as a header can reasonably be argued to be a
transport credential in principle, but Campy enforces none of that binding today, and there's no
defense in depth if the fronting proxy ever derives that header from anything a calling agent can
influence — which matters specifically because these agents are prompt-injectable by construction.
This is also the exact mechanism (`metadata_configuration`) some prospective integrators are being
asked to supply, so the current precedence undermines the very isolation guarantee it's meant to
provide.

**2. No scope tiering (`campy/brain/auth.py:339`, `IAMPrincipalResolver.resolve()`):**
Every successfully SigV4-verified caller is granted `_ALL_SCOPES` (`campy/brain/auth.py:57`) —
including `memory.admin` and `visibility.override` — with no tiering between "this caller is who they
say they are" and "this caller is authorized to do X." Authentication is being used as a stand-in for
authorization.

Separately worth being honest about in documentation (not itself a bug, but context the fix should
account for): SigV4-over-`GetCallerIdentity` authenticates the *caller*, not the *request* — the
signature is computed over a fixed STS URL, so a captured `Authorization` header is replayable against
any Campy endpoint within the STS clock-skew window (~15 min). This is inherent to the pattern (Vault's
`aws` auth method has the same property) and not itself something to "fix," but it means item 1 above
can't be waved away as theoretical — a leaked/replayed header plus the current precedence bug is a
realistic path to cross-workspace access.

### What it does (scope)

1. Invert the precedence in `campy/brain/auth.py:327-333`: the operator-configured
   `self._workspace_map.get(caller_arn)` should win over any client-supplied header. Treat the header
   as, at most, a *request* for a specific workspace that must then be checked against what the
   verified `caller_arn` is actually authorized for (e.g. the operator map must explicitly grant that
   ARN access to the requested workspace, or the request is rejected) — not as an assertion that's
   trusted outright.
2. Add a scope-tiering layer: instead of `_ALL_SCOPES` for every verified caller, derive granted scopes
   from the operator's configuration (extend `self._workspace_map`-style config, or a new
   `principal_scope_map`, keyed by `caller_arn`) so that a verified identity doesn't automatically get
   `memory.admin`/`visibility.override` unless explicitly granted. Preserve a sane default (e.g. the
   current `_ALL_SCOPES` behavior) for callers not present in the new config, so this isn't a breaking
   change for existing single-tenant/local deployments — but make the tiering available and documented
   for multi-tenant deployments.
3. Document the SigV4 replay-window property (in `docs/deployment-agentcore.md` or wherever auth is
   documented) so operators understand the header-binding fix in item 1 is necessary but the underlying
   pattern still has a bounded replay window — this is a documentation addition, not a code fix.

### Acceptance Criteria

- [ ] A verified caller whose ARN is in `self._workspace_map` gets that workspace regardless of what
      `x-campy-workspace-id` header is sent — a test proves a header attempting to override the
      operator map is rejected or ignored.
- [ ] A verified caller whose ARN is NOT in the operator map, but sends a workspace header, either gets
      rejected or falls through to `self._default_workspace_id` — never gets an arbitrary
      attacker-chosen workspace.
- [ ] At least one test exists proving a verified-but-unauthorized-for-scope-X caller cannot exercise
      scope X (e.g. `memory.admin`) when scope tiering is configured.
- [ ] Existing single-tenant/no-tiering-configured deployments retain current behavior (no regression)
      — a test proves the default path still works when no scope map is configured.

      `IAMPrincipalResolver`.
