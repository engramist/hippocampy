# B363 - arc_update_goal_confidence Never Creates VictoryCondition Nodes

State: ready
Priority: P3

Plan: none yet.

### Problem

Handoff from the ARC_AGI peer session (card A215, 2026-08-25; full writeup in that repo at
`docs/handoff/B278-victory-condition-node-creation.md`), independently verified against this
repo's current `main` before filing.

No code path anywhere in hippocampy ever creates a `VictoryCondition` node.
`arc_update_goal_confidence` (`campy/brain/thalamus/tools/arc_queries.py:634-655`) does a bare
`MATCH (vc:VictoryCondition {condition_id: $gid})` on both its read-current-value query (line 643)
and its write-new-value query (line 653) — never `MERGE`/`CREATE`. Confirmed via
`grep -rn "VictoryCondition" campy/ --include="*.py"` across the whole tree: every hit is a
`MATCH`, a schema table/rel declaration (`CREATE REL TABLE ... FROM VictoryCondition TO ...`, not
node creation), or a provenance string (`campy/brain/hippocampus/provenance.py:73`). Zero node
creation.

Consequence: `arc_update_goal_confidence` is called unconditionally every cycle a goal is active
on the ARC side, and it always silently matches zero rows when no `VictoryCondition` node exists
for that `condition_id` — but still returns `{"status": "ok", ...}`, so the caller can't detect
the no-op from the response. Correspondingly, `arc_get_goal_evidence`
(`campy/brain/thalamus/tools/arc_queries.py:497-523`) always returns an empty `goals` list, since
its own query is also a bare `MATCH (vc:VictoryCondition {task_id: $tid})` with nothing upstream
ever having created one.

Real `VictoryCondition` creation logic did exist historically — `git log --all --oneline | grep -i
victory` shows B179 (`c25d157`, "lower victory condition inference threshold and add fallbacks")
and B215-B217 (`08675dc`, "solver plateau/loop/victory improvements") — but confirmed both are on
the archived v1 solver (`agents/arc3/solver.py`), never carried over to the v2 MCP tool surface
(`campy/brain/thalamus/tools/arc_queries.py`) that the current runtime actually calls. B278 (closed
2026-08-03) touched the same file but fixed different, unrelated bugs (a `falsified_count`
persistence issue and an RPE-direction threshold mismatch) — it did not address `VictoryCondition`
creation at all.

**Not urgent per the peer session**: ARC-side already has a local-state mechanism
(`goal_resolver.py::_apply_failure_decay`, in the ARC_AGI repo) that covers the practical gap —
demotes a stuck goal within 2-3 cycles regardless of any graph signal, verified against a real
trace. Nothing is broken end-to-end today, but the graph-side mechanism doesn't do what it looks
like it does, and any future consumer of `arc_get_goal_evidence` (or a `VictoryCondition`-based
feature) would hit the same silent no-op.

### What it does (scope)

1. Wherever a `VictoryCondition` should first come into existence for a `(task_id, condition_id)`
   pair (needs deciding — likely at goal-registration time in the ARC call pattern, not inside
   `arc_update_goal_confidence` itself; see `agents/arc4/graph_queries.py::record_evaluation` in
   the ARC_AGI repo for the actual call site/pattern), add a real `MERGE (vc:VictoryCondition
   {condition_id: $gid}) ON CREATE SET ... ON MATCH SET ...` path.
2. `arc_update_goal_confidence`'s write query should use `MERGE` (with `ON CREATE`/`ON MATCH`)
   instead of a bare `MATCH`, so a call against a not-yet-existing goal doesn't silently no-op.
3. Consider returning whether the write actually created vs. matched an existing node (e.g. a
   `created: bool` field) so callers can distinguish a genuine no-op from a real write, rather than
   both looking like `{"status": "ok"}`.
4. Add real KuzuDB-backed regression coverage (not `MockDB`) exercising the case where no prior
   `VictoryCondition` node exists for the given `condition_id`/`task_id` — the existing test
   coverage apparently never caught this, matching the same test-coverage-gap pattern B278 found
   in this same file.
