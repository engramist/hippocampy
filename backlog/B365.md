# B365 - Reconcile the Two Divergent BrainDaemon Implementations

State: ready
Priority: P1

Plan: none yet — needs a design decision before implementation, see below.

### Problem

Surfaced by external verification (VibeGuide, round 3, 2026-08-25) while confirming B362's fix,
then investigated further here because the review's own suggested remediation ("kill the
duplicate, `git rm brain_daemon.py` at the root") turned out to be wrong once actually checked
against both files' real content.

There are two independent, substantially diverged `BrainDaemon` implementations:

- **Root `brain_daemon.py`** (~920 lines). Not part of the shipped package (`pyproject.toml`'s
  `[tool.setuptools.packages.find]` only includes `campy*`/`adapters*`/`web*`). Has no Principal/
  TransportContext/WorkspaceRouter/IAM auth layer at all — single global `self.db`, no per-caller
  identity, pre-B315 architecture.
- **`campy/brain_daemon.py`** (~731 lines). **This is what actually ships and runs** —
  `campy-daemon = "campy.daemon:main"` → `campy/daemon.py` → `from campy import brain_daemon`.
  Has the full B315 (Principal/TransportContext derivation per-connection), B316 (WorkspaceRouter,
  multi-workspace `_resolve_workspace_db`), and B325 (bind-guard, IAM auth mode, streamable-HTTP
  MCP transport) feature set. Has none of root's memory-safety mitigations (see below).

**Neither file is a strict subset of the other** — this is not "one canonical file plus a stale
copy," it's two files that each independently accumulated real, tested, valuable functionality the
other one lacks:

| Feature | Root `brain_daemon.py` | `campy/brain_daemon.py` |
|---|---|---|
| Principal/TransportContext (B315) | No | Yes |
| WorkspaceRouter, multi-workspace (B316) | No | Yes |
| Bind guard, IAM auth mode, HTTP MCP (B325) | No | Yes |
| `_periodic_checkpoint` (B337) | Yes | No |
| `_periodic_restart` (B342) | Yes | No |
| `_periodic_footprint_watchdog` (B354) | Yes | No |
| B362 connection-reset handling | Yes (this session) | Yes (this session, re-landed) |

Both files are also relied on by multiple CLI code paths as an intentional-looking dual entry
point (not an accident of one person forgetting to delete something): `campy/cli/daemon_ctl.py`
imports the root file by bare name after a `sys.path` insert; `campy/cli/launchd.py`'s
`_daemon_script()` *prefers* the root file over the packaged console script whenever running from
a git checkout (i.e., every dev environment); `campy/cli/main.py`'s non-Darwin `start()`/`stop()`
fallback and `campy/cli/install.py`'s daemon-script resolution both reference the root path
directly. This means **any local dev environment with a git checkout — including this one — has
been running the auth-less root copy** via `campy start`/launchd this whole time, while genuinely
pip/pipx-installed users get the auth-featured, memory-safety-less `campy/brain_daemon.py`.
Practical severity today is low (local single-user tool, filesystem-permission-gated Unix socket,
matching the established threat model elsewhere in this project) but the drift itself — two
"the daemon" files nobody could tell apart without reading both in full — is the real problem: it
is what let B362's fix silently land on the wrong one in the first place.

**Confirmed evidence of active harm, not just theoretical risk**: running
`pytest tests/test_auth_context.py tests/test_daemon.py tests/test_workspace_router.py` together
deterministically fails 6 tests (`AttributeError: 'NoneType' object has no attribute 'has_next'`
in `kuzu_client.py:164`) that all pass cleanly when `tests/test_daemon.py` (the one that imports
the root file under the bare module name `brain_daemon`) is excluded from the same run. Reproduces
identically on unmodified `main` @ `7678843` — this is a pre-existing test-isolation hazard, not
something introduced by B362's re-land. Root cause not yet investigated (likely a module-identity
collision between `sys.modules["brain_daemon"]` and `campy.brain_daemon`'s own import chain
touching shared global state), but it's concrete proof the naming collision is already causing
real problems beyond "confusing to a human reader."

### What it does (scope)

This needs a design decision, not just an implementation:

1. **Decide the reconciliation direction.** Likely: port root's three memory-safety tasks
   (`_periodic_checkpoint`, `_periodic_restart`, `_periodic_footprint_watchdog`, and their
   `_vmmap_parsed`/`_vmmap_swap_summary` helpers) into `campy/brain_daemon.py`, since that's the
   file that actually ships — the auth/workspace-routing feature set is much larger and harder to
   port the other direction. Confirm this direction is right (does the packaged daemon actually
   need self-restart/footprint-watchdog in production the way a long-running dev daemon does?)
   before starting.
2. **Retire the root file properly** once `campy/brain_daemon.py` is the strict superset — either
   delete it and update the CLI call sites that reference it (`daemon_ctl.py`, `launchd.py`'s
   `_daemon_script()`, `main.py`, `install.py`) to point at `campy.brain_daemon`/`campy-daemon`
   directly, or (lower-risk, VibeGuide's suggestion) replace it with a two-line deprecation shim
   (`from campy.brain_daemon import *`) so those call sites keep working unmodified while there is
   only one real implementation underneath.
3. **Fix `tests/test_daemon.py`** once the root file's unique functionality has somewhere to live —
   either it becomes redundant (if shimmed, its dispatch tests would need the real 2-arg
   `_dispatch(request, principal)` signature) or its periodic-restart/footprint-watchdog tests move
   to target `campy.brain_daemon` where that functionality will then live.
4. **Investigate and fix the test-pollution bug** (the 6-test failure combo above) as part of this
   work, or file it separately if it turns out to be unrelated to the module-shadowing itself.
5. **Add a drift-prevention guard** (ratchet-style, per `scripts/check_cypher_ratchet.py`'s
   precedent) once there is only one real file — e.g. a one-assert test that fails if a top-level
   `.py` shadows a module name that also exists inside `campy/`.
6. **Restart the live dev daemon** once the fix lands, and re-verify (the same live cross-agent
   smoke-test standard this whole investigation started from) that nothing regressed for either
   feature set.

### Dependencies

None blocking. B362 (connection-reset handling) is already fixed on both files independently, so
this card is about eliminating the duplication itself, not an urgent bug fix.

### Files to create/modify

- `campy/brain_daemon.py` — gains root's three memory-safety background tasks.
- `brain_daemon.py` (root) — becomes a deprecation shim or is deleted, per the decision in step 2.
- `campy/cli/daemon_ctl.py`, `campy/cli/launchd.py`, `campy/cli/main.py`, `campy/cli/install.py` —
  only if the delete-and-repoint path is chosen over the shim path.
- `tests/test_daemon.py` — rewritten or folded into `tests/test_auth_context.py`, per step 3.

### Acceptance Criteria

- [ ] Exactly one `BrainDaemon` implementation contains the full feature set (auth/workspace
      routing AND memory-safety mitigations) — no functionality lost from either current file.
- [ ] `campy start` (dev checkout, launchd path) and `campy-daemon` (installed package) run the
      *same* code.
- [ ] The 6-test pollution combo (`test_auth_context.py` + `test_daemon.py` +
      `test_workspace_router.py` run together) either no longer reproduces, or is root-caused and
      tracked separately with a clear explanation of why it's unrelated.
- [ ] A regression guard exists preventing a future fix from silently landing on only one of two
      near-identical daemon files ever again.
