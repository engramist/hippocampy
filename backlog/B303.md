# B303 - Plan-Lane Retrieval Quality: Question-vs-Goal Mismatch + Residual Plan Valences

State: done
Priority: P2

Plan: (inline — this card is self-contained)

### Problem (observed 2026-07-14, live end-to-end verification of B299)

B299's mechanics verified working: `current_truth` returns Plan nodes, `compile_context`
bundles a plans section. But the original user-test question STILL fails end-to-end:

- `ask("What work did the GitHub Copilot agent do on B292, B293, and B298?")` →
  "my memory is empty" — even though three perfectly matching plans exist.
- `compile_context` for that query returned three WRONG plans (B249-254, B290, B291 at
  ~0.52 similarity) and none of the Copilot's B292/B293/B298 plans.

Three stacked causes:

1. **Question-vs-goal embedding mismatch.** Plan goals are imperative statements
   ("Implement B292 by splitting tools/__init__.py …"); users ask questions ("what did
   agent X do on B292?"). Their embeddings land far enough apart that unrelated but
   verbose old plans outrank exact matches. `recall_plans` has the same weakness but is
   usually called with goal-like phrasing, which masked it.
2. **Residual wrong Plan valences skew ranking.** B302 repaired Lesson polarity and plans
   linked to *flipped* lessons — but plans whose lessons were *archived*, and plans whose
   valence came directly from the old buggy auto-`report_outcome`, keep their wrong
   valence. Observed: the "✅ B290 COMPLETE & CERTIFIED" plan still has valence -0.8; the
   ranking multiplies by |valence| so wrong-signed plans still rank (and get labeled)
   wrongly.
3. **Weak synthesis fallback.** With a non-empty bundle, the local Ollama model answered
   "memory is empty" — `run_ask`'s prompt does not instruct the model on what the
   `plans` section IS or that a populated bundle means memory is NOT empty.

### What This Card Does

1. **Lexical assist for plan retrieval** (mirrors `current_truth`'s lexical fallback):
   in the shared plan-ranking helper (extracted in B299), also match plans whose `goal`
   text contains card identifiers (`\bB\d+\b`) or quoted phrases present in the query,
   and merge those into the candidate set before ranking. A question mentioning "B292"
   must always surface plans whose goal mentions B292 — exact identifier match should
   not depend on embedding luck.
2. **Extend the B302 sweep to Plans**: add a `campy graph repair-plan-valence` command
   (same file, same dry-run/apply pattern as `repair-outcome-polarity`): for plans with
   `valence_source = 'system'` (or NULL) and no post-B301 audit trail, re-judge
   `goal`+step outcomes with the fixed `infer_outcome_valence`; flip with an audit
   marker on disagreement, set valence NULL on ambiguity. Reuse `find_candidates`'
   structure. NOTE the single-writer constraint: the command must either instruct the
   user to stop the daemon (current behavior — document it in the command help) or be
   routed through the daemon transport; do what `repair-outcome-polarity` does, plus add
   the missing help-text warning to BOTH commands (discovered 2026-07-14: the sweep
   crashes with a raw Kuzu lock error when the daemon is running — turn that into a
   clear actionable message).
3. **Harden the ask prompt**: in `run_ask`'s prompt assembly, describe each bundle
   section type (plans = "documented work plans with per-step outcomes") and state
   explicitly that a non-empty bundle means relevant memory EXISTS and must be used.
   Add a test at the prompt-assembly layer: bundle with a plans section → prompt
   contains the plan goal text and the section explanation.

### Implementation notes (2026-07-15)

- Lexical assist lives in `campy/brain/thalamus/tools/quests.py`
  (`_extract_lexical_terms`, `_lexical_plan_rows`, `_rank_plan_neighbors`
  now takes `lexical_ids` and sorts lexical-exact matches ahead of
  vector-only matches on `(_lexical, _score)`).
- `campy graph repair-plan-valence` added to `campy/cli/graph_repair.py`,
  re-judging `Plan.goal` + `PlanStep.actual_outcome` text; audit trail is
  encoded via `valence_source = "system:b303-audited"` (Plan has no free-text
  marker field like Lesson does). Both repair commands now share
  `_open_repair_client`, which turns a Kuzu lock exception into the
  `launchctl bootout` message instead of a raw traceback.
- Fixed a real bug while hardening the ask prompt: `_bundle_to_prompt` only
  recognized `compact`/`toon`/`text`/`source` item keys, but plan items carry
  `goal`/`status`/`valence`/`steps` — plan content was being silently dropped
  from the prompt entirely, not just under-explained. `_render_plan_item` +
  `_SECTION_DESCRIPTIONS` fix both the drop and the missing explanation.
- New tests: `tests/test_plan_valence_repair.py`,
  `tests/test_ask_prompt_assembly.py`, plus two lexical-assist cases added to
  `tests/test_recall_contract.py`. Baseline was 1555 passed/56 skipped/2
  xfailed; after this card: 1569 passed (14 new)/56 skipped/2 xfailed — same
  failure set, no regressions.
