# B360 - Flaky test_mcp_tool_surface.py Tests Under Full Suite (Pass in Isolation)

State: ready
Priority: P3

Plan: none yet.

### Problem

`tests/test_mcp_tool_surface.py::test_sse_exposes_all_tool_handlers` and
`tests/test_mcp_tool_surface.py::test_memory_os_tools_reachable` intermittently fail when the full test
suite runs (`pytest -q` at repo root), but both pass cleanly every time when run in isolation or as just
`tests/test_mcp_tool_surface.py` on its own.

Found twice, independently, during this session's B358 and B359 work — neither of which touches this
file or anything it obviously depends on:

```
Full suite run (during B358 verification, before any B359 work existed):
FAILED tests/test_mcp_tool_surface.py::test_sse_exposes_all_tool_handlers
FAILED tests/test_mcp_tool_surface.py::test_memory_os_tools_reachable

Full suite run (during B359's ENTITY_RULE follow-up verification):
FAILED tests/test_mcp_tool_surface.py::test_sse_exposes_all_tool_handlers - r...
FAILED tests/test_mcp_tool_surface.py::test_memory_os_tools_reachable - reque...
```

Both times, immediately re-running just the two failing tests (or the whole file) passed cleanly:

```
tests/test_mcp_tool_surface.py::test_sse_exposes_all_tool_handlers .
tests/test_mcp_tool_surface.py::test_memory_os_tools_reachable .
2 passed in 0.13s
```

**This project does not use `pytest-randomly`** (confirmed: not installed, no config for it) — test
collection order is deterministic, not randomized. That rules out "random bad luck from shuffled order"
as the explanation and points instead toward genuine state leaking from an earlier test in the full
suite's fixed collection order (a module-level cache, an unreset environment variable, a monkeypatch that
isn't cleaned up, or similar) — the same *class* of bug this project's own B351/B358 investigations found
elsewhere, just not yet root-caused for this specific pair.

### What it does (scope)

1. Reproduce reliably: run the full suite (or a bisected subset) enough times to confirm the failure
   signature and get a full traceback/assertion message (this card's finding session only saw truncated
   `pytest -q` tail output, not the full failure detail — get that first).
2. Bisect which earlier test(s) in the full suite's collection order leave the state that trips these two
   — likely candidates to check first: anything that monkeypatches `TOOL_HANDLERS`/`TOOLS`/the MCP
   dispatch surface, or anything that mutates global/module-level state these two tests read (their names
   suggest they check tool-handler completeness/reachability across the whole registered surface, so a
   test elsewhere that registers/unregisters a fake tool without cleanup is a reasonable first guess).
3. Fix at the root (proper fixture teardown, `monkeypatch` instead of a raw mutation, or whatever the
   actual leak turns out to be) — not a reordering hack or a `pytest.ini` addopts flag that just hides it.

### Dependencies

None — independent of B358/B359, found incidentally during both (this project's established pattern per
B351/B352/B357/B358: file a card for an incidental finding rather than silently noting it and moving on).

### Files to create/modify

Unknown until bisected — likely `tests/test_mcp_tool_surface.py` itself and/or whichever test elsewhere
in the suite turns out to leak the state.

### Acceptance Criteria

- [ ] Reproduced with a full traceback (not just the truncated `pytest -q` summary line).
- [ ] The specific state-leak source identified (which earlier test, what state).
- [ ] Fixed at the root; verified via at least one full clean `pytest -q` run afterward showing both
      tests passing, plus (per this project's own standard) a repeated-run check if the fix's
      effectiveness isn't obviously deterministic from the root cause alone.
