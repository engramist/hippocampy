# B337 - B311 Round 3: Manual Checkpoint Control + Inverse-Batching Experiment for Daemon Memory Spikes

State: complete — merged via PR #61 (2026-08-20). Effectiveness measured in backlog/B311.md's "Round
3/4" section (2026-08-20): ~30% peak-RSS reduction, but slower post-close memory release than baseline
— a partial win, not a confirmed fix. See B311.md for the full before/after data.
Priority: P1

Plan: none yet — this is a continuation of an open investigation card, not a fresh feature.

### Problem

`backlog/B311.md` is an open investigation card tracking `brain_daemon.py`'s memory spikes
(110-150MB baseline to 600MB-1.2GB+ peaks) during write-heavy KuzuDB traffic, root-caused to
KuzuDB's checkpoint-at-commit-boundary behavior. Two rounds of investigation have run:

- **Round 1** ruled out embedding-model reload and concurrent journaling as *necessary* triggers, and
  strongly implicated KuzuDB's uninstrumented `checkpoint_threshold`/`auto_checkpoint` defaults plus
  the fact that every `execute_write` call is its own independent auto-committed transaction (no
  batching anywhere in the write path).
- **Round 2** tested the two most obvious mitigations against the isolated repro harness, and **both
  came back negative**: `checkpoint_threshold=4MB` tuning alone made peak RSS *slightly worse* (not
  better), and batching writes into one transaction per `arc_perceive_state` call made peak RSS
  *significantly worse* (1879.5MB → 3047.5MB) and, worse, left RSS permanently elevated after
  `db.close()` instead of settling — that batching change was reverted, not merged. Round 2's own
  working theory: Kuzu's auto-checkpoint check fires at transaction-commit boundaries, so batching
  (which reduces commit-boundary count) starves it of chances to fire, letting the WAL grow much larger
  before a checkpoint catches up.

Round 2 explicitly left three next steps untried (see `backlog/B311.md`'s "Next steps, revised"
section):

1. Investigate whether Kuzu exposes a way to force periodic checkpoints independent of commit count
   (e.g. a manual `CHECKPOINT` Cypher statement callable from a background timer/counter task) —
   this would decouple checkpoint cadence from transaction count entirely, sidestepping the
   commit-boundary coupling round 2 found.
2. Try a broader sweep of `checkpoint_threshold` values on the **unbatched** path (both smaller —
   e.g. 256KB — and larger — e.g. 32-64MB) to check whether the relationship is non-monotonic or
   whether 4MB was simply the wrong order of magnitude.
3. Only run a live `brain_daemon.py` + ARC_AGI `make smoke` confirmation once 1 or 2 produces a
   genuinely better before/after profile in the isolated repro.

Separately, an external reviewer who read round 2's own write-up (specifically the "auto-checkpoint
fires at commit boundaries, so fewer/larger transactions starve it of chances to trigger" theory)
pointed out that round 2 only tested *fewer, larger* transactions (batching). The theory, taken at
face value, implies the **inverse** experiment is the more promising one: *more frequent, smaller*
commits — deliberately giving Kuzu's checkpoint check more opportunities to fire while the WAL is
still small, rather than fewer opportunities with a larger WAL each time. This specific inverse
direction was not tested in round 2 and is worth adding as a fourth experiment alongside the three
already-planned next steps.

### What it does (scope)

Using the same isolated repro harness round 1/round 2 built (same scratch KuzuDB schema, same 2000-step
`arc_perceive_state`/`record_transition`/`record_rule` workload, same `ps -o rss=` 1s-interval RSS
sampling methodology — described in `backlog/B311.md`'s "Isolated reproduction" and "Round 2: Mitigation
Experiments" sections), run these experiments in order, stopping early if one clearly wins:

1. **Manual/periodic `CHECKPOINT`.** Check whether Kuzu 0.11.3's Python API exposes a manual
   `CHECKPOINT` statement (try `conn.execute("CHECKPOINT")` or check the `kuzu` package's own docs/
   source for a checkpoint API). If it exists, disable `auto_checkpoint` (or leave it on — test both)
   and add a background counter/timer in a scratch `TunedKuzuClient` (following round 2's pattern) that
   issues a manual checkpoint every N writes or T seconds, independent of transaction-commit count.
   Measure peak RSS and settle behavior against the round 1 unbatched baseline (1879.5MB peak).
2. **Broader `checkpoint_threshold` sweep, unbatched.** Re-run the unbatched path (today's real write
   pattern — no batching) at `checkpoint_threshold` values of 256KB and 32MB (in addition to round 2's
   already-tested 4MB), to check whether the threshold/peak-RSS relationship is non-monotonic or
   whether round 2 simply tried the wrong order of magnitude.
3. **Inverse-batching: smaller, more frequent commits.** If the current write path's natural
   transaction size can be split *smaller* than today's per-call granularity (e.g. one commit per
   individual entity write within `arc_perceive_state`'s loop, instead of the current per-call
   default), test whether more frequent small commits reduce peak RSS relative to round 1's unbatched
   baseline — the inverse of round 2's batching experiment.
4. Report all results — including negative ones — honestly in `backlog/B311.md` itself, following the
   card's own established format (add a "Round 3: ..." section, matching how round 2 was appended
   after round 1). Do not silently drop a negative result; round 1 and round 2 both explicitly valued
   reporting failed experiments, and round 3 should keep that standard.
5. Only if one of 1-3 produces a genuinely better before/after profile in the isolated repro (materially
   lower peak RSS AND full settle after `close()`, not a partial improvement in only one dimension):
   run a live confirmation against the real `brain_daemon.py` + ARC_AGI (`~/Desktop/GitProjects/ARC_AGI`,
   `make smoke`) + local Ollama stack, using the same 2s-interval RSS sampling methodology as the
   original card, and append that result to `backlog/B311.md` as well.
