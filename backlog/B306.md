# B306 - Fix Invalid Cypher in `_stage_exact_facts` / `_stage_semantic_context` (Silently Dead Bundle Stages)

State: complete (2026-08-02)
Priority: P0

Plan: (inline — this card is self-contained and sized for a Sonnet-level implementer)

### Problem (found during B305 implementation, 2026-08-02)

While implementing [B305](B305.md) (bundle relevance floor), a live run against a real
Kuzu DB showed that two bundle stages in `campy/brain/thalamus/bundle_compiler.py` throw
on every single invocation:

```
Parser exception: Invalid input <MATCH (n:GlobalConstraint) OR>: expected rule oC_SingleQuery
```

The offending queries:

```python
# _stage_exact_facts, line ~268
MATCH (n:GlobalConstraint) OR (n:GlobalPreference)
WHERE vector_distance(n.embedding, $query_embedding) < 0.30
RETURN n.text_raw as text, labels(n)[0] as node_type, n.confidence as confidence
LIMIT 10
```

```python
# _stage_semantic_context, line ~318
MATCH (n:Concept) OR (n:Decision) OR (n:Constraint) OR (n:Requirement)
WHERE vector_distance(n.embedding, $query_embedding) < 0.40
RETURN n.text_raw as text, labels(n)[0] as node_type,
       n.pathway_strength as pathway_strength, n.confidence as confidence
ORDER BY vector_distance(n.embedding, $query_embedding) ASC
LIMIT $limit
```

`OR` between node-label patterns inside a single `MATCH` is not valid Kuzu/openCypher
syntax. Both functions wrap the call in a bare `try/except Exception` that prints the
error and returns `None` — so `compile_bundle` never crashes, it just silently produces
an empty section every time. **Neither stage has ever returned real content in
production.** This was invisible because no test seeds real `GlobalConstraint`,
`GlobalPreference`, `Concept`, `Decision`, `Constraint`, or `Requirement` nodes and
exercises these two functions directly — existing coverage only goes through full
`compile_bundle` integration paths, where the failure has always been masked by the
catch-all except.

This is explicitly out of scope for B305: B305 only needs to add/verify similarity
floors on top of whatever a stage already returns, and its acceptance criteria don't
require these two queries to actually work. Filed separately per B305's own note.

### Second, unverified suspicion: `vector_distance` may not be the right primitive either

The rest of the codebase does not filter by a distance function inside a `WHERE`
clause. The one other place vector search happens, `campy/brain/hippocampus/graph/kuzu_client.py:187`,
uses Kuzu's HNSW index explicitly:

```python
CALL QUERY_VECTOR_INDEX('{table_name}', '{index_name}', $embedding, {limit}) YIELD node, distance
```

with a comment noting the index is pinned to `metric=cosine` at creation time (B279).
No code path in this repo currently calls a bare `vector_distance(...)` scalar function,
so its existence in this Kuzu version is unconfirmed — it may not exist at all, may be
named `array_distance`, or may work but silently skip the HNSW index (full scan) since
it's not going through `QUERY_VECTOR_INDEX`. This must be checked against the pinned
Kuzu version before or while fixing the syntax, since fixing only the `OR` issue could
trade one silent failure for another (e.g. "unknown function" caught by the same
`except Exception`).

### What This Card Does

1. **Rewrite `_stage_exact_facts`** as a `UNION` of per-label `MATCH` clauses (the
   standard openCypher pattern for "any of these labels"):
   ```cypher
   MATCH (n:GlobalConstraint) WHERE <distance-condition> < 0.30
   RETURN n.text_raw as text, labels(n)[0] as node_type, n.confidence as confidence
   UNION
   MATCH (n:GlobalPreference) WHERE <distance-condition> < 0.30
   RETURN n.text_raw as text, labels(n)[0] as node_type, n.confidence as confidence
   LIMIT 10
   ```
2. **Rewrite `_stage_semantic_context`** the same way across its four labels (`Concept`,
   `Decision`, `Constraint`, `Requirement`), preserving the existing `ORDER BY` +
   `LIMIT $limit` semantics (note: `ORDER BY`/`LIMIT` apply to the whole `UNION`'d
   result set in Cypher, not per-branch — confirm this still returns the same
   "top N across all four labels" behavior the current code intends).
3. **Resolve the `vector_distance` question first**, against the exact Kuzu version
   pinned in this repo (check `pyproject.toml`/`requirements`): confirm whether
   `vector_distance` is a real scalar function, or whether these queries should call
   `array_distance` instead, or should be restructured to use `QUERY_VECTOR_INDEX` like
   `kuzu_client.py` does (for both correctness and to actually use the HNSW index rather
   than a full scan — small graphs won't notice, larger ones will). Pick whichever
   approach is correct for the pinned version and is consistent with the rest of the
   codebase; document the choice in the PR description.
4. **Narrow the exception handling.** The current bare `except Exception: return None`
   is exactly what let this bug ship silently. At minimum, log the exception with
   enough detail to be noticed (not just swallowed to `print`), or let genuine query
   errors surface in a way tests can catch — the goal is that a future syntax/typo bug
   in these functions fails loudly in CI instead of silently degrading retrieval.

### Validation Note (2026-08-02)

**`vector_distance` does not exist in Kuzu 0.11.3** — confirmed by direct execution
against the pinned version (`/Users/djshelton/.campy/venv`, `kuzu==0.11.3`, matching
`requirements.txt`):

```
>>> conn.execute("MATCH (n:N) WHERE vector_distance(n.embedding, [1.0,0.0,0.0]) < 0.3 RETURN n.id")
Catalog exception: function VECTOR_DISTANCE does not exist.
```

`array_distance` (Euclidean/L2) does exist and runs, but adopting it verbatim would have
silently broken the intended threshold semantics: embeddings in this repo are
L2-normalized (`embeddings.py` calls `model.encode(..., normalize_embeddings=True)`), so
for unit vectors `euclidean_dist = sqrt(2 * cosine_dist)`. The `0.30`/`0.40` thresholds
already in these two functions match a *cosine*-distance reading (equivalent to the
0.70/0.60-similarity convention used elsewhere in the bundle compiler and in B305's card
body) — swapping in raw `array_distance` at the same numeric threshold would have made
the filter roughly an order of magnitude stricter than intended (a 0.30 Euclidean cutoff
on unit vectors corresponds to ~0.955 cosine similarity, not ~0.70), likely filtering out
genuinely relevant matches. Used `array_cosine_similarity` instead — confirmed to return
plain cosine similarity in `[-1, 1]` — and compute distance as `1 -
array_cosine_similarity(...)`, matching the cosine metric `kuzu_client.py` already pins
its HNSW indexes to (`_INDEX_METRIC = "cosine"`).

Two more latent bugs were found and fixed alongside the reported one, both of which
would have kept these stages silently broken even after the `OR`/`vector_distance` fix:

1. `labels(n)[0]` returns `''`, not the label name — in this Kuzu version `labels(n)`
   returns a scalar `STRING` (e.g. `'GlobalConstraint'`), not a list, so indexing it
   with `[0]` does not do what the author intended. Fixed by using `label(n)`, which
   returns the label directly.
2. Row consumption assumed dict-style access (`for record in result: record["text"]`),
   but `db.execute()` (via `KuzuClient`) returns the raw Kuzu `QueryResult`, whose rows
   are positional lists — `record["text"]` would raise `TypeError` even after the query
   itself became valid. Fixed to use `while result.has_next(): row = result.get_next()`
   with positional unpacking, matching the established pattern already used elsewhere in
   this codebase (e.g. `campy/brain/thalamus/tools/quests.py`).

A further, non-obvious finding changed the fix shape from the UNION approach this card
originally proposed: **in Kuzu 0.11.3, `ORDER BY`/`LIMIT` following a chain of `UNION`s
binds only to the last branch, not the combined result set** (confirmed empirically —
a 4-branch `UNION ... ORDER BY ... LIMIT $n` returned all rows from the first three
branches unordered/unlimited, with the cap and sort applied only to the fourth). A
straight port of the card's proposed UNION query would have parsed and run without
throwing, but would have silently failed to cap total rows across labels — the exact
kind of bug this card exists to eliminate. Both functions now issue one query per label
(each independently valid — a single `MATCH`'s `ORDER BY`/`LIMIT` is unaffected by the
UNION issue) and merge results client-side, re-sorting by distance and truncating to the
overall limit in Python for `_stage_semantic_context` (which needs a true global top-N),
and truncating post-concatenation for `_stage_exact_facts` (which has no ranking
signal — the original code had none either).
