# B329 - CRITICAL: npm postinstall Runs Unpinned `curl | sh` From Mutable `main` Branch

State: complete — merged via PR #56 (2026-08-20)
Priority: P0

Plan: none yet.

### Problem

`scripts/npm/package.json` declares `"postinstall": "node install.js"`, and
`scripts/npm/install.js:13` runs:

```
curl -fsSL https://raw.githubusercontent.com/engramist/hippocampy/main/scripts/install.sh | sh
```

This fetches and executes a shell script from the mutable `main` branch, automatically and
non-interactively, every time anyone runs `npm install` on the npm package, with no checksum and no
signature verification. Anyone who lands a commit on `main` (or anyone able to MITM that specific
`raw.githubusercontent.com` fetch) gets code execution on every subsequent install, with the
installing user's privileges. This was flagged as CRITICAL in an external security audit of the repo.

### What it does (scope)

1. Pin the fetched URL to a specific tag or commit SHA instead of `main` — e.g.
   `https://raw.githubusercontent.com/engramist/hippocampy/v${package.json version}/scripts/install.sh`
   or a commit SHA baked in at npm-publish time.
2. Publish a checksum (SHA-256) for `install.sh` alongside the pinned reference, and have
   `install.js` verify the downloaded script's hash before executing it — abort with a clear error
   message if the hash doesn't match.
3. Make the shell install an explicit, opt-in user action rather than an automatic `postinstall`
   hook: change `postinstall` to a script that prints instructions (e.g. "run `npx hippocampy-install`
   to finish setup") instead of silently executing arbitrary remote code, OR gate the automatic
   execution behind an explicit environment variable / CLI flag the user must pass
   (e.g. `HIPPOCAMPY_AUTO_INSTALL=1 npm install`). Prefer the opt-in-instructions approach unless it
   would break the existing one-click-install user experience documented elsewhere in this repo (check
   `docs/one-click-install-release-gate.md` and `README.md` for what installation experience is
   currently promised before choosing).
4. If the npm package is versioned independently of the pinned commit/tag, ensure the pin is updated
   as part of the existing release process (`scripts/release_build.sh` or equivalent) so it doesn't
   silently go stale on the next release.

### Acceptance Criteria

- [ ] `install.js` no longer fetches from the mutable `main` branch — it references a specific
      tag/SHA.
- [ ] The downloaded script's contents are verified against a published checksum before execution;
      a mismatch aborts with a non-zero exit and a clear error, not a silent partial run.
- [ ] Either (a) the automatic `postinstall` hook no longer executes remote code without explicit user
      opt-in, or (b) if automatic execution is kept, the checksum verification in the item above is
      the mitigating control — document explicitly in the card outcome which approach was taken and
      why.
- [ ] `README.md` / `docs/one-click-install-release-gate.md` accurately describe the resulting install
      flow (no stale claims about what `npm install` does).
- [ ] Manual verification: run `npm install` against the built package in a clean temp directory and
      confirm the new pinned+verified flow behaves correctly (or that the opt-in message prints
      correctly and no code executes automatically, per whichever approach was chosen).
