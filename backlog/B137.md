# B137: Fix Double `register_plan` Per Solve Step — Conflicting Active Plans

**Status**: Ready  
**Assigned**: TBD  
**Depends on**: None  
**Complexity**: Small (1–2 hours)  
**Priority**: P2 (MEDIUM — creates redundant brain state and confuses plan tracking; does not crash but corrupts plan ledger)  
**Plan**: backlog/plans/B-137-fix-double-register-plan.md

## Problem Statement

`SolveEngine.solve()` calls `register_plan` twice per solve step — once for the top-level plan and once for the current chunk plan — without checking whether the current plan is still valid or has changed. This results in:

- Two conflicting "active" plans in the brain ledger on the same step
- The same plan re-registered with identical goals across consecutive steps
- Final plan ledger shows 6 duplicate `register_plan` calls in steps 9–14

Evidence from `master_timeline.json`:
```
step 9:
  event #244: register_plan  goal="Move unknown toward goal (dist=16.5)"  steps=5
  event #245: register_plan  goal="Explore: move token southwest"        steps=3

step 10:
  event #261: register_plan  goal="Move unknown toward goal (dist=16.5)"  steps=5
  event #262: register_plan  goal="Explore: move token southwest"        steps=3

(continues for steps 11, 12, 13, 14)
```

Same goals re-registered 6 times each. `x4 [register_plan] goal=Move unknown toward goal (dist=16.5)` flood confirmed in trace.

This wastes brain storage (2 write ops per step × 6 steps = 12 unnecessary writes) and makes plan history unreadable.

## What This Card Builds

1. Adds a guard in `SolveEngine.solve()` before each `register_plan` call that skips re-registration if:
   - The current `plan_id` matches the last registered plan
   - The goal string is identical to the previously registered goal
   - Dissonance is not flagged (i.e., plan is still valid)
2. A `plan_registration_skipped` trace event is emitted when skipped, with reason.
3. Plan re-registration is forced when `dissonance=True` or `plan_id` has changed.

## Files to Create/Modify

- `agents/arc3/solver.py` — add `_last_registered_plan_id` and `_last_registered_goal` tracking; wrap `register_plan` calls in idempotency guard

## Outcome Statement

After this card, the brain plan ledger contains only meaningful plan transitions. Duplicate registrations are eliminated, plan history becomes auditable, and brain write volume is reduced significantly.
