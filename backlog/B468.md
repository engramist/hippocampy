# B468 - Consolidation Loop LLM Steps Freeze the Daemon

State: fixed (2026-10-06); real-model confirmed (LongMemEval R10b, 35/35 questions, no offline)
Priority: P1

### Problem Statement

The first real LongMemEval runs (campy-benchmarks R10, 2026-10-06) failed
three times out of three with `notify_turn: adapter reported daemon offline:
'{"status": "queued_offline"}'`, after 7 questions (oracle) and inside the
first question (`s`, 523 turns). The harness marks the whole suite invalid,
so no results survived.

With `--keep-store`, the per-question daemon's log showed the loop finish
Step 2/3 for a long assistant turn (`step2_3_total ... typed_entities=29`),
then three minutes of silence, then `openai: Retrying request to
/chat/completions`. Ollama's log for that request shows llama3.1:8b
generating 8,119+ tokens at ~46 tok/s, a degenerate loop on a prompt that
should return one small JSON object, until the client's 180 s Ollama timeout
cancelled it (`[GIN] ... | 500 | 3m0s`). All three failures have the same
3m0s 500.

The user's personal daemon runs the same path on every captured turn, so a
long captured assistant message could freeze it the same way.

### Root cause

Two defects, both needed for the outage:

1. **Synchronous LLM calls on the daemon's event loop.** `_loop_worker` runs
   `run_loop` as a task on the daemon's own event loop
   (`brain_daemon.py`, `asyncio.create_task(self._loop_worker())`). Step 2
   (`classify_concept` → `_classify_with_llm`), Step 3b
   (`extract_semantic_relations`) and Step 6 (`arbitrate`) are plain `def`
   functions calling the blocking `LLMClient.chat()`, invoked directly from
   the coroutine. While one waits, the daemon serves nothing: the adapter's
   socket call times out, falls back to HTTP, times out again, and reports
   the daemon offline. With `max_retries` 3 for Ollama, one bad message
   can freeze it for up to ~12 minutes.
   B447's comment in `orchestrator.py` said these sync steps were "ruled
   out" because other MCP calls kept completing during its stalls; that held
   for those stalls, but not in general.
2. **No output cap on JSON-only calls.** None of the three steps passed
   `max_tokens`, so a degenerate generation ran to the client timeout.

### What It Does (Scope)

- `orchestrator.run_loop` runs Step 2, Step 3b and Step 6 through
  `asyncio.to_thread`, so the event loop keeps serving requests while the
  LLM answers. (Step 7.5 already used `achat`.)
- Step 2, Step 3b and Step 6 pass `max_tokens=256` (each answers with one
  short JSON object). Every production client accepts it: `LLMClient.chat`
  forwards kwargs to the OpenAI-compatible endpoint, and Bedrock's `chat`
  ignores unknown kwargs.
- The B447 comment in `orchestrator.py` is corrected.

### Not changed

- The 180 s Ollama timeout and `max_retries` defaults. With the cap, a
  runaway answer stops at 256 tokens (~5 s); the timeout stays a backstop.
- Other synchronous calls in the loop (`retrieve_candidates`, NER,
  embeddings already go through `to_thread`): local and fast, no LLM.
- The harness discarding every result when one question fails is
  campy-benchmarks' concern (reported on hippocampy#278).
