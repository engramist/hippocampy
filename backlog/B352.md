# B352 - Flaky Timing Assertion in test_periodic_checkpoint_task_interval

State: complete
Priority: P3

Plan: none yet.

### Problem

`tests/test_manual_checkpoint.py::test_periodic_checkpoint_task_interval` has now failed twice,
independently, on unrelated PRs' CI runs — [PR #83](https://github.com/engramist/hippocampy/pull/83)
(2026-08-21) and [PR #89](https://github.com/engramist/hippocampy/pull/89) (2026-08-22), both docs-only
changes that could not plausibly have caused it. Both failures, and this is the giveaway: the exact same
assertion, different observed values —

```
AssertionError: Spacing 0.17208034300000463 not near 0.1   (PR #83)
AssertionError: Spacing 0.23440369400003647 not near 0.1   (PR #89)
```

The test (`tests/test_manual_checkpoint.py:104-140`) runs a real periodic-checkpoint loop
(`_test_periodic_checkpoint`, `tests/test_manual_checkpoint.py:143-150`) at a 100ms interval for ~350ms,
then asserts every consecutive checkpoint-call spacing falls within `0.05 < spacing < 0.15` — a ±50%
tolerance band around 100ms. But each loop iteration does a REAL `asyncio.sleep(0.1)` followed by a REAL
`db.checkpoint()` call (actual KuzuDB disk I/O, not mocked — only the *call site* is wrapped to record
timestamps, the underlying checkpoint still executes). On a loaded or throttled CI runner (GitHub Actions
runners are shared, variable-performance VMs), the combination of event-loop scheduling jitter plus real
checkpoint I/O latency can easily push a single iteration's wall-clock spacing past 150ms — both observed
failures (172ms, 234ms) are consistent with one slow iteration among several fast ones, not a systemic
timing bug in the checkpoint task itself (the assertion `len(checkpoint_calls) >= 2` — that multiple
checkpoints happen at all — has never been reported failing, only the tight spacing-tolerance check).

This is a flaky-by-design timing assertion (asserting real-world wall-clock precision on an operation
that includes real disk I/O, with a tolerance band too tight for a shared/variable-load CI environment),
not evidence of an actual regression in checkpoint cadence behavior. Confirmed pre-existing and unrelated
to either PR it was seen failing on — rerunning the CI job with no code changes made it pass both times.

### What it does (scope)

1. Loosen the tolerance band, and/or switch from asserting every individual consecutive spacing to
   asserting the *average* spacing across all observed intervals falls within tolerance — averaging
   smooths out one-off scheduling/I/O hiccups without losing the test's actual intent (verify the task
   fires at roughly the configured cadence, not that every single interval is precise to the millisecond).
2. Alternatively (or additionally): mock `db.checkpoint()` entirely for this specific timing assertion
   (a separate test already or easily could verify checkpoint() is actually called via a real DB; this
   test's purpose is cadence, not I/O correctness) so the measured spacing reflects only `asyncio.sleep`
   scheduling, not real disk I/O latency — removes the dominant source of the observed jitter.
3. Whichever fix is chosen, verify by running the test repeatedly (a loop of at least 20-30 runs) both
   locally and ideally under artificial load (e.g. `stress` or a concurrent CPU-bound background process)
   to confirm the new tolerance/approach doesn't just move the flakiness threshold higher without
   eliminating it.

### Dependencies

None — fully independent of B342/B311's memory investigation and of B351's AF_UNIX fix; found
incidentally on two unrelated PRs' CI runs while verifying other changes didn't introduce regressions.

### Files to create/modify

- `tests/test_manual_checkpoint.py` — `test_periodic_checkpoint_task_interval`, and possibly
  `_test_periodic_checkpoint` if the mock-the-checkpoint-call approach is chosen.

### Acceptance Criteria

- [ ] The test passes reliably under normal CI load (no special-casing or skip markers).
- [ ] The fix addresses the actual cause (real I/O latency variance under a tight per-interval
      tolerance), not just a symptom (e.g. blindly widening the tolerance further without addressing why
      individual spacings can vary this much).
- [ ] A brief note in the test's docstring on why the original per-interval ±50% tolerance was
      insufficient, so this doesn't regress if someone tightens it again later without this context.

### Outcome

Closed 2026-08-28. Fixed at the root per this card's preferred option (item 2): `mock_checkpoint()` no
longer calls through to the real `client.checkpoint()` (actual disk I/O) — it just records the
timestamp and returns `True`, removing the dominant source of jitter entirely rather than just
widening a tolerance around it. Also switched the assertion from every individual consecutive spacing
to the average spacing across all observed intervals (this card's item 1), since that's what the test
actually cares about. Added the requested docstring note explaining why, referencing this card and
its duplicate B361.

Verified via repeated runs: 30/30 clean-load runs passed; 20/20 more passed under artificial
concurrent CPU load (4 busy-loop background processes). `tests/test_manual_checkpoint.py::test_checkpoint_configuration_defaults`
was separately touched by the same PR for an unrelated reason (B349's checkpoint-interval default
change from 60s to 15s landed in the same working session) — not a regression, a coincidental overlap
in the same file.
