# B432 — `explore_graph` (Live MCP Tool) Is Structurally Broken Against the Shipped Oxigraph Engine

**Status:** Fixed (2026-09-16)
**Found by:** B427 batch 2 (triaging `tests/test_explore_graph_real_kuzu.py` for migration off
`KuzuClient` — the file exists specifically to validate multi-hop traversal against a *real*
database, per its own B280 docstring; running it against real `OxigraphClient` instead of real
`KuzuClient` surfaced this).

### Fix summary

Both bugs fixed with dedicated Oxigraph-native mechanisms, no domain-semantics guessing:

- **Bug 1 (start-node lookup):** the 12 `explore.start_node_<table>` NamedQueries
  (`queries/explore.py`) now carry `sparql=None`. `gateway.py`'s `_handle_oxigraph_handler`
  gained an `explore.start_node_*` branch that calls a new `OxigraphClient.get_node(table, uri)`
  method — hydrates the node's real properties (via a new shared `_hydrate_node_columns()`
  helper, factored out of the existing `vector_search`/kept as-is in `fts_search`) and returns
  them shaped like Kùzu's own `RETURN n AS node` (including `_label`/`_id` keys
  `_node_payload()` already expects). `tests/test_b395_sparql.py`'s blanket
  `assert query.sparql is not None` was updated with the same documented-exception pattern
  already used for `capability.reuse_candidates`/`capability.create_edge_*`.
- **Bug 2 (frontier expansion):** `OxigraphClient` gained `expand_frontier(frontier_uris,
  edge_types, direction)` and `get_node_generic(uri)` (discovers a neighbor's table from its own
  `a campy:<Table>` triple, since frontier hops can land on any traversable node table). Walks
  the store directly via `quads_for_pattern` rather than SPARQL, because `write_edge` always
  asserts an edge's *plain* triple regardless of reification class — a bare triple-pattern scan
  finds every edge type structurally, matching real per-hop `?conf` lookup for star-reified
  edges (`_edge_confidence()`, defaulting to 1.0 for plain edges, matching the Kùzu path's own
  `coalesce(r.confidence, 1.0)`). `explore_graph.py`'s `_execute_frontier_query` now
  duck-type-dispatches on engine (`type(db).__name__ == "OxigraphClient" or (hasattr(db,
  "store") and not hasattr(db, "conn"))`, matching the existing convention already used in
  `schema.py`/`export.py`) to either path, converging both into a common `raw_rows` shape before
  shared post-processing.
- `tests/test_explore_graph_real_kuzu.py` fully migrated onto `OxigraphClient` (all 8 tests
  pass, including a query-budget test reformulated to count `expand_frontier()` calls instead of
  Kùzu `db.execute()` calls — the equivalent per-hop cost unit on this engine).
- Verified live: multi-hop chains, cycles, direction filtering, depth caps, default (all
  92-rel-type) edge-type traversal, and the `context_window` temporal-context feature (which
  reuses the same frontier-expansion path) all confirmed working end-to-end against a real
  `OxigraphClient` with the full production schema.
**Severity:** Critical — `explore_graph` is a live, registered MCP tool
(`campy/brain/thalamus/tool_schemas.py:222`) that silently does nothing useful in production
today. Every call reports "Start node X not found" (or, if that's fixed, still cannot traverse
past hop zero).

## Reproduction

```python
db = OxigraphClient(tmp_path)
init_schema(db, SEED_PATH, EMBEDDING_MODEL)
db.write_node("Concept", {"concept_id": "n0", "text_raw": "node n0", "confidence": 0.9})
db.write_node("Concept", {"concept_id": "n1", "text_raw": "node n1", "confidence": 0.9})
db.write_edge("REQUIRES", mint_uri("Concept", "n0"), mint_uri("Concept", "n1"), {"confidence": 0.9})

await explore_graph({"start_node_id": "n0", "session_id": "t", "depth": 3, "edge_types": ["REQUIRES"]}, db, {})
# -> {'start_node_id': 'n0', 'paths': [], 'total_nodes_visited': 0,
#     'exploration_complete': False, 'error': 'Start node n0 not found'}
```

The node demonstrably exists (`db.write_node` succeeded) — the tool cannot find it.

## Two independent, stacked bugs

### Bug 1 — start-node lookup returns bare URI strings, not hydrated nodes

`campy/brain/hippocampus/graph/queries/explore.py`'s `explore.start_node_<table>` SPARQL
bodies (e.g. `explore.start_node_concept`) `SELECT ?node ?internal_id` where `?node` is the
*subject variable itself* (bound to a URI term) and `?internal_id` is `BIND(STR(?node) AS
?internal_id)` — also just the URI as a string. Confirmed directly:

```python
gw.run_sync("explore.start_node_concept", id="n0")
# -> [{'node': 'https://campy.dev/id/Concept/n0', 'internal_id': 'https://campy.dev/id/Concept/n0'}]
```

`explore_graph.py`'s `_node_payload()` expects `node` to be a **dict of hydrated properties**
(`node.get("_label")`, `node.get(pk)`, `node.get("text_raw")`, etc. — the shape Kùzu's
`RETURN n AS node` produces). Calling `.get()` on a bare string raises `AttributeError`. That
exception is caught by the bare `except Exception: continue` in `explore_graph()`'s start-node
lookup loop (`campy/brain/thalamus/tools/explore_graph.py` ~line 260), so every table lookup
"fails" silently and the loop exhausts all 12 node tables before reporting "not found" — for
every single call, regardless of whether the node exists.

### Bug 2 — frontier expansion is 100% Kùzu-only Cypher, bypasses the gateway entirely

Even with Bug 1 fixed, multi-hop traversal cannot work: `_execute_frontier_query()`
(`campy/brain/thalamus/tools/explore_graph.py` ~line 73) calls `db.execute(query)`
**directly** — not through `GraphGateway`/a `NamedQuery` at all — where `query` comes from
`campy/brain/hippocampus/graph/queries/explore.py`'s `build_frontier_query()`:

```python
def internal_id_literal(internal_ids):
    parts = [f"INTERNAL_ID({int(iid['table'])}, {int(iid['offset'])})" for iid in internal_ids]
    return "[" + ", ".join(parts) + "]"

def build_frontier_query(edge_types, direction, internal_ids):
    ...
    return f"{match_clause} WHERE id(a) IN {id_literal} RETURN a, b, label(r), coalesce(r.confidence, 1.0)"
```

`INTERNAL_ID(table, offset)`, `id(a)`, and `label(r)` are Kùzu-only Cypher builtins (Kùzu's
physical row-id addressing scheme — this exact mechanism is what the original B280 fix
depended on, per `docs/`/memory: "fix is unlabeled nodes + INTERNAL_ID(table,offset) literal
(no working param form)"). None of this has any SPARQL translation, and `db.execute()` on
`OxigraphClient` expects SPARQL text, not Cypher — passing it Kùzu Cypher either raises or
(more likely, given pyoxigraph's parser) fails to parse and is again swallowed by the bare
`except Exception: _logger.exception(...)` in `_execute_frontier_query()`.

`explore_graph.py`'s partial gateway migration (the start-node lookup uses
`gw.run_sync(f"explore.start_node_{table}", ...)`) only covers depth-0 node resolution.
Frontier expansion — the actual multi-hop traversal this tool exists for — was never migrated
off raw Kùzu Cypher at all.

## Why this went undetected

`tests/test_explore_graph.py` (the always-run suite) uses a hand-rolled `MockDB` that
pattern-matches on query substrings — it never runs real Cypher OR real SPARQL, so it cannot
distinguish "the query is syntactically valid Kùzu Cypher" from "the query actually returns
correct results on the shipped engine." `tests/test_explore_graph_real_kuzu.py` (B280's
regression suite) only ever ran against real `KuzuClient` — never against `OxigraphClient` —
so this class of defect (right logic, wrong query language / wrong result shape) had no test
surface at all until B427 attempted the engine swap.

## What needs deciding (do not implement without this)

1. **"Internal id" has no meaningful RDF equivalent.** Kùzu's `INTERNAL_ID(table, offset)` is
   a physical-storage addressing trick used purely to avoid re-resolving a node by its
   business primary key on every hop. On Oxigraph, the node's own URI already serves that role
   (it's globally unique and directly addressable via `quads_for_pattern`) — the "internal id"
   concept should likely just become "use the URI," but every downstream consumer of the
   `{table, offset}` shape (`internal_id_cache`, `internal_id_literal`,
   `_add_temporal_context`) needs updating in lockstep, not patched individually.
2. **Frontier expansion needs a real Oxigraph-native strategy**, e.g. either:
   - A Python handler that walks `store.quads_for_pattern()` directly per hop (mirroring how
     `gateway.py`'s existing star/occurrence handlers already do direct store access) — most
     flexible for runtime-chosen `edge_types`/`direction`, since those can't be baked into a
     static registered `NamedQuery`.
   - A parameterized SPARQL query built per call (same shape as today's Cypher-string-building
     approach, just emitting SPARQL property-path syntax instead) — keeps the "build query
     text from runtime params" pattern but changes the target language.
3. **Fix Bug 1 regardless of which direction is chosen for Bug 2** — the start-node lookup
   needs `?node`'s actual properties selected (mirroring how `arc.py`'s / `capability.py`'s
   NamedQueries do `OPTIONAL { ?target campy:entity_type ?entity_type }` per real column),
   not just the subject URI.

Given the shape of the fix touches a live tool's core traversal algorithm and has no
1:1 mechanical translation, this needs the same explicit design checkpoint B430 got before
implementation — do not guess at the traversal-rewrite strategy silently.
