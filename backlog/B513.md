# B513: ONNX embedding batches grow the footprint to about 1.2 GB (arena + wide padding)

**Status:** ready · **Found:** 2026-10-24, while measuring B512 (not caused by it)

`embed_batch` of 1,000 real texts (about 84 characters on average, longest 489) takes a fresh
process from about 250 MB to a 1,228.8 MB physical footprint (peak RSS about 1.35 to 1.39 GB), and
a second identical batch adds about 100 MB more. Identical with fastembed 0.8.0 and with the direct
embedder, so the cause is in how the session is used: batches of 256, padded to the longest text in
the batch, with ONNX Runtime's default memory arena (`enable_cpu_mem_arena`) never shrunk.

Options to measure, none assumed: smaller batches, length-sorted batching to cut padding,
`enable_cpu_mem_arena=False`, `memory.enable_memory_arena_shrinkage`. Gate: vectors must stay
bit-identical (padding changes can move values by float noise, so re-run the B512 parity script;
`tests/test_onnx_embedder.py` already compares batch sizes at 1e-6). Relevant to B353's "stay
light" goal: the daemon embeds in batches during ingest and re-embed.
