# B373 - `_resurrect_archived` Blocks the Event Loop for Minutes Under Real Load (B371's Missing Live Stack Trace)

State: complete
Priority: P1

Plan: none yet.

### Problem

B371 investigated a live daemon hang (elevated CPU, a raw-socket call timing out) and disproved its own
leading hypothesis (a busy loop in `_index_hygiene`), but explicitly left one item open: "the original
CPU spike + socket timeout is real and not explained by any of the above... would need a live stack
trace captured during a future occurrence." This card is that occurrence.

**Live capture, 2026-08-30**, during a real cross-repo live-smoke run (`arc-agi-38` session) against
this exact daemon: the daemon hit ~130% CPU, `STAT=R`, and a raw socket `tools/list` call would have
timed out again. Captured `sample <pid> 5` **during** the hang (not after, unlike B371's own attempt) —
independently, the `arc-agi-38` session captured two of its own samples 46 seconds apart. All three
samples show the **identical** call stack, 100% of samples, on the daemon's main thread:

```
task_wakeup -> task_step -> ... -> kuzu::main::Connection::executeWithParams
  -> ClientContext::executeNoLock -> TransactionHelper::runFuncInTransaction
  -> PlanMapper::mapOperator -> TaskScheduler::scheduleTaskAndWaitOrError
  -> std::condition_variable::wait -> pthread_cond_wait
```

This directly answers B371's open question 3 with certainty: something in the sweep pipeline **does**
block the main asyncio event loop synchronously, via a raw Kuzu call made directly on the event loop
thread (not offloaded to a worker thread) — not "the CPU was merely busy elsewhere."

`daemon.log`'s timestamps (a direct product of B371's own logging fix — without it this correlation
would have been impossible) pinpoint the window precisely: the last log line before the stall was
`[Supernode] pruned cache edges...` at `21:39:49.653` (`run_sweep()`'s step 1.2), and nothing logged
again until `[IndexHygiene] Message archived_ratio=1.00...` at `21:41:11.949` (step 2.5) — an **82-second
gap**, during which the independent 15-second periodic-checkpoint task also went completely silent,
confirming total event-loop starvation, not just one slow step.

**Root cause, found by reading every function in that window (`_apply_valence_decay`, step 1.5;
`_resurrect_archived`, step 2) and measuring against the real production DB:** `_resurrect_archived`
fetches every archived+embedded node in each sweepable table, then calls `db.vector_search()` — a
synchronous, unthreaded Kuzu HNSW query — **once per node, in an unbounded loop, directly on the event
loop thread**. Measured live against this exact daemon's real DB: the `Message` table alone has
**18,120** archived+embedded rows (its `archived_ratio` has been pinned at 1.0 for months — the same
fact B371's investigation already established). A single `vector_search` call measured at ~28ms in
isolation; at that rate, one full unbounded pass over Message's archived population is **~515 seconds**
— and this runs, unconditionally, every single sweep cycle (every 300s), forever, growing as more
messages accumulate. This directly explains why these incidents get worse with daemon uptime (more
archived history) and why B371's earlier isolated timing of `_index_hygiene` (13.5ms, correctly ruling
it out) didn't predict this: that measurement was on an idle DB and measured the wrong function — a
completely different, uncapped, per-node loop in a neighboring step was the actual mechanism.

### What it does (scope) — implemented

1. **Bounded the per-sweep cost**: `_resurrect_archived` now takes a `candidate_limit` parameter
   (`[pruning] resurrection_candidates_per_sweep` in `campy.toml`, default 200) that caps how many
   archived+embedded nodes are considered per table per sweep, via a `LIMIT` clause on the fetch query.
   Not a smart "most-worth-checking" ordering — plain scan order, capped — a documented simplification,
   not a claimed optimum.
2. **Moved the scan off the event loop thread**: extracted the per-table fetch + per-node
   `vector_search` loop into a new synchronous helper, `_resurrect_candidates_sync`, called via
   `await asyncio.to_thread(...)` from `_resurrect_archived`. The resurrection write-back (`execute_write`,
   already properly threaded internally) stays on the async side. This means even the now-bounded
   per-sweep work can never block anything else in the daemon.
3. Both fixes are independent and complementary: the cap bounds the worst case in absolute terms; the
   thread offload means even the bounded amount of work can't stall the event loop while it runs.

### Acceptance Criteria

- [x] Root cause identified with a live stack trace captured during an actual occurrence (not inferred
      after the fact) — cross-confirmed independently by two sessions' samples, both identical.
- [x] The specific unbounded/synchronous mechanism identified and measured against the real production
      DB (18,120 real archived rows, ~28ms/call, ~515s unbounded estimate).
- [x] Fixed: bounded per-sweep cost (config-driven cap) + moved off the event loop thread
      (`asyncio.to_thread`).
- [x] Verified against the real production DB, not just mocks: `_resurrect_archived` now completes in
      **0.83s** (was unbounded/~515s estimated, ~80s observed in the live incident) against the real
      18,120-row Message archive, with an independent heartbeat task ticking 17 times during the call —
      direct proof the event loop stayed responsive throughout.
- [x] Existing `_resurrect_archived` tests pass unchanged (6/6); new tests added for the cap
      (`test_resurrect_applies_candidate_limit_to_the_query`) and the non-blocking behavior
      (`test_resurrect_does_not_block_the_event_loop`, which simulates the real incident's shape with a
      slow mock DB and an independent heartbeat task).

### Outcome

Closed 2026-08-30. See "What it does (scope)" and "Acceptance Criteria" above — implemented and verified
in the same investigation session that captured the live evidence, per explicit instruction to move
fast given the narrow live-occurrence window. Not addressed in this card, deliberately out of scope: the
other ~20 direct, unthreaded `db.execute()` call sites elsewhere in `sweep.py` carry the same class of
risk in principle but were not individually profiled or confirmed as actual contributors to any real
incident — fixing all of them without individual justification would be speculative, not evidence-based.
Worth a systematic follow-up pass if further incidents implicate a different step.
