# B230 - Packaging Hardening for Installed Mode

State: complete
Priority: P0

Plan: backlog/plans/B-230-packaging-hardening-installed-mode.md

### Problem

SideQuests currently works best from a cloned source tree with `pip install -e .`. That is acceptable for private testing, but it is not sufficient for a one-line public installer. Public users need `pipx install`, `uv tool install`, PyPI wheels, and Smithery-style installs to work without relying on repository-relative files.

The provisional patent filing is complete, so publication is no longer blocked by the pre-filing disclosure constraint. The next blocker is packaging correctness.

### What This Card Does

Hardens SideQuests so it can run correctly when installed as a wheel/sdist rather than from an editable source checkout.

This card audits runtime path assumptions, package-data inclusion, daemon entry points, adapter paths, config templates, schema/seed assets, web assets, and tests package-installed behavior in a clean environment.

### Acceptance Criteria

- [ ] `python -m build --wheel --sdist` succeeds from a clean checkout.
- [ ] `twine check dist/*` passes without warnings.
- [ ] A fresh virtual environment can install the generated wheel and run `sidequests --help`.
- [ ] Installed `sidequests install --help`, `sidequests status --help`, `sidequests activity --help`, and `sidequests wiki --help` run without importing source-tree-only paths.
- [ ] Package data includes required defaults, templates, schemas, seed files, adapters, and web assets.
- [ ] Runtime user data remains under `~/.sidequests`; package data is never written in place.
- [ ] Daemon launch path works from installed-package mode, not only from repo root.
- [ ] Codex, Claude Code, Claude Desktop, and VS Code registrations point at stable installed entry points or generated wrapper scripts.
- [ ] Editable install remains supported for development.
- [ ] README clearly distinguishes dev/source install, package install, and public one-line install readiness.
