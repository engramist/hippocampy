# B452 - FootprintWatchdog Did Not Catch a 43 GB Blowup (vmmap Times Out; Thresholds Too Slow)

State: fixed (2026-09-27)
Priority: P1

`_periodic_footprint_watchdog` (B354) is designed around physical footprint, not
RSS, and that was right: during B451 RSS stayed ~4.5 GB while footprint hit
43 GB. But it shells out to `vmmap -summary` with a 10s timeout, and under this
load `vmmap` timed out — logged as "vmmap check failed ... skipping this check"
(seen for hours on 2026-09-23) and, when the *startup* baseline read fails,
"watchdog disabled for this process's lifetime". Even when healthy it needs 6
consecutive checks 300s apart above a +4 GB baseline (~30 min) — the blowup took
~10. Result: macOS jetsam killed the daemon (no graceful shutdown, ~4 min
downtime) instead of the watchdog restarting it cleanly.

Suggested: read `ri_phys_footprint` in-process via `proc_pid_rusage`
(ctypes, instant, no subprocess) or use the `footprint` CLI (returned in <1s
at 46 GB); tighten the growth-rate check (e.g. >8 GB in 2 checks 60s apart
restarts); never disable for a transient baseline failure — retry.


## Completion notes (2026-09-27)

Deliberately did NOT touch `growth_threshold_mb` / `consecutive_breaches_required`
/ `check_interval_seconds` -- `campy.toml`'s own comment documents a real 2026-08-22
incident where *tightening* these caused a live restart loop, with an explicit
"if this ever fires again, investigate before assuming the fix is 'raise it
further'" note. Re-tightening them now, right after that lesson, would be
repeating the mistake. B452's actual bug was the *sampling mechanism*, not the
thresholds:

- New `_footprint_parsed()` uses `footprint -j` (a built-in macOS tool, JSON
  output) instead of `vmmap -summary`'s text parsing. Confirmed by direct A/B
  timing: 0.68s vs 0.039s at idle; `footprint` stayed fast even run directly
  against the real 46GB blowup process (vmmap was timing out at 10s repeatedly
  under that same load, which is why the watchdog went dark for hours during
  B451). Same return-dict contract as `_vmmap_parsed()`, so it's a drop-in
  swap at the watchdog's two call sites; `_vmmap_parsed`/`_vmmap_swap_summary`
  are untouched (still used by the SIGUSR1 manual diagnostic, a low-frequency,
  operator-triggered path where speed doesn't matter).
- Baseline establishment now retries up to 5 times (spaced by
  `check_interval_seconds`) instead of permanently disabling the watchdog for
  the process's entire lifetime on one failed sample -- the daemon's own cold
  start (RocksDB WAL replay, embedding warm-up) is itself a burst of activity
  that can plausibly fail a single early sample.

**Tests**: `tests/test_b452_footprint_sampler.py` (4 tests, real subprocess
calls against the test's own PID: reads a sane footprint, stays under 3s,
degrades gracefully on a bogus PID, same dict shape as `_vmmap_parsed`).
Existing watchdog tests in `test_auth_context.py` renamed to patch
`_footprint_parsed` (7 tests, all still pass unmodified in behavior) plus one
new test for the baseline-retry-then-succeed path. Confirmed load-bearing via
`git stash` revert (import error without the fix). Full suite: 2893 passed
(was 2888), 35 skipped, 2 xfailed.
