# B350 - Longer Live ARC_AGI Episode to Observe a Real Spike-and-Release Under B337's Fix

State: ready — requires the ARC_AGI-side Claude Code session (cross-repo)
Priority: P1

Plan: none yet.

### Problem

`backlog/B311.md`'s Round 6 got the first-ever live confirmation of B337's periodic-checkpoint
mitigation (a gap every prior round had deferred), via cross-repo collaboration with the ARC_AGI-side
Claude Code session. The result was genuinely useful but explicitly partial: the episode ended early
via `STALL_CHECK` (`no_progress=8, threshold=8`) after only ~148 seconds — under 10 checkpoint
opportunities at the tested 15s interval — and showed smooth, monotonic RSS growth with **zero**
drops across all 74 samples. That's consistent with the fix working, but Round 6's own write-up is
explicit that it **cannot distinguish** "the fix prevented a spike" from "this particular short episode
never would have spiked regardless, fix or no fix." The original 2026-08-08 field report that started
this whole investigation showed dramatic oscillation (632→128→809→1119→118 MB) over a ~308-second
episode — a real spike-and-release is the pattern this investigation has been trying to fix, and it's
never actually been observed *with the fix active*. Only the *absence* of oscillation has been observed
once, which is a weaker claim.

### What it does (scope)

1. Coordinate with the ARC_AGI-side Claude Code session (check `ListAgents` for the current live peer —
   was named `arc-agi-4d` as of this card's filing; it has real `ARC_API_KEY` access this side of the
   collaboration doesn't) to run a **longer, non-early-terminating** live episode: multiple puzzles
   back to back (not the 1-puzzle `make smoke` default), or a puzzle/configuration less prone to
   triggering `STALL_CHECK` early — check `run_single_puzzle.py --live-smoke`'s flags for options to
   run more puzzles per invocation or disable/raise the stall threshold for this specific diagnostic
   purpose (don't permanently change ARC_AGI's default stall behavior — this is a one-off diagnostic
   run, coordinate accordingly).
2. Sample RSS the same way Round 6 did: `ps -o rss= -p <pid>` every ~2s for both `brain_daemon.py` and
   the ARC client process, for the full episode duration — long enough to span at least several minutes
   and multiple write-heavy phases, aiming to match or exceed the original field report's ~308-second
   window.
3. Whatever the current shipped/active `[checkpoint] interval_seconds` value is at the time this card is
   worked (check `campy.toml` — it may have changed if B349 landed first; if so, use that value, don't
   assume 15s), run the episode with periodic checkpointing active.
4. Analyze the resulting trajectory: does a real spike-and-release ever occur? If yes, is its peak
   materially lower than the original field report's ~1.1GB-over-baseline spike, and does it recover
   faster? If no spike occurs at all even over a longer, higher-volume episode, that's a *stronger*
   positive result than Round 6's short episode could establish — say so explicitly if that's what's
   found, don't undersell a genuinely better result out of excess caution.
5. Append the findings to `backlog/B311.md` as the next round (check current round number first — do
   not overwrite or renumber existing rounds), following the same honesty discipline as every prior
   round: report what was and wasn't established, include raw data (check in the CSV the same way
   Round 6's `backlog/data/b311_round6_live_confirm.csv` was, using a similarly-named file for this
   round).
