# B324 - AWS Bedrock LLM Provider

State: done
Priority: P0

Plan: (inline — self-contained, sized for a Sonnet-level implementer)

Depends on: nothing hard. Composes with **B315/B316** (cloud deployment) — Bedrock uses the
same IAM identity plane, so it lands naturally alongside them.

### Why

Campy running in a customer's AWS account must be able to use whatever models that customer's
Bedrock gives them, rather than requiring a local Ollama install. A team deploying into their
own VPC has already made the model-governance decision at the Bedrock level — model access,
guardrails, logging, region, data-residency — and Campy needs to inherit it rather than route
around it.

There is also a hard blocker for cloud deployment today: the default provider is `ollama`
against `http://localhost:11434/v1`. An ECS task has no local Ollama, so the synthesis path
(`ask`, consolidation, lesson synthesis) is dead in a cloud deployment until this exists.

### Current State (verified in code)

`campy/brain/llm/provider.py` (235 lines) is a clean, small seam:

- `LLMClient` (line 61) — wraps a client and exposes `chat()` (line 73) and
  `chat_with_usage()` (line 95); tracks `last_usage` with prompt/completion/total tokens
- `create_llm_client(config)` (line 130) — factory reading `config["llm"]`:
  `provider`, `model`, `base_url`, `api_key`, `timeout_seconds`, `max_retries`
- `create_llm_client_for_step(config, step_name)` (line 197) — per-step overrides
- Providers today: `ollama`, `openai`, `anthropic`, `google`

**The structural catch:** every existing provider is constructed as
`OpenAI(base_url=..., api_key=...)`, and `LLMClient` assumes the OpenAI response shape —
`response.choices[0].message.content`, `response.usage.prompt_tokens`.

**Bedrock does not speak the OpenAI chat-completions API.** It is `bedrock-runtime` with
SigV4 auth and its own request/response shapes. So Bedrock cannot be a fifth
`OpenAI(base_url=...)` branch — it needs a sibling client class implementing the same
interface.

### What This Card Does

**Task 1 — Extract the interface.**

`create_llm_client` currently returns `LLMClient` concretely. Introduce a `Protocol` (or ABC)
capturing what callers actually use — `chat()`, `chat_with_usage()`, `achat()` if present, and
the `last_usage` attribute — and have the factory's return type be that protocol.

Read the whole file first and enumerate every attribute callers touch; grep for
`create_llm_client` and `last_usage` across `campy/` to catch anything the class exposes
implicitly. A missed attribute surfaces as an `AttributeError` deep inside consolidation, far
from this change.

**Task 2 — `BedrockLLMClient`, using Converse.**

New module `campy/brain/llm/bedrock.py`. Implement the protocol over
`boto3.client("bedrock-runtime").converse(...)`.

**Use the Converse API, not `InvokeModel`.** This is the load-bearing choice: `InvokeModel`
requires a different request/response body per model family (Anthropic, Llama, Mistral, Titan,
Nova all differ), which would mean per-family branching that breaks whenever the customer picks
a different model. Converse normalizes all of them behind one request shape — which is exactly
the requirement, since the customer chooses the model, not us.

Mapping notes:

- OpenAI-style `messages` use `{"role", "content": str}`. Converse expects
  `{"role", "content": [{"text": ...}]}`, and **`system` is a separate top-level parameter**,
  not a message role. Extract system messages out of the list and pass them as `system=[...]`.
- Converse requires alternating user/assistant roles and rejects consecutive same-role
  messages. Merge adjacent same-role messages before sending.
- `temperature` goes in `inferenceConfig`, not at top level.
- Usage comes back as `response["usage"]` with `inputTokens` / `outputTokens` / `totalTokens`
  — map to the existing `prompt_tokens` / `completion_tokens` / `total_tokens` keys so
  B180's usage tracking keeps working unchanged.
- Text is at `response["output"]["message"]["content"][0]["text"]`. Handle an empty content
  list rather than indexing blindly.

**Task 3 — Auth and configuration.**

No API key. Use boto3's default credential chain, which resolves the ECS task role in
deployment and the developer's profile locally. That means Bedrock composes with B315/B316:
the same IAM identity that scopes the workspace also authorizes the model call, and there is
no secret for Campy to store or rotate.

Config keys under `config["llm"]`:

```
provider = "bedrock"
model    = "us.anthropic.claude-sonnet-4-5-20250929-v1:0"   # or any Bedrock model id
region   = "us-east-1"          # optional; falls back to AWS_REGION / boto3 default
profile  = "..."                # optional, local dev only
```

**Model IDs need care.** Bedrock has both bare model IDs and cross-region *inference profile*
IDs prefixed by geography (`us.`, `eu.`, `apac.`). Several current models are only invocable
via an inference profile, and passing a bare ID returns a validation error that does not
explain this. Detect that specific failure and raise a message naming the likely fix, rather
than surfacing the raw boto error — the person hitting it will otherwise have no idea.

Honor the existing `timeout_seconds` / `max_retries` config through botocore's `Config`
(`read_timeout`, `retries={"max_attempts": ...}`) so behavior matches other providers.

**Task 4 — Wire into the factory and the installer.**

- Add the `bedrock` branch to `create_llm_client`, and confirm `create_llm_client_for_step`
  inherits it (read line 197 — if it re-implements provider dispatch, fix both).
- Add Bedrock to the guided installer's provider choice (`campy/cli/install.py`, `setup.py` —
  B13 built this flow) with region and model prompts, and no API-key prompt.
- Add it to `campy/cli/smoke_test.py` so `campy doctor`-style verification covers it.
- `boto3` must be an **optional** dependency. Import it inside the branch, and if it is
  missing raise a message naming the extra to install. Local users must not be made to
  install AWS libraries.

**Task 5 — Do NOT move embeddings to Bedrock. Explain why in the PR.**

This is the trap in the request, and it must be stated rather than discovered later.

`campy/brain/hippocampus/graph/embeddings.py` uses a local `SentenceTransformer`, and **every
embedding column across ~53 node tables is `FLOAT[384]`**, with Kùzu HNSW indexes built on that
fixed dimension. `schema.py` has a startup dimension check specifically to stop a mismatched
model corrupting the index.

No Bedrock embedding model outputs 384 dimensions. Titan Text Embeddings V2 supports 1024/512/256;
Cohere Embed outputs 1024. So switching embeddings to Bedrock is **not** a provider swap — it is
a schema migration across every embedding column, a full re-embed of the existing graph, and an
index rebuild, with silently-degraded recall if any part is missed.

**Recommendation: keep local SentenceTransformer embeddings even in cloud deployments.** It is a
small CPU model, it runs fine in a container, and it avoids the entire dimension problem. Revisit
only if a deployment forbids shipping model weights — and then as its own card with a re-embed
plan, not as part of this one.

**Known cost of that recommendation, state it in the PR.** `sentence-transformers==3.3.1`
(`requirements.txt:8`) pulls in `transformers`, which currently carries several HIGH advisories
in this repo's own `pip-audit` run — two of them marked *"no fix available yet — consider
removing this dependency."* Keeping local embeddings therefore keeps that dependency inside any
container shipped to a customer, and an enterprise security review **will** raise it.

This does not reverse the recommendation: the `FLOAT[384]` dimension problem is concrete and
immediate, while the CVEs are a posture issue with mitigations (pinned base image, no untrusted
model loading, network-isolated inference). But it does mean a cloud deployment needs a
dependency-posture review as its own piece of work, and that review should also cover
`starlette` (via `fastapi==0.115.6`, `requirements.txt:18`) — the web/SSE surface matters much
more behind an ALB than it does bound to localhost. Neither belongs in this card; note both as
follow-ups so the decision is recorded rather than rediscovered during a customer review.

**Task 6 — Bake the embedding model into the image (egress-wall requirement).**

Found by the customer's architecture review, and it is a hard blocker for their cloud tier —
not a preference.

Their build sandbox enforces a default-deny egress allowlist covering their core toolchain
hosts (source control, package registries, and a handful of vendor hosts) — **`huggingface.co`
is absent, and so is any Ollama endpoint.**

Verified on our side: `campy/brain/hippocampus/graph/embeddings.py:83` calls
`SentenceTransformer(model_name)` with no cache pinning and no `local_files_only`, so the model
is fetched from HuggingFace on first use. Inside a cloud-tier task that fetch is **denied by
Network Firewall**, and embeddings — therefore all of recall — are dead.

Task 5's recommendation (keep embeddings local rather than move to Bedrock) still stands; the
dimension problem is unchanged. But it only holds if the model never needs the network:

- Pre-download the model into the container image at build time and set the cache location
  (`HF_HOME` / `SENTENCE_TRANSFORMERS_HOME`) to that path.
- Pass `local_files_only=True` (or the equivalent for the pinned `sentence-transformers`
  version — check `3.3.1`'s signature) so a cache miss **fails loudly at startup** rather than
  silently attempting a download that a firewall will drop. A blocked download surfaces as a
  hang or an opaque connection error; an explicit local-only failure names the problem.
- Assert the model loads with networking unavailable.

This closes the objection completely: no allowlist change requested, no runtime download, no
dimension migration.

- [ ] `pytest tests/ -q` failure set identical to pre-change baseline

### What This Card Does NOT Do

- Does not move embeddings to Bedrock — see Task 5, that is a schema migration
- Does not implement Bedrock Guardrails, model-invocation logging, or provisioned throughput.
  Guardrails is a plausible follow-up for a governed deployment and is a `converse()` parameter,
  so this card's shape accommodates it.
- Does not add streaming (`converse_stream`) — Campy's synthesis path is non-streaming today
- Does not add Bedrock Agents or Knowledge Bases; this is model inference only
- Does not change the default provider. `ollama` stays the default; Bedrock is opt-in.

### Outcome

A Campy deployed in a customer's AWS account can use any model their Bedrock account exposes,
authenticated by the task role with no stored secret, and adding a new model family later is a
config change rather than a code change. This is also the card that unblocks synthesis
(`ask`, consolidation, lesson synthesis) in any cloud deployment, since `localhost:11434` does
not exist in ECS.
