### Problem

Campy's embedding backend (`campy/brain/hippocampus/graph/embeddings.py`) uses `sentence-transformers`,
which pulls in the full PyTorch stack. Per B342's investigation (`vmmap` sampling throughout that
card, and specifically this initiative's own baseline checks), this is the dominant contributor to
`brain_daemon.py`'s ~1.2-2GB fresh-start physical footprint — confirmed by elimination via B353's KuzuDB
isolation test (bare KuzuDB alone: 68.2-77.6MB, nowhere near the observed daemon baseline).

Per B353's reframing: this baseline, not the growth-over-time problem B311/B342 chased, is what actually
determines whether Campy "feels light" to a user glancing at Activity Monitor. This card is the
highest-leverage single change in the whole initiative for that stated goal.

### What's already verified (do not re-verify, build on this)

`fastembed`'s model catalog (`fastembed==0.8.0`, checked directly by downloading and inspecting the
wheel) natively supports `sentence-transformers/all-MiniLM-L6-v2` — the *exact* model this codebase
already uses and has already indexed data with — sourced from `qdrant/all-MiniLM-L6-v2-onnx`, a
third-party ONNX conversion of the same weights (not a different model).

A parity test (`b342_embedding_parity_test.py`, in this session's scratchpad — re-derive if needed, the
approach is simple: embed the same real sentences with both backends, compare) against 200 real, diverse
sentences from `campy/data/GistSeedExamples.md` found: per-sentence cosine similarity of **1.000000**
(min=max=mean, std=0.0) across all 200, and **100% top-10 retrieval overlap with exact rank order match**
across 15 random queries. This is a stronger result than typical PyTorch-vs-ONNX-Runtime numerical
differences would predict — genuinely close to perfect parity on real text, not an approximation.

**This means: this is a same-vector migration, not an approximation, for realistic text.** The caveat
carried over from B353: not directly tested against extreme edge cases (near the 256-token truncation
limit, code snippets, non-English text).

### What it does (scope)

1. Add `fastembed` as a dependency (`pyproject.toml`). Remove `torch`/`sentence-transformers` **only
   after confirming nothing else needs them** — checked so far: `sentence_transformers` is referenced in
   exactly two places, `campy/brain/hippocampus/graph/embeddings.py` (the actual embedding logic, being
   replaced by this card) and `campy/cli/install.py:552` (an install-verification smoke-test string that
   imports `SentenceTransformer` to confirm the install worked — this needs updating to verify `fastembed`
   instead, not just deleted). Re-check at implementation time in case anything changed since this card
   was written.
2. Replace `campy/brain/hippocampus/graph/embeddings.py`'s `sentence-transformers`-based implementation
   with `fastembed.TextEmbedding`, using `sentence-transformers/all-MiniLM-L6-v2` as the model name (same
   model — do not substitute a different one, see "Explicitly out of scope" below).
3. **Hardening, carried over from the external plan's round 2 (this part of it was correct and worth
   keeping):** pin ONNX Runtime's session options to prevent its own thread-pool sprawl —
   `intra_op_num_threads=1`, `inter_op_num_threads=1`, `execution_mode=ORT_SEQUENTIAL`. Without this, ONNX
   Runtime defaults to spawning worker threads equal to CPU core count, which on a high-core-count
   machine could reintroduce a different flavor of the same executor-thread-sprawl class of problem B342
   investigated for `asyncio.to_thread` — not proven to be an issue here, but cheap to prevent and matches
   the "keep this daemon boring and predictable" spirit of everything else in this initiative.
4. Preserve the existing `embed()`/`_embed_st()`/`_embed_with_fallback()` call-site contract in
   `embeddings.py` (whatever the current function signatures are) so nothing calling into this module
   needs to change — this should be an internal swap, not a call-site migration.
5. Measure the actual baseline footprint before/after via `vmmap -summary` (the same technique used
   throughout B342), on a fresh daemon start with no traffic — document the before/after numbers in this
   card's own follow-up notes once implemented, the way every B342 round documented its measurements.
6. Re-run the parity test as a regression check against the *actual* shipped integration (not just the
   standalone script), to confirm the real `embeddings.py` code path produces the same result as the
   scratchpad test did.

### Explicitly out of scope (do not do this as part of B355)

- **Do not switch to a different model** (e.g. `bge-small-en-v1.5`, which the external plan's round 1
  proposed and round 2 correctly walked back). A different model is a different embedding space; every
  vector already indexed in KuzuDB would need re-embedding (`campy reembed --confirm`) and the retrieval-
  quality change would need its own dedicated evaluation, not bundled into a memory-footprint card. If a
  model upgrade is wanted later, file it as its own card, separate from this initiative.
- **Do not touch KuzuDB configuration** — that's B356, deliberately deferred and separate.
- **Do not touch the restart/watchdog mechanisms** — those are B354, separate.

### Correction: The 228MB Figure Was Isolated-Test-Only, Not the Real Daemon's Baseline (2026-08-22)

Found while restarting the live daemon to prepare for an ARC-side smoke test, before doing anything else
with it: `vmmap -summary` on the freshly-restarted live PID showed **1.2GB**, not the ~228MB this card
originally reported. Investigated immediately rather than letting the discrepancy sit.

**Root cause: the original 228MB measurement tested `campy.brain.hippocampus.graph.embeddings` in
complete isolation — it never imported `spacy`.** The real daemon always does (`step1_ner.py` imports
`spacy` at module level, pulled in eagerly via `brain_daemon.py`'s own import chain through
`orchestrator.py`, before `start()` even runs — confirmed by checking the import graph directly). spaCy's
own ML backend, `thinc`, imports `torch` unconditionally as part of its own module initialization — **this
has nothing to do with which embedding backend Campy uses.** Verified directly: a bare `import spacy`, no
model loaded, no embeddings touched at all, jumps a fresh Python process's footprint from ~9KB to ~178MB
and pulls in `torch`/`thinc`. `spacy.load(en_core_web_md)` itself (the actual NER model weights) is lazy
— only loaded on first real message via `step1_ner.get_nlp()` — so a fresh-start/no-traffic baseline
reading does not include the full model weights, only spaCy's own `torch` import cost.

Two more things were confirmed while investigating this, both correcting statements made earlier in this
card: `sentence-transformers`/`torch` were changed in `pyproject.toml`/`requirements.txt` (declared
dependencies, affecting future installs) but were **never actually uninstalled from the live `.venv`** —
`pip show sentence-transformers torch` on the live daemon's own venv still returns version numbers.
Removing them now would not have prevented today's finding regardless, since `torch` loads via `spacy`/
`thinc` independent of the embedding backend either way — but "removed from dependencies" and "actually
uninstalled from the environment that's running" are two different claims, and only the first was true.

**What is still real and unaffected by this correction:** a fair, apples-to-apples comparison — spaCy
loaded first (establishing the unavoidable `torch`/`thinc` floor), then each embedding backend layered on
top of that same starting point:

```
spaCy loaded alone (baseline for this comparison):        ~178MB
+ fastembed (current):                                    +186MB  ->  ~364MB
+ sentence-transformers/PyTorch (old, still installed):  +1,220MB  ->  ~1.4GB
```

**B355's own contribution is real: roughly a 6.5x reduction (1,220MB -> 186MB) in what the embedding
backend specifically adds on top of the daemon's other costs.** What was wrong was extrapolating that
isolated module-level number into a claim about the *whole daemon's* baseline, which also includes
spaCy's unavoidable `torch` floor, the full production KuzuDB schema (53+ node tables with HNSW indexes),
the web server, and other subsystems the original 228MB test never touched.

**Best estimate for what the full daemon's baseline was before B355** (extrapolated, not directly
re-measured under identical conditions — labeled as an estimate, not a fact, per this project's own
discipline established throughout B311/B342): today's real ~1.2GB measurement, minus fastembed's ~186MB
contribution, plus the old backend's ~1,220MB contribution, lands around **~2.2GB** — consistent with (and
a plausible explanation for) the ~1.9-2.1GB figures B342/B353's own isolated harness testing repeatedly
measured throughout that investigation, none of which loaded spaCy either.

**Corrected bottom line:** the real daemon's fresh-start baseline dropped from an estimated ~2.2GB to a
directly-measured ~1.2GB — a genuine, real reduction, but roughly 45-50%, not the 8-9x this card
originally claimed. All five places this session documented the 228MB/8-9x figure (this card, B353,
`docs/ARCHITECTURE.md` in two places, `README.md`) are being corrected in the same pass as this note.
