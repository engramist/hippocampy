# B580 - A text parameter that starts with "http(s)://" is bound as an IRI, so capture fails on a turn that begins with a URL

State: done (2026-11-20)
Priority: P1 (capture loses whole conversations; silent mistyping otherwise)
Found: 2026-11-20, in passing (plan lead), when LongMemEval question 6a1eabeb failed twice during job 1014's capture.

## What happens

`_format_sparql_term` (campy/brain/hippocampus/graph/oxigraph_client.py) binds every `str` parameter that starts with
`http://` or `https://` as an IRI (`<...>`), not only node ids. A Message's own text is a `str` parameter too. When a user
turn begins with a URL, its text is written as an IRI:

- with a backslash, space or newline in it (here `https://www.youtube.com/watch?v=...&ab\_channel=redfoo\n\nin this song ...`),
  Oxigraph rejects the query: `error at 25:71: expected IRIs are only allowed to contain escape sequences \uXXXX and \UXXXXXXXX`;
- the daemon returns the error to notify_turn; the MCP adapter (`mcp_server.py`) treats every soft failure as
  `DAEMON_OFFLINE` and queues the turn offline; the benchmark harness then marks the question failed after a retry.
- A clean URL with no such characters would be stored silently as an IRI node instead of a literal string (a type error
  that queries over `text_raw` would miss).

Evidence: the kept failed stores of job 1014 (`fail_open_state.json` in both: the error above); the offline-queued turn is
the URL turn. In LongMemEval-s's first 100 stratified questions only this one question has a turn starting with a URL;
the other 11 with backslash URLs mid-text bind as literals and pass.

## Fix (general construction)

Bind as an IRI only what is known to be an IRI: values under the store's own bases (`CID_BASE`, `CAMPY_NS`) or values the
caller marks as IRIs (for example an explicit wrapper type), never a free-text parameter because of its prefix.
Audit callers that pass external `http(s)` IRIs as plain strings (vocabulary IRIs, PROV, schema.org) and give them the
explicit marker. Separately, the adapter should not report a query error as the daemon being offline.

## Tests

- A Message whose text starts with `https://...` and holds a backslash, a space and a newline is captured, and its
  `text_raw` reads back equal, as a literal.
- An explicitly marked external IRI still binds as an IRI.
- notify_turn's query error is reported as an error, not as `queued_offline`.

## Principle

P2 (the graph store is the source of truth: a turn must not be lost or mistyped on its way in), P6.

## Note

Do not change the tree job 1014 runs on (hc-lme); a fix lands on main after 1014's capture ends, and 1014's one lost
question (6a1eabeb) is recorded with its result.

## Done (2026-11-20)

- `oxigraph_client._format_sparql_term`: a `str` binds as an IRI only when it lies under the store's own bases
  (`CID_BASE`, `CAMPY_NS`, `DATA_BASE`) **and** is a syntactically valid IRI (no whitespace, control characters,
  `<>"{}|^\`` or backslash), or when it is an explicit `IRI(...)` / `ox.NamedNode`. Anything else, an http(s) string
  included, binds as a literal. (Review session addition: the own-base rule had the same hole, since a pasted node id
  followed by text would have broken the same way.)
- `brain_transport`: `DaemonReplyError` for errors the daemon replies with; `call_brain_soft(raise_daemon_errors=...)`
  records them as soft failures and, when set, re-raises them. Both MCP adapters set it, so a daemon-replied error is
  an MCP error and the turn is not queued offline.
- `brain_transport.replay_offline_queue`: an entry the daemon replies to with an error is dropped with a soft-failure
  record; an entry that finds the daemon unreachable is kept with all after it (before, the queue was unlinked first,
  and every failed replay, an unreachable daemon included, was silently lost).
- Audit before the change: the full suite with the old prefix rule instrumented logged 0 bindings of an external
  http(s) IRI through a parameter, with the instrumentation proven live; no caller needed the new `IRI` marker.
- Exposure (counts on copies): LoCoMo-10 0 of 5,882 turns start with a URL, and the 5 s4p stores hold 0 IRI objects
  outside `https://campy.dev/`; LME-s 100: 1 turn (question 6a1eabeb); personal store copy (20,070 Messages): 0 Messages
  with `text_raw` stored as an IRI, 0 non-campy IRI objects, and no offline queue file (0 queued entries).
- Tests: `tests/test_b580_iri_binding.py` (six).
