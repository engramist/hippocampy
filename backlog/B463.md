# B463 - ask Can't Reach the Current Value When the Question Uses a Category Word

State: complete (2026-10-05; real-model confirmed)
Priority: P1

### Problem Statement

LoCoMo `p1_current_db`, "What is our active production database engine and
version?", expects "PostgreSQL 16". llama3.1:8b answered "our active
production database engine is 'Primary database' ... the version is not
specified" in every real-model run, before and after B459/B460. It is the one
probe the real-model LoCoMo run still fails (judge 0.9643, 27/28).

The scenario (`locomo_01_db_migration`):

- user: "Our service uses PostgreSQL 14 hosted on AWS RDS. Constraint: all
  tables must use UUID primary keys."
- assistant: "Noted. Primary database is PostgreSQL 14 with UUID primary keys
  across all tables."
- user / assistant: index bloat, BIGINT sequence IDs for analytics tables.
- user: "CRITICAL UPDATE: We have completely migrated from PostgreSQL 14 to
  PostgreSQL 16. Constraint: do NOT use PostgreSQL 14 anymore, all new
  deployments target PostgreSQL 16."
- assistant: "Acknowledged. PostgreSQL 14 is deprecated. All deployments must
  strictly target PostgreSQL 16."

The bundle `ask` got held one item that mattered, the Concept "Primary
database". No user statement, no graph section.

### Root cause

The question names a category ("database engine"); memory names the
instance ("PostgreSQL 14", then "PostgreSQL 16"). No stage of the bundle
compiler links the two:

- **Conversation stage** (`GraphGateway._bundle_conversation`, B454/B459):
  no user message contains any query content word (active, production,
  database, engine, version), so there is no lexical hit; "CRITICAL UPDATE
  ..." scores 0.253 with all-MiniLM-L6-v2 against the 0.30 floor (a long
  statement naming two versions embeds far from a short question). The only
  vector hits >= 0.30 are the two assistant turns (0.339 and 0.318), and
  assistant text is never evidence (ISSUE-024). They are on topic and they
  name "PostgreSQL 14", but the stage only used them to pick B459's anchor
  word.
- **Semantic stage**: reaches "Primary database" (the category, as extracted
  from the assistant turn), which carries no value.
- **Graph-structure stage**: its anchors need cosine >= 0.70 to the
  question; no Concept gets there, so no traversal happens. Even from
  "Primary database" there is no edge to the versions: in the pre-B460 store
  the only edge was a nonsense "PostgreSQL CHOSEN_OVER Primary database",
  and the base name "PostgreSQL" has no edge to its versions.

What does exist since B460 is "PostgreSQL 16 REPLACES PostgreSQL 14" (Step 1b
grammar on the user's statement, current value as head). The gap is
general: whenever a question names the category and a later statement
replaced the instance, nothing in the question points at the replacement.

Sandbox reproduction (`diag_bundle.py` on a kept `--isolated` LoCoMo store,
stub LLM, hashed embeddings): the p1 bundle is empty (0 sections); the
graph holds Concepts "PostgreSQL 14" and "PostgreSQL 16" with the REPLACES
edge, no "Primary database" (the stub LLM extracts less), and no
Concept-to-Message provenance edge exists in the schema at all.

### What It Does (Scope)

The conversation stage follows supersession edges from what its on-topic
messages name:

1. **On-topic messages**: the messages, of ANY role, that pass the stage's
   existing evidence test (vector hit >= 0.30, or a lexical hit with two
   query words or B459's anchor word), top `limit` by the fused rank. The
   test is unchanged; assistant turns now also pass it as guides. They choose
   which entities to follow; they are never added to the bundle.
2. **Named superseded entities**: Concept names on the tail of a REPLACES
   edge that an on-topic message contains as whole words, and not only
   inside a longer Concept name the message also contains ("we use JSON
   REST" names "JSON REST", not the unrelated "REST" that gRPC replaced in
   another conversation).
3. **Current value**: REPLACES edges are followed to the head of the chain
   (Jaeger -> Zipkin -> OpenTelemetry gives OpenTelemetry; cycle-safe;
   archived or flagged heads are not followed).
4. **Evidence**: the user's own statements naming the head (FTS phrase
   search, new `VectorStore.search_phrase`, then a whole-word check; not
   archived, not questions), the 2 newest per head.
5. **Ranking**: each such statement inherits the fused rank of the on-topic
   message that named the entity, then competes in the stage's existing
   top-`limit` cut and chronological order. It ranks with its topic; it never
   adds more than the stage's `limit`.

For p1: "Noted. Primary database is PostgreSQL 14 ..." (on topic, 0.339)
names "PostgreSQL 14" -> "PostgreSQL 16 REPLACES PostgreSQL 14" -> the user's
"CRITICAL UPDATE: ... migrated from PostgreSQL 14 to PostgreSQL 16 ..." joins
the bundle.

Facts in the bundle are still only user statements, and the edge they hang
on was itself extracted from a user statement by grammar (B460). No
similarity floor or threshold changed.

Considered, not done:

- **Graph-structure stage expansion from semantic-stage concepts**: the
  concept the question reaches ("Primary database") has no edge to the
  versions, and the stage's anchors need cosine >= 0.70; a REPLACES edge in
  the bundle without the user's statement is also weaker evidence than the
  statement itself.
- **Linking or merging a base name with its versions** ("PostgreSQL" <->
  "PostgreSQL 16"): would not have helped here (the question never reaches
  "PostgreSQL" either), and merging versions erases exactly the distinction
  a supersession question asks about.
- **Retrieved concept names as extra lexical terms**: "Primary database"
  would add "primary", which matches "UUID primary keys" (the old value's
  message), not the new one.

### Not changed / limits

- **Pre-B460 stores** whose supersession edges are CHOSEN_OVER (often
  inverted) are not followed: only REPLACES, which B460 writes with the
  current value as head. Repairing old edges is B460's follow-up.
- If no on-topic message names the instance (no assistant acknowledgement,
  no user hit), nothing changes: the question still has to reach the topic.
- When the store has no Concept for the longer name, a shorter one can
  still be matched inside it. Sandbox LoCoMo (31 concepts, no "JSON REST"):
  `p_4_active` (api_format) gains "REST has been replaced by gRPC ... for
  rpc_framework" as a 4th message; the api_format statements are all still
  there. The real-model store has "JSON REST" (B460's audit names it).
- `p3_analytics_pk` (primary key format) gains the PostgreSQL 16 statement:
  its on-topic "Our service uses PostgreSQL 14 ... UUID primary keys" names
  PostgreSQL 14. Same scenario, one extra message; the BIGINT answer stays.

### Sandbox end to end (2026-10-04)

`run_all.py --isolated --keep-store --suite locomo --judge none` on this
branch (stub LLM, hashed bag-of-words embeddings): valid, 395 calls, 0
failures; scores identical to the B460 sandbox runs (the stub's answers are
not meaningful). Then, on the kept store, `compile_bundle` for all 28 probe
questions with main's code and with this branch's:

- 26 bundles identical; no probe loses an item.
- `p3_analytics_pk` and `p_4_active` gain one message each (see limits).
- `p1_current_db` is unchanged and empty in the sandbox: with hashed
  embeddings no message clears the 0.30 floor for it, so there are no
  on-topic messages to follow. With the query vector set to the measured
  real-store condition (cosine 0.339 to "Noted. Primary database is
  PostgreSQL 14 ...", the only Message hit >= 0.30), the conversation stage
  on the same store returns nothing on main and the user's "CRITICAL UPDATE
  ... PostgreSQL 16" statement on this branch, through the REPLACES edge Step
  1b wrote there.
- `compile_bundle` time for the 28 questions: 11.1 ms (main) vs 13.1 ms per
  bundle.

### Cost on a large store (2026-10-04)

Measured on a copy of the user's `~/.campy` (20k Messages, 405 Concepts,
183 CHOSEN_OVER, **0 REPLACES** -- it predates B460), 6 real questions x 3:
the step costs 1.3 ms, conversation stage 33 ms (main) -> 37 ms. To test
the growth case, synthetic Concepts and random REPLACES edges were added to
the copy (names include common words -- "database", "Python", "Kuzu" -- so
`mentions` and the longer-name scan do fire):

| REPLACES / Concepts | main stage | branch before fix | after fix |
|---|---|---|---|
| 1,000 / 5,405 | 30 ms | 253 ms (step 212) | 105 ms (step 66) |
| 5,000 / 20,405 | 30 ms | 953 ms (step 912) | 301 ms (step 251) |

~90% of the original cost was regex compilation in `spans` (one pattern per
on-topic-message x old-name pair, past `re`'s 512-entry cache), not the
SPARQL; a substring test before the regex removes it with identical
results. What remains is linear in REPLACES edges: the full edge load is
~200 ms of the 251 ms at 5k (a `CONTAINS` longer-name scan, ~70 ms, runs
only for a mentioned name). Not cached here: the store has no write
generation to key a cache on, and a personal store holds 0 REPLACES today.
If REPLACES counts reach the thousands, load only the edges whose old
concept the on-topic text names, or add a generation counter and cache.
