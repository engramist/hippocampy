### The finding

`campy-benchmarks/locomo/runner.py:49`, `membench/runner.py:43`, and
`arc_bridge/runner.py:43` all call `client.run_sweep()` between
writing session turns and evaluating probes, intending to force a
synchronous consolidation pass so probe queries run against fully
processed memory rather than racing the async pipeline. `mcp_client.py
:279-280` wires this to `call_tool("run_sweep", {})` — a real MCP
`tools/call` request for a tool literally named `run_sweep`.

**That tool has never existed.** `run_sweep` is a real Python function
(`campy.brain.brainstem.sweep.run_sweep`, called internally by
`BrainDaemon._background_sweep` on a `sweep_interval_seconds` timer,
**default 300 seconds**) but it has never been registered as one of
the ~65 MCP tools in `TOOL_HANDLERS`/`tool_schemas.TOOLS`. Every call
fails server-side with `"Unknown method: run_sweep"`, caught by
`mcp_client.py`'s catch-all `except Exception: return None` in
`_send_request`, so the harness never sees an error — it just silently
never synchronizes. Confirmed via `~/.campy/activity.log`: **74**
`"Unknown method: run_sweep"` entries logged during a single B446 run,
100% failure rate, and via `campy-benchmarks`' own git log
(`495a0e6`, the repo's *initial* commit) that this call has been
present, and therefore broken, since the harness was first written —
this predates B434 entirely and is not something B434/B436/B438 could
have fixed.

Separately, `memory_gym/runner.py` doesn't attempt any synchronization
at all — it calls `notify_turn` once then immediately calls
`current_truth` with no wait and no `run_sweep()` call, so it has the
same underlying race with no mitigation attempt whatsoever.

Also worth noting: even a *working* `run_sweep` MCP tool would call
the wrong mechanism conceptually — `sweep.py`'s `run_sweep()` is the
pathway-strength decay/pruning pass, not the Gated Consolidation Loop
that actually turns raw turns into queryable Concepts/Entities (that's
`campy.brain.temporal_lobe.loop.orchestrator.run_loop`, fed by an
`asyncio.Queue`, see [B447](B447.md)). Wiring up the literal
`run_sweep` function as an MCP tool would still not give the harness
what it actually needs.

### Recommendation (not prescribed — two real options)

1. **Harness-side fix (lower risk, self-contained, no hippocampy core
   change):** replace `client.run_sweep()` calls (and add equivalent
   handling to `memory_gym/runner.py`) with a poll/backoff helper —
   after writing turns, poll `current_truth`/`ask` for the expected
   content with retries and a bounded total wait, rather than assuming
   a single synchronous call can force completion. This accepts
   Campy's actual eventual-consistency model instead of fighting it,
   and can be committed directly to `campy-benchmarks`' local `master`
   per this session's established practice for that repo.
2. **Core-side addition (bigger, needs its own hippocampy card/PR):**
   expose a real "drain the consolidation queue" or "wait until queue
   is empty" MCP tool/primitive, which would be a more robust building
   block for any caller (not just this benchmark harness) that needs a
   synchronous consolidation guarantee. Only worth it if there's a
   real caller need beyond this one harness.

This card intentionally doesn't pick one — resolve alongside
[B447](B447.md), since a poll/backoff harness fix (option 1) is
pointless to implement or test until B447's stall no longer prevents
consolidation from ever completing at all.
