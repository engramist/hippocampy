# B342 - Live brain_daemon.py Observed at ~5.4GB RSS (99GB Physical Footprint) with Near-Empty Graph

State: open — root cause not fully identified. The 2x2 (checkpoint on/off x embedding on/off) is
complete and its behavioral finding stands: quiet-window reclaim tracks embedding-call presence exactly,
independent of checkpoint status. **Correction, same day, immediately following the 2x2:** the 2x2's
framing of that result — "embedding activity is necessary and sufficient" — is now known to overstate
the mechanism. A follow-up control test swapped the embedding calls for pure-Python/hashlib CPU work
(zero ML/PyTorch code touched, routed through the same `asyncio.to_thread` call pattern) during the same
quiet window, and reclaim still happened — a ~49MB drop at roughly the same point in the window as the
embedding-ON cells. **Embedding is not what's necessary; periodic background-thread activity via
`asyncio.to_thread` is the more likely common factor**, and the 2x2's embedding-OFF cells (c) and (d)
never exercised `asyncio.to_thread` at all (they were pure `asyncio.sleep`), which is the actual variable
that changed, not embedding specifically — this was not distinguished at the time cells (c)/(d) were
designed. Confirmed still true regardless: NOT a Python-level object leak, NOT explained by write
pace/gap duration, NOT explained by "any quiet window" alone (a quiet window with literally nothing
running in it, not even a to_thread call, shows zero reclaim — that part of the 2x2 stands). Also still
true: checkpoint status makes no difference either way (this round's control ran checkpoint-ON only,
inherited from cell (a)'s config — not yet re-checked with checkpoint OFF, though there's no reason
to expect it would matter given the 2x2's own checkpoint-irrelevance finding). B311.md's correction
(B337's periodic checkpoint is not the reclaim mechanism) still stands independent of this correction.
Next: isolate whether it's `asyncio.to_thread` / thread creation specifically, or just "any CPU-bound
work regardless of how it's scheduled" (e.g. an in-event-loop CPU burn with no thread offload at all) —
that would separate "thread lifecycle" from "sustained CPU activity" as the actual trigger.
Escalated from P3:
this is degrading a core feature (`ask`) on the live process, not just consuming disk-adjacent virtual
memory.
Priority: P1

### Problem

While measuring B311/B337's checkpoint mitigation (2026-08-20), a real `brain_daemon.py` process
already running on the investigating machine (PID 17813, started that day) was observed at **~5.4 GB
RSS**, sampled read-only via `ps -o rss=` (not restarted or otherwise touched). `GET /api/stats` on
that same daemon reported a nearly empty graph: 5 concepts, 0 decisions, 2 constraints, 8 messages, 57
main quests, 9 side quests — nowhere near the tens-of-thousands-of-rows scale that produces B311's
transient checkpoint-boundary spikes.

This is very likely a **different phenomenon than B311**: B311 is about transient spike-then-release
behavior during write-heavy bursts, root-caused to KuzuDB's checkpoint timing. A daemon sitting at a
steady 5.4GB with almost no graph data looks like baseline/steady-state overhead instead — most
plausibly the embedding model (`sentence-transformers`, loaded once at startup and held for the
process lifetime per `campy/brain/hippocampus/graph/embeddings.py`) plus its ML framework dependencies
(PyTorch et al., commonly 1-3GB resident even before doing any real work), possibly compounded by
however long this particular process had been alive and how many requests it had served. Genuinely
unknown without instrumentation — this card is a flagged observation, not a diagnosis.

### What it does (scope)

This is an investigation card, not a fix — same category as B311 originally was. Suggested steps for
whoever picks this up:

1. Reproduce in isolation: start a fresh `brain_daemon.py` against an empty/near-empty database, sample
   RSS immediately after startup (before serving any real traffic) to establish what the embedding
   model + framework baseline actually costs on its own.
2. If the fresh-start baseline is already multi-GB, that's expected-but-worth-documenting overhead, not
   a bug — the fix (if any) would be about choosing a lighter embedding backend or documenting the
   real resource floor for deployment sizing, not a leak fix.
3. If the fresh-start baseline is much lower (e.g. a few hundred MB, consistent with B311's originally
   reported 110-150MB idle baseline), then something about the *specific* long-running process
   observed here grew over its lifetime with near-zero data growth to explain it — that would be a
   genuine, distinct leak investigation, structured the same way B311's rounds 1-2 approached their
   isolated repro (reproduce, instrument, narrow root cause).
4. Either way, document the finding — even "this is normal, embedding models are just this large" is a
   useful, actionable answer for anyone sizing a deployment.

### Deeper Diagnostic (2026-08-21), Same PID — Findings, Not a Root Cause

User authorized shutting the process down to investigate; a diagnostic pass was done first while it was
still up, since that state is lost once it restarts. All checks below were read-only (`ps`, `vmmap`,
`lsof`, log tail, MCP calls) — nothing was modified or killed as part of this pass.

**The real number is far worse than `ps` showed.** `vmmap -summary 17813` reported:

```
Physical footprint:         99.0G
Physical footprint (peak):  99.0G
MALLOC_SMALL   VIRTUAL=95.4G  RESIDENT=843.7M  SWAPPED=94.5G   24433 regions
```

`ps -o rss=` only counts uncompressed resident pages (it showed ~1.8GB at the time of this check,
5.4GB at an earlier check the same session — consistent with the spike/release pattern, not a
correction). macOS's "physical footprint" additionally counts compressed/swapped pages charged to the
process, and is the more accurate memory-pressure figure on this platform. 94.5 of 95.4GB in one malloc
zone sitting swapped out, spread across 24,433 individual regions, on a process serving 5 concepts and
8 messages, is not explainable by graph data volume or a reasonable embedding-model baseline — this
reads as a real, severe leak.

**The daemon is functionally degraded, not just large.** `mcp__campy__ask` (retrieval + thalamic
compression + LLM synthesis) returned `"Brain: OFFLINE - memory unavailable"`. `mcp__campy__current_truth`
(lighter — no LLM call) worked normally against the same process. `GET /health` and `GET /api/stats`
on the same PID also responded normally. This points at the heavier synthesis path specifically
struggling — consistent with swap-thrashing degrading anything that touches a meaningful working set,
while cheap fixed-cost endpoints stay fine.

**No smoking gun found at the Python level, and none should be assumed.** Checked
`campy/brain/brainstem/sweep.py`'s `run_sweep()` — the repeating `[Sweep] ... errors=21` line
(identical every cycle in `~/.campy/daemon.log`) comes from a fresh local counter
(`inferred = errors = 0`) per call, not an accumulating list or retained exception objects; this
specific pattern doesn't look like the leak source on inspection, but this was a code-reading check,
not a heap profile. `py-spy` was not available in this environment to get an actual live Python-object
breakdown, which is what this needs next — `ps`/`vmmap`/log-reading can describe the symptom but can't
identify which Python objects are actually accumulating.

**Separate finding, not the memory bug but worth its own fix:** `mcp__campy__current_truth`'s returned
`memory_link`/`panel_url` fields point at `http://127.0.0.1:7800/...`, but the only thing actually
listening (confirmed via `lsof -iTCP -sTCP:LISTEN`) is port 7799 — same PID, same process. Something in
the dashboard-link generation path hardcodes or misconfigures port 7800. Every link Campy's own MCP
tools hand back to a caller is currently dead. Worth a quick, separate fix.

**Separate finding, a real hygiene risk:** confirmed two different `brain_daemon.py` files exist —
the top-level `brain_daemon.py` (what's actually running — verified via the live process's own command
line) and `campy/brain_daemon.py` (different size, different module docstring: "HippoCampy Daemon" vs
"HippoCampy Brain Daemon"). Not resolved which is canonical or whether one is dead code from an
in-progress migration (see `docs/codebase-anatomy-refactor-plan.md`) — flagged so future edits (like
B337's, which touched the top-level file) don't silently target the wrong copy.

**What this diagnostic did NOT establish:** the actual root cause. Next steps, in order of leverage:
1. Get `py-spy dump`/`py-spy dump --locals` (or equivalent, e.g. running the daemon under `tracemalloc`
   from a fresh start) on a process that's grown large, to see actual Python object types/counts, not
   just OS-level malloc zone size.
2. Establish a fresh-start baseline (this card's original acceptance criteria, still unmet) to know how
   much of the footprint is "normal" embedding-model overhead vs. genuine growth over the 10+ hour
   uptime this instance had.
3. Resolve which `brain_daemon.py` is canonical before spending more investigation time on either copy.

### Reframe: Idle Growth Reclaims on Active Writes, Not on Checkpoint Cadence Alone (2026-08-21)

`backlog/B311.md`'s Round 7 (a 30.6-minute live ARC episode, same daemon/PID as this card's earlier
diagnostic) surfaced a specific, testable observation directly relevant to root-causing this leak: the
daemon had drifted from a 1,222 MB fresh-start baseline (Round 6) up to 7,274 MB over roughly 2 mostly-idle
hours — consistent with this card's core finding — but **within ~90 seconds of active ARC write traffic
resuming, RSS dropped to a ~250-370 MB floor and stayed there**, despite `[checkpoint] interval_seconds=15`
periodic checkpointing having been running continuously the entire idle period too, not just once writes
resumed.

This narrows item 1's question. It's no longer just "what Python objects are accumulating" — it's more
specifically: **does KuzuDB's checkpoint mechanism (manual or auto) actually reclaim/compact memory when
there's little-to-no pending write volume for it to act on, or does meaningful reclaim require real write
pressure regardless of how often checkpoint fires?** If the latter, that would mean B337's periodic
checkpoint (which fires on a fixed timer regardless of activity) is not actually protecting against
*idle*-period growth at all — only against growth during active write bursts (which Round 7 also
confirmed it does handle, via the observed sawtooth). Two different problems wearing one number.

**Suggested addition to next-step 1's profiling session:** deliberately capture tracemalloc/gc snapshots
(via B344's new `SIGUSR1` hook — no sudo needed, see below) at three points: (a) fresh start, (b) after
a period of idle-but-not-zero background activity (Claude Code capture/journaling continues even when no
one is actively using the daemon, per `~/.campy/activity.log`'s continuous entries), (c) shortly after
resuming active write traffic. Comparing (b) against (a) shows what idle time alone adds; comparing (c)
against (b) shows what write-triggered reclaim actually releases. This directly tests the reframed
hypothesis instead of just describing the symptom again.

**The sudo blocker on next-step 1 is resolved, differently than planned.** `py-spy` needs `task_for_pid`
(root on macOS) to attach *externally* — confirmed blocked when the operator doesn't have sudo access.
B344 (merged) adds a self-triggered alternative: `kill -USR1 <pid>` makes the daemon dump its own
`tracemalloc`/`gc` snapshot to `~/.campy/memory_debug.log`, no external attach or elevated permissions
needed, since a process can always introspect itself. One real caveat learned building it, left in
B344's own code comments: `tracemalloc` is too expensive to run during the daemon's allocation-heavy
startup phase (measured: 43x slower schema init) — it must be started lazily, well after startup, which
B344's hook already does correctly.

### Not a Python-Level Leak — Confirmed with the New Safe Diagnostic (2026-08-21)

B344's `SIGUSR1` diagnostic (`gc.get_objects()` grouped by type, no `tracemalloc` — see that card for
why) was used to sample the live daemon three times: right after a restart, ~2 minutes later, and
again ~2 hours later, after the daemon had drifted from a fresh-start baseline back up to real growth
(same pattern this card and B311's round 6/7 have repeatedly observed on this machine):

| Snapshot | Elapsed since restart | `ru_maxrss` (peak, this process's lifetime) | `gc` object count |
|---|---|---|---|
| 1 | ~0 min | 1.26 GB | 500,890 |
| 2 | ~2 min | 1.33 GB | 500,277 |
| 3 | ~119 min | **14.9 GB** | 500,564 |

**The `gc` object count is flat across nearly two hours while `ru_maxrss` grew roughly 12x.** Per-type
deltas between consecutive snapshots were small (dozens, not thousands or millions) and mixed positive
and negative — normal object churn, not accumulation. This is decisive: if this were a classic Python
leak (a growing list, dict, cache, or retained-reference cycle), the object count and the specific
growing type would show it. They don't. **Whatever is growing lives entirely outside memory `gc` can
see** — i.e., not CPython-managed objects at all, which points strongly at native allocations: KuzuDB's
C++ buffer pool is the leading candidate, given B311's entire root cause already traces to KuzuDB's
checkpoint/buffer-pool behavior, and the embedding model (loaded once at startup, not re-loaded) is a
less likely fit for *ongoing* growth.

**The idle period was not actually write-free**, which sharpens rather than undermines the reframe two
sections up. `~/.campy/daemon.log` shows continuous `[Capture:claude_code] scanned=1 journaled=1
ingested=1`-style lines throughout — roughly one small write every 10-60s the entire time, from Campy's
own background journaling of this Claude Code session's activity (by design, per this project's
architecture). So the real distinction round 7 vs. this snapshot sequence draws out is not "writes vs.
no writes" — it's **"low-volume, frequent small writes don't trigger the same reclaim a high-volume
write burst does."** A working hypothesis, not yet confirmed at the code level: `CHECKPOINT` flushes
the WAL to the main store for durability, but flushing is not necessarily the same operation as
*evicting pages from / shrinking* the buffer pool — a large write burst might incidentally trigger
buffer-pool trimming as a side effect of the sheer volume of pages touched, while a trickle of tiny
writes over hours might never cross whatever internal threshold (if any) triggers that trimming,
even though the periodic 15s checkpoint task is firing the whole time regardless.

**What would confirm this precisely, not yet done:** check whether KuzuDB 0.11.3's Python API exposes
any buffer-pool-size or memory-usage introspection (distinct from OS-level `ps`/`vmmap`) — if so,
correlating that against the write-volume pattern directly would settle the checkpoint-flush-vs-evict
question. If no such API exists, the next-best test is empirical: deliberately drive a long period of
many *small* writes (no capture journaling, a synthetic loop of tiny individual writes) against a
disposable instance and see whether RSS still grows unboundedly despite 15s periodic checkpointing —
isolating "write volume" from "write burst-iness" as the actual variable that matters.

**KuzuDB has no buffer-pool introspection API to check directly.** `dir(kuzu.Database)` /
`dir(kuzu.Connection)` on 0.11.3 exposes no memory/buffer-pool usage reporter — `buffer_pool_size` is
only a max-size *configuration* input, never a live-usage output, and no `CALL` table function
(`show_tables`, `db_version`, `current_setting`, `storage_info` — all confirmed to exist and take
different arguments) surfaces it either. So this had to be settled empirically, per the "next-best
test" noted above.

### Isolated Repro: Growth-Without-Reclaim Reproduced, Hypothesis Corrected (2026-08-21)

Built a synthetic trickle-write harness (`arc_perceive_state` calls, one tiny single-entity write per
tick, real periodic-checkpoint task active throughout, same shape as B311's rounds 4-7 harness but with
a configurable gap between individual writes instead of a tight loop). Three runs, `ps -o rss=` sampled
every 1-2s:

| Run | Writes | Gap between writes | Result |
|---|---|---|---|
| A | ~2000 | 0.3s | Smooth, steady climb (1212→1468 MB) over the full ~590s observed window, **zero drops**. Cut short by tooling before the writer naturally stopped. |
| B | many (uncounted, job killed) | 0s (continuous) | Same shape: smooth climb (1245→2385 MB) over ~300s, **zero drops**. Also cut short mid-write by tooling. |
| C | 79 | 3s | Slower climb (94→1259 MB), then **settled cleanly to a flat 1116 MB** once writing stopped and the process reached its idle-after-close phase. |

**Initial read of A vs. C (now corrected, see below):** gap duration between writes looked like the
variable that mattered — 0.3s never reclaimed, 3s did. But A and C also differ in total write count
(~2000 vs. 79), a real confound this card should have caught before drawing that conclusion from two
runs alone.

**Controlled follow-up, write count held constant:** re-ran at 0.3s gaps but stopped after ~69 writes
(matching C's ~79) instead of running for a fixed duration. Result: peak 1276.9 MB, then a clean single
drop to a flat 1138.8 MB the moment writing stopped — **the same shape as run C**, despite the 10x
faster write pace. Gap duration between individual writes does not explain the difference between A/B
and C after all.

**Corrected hypothesis, now consistent with every observation to date, not just the latest one:**
reclaim doesn't depend on write pace or burst-vs-trickle shape — it depends on whether the write stream
goes **genuinely quiet** (no new writes arriving at all) for some period. Checked against everything
this investigation has found:
- B311 rounds 1-2's original 2000-step burst: grows during the burst, reclaims once the burst *fully
  stops* — consistent.
- B311 round 5's 600-step burst + 90s idle: reclaims during the *subsequent* idle window, not during
  the burst — consistent.
- B311 round 7's live 5-puzzle sawtooth: ~5-7 reclaim events, roughly aligned with *puzzle-to-puzzle
  boundaries* — each transition is a genuine "writing stopped" moment, giving repeated real
  opportunities to reclaim — consistent, and explains why real traffic looks different from any of this
  card's synthetic single-continuous-run tests.
- This card's original ~2 hour "idle" observation: continuous small writes every 10-60s from Claude
  Code capture journaling **never let the write stream go fully quiet** — consistent with why it never
  reclaimed at all, for two hours straight.
- Runs A and B here: writer never stopped (tooling killed the process mid-write) — consistent with zero
  reclaim observed.
- Run C and the matched-count follow-up: writer completed and genuinely stopped — both reclaimed
  cleanly, regardless of pace.

This supersedes the "low-volume trickle vs. high-volume burst" framing two sections up — that framing
fit the data available at the time but didn't survive a properly controlled follow-up, and is being
left in place above (not deleted) so the correction is visible, matching this project's own standard
for B311's investigation cards.

**Still not confirmed at the code level:** *why* a genuinely quiet write stream triggers reclaim where
a merely-infrequent one doesn't — still consistent with the checkpoint-flush-vs-evict mechanism
hypothesis, but could equally be something else entirely (e.g. an idle-timeout-driven internal Kuzu
behavior unrelated to checkpointing specifically). Next step: instrument whether reclaim timing
correlates with the periodic checkpoint task specifically firing during a quiet window, vs. firing on
its normal schedule regardless of quiet-vs-busy state — if reclaim happens at a fixed delay after
writing stops regardless of where in the 15s checkpoint cycle that stop occurred, that would point away
from checkpoint-boundary-specific behavior and toward a more general idle-detection mechanism.

### Outcome

Root cause narrowed substantially across two rounds of investigation today, with one intermediate
hypothesis tested, found incomplete, and corrected in the open rather than quietly replaced. **Ruled
out, with direct evidence:** a classic Python-level object leak — `gc` object counts stayed flat while
`ru_maxrss` grew ~12x over 2 hours. **Ruled out, with a controlled follow-up:** write pace / gap
duration between individual writes as the variable controlling reclaim. **Current best-supported
hypothesis, consistent with every observation across this card and all of B311's rounds:** reclaim
requires the write stream to go genuinely quiet (no writes at all, for some period) — continuous
low-volume "idle" activity (like background capture journaling) prevents that quiet window from ever
occurring, which is why this exact daemon can sit "idle" from a user's perspective while still growing
unboundedly for hours. This is real, actionable progress — it explains why B311's fix (which handles
active write bursts well, confirmed round 7) doesn't help B342's failure mode at all, since B342's
problem is specifically the *absence* of a quiet window, not anything a write-triggered mechanism can
fix. Still open: the exact code-level mechanism inside KuzuDB, and what — if anything — could induce a
"quiet enough" window deliberately (e.g., pausing capture journaling briefly on a timer) without
disrupting the daemon's actual job.

### Correction: The Quiet-Window Hypothesis Is Refuted, Directly Tested (2026-08-21, same day)

Built the direct test the previous round called for: write for 60s, then go **genuinely quiet for 90
seconds** — zero writes, but the process stays alive, the database connection stays open, and the
periodic 15s checkpoint task keeps running throughout (6 checkpoint opportunities during the quiet
window) — then write again for 60s, then close normally.

Result, `ps -o rss=` sampled every 1s, phase boundaries confirmed against the harness's own markers:

| Phase | Elapsed | RSS |
|---|---|---|
| Write phase 1 (60s, 174 writes) | 0-77s | 83 MB → 1294 MB (climbing) |
| **Quiet phase (90s, zero writes, DB open, checkpoint still firing)** | 82-158s | **flat at 1294.2-1294.3 MB the entire time** |
| Write phase 2 (60s, 173 more writes) | 164-220s | 1298 MB → 1328 MB (climbing again) |
| `db.close()` + 20s idle | 225s+ | drops to 1172.5 MB, flat |

**This refutes last round's hypothesis outright — reported plainly, not softened.** A 90-second
genuinely-quiet window, with the connection open and periodic checkpointing actively running the whole
time, produced **zero reclaim**. RSS just stopped growing; it did not shrink. The only event that moved
RSS downward in this entire run was `db.close()` at the very end — and even that was a partial drop
(1328→1172 MB), not a return to baseline. This means the earlier round's matched-write-count tests,
which appeared to show "reclaim once writing stops," were very likely actually showing **"reclaim when
the database connection closes"** — since in those tests, writes stopping and `db.close()` happened back
to back, with no way to distinguish the two. This test separates them cleanly, and the answer is:
closing the connection is what did it, not the quiet period itself.

**This directly conflicts with B311's round 7 live data**, which showed *repeated* reclaim during one
continuous ~30-minute session — the real daemon never closes and reopens its database mid-episode, so
if `db.close()` were the only reclaim trigger, round 7 should have shown none at all. It showed several.

**The likely resolution, not yet tested:** this isolated harness only exercises
`arc_perceive_state`'s pure KuzuDB write path — confirmed in B311's own investigation that this path
never calls the embedding function. But a real ARC episode, and even normal "idle" capture-journaling
activity, goes through the Loop worker's message processing, which — per this codebase's own Step 2
System 1 classifier — calls the embedding model to classify captured content. **This isolated harness
has never once exercised the embedding path**, and B342's live observations, round 7's live sawtooth,
and this card's original steady-state overhead question all involve a daemon doing real embedding work
that this harness doesn't reproduce. The buffer-pool-reclaim hypothesis may be right, wrong, or
incomplete — this test only rules it out for a KuzuDB-writes-only workload, which increasingly looks
like it was never a faithful proxy for what the real daemon does even when "idle."

**Next test, not yet run:** extend the isolated harness to also call the real embedding function
(`campy.brain.hippocampus.graph.embeddings`, whatever the current entry point is) on each write cycle,
matching what real captured-message processing actually does, and re-run the same write/quiet/write
structure. If reclaim now shows up during the quiet window, embedding-model activity (not KuzuDB
buffer-pool behavior specifically) is implicated instead — a materially different fix target. If it
still doesn't reclaim, the isolated harness needs to get closer to real daemon behavior in some other
way before it can be trusted to answer this question, and a live-daemon test (coordinating with the
ARC agent again, this time watching a deliberately quiet window against the *real* daemon rather than a
synthetic stand-in) becomes the more reliable next step.

### The Embedding Model Is Implicated — a Real Difference, Same Day (2026-08-21)

Ran exactly the test the previous section called for: identical write(60s)/quiet(90s)/write(60s)
structure, real periodic checkpoint task running throughout as before, but this time the "quiet" phase
(zero KuzuDB writes) periodically calls the real embedding function (`emb.embed(...)`, prewarmed at
startup the same way `brain_daemon.py` does it) every 10 seconds — mimicking what continuous background
capture-journaling + Loop message classification actually does on the live daemon, isolated from any
new graph writes. Only one variable changed from the refuted test: embedding calls now happen during
the quiet window; nothing else did (same checkpoint interval, same write phases, same everything else).

Result (`ps -o rss=`, phase timing confirmed against the harness's own markers — quiet-with-embed phase
runs roughly t+65s to t+155s):

```
t+ 97s: 1310.5 MB
t+102s: 1310.5 MB   <- flat, same as the refuted test looked at this point
t+128s: 1310.5 MB
t+133s: 1310.5 MB
t+138s: 1206.3 MB   <- a real ~104MB drop, DURING the quiet-for-writes window
t+159s: 1206.4 MB   <- flat at the new, lower level for the rest of the quiet phase
```

**This is a genuinely different outcome than the refuted test, with only one variable changed.** The
no-embed quiet test showed zero movement for the entire 90s window. This test — identical in every
other respect — shows a real, partial reclaim event roughly 70+ seconds into the same quiet window,
correlating with ongoing (if sparse) embedding activity rather than any KuzuDB write. It's not a full
reclaim back to baseline (RSS was still ~1206MB at the end of the quiet phase, far above the ~85MB
fresh-start baseline, and climbed further during write phase 2 same as before) — but it's the first time
in this entire investigation that *anything* moved memory downward during an active (non-closing)
window, rather than only at final `db.close()`.

**This raises a real question about B311's own interval-sweep result, flagged here rather than silently
assumed away:** B311's rounds 1-2 and 4-7's isolated repro harness — the one that produced the "15s
checkpoint interval is a non-monotonic optimum" finding — never called the embedding function either
(confirmed in B311's own round-1 investigation: `arc_perceive_state`/`record_transition`/`record_rule`
"never call emb.embed() at all"). If embedding-model memory behavior, not KuzuDB checkpoint cadence, is
what's actually driving reclaim, then B311's synthetic interval sweep may have been measuring an
artifact of a KuzuDB-only environment rather than the mechanism that matters for the real daemon. This
does **not** undermine B311's round 7 live confirmation — real ARC episodes do exercise embeddings (for
goal reasoning / Loop classification), so round 7's genuine live sawtooth stands regardless of which
exact mechanism produced it. But it does mean the *specific* 15s-interval-is-optimal conclusion from
B311's rounds 4-5, measured on a KuzuDB-only synthetic harness, has not been re-validated against a
harness that also exercises embeddings — worth a note on B311 itself, not just here, since this could
change the tuning recommendation B311 currently leaves as future work (B349).

**Not yet established:** whether the periodic checkpoint task is doing anything at all in this result,
or whether embedding-model memory management (PyTorch/sentence-transformers' own allocator behavior)
would show the identical partial-reclaim pattern with checkpointing disabled entirely. That's the
clean next isolation: repeat this exact test with `auto_checkpoint=False` and no periodic checkpoint
task, embedding calls still active during the quiet phase, to see whether the ~104MB drop still happens
without any KuzuDB checkpoint involved.

### Checkpoint Is Not Necessary — Reclaim Happens With It Fully Disabled (2026-08-21, same day)

Ran exactly that isolation: identical write(60s)/quiet-with-embed(90s)/write(60s) structure, but this
time `KuzuClient` was constructed with `auto_checkpoint=False` (disabling Kuzu's own internal
auto-checkpoint, not just skipping the manual periodic task) and no periodic checkpoint task was started
at all. Embedding calls during the quiet phase, same as the previous test. Writes still happen in phases
1 and 2 (this isolates checkpoint from the reclaim mechanism, not writes from it).

Result — reclaim happened anyway, in more than one place:

```
t+ 51s: 1265.6 MB   <- during write-phase1 itself
t+ 56s: 1170.8 MB   <- a ~95MB drop, mid-burst, no checkpoint running at all
...
t+ 87s: 1191.3 MB   <- into the quiet-with-embed phase (~65-155s)
t+ 92s: 1127.5 MB
t+ 97s: 1052.8 MB   <- another clear drop, ~139MB total over these samples
t+113s: 1031.9 MB   <- settles, flat for the rest of the quiet phase (t+113 to t+159)
```

**This is decisive: reclaim occurs with zero checkpointing involved, neither Kuzu's own auto-checkpoint
nor B337's manual periodic task.** Both a mid-write-burst drop and a quiet-phase drop happened in a run
where `CHECKPOINT` was never once issued. This rules out the checkpoint mechanism as *necessary* for
this class of reclaim — whatever produces it does not require KuzuDB's checkpoint machinery at all.

**This calls B311's own causal claim into question, not just a footnote for B342.** B311's rounds 4-7
concluded periodic checkpointing was the active ingredient behind the observed peak-RSS improvement and
post-close release (round 5's interval sweep) and behind round 7's live sawtooth. Both of those
conclusions were drawn from harnesses/traffic that also happen to correlate with checkpoint activity —
round 5's synthetic sweep varied the checkpoint interval directly (so at minimum that comparison's
*relative* ranking between intervals is still meaningful on its own terms), but round 7's live traffic
was never tested *without* the periodic checkpoint task running, so "the fix works" was never isolated
from "something else that also happens to be present during real traffic (embedding calls) is what
actually works." This card's evidence now suggests the latter is a real, live possibility. **This does
not mean B337's fix is wrong or should be reverted** — it may still help, or be neutral, or the two
mechanisms may compound. It means the *causal story* B311 currently tells (periodic checkpoint → 
reclaim) is unconfirmed, and B311 itself should be updated to say so plainly rather than have this
project's most-cited investigation card carry a claim contradicted by a sibling card's later evidence.
Filed as an explicit action: cross-reference this finding into `backlog/B311.md` directly, not just
here.

**What would fully settle this, not yet run:** the mirror-image isolation — embedding calls disabled
entirely (or removed), only KuzuDB writes plus periodic checkpointing, using this same write/quiet/write
structure. B311's own original harness never included embedding calls (confirmed above), so in one
sense this has already been tested — but always as a single-condition experiment (checkpoint present or
absent), never side-by-side against the same embedding-present harness this round used. A clean 2x2 (
checkpoint on/off × embedding on/off, all four combinations, same structure) would fully separate the
two candidate mechanisms rather than continuing to test one substitution at a time.

### The Clean 2x2 Is Complete — Embedding Is Necessary And Sufficient, Checkpoint Is Irrelevant (2026-08-21, same day)

Ran the remaining two cells of the 2x2 using the same harness (`b342_embed_quiet_workload.py`, extended
with a `--no-embed` flag so the quiet phase can be tested with the embedding task genuinely not started,
rather than just spaced out) and the same write(60s)/quiet(90s)/write(60s) structure throughout.

**Cell (c), checkpoint ON + embedding OFF:** not re-run — confirmed to already be the same condition as
the earlier "Correction: The Quiet-Window Hypothesis Is Refuted" test (`b342_quiet_window_workload.py`).
Checked directly: both used `--write-phase1 60 --quiet-phase 90`, checkpointing enabled via a periodic
task, and zero embedding calls of any kind. That test's result stands as cell (c): RSS flat for the
entire 90s quiet window, zero reclaim.

**Cell (d), checkpoint OFF + embedding OFF (new this round):** `KuzuClient(auto_checkpoint=False)`, no
periodic checkpoint task, `--no-embed` so `periodic_embed_task` is never started. Full RSS trace
(relative to end of schema init):

```
t+  0s:  734.4 MB   <- start
t+ 10s:  604.0 MB   <- settles after schema-init overhead drops off
t+ 66s:  668.0 MB   <- end of write-phase1, climbing steadily as expected
t+ 72s..153s: 668.0 MB FLAT  <- the entire quiet phase (90s), zero movement
t+159s:  670.1 MB   <- write-phase2 resumes, climbing again
t+215s:  732.8 MB   <- end of write-phase2
t+220s:  978.0 MB   <- jump of ~245MB right at db.close()
t+220s..235s: 978.0-1040.6 MB  <- stays flat-to-rising through the rest of the
                                   20s idle-after-close window; no decline
```

Zero reclaim during the quiet phase — matching cell (c) exactly. And unlike cell (b) (checkpoint OFF +
embedding ON, PR #76), which showed a jump at close followed by a clear decline within the same 20s
idle-after-close window (1195.0 MB -> 891.7 MB, checked directly against that run's saved trace), cell
(d)'s jump at close is *not* followed by any decline in the time available — it stays flat or ticks
slightly upward through the end of the process's life.

**All four cells, summarized:**

| Cell | Checkpoint | Embedding | Quiet-window reclaim? |
|------|-----------|-----------|------------------------|
| (a)  | ON        | ON        | Yes (partial), PR #75 |
| (b)  | OFF       | ON        | Yes, PR #76 |
| (c)  | ON        | OFF       | No (original refuted quiet-window test) |
| (d)  | OFF       | OFF       | No (this round) |

This is a clean, symmetric result: reclaim tracks embedding presence exactly, in both checkpoint
conditions. Checkpoint status has no bearing on whether the quiet-window reclaim happens. **Embedding
activity is both necessary and sufficient for the quiet-window reclaim observed throughout this
investigation.**

**A new, separate observation, not yet explained:** in both checkpoint-OFF cells ((b) and (d)), RSS
jumps *up* sharply right at `db.close()` — plausibly the cost of flushing/checkpointing an entire run's
worth of un-checkpointed WAL in one shot, since checkpointing was disabled the whole time. Cell (b)'s
jump was followed by a decline within the idle-after-close window; cell (d)'s was not, in the time
available. This is a real difference between the two cells but is not central to the necessary/
sufficient question the 2x2 was built to answer, and has not been investigated further — flagged here so
it isn't lost, not claimed as understood. It does NOT undermine the main conclusion above, since both
checkpoint-OFF cells behave identically *during the quiet phase itself*, which is what the 2x2 isolates.

**What this means for B311:** the causal question B311 raised (does periodic checkpointing, B337's fix,
actually produce the reclaim it credited itself with) is now answered — no, not on its own. The
mechanism is embedding-model memory behavior, and checkpointing being enabled or disabled doesn't change
whether that mechanism fires. B337's periodic checkpoint may still have secondary value (e.g. avoiding
the close-time jump seen here when checkpointing is off), but it is not "the fix" for the sawtooth
reclaim pattern B311 documented. See `backlog/B311.md` for the corresponding correction.

**Not yet understood, still open:** *why* embedding-model activity (sentence-transformers /
PyTorch) triggers a drop in process RSS. Candidate mechanisms not yet tested: PyTorch's own allocator
(CPU allocator arena behavior, e.g. `torch.no_grad()` context effects on cached buffers), glibc/macOS
malloc trimming triggered incidentally by the allocation pattern embedding calls produce, or something
in `sentence-transformers`' tokenizer/model call path that releases memory as a side effect unrelated to
embeddings specifically (worth testing: does *any* CPU-bound Python workload during the quiet window
produce the same reclaim, or is it embedding-call-specific?). That would be the next real step toward an
actual root cause, as opposed to the necessary/sufficient behavioral finding this round establishes.

### Correction: Reclaim Is Not Embedding-Specific — A Pure-CPU Control Reproduces It (2026-08-21, same day)

Ran the exact test the previous section flagged as the next real step. New harness
(`b342_cpu_quiet_workload.py`, scratchpad dir), same write(60s)/quiet(90s)/write(60s) structure and same
checkpoint config as cell (a) (checkpoint ON, 15s interval). The embedding model is still loaded and
prewarmed at startup — same starting memory condition as every embedding-ON cell — but during the quiet
phase, instead of calling `emb.embed()`, a periodic task runs pure-Python `hashlib.sha256` work in a
background thread via `asyncio.to_thread`, touching zero ML/PyTorch/sentence-transformers code. The burn
duration per call (7ms) was calibrated against a direct measurement of steady-state `emb.embed()` latency
on this machine (first call 371ms including lazy-init overhead beyond prewarm, subsequent calls 6.4-8.0ms
— 7ms used as the match target) so the two conditions are comparable in per-tick CPU cost, not just
cadence.

Result:

```
t+ 66s: 1207312 KB   <- quiet phase in progress, flat for the preceding ~35s
t+105s: 1207328 KB   <- last sample before the drop
t+106s: 1158096 KB   <- ~49MB drop in about 1 second
t+106s..156s: 1158096-1158144 KB FLAT  <- rest of the quiet phase, no further movement
```

The drop happened at t+106s, roughly 40s into the 90s quiet window — the same general region of the
window where the embedding-ON cells' drops occurred (cell (a)'s was ~70+s in; this one somewhat earlier,
within the run-to-run variability already seen elsewhere in this investigation). **Reclaim occurred with
zero ML code executed during the quiet phase.** This directly contradicts the "embedding is necessary"
framing the 2x2 concluded with — the actual distinguishing factor between the 2x2's embedding-ON and
embedding-OFF cells was never embedding specifically, it was whether `asyncio.to_thread` (a real OS
thread handoff, via the default executor) was being invoked at all during the quiet window. Cells (c)
and (d) used plain `asyncio.sleep`, no thread offload of any kind — that confound was not visible until
this control test isolated it.

**This does not overturn the checkpoint-irrelevance finding** — this control run used checkpoint ON
only (inherited from matching cell (a)'s config), so it doesn't directly re-test checkpoint OFF, but
there is no principled reason from anything seen so far to expect checkpoint status would change this
result, given the 2x2 already showed checkpoint status doesn't affect whether embedding-driven reclaim
happens either.

**What is still not known:** whether the trigger is `asyncio.to_thread` / thread creation and teardown
specifically (the default executor's `ThreadPoolExecutor` may create or reap worker threads on this kind
of intermittent, spaced-out usage pattern, and thread stack allocation/deallocation is a plausible thing
for an allocator to notice and trim around), or whether it's simply "CPU-bound work happened, regardless
of how it was scheduled" (an in-event-loop CPU burn, no `to_thread` at all, would separate these two).
That is the next isolation: same quiet-phase structure, same 7ms-per-tick CPU cost, but executed directly
on the event loop thread rather than offloaded — if reclaim still happens, threading is not the
mechanism and it really is just "any CPU-bound activity, on any thread." If it does not happen, thread
lifecycle specifically (not CPU cycles) is implicated.

This is now the second time this investigation has had to correct its own framing after a cleaner test
than the one before it — first "any quiet window" (refuted by the pure-sleep quiet test), then "embedding
presence" (refuted by this CPU-only control). Both corrections are left in place rather than edited away,
per this project's established discipline, so the reasoning trail stays honest about what was actually
ruled out at each step versus what was assumed.
