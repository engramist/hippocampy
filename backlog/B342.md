# B342 - Live brain_daemon.py Observed at ~5.4GB RSS (99GB Physical Footprint) with Near-Empty Graph

State: open — deeper diagnostic done (2026-08-21), root cause still not identified. Escalated from P3:
this is degrading a core feature (`ask`) on the live process, not just consuming disk-adjacent virtual
memory.
Priority: P1

### Problem

While measuring B311/B337's checkpoint mitigation (2026-08-20), a real `brain_daemon.py` process
already running on the investigating machine (PID 17813, started that day) was observed at **~5.4 GB
RSS**, sampled read-only via `ps -o rss=` (not restarted or otherwise touched). `GET /api/stats` on
that same daemon reported a nearly empty graph: 5 concepts, 0 decisions, 2 constraints, 8 messages, 57
main quests, 9 side quests — nowhere near the tens-of-thousands-of-rows scale that produces B311's
transient checkpoint-boundary spikes.

This is very likely a **different phenomenon than B311**: B311 is about transient spike-then-release
behavior during write-heavy bursts, root-caused to KuzuDB's checkpoint timing. A daemon sitting at a
steady 5.4GB with almost no graph data looks like baseline/steady-state overhead instead — most
plausibly the embedding model (`sentence-transformers`, loaded once at startup and held for the
process lifetime per `campy/brain/hippocampus/graph/embeddings.py`) plus its ML framework dependencies
(PyTorch et al., commonly 1-3GB resident even before doing any real work), possibly compounded by
however long this particular process had been alive and how many requests it had served. Genuinely
unknown without instrumentation — this card is a flagged observation, not a diagnosis.

### What it does (scope)

This is an investigation card, not a fix — same category as B311 originally was. Suggested steps for
whoever picks this up:

1. Reproduce in isolation: start a fresh `brain_daemon.py` against an empty/near-empty database, sample
   RSS immediately after startup (before serving any real traffic) to establish what the embedding
   model + framework baseline actually costs on its own.
2. If the fresh-start baseline is already multi-GB, that's expected-but-worth-documenting overhead, not
   a bug — the fix (if any) would be about choosing a lighter embedding backend or documenting the
   real resource floor for deployment sizing, not a leak fix.
3. If the fresh-start baseline is much lower (e.g. a few hundred MB, consistent with B311's originally
   reported 110-150MB idle baseline), then something about the *specific* long-running process
   observed here grew over its lifetime with near-zero data growth to explain it — that would be a
   genuine, distinct leak investigation, structured the same way B311's rounds 1-2 approached their
   isolated repro (reproduce, instrument, narrow root cause).
4. Either way, document the finding — even "this is normal, embedding models are just this large" is a
   useful, actionable answer for anyone sizing a deployment.

### Dependencies

None. Unrelated to B311/B337 — do not conflate the two investigations; they may turn out to share a
root cause (both are "the daemon uses more memory than expected"), but nothing established here
implies that, and treating them as the same bug without evidence would be exactly the kind of
unsupported-leap this project's own investigation cards (B311's rounds 1-2 in particular) have been
careful to avoid.

### Files to create/modify

None yet — pure investigation. Likely candidates once root-caused:
`campy/brain/hippocampus/graph/embeddings.py` (if it's the embedding model baseline),
`campy/brain_daemon.py` (if it's process-lifetime accumulation).

### Acceptance Criteria

- [ ] A fresh-start (no traffic) RSS baseline for `brain_daemon.py` is measured and documented.
- [ ] A determination is made and documented: is 5.4GB-class RSS with near-empty data (a) normal
      embedding-model/framework overhead, or (b) genuine unbounded growth unrelated to graph data

- [ ] If (b): root cause identified with reproducible evidence, following the same investigation
      discipline as B311 (report negative results honestly, don't declare a fix until measured).

### Cross-Reference: Fresh-Start Baseline Confirmed Elevated, Independently (2026-08-21)

While collaborating on B311's round 6 live confirmation, the ARC_AGI-side session restarted this exact
daemon (`launchctl kickstart -k`, new PID 14313) and measured RSS *before any episode traffic ran*:
**1,222 MB fresh-start baseline** — roughly 8-10x the original 2026-08-08 report's 110-150MB idle
baseline. They noted the on-disk KuzuDB file is now 331MB, vs. whatever it was when the original
baseline was measured. This is a second, independent data point (different measurement, different
session, same day) supporting acceptance criterion 1's core question: the fresh-start baseline itself
has grown substantially, separately from any transient spike behavior. Doesn't resolve item 2 (normal
overhead vs. genuine leak) on its own — a 331MB on-disk graph could plausibly explain some baseline
growth via larger HNSW indexes/buffer pool needs, but "some" isn't quantified, and it doesn't explain
the 99GB-physical-footprint reading from the diagnostic below, which happened on the *other* (now
replaced) PID 17813 at a much later point in its uptime. Full details: `backlog/B311.md`'s "Round 6."

### Deeper Diagnostic (2026-08-21), Same PID — Findings, Not a Root Cause

User authorized shutting the process down to investigate; a diagnostic pass was done first while it was
still up, since that state is lost once it restarts. All checks below were read-only (`ps`, `vmmap`,
`lsof`, log tail, MCP calls) — nothing was modified or killed as part of this pass.

**The real number is far worse than `ps` showed.** `vmmap -summary 17813` reported:

```
Physical footprint:         99.0G
Physical footprint (peak):  99.0G
MALLOC_SMALL   VIRTUAL=95.4G  RESIDENT=843.7M  SWAPPED=94.5G   24433 regions
```

`ps -o rss=` only counts uncompressed resident pages (it showed ~1.8GB at the time of this check,
5.4GB at an earlier check the same session — consistent with the spike/release pattern, not a
correction). macOS's "physical footprint" additionally counts compressed/swapped pages charged to the
process, and is the more accurate memory-pressure figure on this platform. 94.5 of 95.4GB in one malloc
zone sitting swapped out, spread across 24,433 individual regions, on a process serving 5 concepts and
8 messages, is not explainable by graph data volume or a reasonable embedding-model baseline — this
reads as a real, severe leak.

**The daemon is functionally degraded, not just large.** `mcp__campy__ask` (retrieval + thalamic
compression + LLM synthesis) returned `"Brain: OFFLINE - memory unavailable"`. `mcp__campy__current_truth`
(lighter — no LLM call) worked normally against the same process. `GET /health` and `GET /api/stats`
on the same PID also responded normally. This points at the heavier synthesis path specifically
struggling — consistent with swap-thrashing degrading anything that touches a meaningful working set,
while cheap fixed-cost endpoints stay fine.

**No smoking gun found at the Python level, and none should be assumed.** Checked
`campy/brain/brainstem/sweep.py`'s `run_sweep()` — the repeating `[Sweep] ... errors=21` line
(identical every cycle in `~/.campy/daemon.log`) comes from a fresh local counter
(`inferred = errors = 0`) per call, not an accumulating list or retained exception objects; this
specific pattern doesn't look like the leak source on inspection, but this was a code-reading check,
not a heap profile. `py-spy` was not available in this environment to get an actual live Python-object
breakdown, which is what this needs next — `ps`/`vmmap`/log-reading can describe the symptom but can't
identify which Python objects are actually accumulating.

**Separate finding, not the memory bug but worth its own fix:** `mcp__campy__current_truth`'s returned
`memory_link`/`panel_url` fields point at `http://127.0.0.1:7800/...`, but the only thing actually
listening (confirmed via `lsof -iTCP -sTCP:LISTEN`) is port 7799 — same PID, same process. Something in
the dashboard-link generation path hardcodes or misconfigures port 7800. Every link Campy's own MCP
tools hand back to a caller is currently dead. Worth a quick, separate fix.

**Separate finding, a real hygiene risk:** confirmed two different `brain_daemon.py` files exist —
the top-level `brain_daemon.py` (what's actually running — verified via the live process's own command
line) and `campy/brain_daemon.py` (different size, different module docstring: "HippoCampy Daemon" vs
"HippoCampy Brain Daemon"). Not resolved which is canonical or whether one is dead code from an
in-progress migration (see `docs/codebase-anatomy-refactor-plan.md`) — flagged so future edits (like
B337's, which touched the top-level file) don't silently target the wrong copy.

**What this diagnostic did NOT establish:** the actual root cause. Next steps, in order of leverage:
1. Get `py-spy dump`/`py-spy dump --locals` (or equivalent, e.g. running the daemon under `tracemalloc`
   from a fresh start) on a process that's grown large, to see actual Python object types/counts, not
   just OS-level malloc zone size.
2. Establish a fresh-start baseline (this card's original acceptance criteria, still unmet) to know how
   much of the footprint is "normal" embedding-model overhead vs. genuine growth over the 10+ hour
   uptime this instance had.
3. Resolve which `brain_daemon.py` is canonical before spending more investigation time on either copy.

### Reframe: Idle Growth Reclaims on Active Writes, Not on Checkpoint Cadence Alone (2026-08-21)

`backlog/B311.md`'s Round 7 (a 30.6-minute live ARC episode, same daemon/PID as this card's earlier
diagnostic) surfaced a specific, testable observation directly relevant to root-causing this leak: the
daemon had drifted from a 1,222 MB fresh-start baseline (Round 6) up to 7,274 MB over roughly 2 mostly-idle
hours — consistent with this card's core finding — but **within ~90 seconds of active ARC write traffic
resuming, RSS dropped to a ~250-370 MB floor and stayed there**, despite `[checkpoint] interval_seconds=15`
periodic checkpointing having been running continuously the entire idle period too, not just once writes
resumed.

This narrows item 1's question. It's no longer just "what Python objects are accumulating" — it's more
specifically: **does KuzuDB's checkpoint mechanism (manual or auto) actually reclaim/compact memory when
there's little-to-no pending write volume for it to act on, or does meaningful reclaim require real write
pressure regardless of how often checkpoint fires?** If the latter, that would mean B337's periodic
checkpoint (which fires on a fixed timer regardless of activity) is not actually protecting against
*idle*-period growth at all — only against growth during active write bursts (which Round 7 also
confirmed it does handle, via the observed sawtooth). Two different problems wearing one number.

**Suggested addition to next-step 1's profiling session:** deliberately capture tracemalloc/gc snapshots
(via B344's new `SIGUSR1` hook — no sudo needed, see below) at three points: (a) fresh start, (b) after
a period of idle-but-not-zero background activity (Claude Code capture/journaling continues even when no
one is actively using the daemon, per `~/.campy/activity.log`'s continuous entries), (c) shortly after
resuming active write traffic. Comparing (b) against (a) shows what idle time alone adds; comparing (c)
against (b) shows what write-triggered reclaim actually releases. This directly tests the reframed
hypothesis instead of just describing the symptom again.

**The sudo blocker on next-step 1 is resolved, differently than planned.** `py-spy` needs `task_for_pid`
(root on macOS) to attach *externally* — confirmed blocked when the operator doesn't have sudo access.
B344 (merged) adds a self-triggered alternative: `kill -USR1 <pid>` makes the daemon dump its own
`tracemalloc`/`gc` snapshot to `~/.campy/memory_debug.log`, no external attach or elevated permissions
needed, since a process can always introspect itself. One real caveat learned building it, left in
B344's own code comments: `tracemalloc` is too expensive to run during the daemon's allocation-heavy
startup phase (measured: 43x slower schema init) — it must be started lazily, well after startup, which
B344's hook already does correctly.

### Outcome

Not yet fixed or root-caused. This pass upgraded the finding from "a large number worth a look" (P3)
to "a real, severe, functionality-degrading leak with the actual mechanism still unknown" (P1) — the
daemon was authorized for restart by the user for a separate, coordinated purpose (B311's live
confirmation run), so the specific PID this diagnostic describes will not persist for further
inspection. Whoever picks this up next should instrument *before* the next long-uptime process gets
large, not after.
