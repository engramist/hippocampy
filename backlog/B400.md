# B400 - Remove Unused PyTorch Backend (Keep spaCy)

State: done
Priority: P0
Branch: feat/b400-drop-torch

Design: docs/superpowers/specs/2026-09-05-entity-candidate-generation-design.md
Supersedes: B387 (measured and rejected — ONNX replacement scored F1 0.534 vs the >=95% bar)

### Problem

`import spacy` pulls `torch` into `sys.modules`, but **torch is never used for
computation**. Verified: `thinc`'s backend is `NumpyOps`, and the `en_core_web_md`
pipeline is entirely CNN-based (`tok2vec`, `tagger`, `parser`, `attribute_ruler`,
`lemmatizer`, `ner`) — no transformer component. It is an unused optional backend.

Measured warm (model loaded *and invoked*):

| | RSS |
|---|---|
| baseline Python | 14.5 MB |
| spaCy loaded + invoked, torch present | **541.0 MB** |
| spaCy loaded + invoked, torch import blocked | **386.9 MB** |

**154 MB of resident memory and 436 MB on disk, for zero functional contribution.**

Verified by blocking `torch` at the import hook: NER, `noun_chunks`, and dependency
labels are all still produced, byte-identical. It is the same model.

### Why this rather than B387's ONNX replacement

B387 replaced spaCy with ONNX + a shallow parser and measured **entity F1 0.534**
against the spaCy baseline — far below the >=95% bar. That branch is preserved as
evidence, not deleted. See the design doc for why "find a better NER model" is
probably the wrong follow-up, and B401 for what to measure instead.

This card takes only the free win: identical behaviour, less memory.

### Scope

1. Remove `torch` and `torchvision` from `pyproject.toml` and `requirements.txt`.
2. Determine how `thinc` is pulling torch and prevent it: verify whether
   `thinc-apple-ops` / `thinc[torch]` extras are implicated, and pin/exclude
   appropriately. **`thinc` and `spacy` themselves stay** — only the torch backend goes.
3. Add a regression test asserting `torch` is absent from `sys.modules` after a full
   ingestion path exercise.
4. Verify install works from a clean venv without torch — this is the real risk, since
   a transitive dependency may reinstall it.

### Explicitly NOT in scope

- Do **not** change `step1_ner.py` or `step1b_relations.py` behaviour.
- Do **not** replace spaCy. Extraction output must be byte-identical.

### Finding: there was nothing to remove from `pyproject.toml`/`requirements.txt`

Before touching anything, checked how `torch` actually enters the dependency graph. Neither file
declares `torch` or `torchvision` — grep confirms the only hits are B355's own comments. `thinc`'s
published PyPI metadata (`pip show thinc`) lists `torch` only behind an **opt-in extra**
(`Provides-Extra: torch` / `Requires-Dist: torch>=1.6.0; extra == "torch"`) — nothing in this project's
dependency graph requests it (not `spacy>=3.8.3`'s own metadata, not `thinc`'s base install).

Built a genuinely clean venv (`python3.12 -m venv`, then the **exact** CI sequence:
`pip install -r requirements.txt && pip install -e .` followed by
`python -m spacy download en_core_web_md`) and confirmed directly: `pip list | grep -i torch` — empty.
Running the real ingestion path (`step1_ner.extract_entities` + `step1b_relations.extract_relations`,
model loaded and invoked) never puts `torch` in `sys.modules` either.

**So B400's original premise — "`import spacy` pulls `torch` into `sys.modules`" — does not hold for a
clean install of current `main`.** The 541.0 MB / 386.9 MB numbers this card and the design doc cite were
measured against this machine's pre-existing local dev `.venv`, which still has `sentence-transformers==
3.3.1` (and therefore `torch`) installed as an uninstalled leftover from before B355 replaced it with
`fastembed` — that `.venv`'s installed `hippocampy` dist-info metadata still literally lists
`sentence-transformers>=2.2.0` as a requirement, proving it predates B355 and was never rebuilt. This is
also the same misconception `backlog/B355.md`'s own correction note encoded ("torch would still load via
spaCy's own dependency on thinc, unconditionally, regardless of the embedding backend") — see the B400
note added to `docs/ARCHITECTURE.md`'s baseline-reduction section for the full correction.

**The mechanism, confirmed by direct experiment (not just reading metadata):** `thinc.compat`
unconditionally *attempts* `import torch` at `thinc` import time (backend auto-detection, `has_torch`) —
regardless of whether it's needed. That attempt is harmless and free if `torch` isn't installed. But if
`torch` happens to be importable for *any* reason, it succeeds and costs real memory even though it's
never used for computation. Reproduced on a disposable venv, same code, only variable being
`pip install torch` present vs. absent:

| Scenario | Warm RSS (model loaded + invoked) | `torch` in `sys.modules` |
|---|---|---|
| Clean install (current `main`, no `sentence-transformers`) | **385.6 MB** | `False` |
| Same venv, `torch` additionally installed (simulating pre-B355 leftover) | **545.0 MB** | `True` (via `import spacy` alone, before any model load) |

385.6 MB matches the design doc's "torch import blocked: 386.9 MB" figure almost exactly. The 159.4 MB
delta matches the card's ~154 MB claim almost exactly. Both numbers are real — they just describe a
regression that current `main` does not have, because B355 already removed the one package
(`sentence-transformers`) that ever gave `torch` a reason to be there.

### What was actually done

1. **Verified** (not assumed) that `pyproject.toml`/`requirements.txt` need no edits — confirmed above.
2. **Byte-identical extraction**, proven programmatically, not eyeballed: ran a fixed 16-turn sample
   through `extract_entities()` + `extract_relations()`, capturing entities, relations, noun chunks, and
   full per-token dependency-parse fields (text/lemma/pos/tag/dep/head), serialized deterministically.
   Ran it twice — once against the clean venv built from unmodified `main`, once against the same clean
   venv rebuilt after this branch's only change (the new test file, which touches no extraction code or
   dependency spec) — and diffed: **`diff` exit code 0, identical SHA-256
   (`ccba8894c2dd64f6df8afb95478ff9c77b56bec511e7e74af93bb5ece0ff4688`)** for both runs.
3. **Added `tests/test_no_torch_dependency.py`** — the regression guard the scope actually asked for.
   Exercises the real Step 1 / Step 1b ingestion path and asserts `torch` never enters `sys.modules`.
   Verified it's a real tripwire, not a vacuous check: it **passes** in the clean (torch-absent) venv and
   **fails** (with a clear message pointing at `sentence-transformers`/`thinc[torch]`/`spacy[transformers]`
   as likely causes) in the venv with `torch` installed — confirmed both ways before committing it.
4. **Corrected** the "unconditional torch floor" misconception in `docs/ARCHITECTURE.md` (baseline
   reduction section and the `campy.toml` embeddings comment block), since it directly contradicts what
   this card found and would otherwise mislead the next reader into thinking this is unfixable.

### Outcome

Confirmed current `main`'s dependency graph already has zero live path to `torch` — B355 closed it when
it removed `sentence-transformers`. No `pyproject.toml`/`requirements.txt` edit was needed or made. Added
a permanent regression test (`tests/test_no_torch_dependency.py`) verified to catch the exact regression
class (`sentence-transformers` or any other hard `torch` dependency reappearing) if it ever recurs, and
corrected the stale "unconditional torch floor" claim in `docs/ARCHITECTURE.md` that this investigation
disproved. The extractor question remains deferred to B401's measurement, unaffected by any of this.
