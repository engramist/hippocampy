# B574: the memory guard and the GPU queue runner do not start after a reboot

**Status:** Open. Found 2026-11-16 while diagnosing the baselines' two memory-guard stops.

**Principles:** P6 (measure correctly before believing): a GPU run recorded as guarded must actually have run under the guard.

**What.**
- The lead's GPU queue runner (`runner.sh`) and memory guard (`memguard.sh`) are started by hand as background shells. Nothing starts them at login or boot.
- The machine rebooted on 2026-11-10 at 07:50. The memory log has no entries from then until 2026-11-16 at 16:44.
- So the re-capture, vecq, S3-OT and S3-asbuilt judging all ran unguarded, while the plan's standing constraint assumes a guard.
- They are running again, but only as children of one agent session, which a reboot or the session's end will stop.

**Fix (to design).**
- A per-user launch agent (or an equivalent) keeps both running across reboots.
- A check, run at the start of every queued job, refuses to start when the guard is not running, and writes the refusal to the chain log.
- Nothing about the guard's threshold changes: that line is the user's.

**Done when:**
- After a reboot, both are running without anyone acting.
- A job queued while the guard is down does not start, and the chain log says why.
