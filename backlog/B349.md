# B349 - Tune campy.toml's Shipped Checkpoint Interval Default (Currently 60s, Round 5 Recommends 15-30s)

State: ready
Priority: P1

Plan: none yet.

### Problem

`backlog/B311.md`'s Round 5 swept `[checkpoint] interval_seconds` (0/none, 60s shipped default, 30s,
15s, 5s) against a single isolated synthetic workload (600 write-heavy steps, 90s post-close idle
window for comparison) and found a clear, non-monotonic optimum at 15s — both lowest peak RSS (1445MB
vs. the 60s default's 1985MB) and best post-close release (756MB vs. the default's 1947MB after 90s).
Round 6 additionally ran a live confirmation at 15s (via cross-repo collaboration with the ARC_AGI-side
Claude Code session) and found smooth, non-spiking growth under real traffic — consistent with, though
not proof of, the same benefit.

Despite this, `campy.toml`'s shipped default is still `60`. Round 5's own write-up was explicit that
"15s tested best here, but this is one workload shape on one machine, not a robust optimum" and
recommended a proper tuning pass before changing the shipped default — that pass has not happened.

### What it does (scope)

1. Re-run (or extend) round 5's interval sweep across more than one workload shape — the existing sweep
   used one synthetic write pattern (`arc_perceive_state`/`record_transition`/`record_rule` in a fixed
   ratio). Vary at least: total write volume (shorter and longer bursts than the 600-step baseline) and
   write pattern (e.g. heavier `record_rule` load vs. heavier `arc_perceive_state` load, since real
   traffic won't always match the original synthetic ratio) to see whether 15s remains the optimum or
   whether it was specific to that one shape.
2. Coordinate with the ARC_AGI-side Claude Code session (check `ListAgents` for the current live peer —
   was named `arc-agi-4d` as of this card's filing, confirm current name) for at least one additional
   live confirmation run at whatever interval this card's sweep recommends, ideally a **longer** episode
   than Round 6's (which ended early via `STALL_CHECK` after ~148s) — see B350, which is specifically
   about getting that longer episode; this card can consume B350's data once available rather than
   duplicating the live-run effort.
3. Consider whether a single fixed interval is even the right model, or whether an adaptive approach
   (e.g. checkpoint after N writes OR T seconds, whichever comes first, rather than pure fixed-interval)
   would perform better across varying load — round 5/6 only tested fixed intervals; this is a legitimate
   alternative design worth at least a brief evaluation before committing to "just change the fixed
   default," even if the conclusion is "fixed interval is fine, adaptive isn't worth the complexity."
4. Based on findings, update `campy.toml`'s shipped default `interval_seconds` value (currently `60`)
   and its surrounding comment block (which currently says "Recommended: 60-300 seconds depending on
   write load" — update this guidance to reflect what was actually learned, not left stale).
5. Update `backlog/B311.md` with a "Round 7" (or next available round number — check current state)
   section documenting this tuning pass, following the same rigor/honesty standard as prior rounds.

### Dependencies

Read `backlog/B311.md` in full (all rounds) before starting — do not re-derive the existing sweep
methodology from scratch, reuse/extend it. Check whether B350 (longer live episode) has already landed
useful data before duplicating that specific piece of work.
