# B362 - brain_daemon.py's _handle_connection Doesn't Catch Connection-Reset Errors

State: ready
Priority: P3

Plan: none yet.

### Problem

Observed live 2026-08-25 while watching `~/.campy/daemon.log` during ARC_AGI's `make smoke` run
(peer session, A188-A206 Reasoner sanity check) at the user's request. Four occurrences of an
unhandled, chained traceback appeared back-to-back:

```
Unhandled exception in client_connected_cb
transport: <_SelectorSocketTransport closed fd=12>
Traceback (most recent call last):
  File "brain_daemon.py", line 309, in _handle_connection
    await writer.drain()
  ...
ConnectionResetError: Connection lost

During handling of the above exception, another exception occurred:

Traceback (most recent call last):
  File "brain_daemon.py", line 319, in _handle_connection
    await writer.wait_closed()
  ...
BrokenPipeError: [Errno 32] Broken pipe
```

`_handle_connection` (`brain_daemon.py:297-319`) wraps the read/dispatch/write loop in a
`try/finally` — the `finally` always calls `writer.close()` + `await writer.wait_closed()`, but
nothing catches `ConnectionResetError`/`BrokenPipeError` around either the loop's `writer.drain()`
(line 309) or the cleanup's `wait_closed()` (line 319). When a client disconnects abruptly while a
response is in flight, the reset propagates all the way out of the callback, asyncio logs it as an
"Unhandled exception in client_connected_cb" with a full traceback, and the cleanup's own
`wait_closed()` call on the already-broken socket raises a second, chained exception on top of the
first. Not new to today — `grep -c "Unhandled exception in client_connected_cb"
~/.campy/daemon.log` shows 250 total occurrences across the log's history — but this is the first
time it's been directly correlated with a live incident: the same ~30s window
(`~/.campy/activity.log`, `2026-08-25T16:26:46Z`-`16:26:52Z`) shows this session's own
`notify_turn`-driven `current_truth`/`upsert_lesson` calls (B298's memory piggyback) failing with
`DAEMON_OFFLINE: socket transports failed ... TimeoutError` before self-recovering by 16:27:17 —
consistent with the daemon being busy/contended handling the ARC session's concurrent traffic
during that window, not a crash (the daemon process itself never went down; `readiness_probe`
succeeded normally ~30s later).

### What was NOT established

- No evidence of actual data corruption or malformed graph writes — the concurrently-running ARC
  session's own tool calls in `~/.campy/activity.log` all show `"status": "ok"` through this
  window, and this session's own soft-failures were classified and logged as `degraded` (graceful
  fallback), not silently swallowed or written incorrectly.
- Root cause of *why* the daemon was briefly unresponsive to a second client during this window
  (single-threaded asyncio event loop contention from a burst of ARC tool calls? a slow LLM-backed
  call blocking the loop? something else?) was not investigated — this card is about the missing
  exception handling that turns an ordinary client disconnect into log noise, not about the
  underlying contention.

### What it does (scope)

1. Wrap `writer.drain()` (line 309) and `writer.wait_closed()` (line 319) in
   `except (ConnectionResetError, BrokenPipeError, ConnectionError): pass` (or log at debug level)
   so an abrupt client disconnect is handled as the ordinary occurrence it is, not an unhandled
   exception with a scary chained traceback.
2. Optionally investigate whether the brief unresponsiveness itself (the DAEMON_OFFLINE window)
   points to a real concurrency bottleneck worth addressing separately — out of scope for this
   card's minimal fix, noted for follow-up if it recurs.
