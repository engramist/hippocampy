# B311 - Investigate Brain Daemon's Large Transient Memory Spikes (100-150MB Baseline to 600MB-1.2GB Peaks) During ARC Live-Smoke Runs

State: open — investigating (round 4, 2026-08-20). B337 shipped manual/periodic checkpoint control
(round 3's step 1) and merged (PR #61). Round 4 measured it against the same isolated-repro
methodology: peak RSS dropped ~30% relative to an unbatched/no-checkpoint baseline, but post-close
memory release is markedly slower under the treatment — genuinely a partial win, not a fix. See
"Round 4: Measuring B337's Periodic Checkpoint" below. Still an investigation card — the daemon still
spikes, just to a lower ceiling, and next steps are identified.
Priority: P2

Plan: none yet — this is an investigation card. A fix plan should be written once the trigger is identified (see "Suggested investigation steps" below).

### Problem

Found live 2026-08-08 while running ARC_AGI's `make smoke` (`agents/arc4/`, the ARC-AGI-3 client) against a real Ollama+`brain_daemon.py` stack, per explicit user request to compare memory usage between the ARC client process and the Campy brain daemon it talks to over the MCP seam. Sampled both processes' RSS every 2 seconds for a full ~308-second live episode (`ps -o rss= -p <pid>`, 154 samples per process, raw CSV preserved in this write-up below).

**ARC client (`run_single_puzzle.py`)**: flat and boring, exactly as expected of a thin client — min 24.8MB, max 78.9MB, no growth over the run.

**`brain_daemon.py`**: highly volatile. Idle/baseline RSS sits around 110-150MB, but the same long-running daemon process spiked to over 1GB twice during this one ~5-minute episode:

```
20:06:58  daemon= 632.0MB   <- spike #1, already climbing when sampling started
20:07:14  daemon= 619.0MB
20:07:31  daemon= 128.2MB   <- back to baseline
20:07:47  daemon= 137.1MB
20:08:03  daemon= 809.6MB   <- spike #2 begins
20:08:19  daemon= 849.3MB
20:08:35  daemon= 893.1MB
20:08:51  daemon=1119.4MB   <- peak, ~10x idle baseline
20:09:08  daemon= 801.0MB
20:09:24  daemon= 118.2MB   <- back to baseline
20:09:40  daemon= 139.5MB   <- stays here for the remaining ~150s of the run
```

Full numeric summary across all 154 samples (2s interval, ~308s total):

| | min | max | first sample | last sample |
|---|---|---|---|---|
| ARC client RSS | 24.8 MB | 78.9 MB | 76.7 MB | 48.4 MB |
| `brain_daemon.py` RSS | 67.7 MB | **1220.3 MB** | 632.0 MB | 140.8 MB |

Separately, before this timed profile, three single-point `ps aux` checks of the same long-running daemon PID (21539, uptime spanning the whole session, never restarted) taken minutes apart during other live-smoke runs earlier the same session showed RSS values of **2018MB**, **56MB**, and **578MB** respectively — consistent with the same spike/release pattern being sampled at different phases, not measurement noise from a different process.

**This is not a leak** — there is no net upward drift across the ~5-minute profiled run (it actually ends lower than it started, since sampling began mid-spike). The daemon reliably returns to its ~110-150MB baseline after each spike. But a background daemon meant to run persistently on a user's machine repeatedly ballooning to over 1GB (roughly 10x its resting size) twice in a single 5-minute client episode is a real resource-usage characteristic worth understanding — it risks memory pressure on constrained machines, could compound badly if multiple MCP clients/episodes run concurrently, and the repeated large-allocate-then-release cycle itself costs CPU (allocation + GC) that a steadier memory profile would avoid.

### What was NOT established (be honest about the gap)

- **Root cause is unknown.** I did not correlate the spike windows against `brain_daemon.py`'s own internal operations (no per-request timestamps were found in `~/.campy/daemon.log` in a form correlatable to the 20:06:58-20:09:08 window from the ARC_AGI side — the log's existing entries near that time were from an unrelated, already-resolved earlier crash incident in the same session, not from this run).
- I have **hypotheses, not evidence**, for the trigger (see below) — none were tested against the actual daemon internals from this investigation.
- I did not check whether the spikes correlate with specific MCP tool calls (e.g., `ingest_perception`, `arc_record_rule`, embedding/vector-search calls), specific ARC workflow phases (perceive vs. evaluate), or something unrelated to ARC entirely (e.g., campy's own background `[Loop]`/`[Capture:claude_code]` journaling activity visible interleaved in `~/.campy/daemon.log`, which was actively running throughout this same session for unrelated reasons — Campy journals Claude Code's own conversation activity in the background, and that traffic was present in the log throughout, so it cannot be ruled out as a contributing or even primary cause without further isolation).

### Suggested investigation steps

1. **Reproduce in isolation.** Run a `brain_daemon.py`-only workload (no ARC_AGI, no concurrent Claude Code journaling activity) that exercises `arc_perceive_state`/`ingest_perception`-equivalent calls repeatedly, and see if the same spike pattern appears. If it doesn't, the trigger is more likely on the ARC-calling side (embedding load triggered by ARC-specific tool calls) or the concurrent journaling activity, not something ARC-independent.
2. **Instrument memory at the call level.** Add temporary logging (or use `tracemalloc`/`memory_profiler`) around the daemon's tool-dispatch loop (`_handle_connection` / wherever `TOOL_HANDLERS` entries are invoked, per B278/B309's registration pattern) to see which specific tool call(s) precede a spike.
3. **Check the embedding model.** `campy/brain/hippocampus/graph/embeddings.py`'s `embed()` (referenced in B278's `arc_classify_game_archetype` implementation) loads `sentence-transformers/all-MiniLM-L6-v2` — check whether this model is being re-loaded per call (expensive, spiky) vs. held warm, and whether batch embedding calls could be producing large transient tensors that Python's GC is slow to reclaim.
4. **Check KuzuDB buffer/cache behavior.** Large graph writes (A175-A185's `Transition`/`Rule`/`GridEntity` traffic, now genuinely live per this session's A175-A179 completion) could be triggering large transient buffer-pool allocations in KuzuDB during write-heavy bursts.
5. **Check for GC-deferred reclaim vs. a real spike.** Confirm with `gc.collect()` timing whether forcing garbage collection immediately after a spike brings RSS down faster than observed here (~15-20s to release) — if so, tuning GC thresholds/generation behavior could be a cheap mitigation even before the root allocation source is found.

### Campy-Side Investigation Update (2026-08-09)

Followed the card's own "Suggested investigation steps" 2-5 via static code review plus an isolated
reproduction (step 1). Did not have live ARC_AGI/Ollama available on the campy side, so this is a
structurally-faithful standalone repro, not the exact original conditions — see caveats below.

**Hypothesis 1 (embedding model reload) — ruled out for this write path, and unlikely in general.**
`campy/brain/hippocampus/graph/embeddings.py`'s `_get_st_model()` (line 78) is a lazy module-level
singleton (`if _st_model is None: ...`) — loaded once at daemon startup via `prewarm()` and reused
for the life of the process, never reloaded per call. `campy.toml`'s `[embeddings]` section confirms
the default provider is `sentence-transformers` (local) — the "Ollama" in "Ollama+brain_daemon.py
stack" refers to the separate `[llm]` provider (chat/reasoning), a different config axis from
embeddings entirely. More specifically for this card: `arc_perceive_state`, `record_transition`, and
`record_rule` (`campy/brain/thalamus/tools/arc_queries.py`) — the write-heavy ARC path B309 made live
— never call `emb.embed()` at all. They write plain graph properties with no vectors attached, so
neither half of hypothesis 1 (reload cost, or large transient embedding tensors) applies to this path.

**Hypothesis 4 (concurrent Claude Code journaling) — ruled out as a *necessary* trigger.** The isolated
reproduction below ran with zero Claude Code capture connectors, zero ARC_AGI process, and zero Ollama
traffic, and still produced the same class of spike-and-release behavior. This doesn't rule out
journaling as an *additional contributing* factor in the original field session (untested here), only
that it is not required to produce this pattern.

**Hypothesis 2 (KuzuDB buffer/checkpoint bursts) — strongly implicated, with a concrete mechanism.**
`KuzuClient.__init__` (`campy/brain/hippocampus/graph/kuzu_client.py:55`) calls
`kuzu.Database(db_path, read_only=read_only)` and never sets `buffer_pool_size`, `checkpoint_threshold`,
or `auto_checkpoint` — confirmed via `grep -rn "buffer_pool\|KuzuClient(" campy/` that no call site
anywhere in the codebase overrides these. Per kuzu==0.11.3's own Python docstring
(`kuzu/database.py:48-49`): `buffer_pool_size` "Defaults to ~80% of system memory" — on the 32GB
machine this was tested on, a ~25.6GB ceiling, never remotely approached by the observed 1-2GB spikes
(so the spikes are *not* eviction-under-pressure against that ceiling). `checkpoint_threshold` defaults
to an internal auto value (Python-level sentinel `-1`, undocumented past that) with `auto_checkpoint =
True` — i.e., Kuzu automatically checkpoints (merges WAL into the main store) once the WAL crosses an
un-tuned, un-inspected internal threshold. A concrete architectural amplifier: every `execute_write`
call (`kuzu_client.py:70-78`) is its own independent auto-committed transaction — there is no batching
anywhere in the write path. A single `arc_perceive_state` call with N entities issues 1 (GridSnapshot
MERGE) + N (GridEntity MERGE) + up to 1 (ActionEffect MERGE) + up to N (MOVED_BY edge MERGE) separate
transactions — up to 2N+2 individual commits per MCP tool call, each a candidate WAL-growth/checkpoint
trigger point. `record_transition` and `record_rule` add further per-call transactions on top.

**Hypothesis 3 (GC-deferred reclaim) — logically de-prioritized for this path, not directly instrumented.**
No `gc.collect()`-timing test was run. But the ARC write path creates no Python-level objects anywhere
near large enough to explain multi-hundred-MB to multi-GB swings (small dicts/strings only — no
embedding vectors on this path, per hypothesis 1's finding above), so Python-GC-deferred reclaim cannot
be the *primary* driver here even before instrumenting it: growth of this magnitude is far more
consistent with native (Kuzu C++) buffer-manager/mmap memory, which is invisible to and unaffected by
Python's `gc.collect()`.

**Isolated reproduction (step 1).** Built a scratch KuzuDB with campy's real `init_schema()` (same ~50
node tables + ~20 HNSW indexes as production), then — in a *separate* monitored phase, to avoid
conflating one-time schema/index-creation cost with runtime behavior — drove 2000 iterations of a
workload calling the real `arc_perceive_state` / `record_transition` / `record_rule` handlers directly
(3-8 synthetic GridEntities per step, an action + effect every step) against the pre-built DB. No
ARC_AGI process, no Ollama, no Claude Code capture connectors were running. RSS of the worker process
was sampled every 1s via `ps -o rss= -p <pid>` (same tool as the original card's methodology), for the
full ~477s run (8s baseline idle + 447s workload + 30s idle after `db.close()`):

| | value |
|---|---|
| baseline (idle, post-open, pre-workload) | ~430-460 MB |
| peak RSS during workload | **1879.5 MB** |
| large drop events (≥150MB in a single ~1-2s sample) | **9**, e.g. 1766→1460MB, 1635→1243MB, 1187→820MB, 1013→784MB |
| RSS after workload stop + `db.close()` + 30s idle | flat **408.8-417.9 MB** across all 31 samples of the idle window |

This reproduces the qualitative shape of the field observation — sustained growth into the
several-hundred-MB-to-~2GB range, punctuated by sharp partial-to-large drops, followed by a full,
stable settle after activity stops — from the KuzuDB + embedding stack alone. The settled plateau here
(~418MB) is higher than the field's ~110-150MB baseline, which is expected: this run persisted roughly
2000 steps × ~5 entities × 3 write calls (tens of thousands of rows) into the scratch DB, far more
total data than one ~5-minute ARC episode would normally write.

**Caveats (matching this card's own "be honest about the gap" standard):**
- Not run against the real `brain_daemon.py` process or a live ARC_AGI + Ollama stack end-to-end —
  this is a structurally-faithful standalone repro, not the original conditions.
- Could not correlate drop timings against Kuzu's internal checkpoint events directly — there is no
  Python-level hook or log for Kuzu's internal checkpointing, consistent with this card's original note
  that `~/.campy/daemon.log` has no correlatable per-checkpoint timestamps (confirmed again here: grep
  for "checkpoint" in the real daemon.log only matches unrelated `[Loop]`-captured conversational text
  about git checkpoints, not database internals).
- Whether concurrent journaling *amplifies* (rather than merely being unnecessary for) the pattern is
  untested.
- The tail of the raw sample data (final ~3 samples, jumping from ~418MB to 1.8GB to 4.7GB within 2
  seconds, well after the worker process's own log confirmed it had already reached its `MARK done`
  idle-complete line) is judged to be measurement contamination — almost certainly the monitor shell
  loop's `kill -0 $PID` outliving the actual worker (zombie-reap delay or PID reuse by an unrelated
  process) — and is excluded from the analysis above rather than silently dropped.

### Round 2: Mitigation Experiments (2026-08-09, same day)

Tested the two candidate mitigations from round 1's next-steps list against the same isolated repro
harness (same scratch schema, same 2000-step `arc_perceive_state`/`record_transition`/`record_rule`
workload, same `ps -o rss=` 1s-interval methodology). Both came back negative or inconclusive — this
section reports that honestly rather than presenting only the experiments that "worked."

**Experiment A — `checkpoint_threshold` tuning alone (unbatched writes, as today's code is).** Added a
scratch-only `TunedKuzuClient` that passes an explicit `checkpoint_threshold` (Kuzu's WAL-size-in-bytes
auto-checkpoint trigger) instead of leaving it at Kuzu's internal auto default. Re-ran the full 2000-step
workload at `checkpoint_threshold=4MB` (4194304 bytes):

| | round 1 baseline (default, untuned) | checkpoint_threshold=4MB |
|---|---|---|
| peak RSS | 1879.5 MB | **2007.6 MB** (higher) |
| large drop events (≥150MB) | 9 | **11** (more frequent, not smaller) |

Lowering the threshold did not reduce peak RSS or produce smaller/more-frequent spikes as hypothesized —
if anything peak RSS was slightly higher. This does not confirm checkpoint size as a simple direct lever
in the way round 1 predicted; the growth pattern may be driven more by total working-set size touched
during the run than by raw WAL-byte accumulation between checkpoints.

**Experiment B — batching `arc_perceive_state`'s writes into one transaction per call.** Implemented
`KuzuClient.execute_write_batch()` (wraps a list of statements in an explicit `BEGIN TRANSACTION` /
`COMMIT`, confirmed empirically that Kuzu 0.11.3 supports parameterized multi-statement transactions
with correct read-your-own-writes semantics within the transaction, and auto-aborts the whole
transaction if any statement errors) and rewrote `arc_perceive_state` to queue its GridSnapshot +
GridEntity + ActionEffect + MOVED_BY writes into one batch instead of up to `2N+2` separate
auto-committed transactions. All 18 tests in `tests/test_arc_queries.py` passed (including the two
real-KuzuDB `b309_db` integration tests exercising MOVED_BY correctness), so the change was behavior-
preserving. Re-ran the isolated repro with the batched write path:

| | round 1 baseline (unbatched, untuned) | batched, untuned | batched, checkpoint_threshold=1MB |
|---|---|---|---|
| workload wall-clock time | 447s | **211s** (2x faster) | 213s |
| peak RSS | 1879.5 MB | **3047.5 MB** | 2411.8 MB |
| drop events during workload | 9 | **0** | 1 |
| RSS after `db.close()` + 30s idle | flat 408.8-417.9 MB | **stuck flat ~3045 MB — never released** | still climbing, 2174-2412 MB |

Batching is genuinely faster (fewer transactions = less overhead) and did not break correctness, but it
made the memory picture *worse*, not better — and combining it with an aggressive 1MB checkpoint
threshold only partially offset the damage, still leaving RSS elevated and non-settled after close.
Working theory: Kuzu's auto-checkpoint check appears to fire at transaction-commit boundaries. Batching
drastically reduces how many commit boundaries occur per unit of data written, so the WAL grows for much
longer before Kuzu gets a chance to trigger a checkpoint — and by the time `close()` forces one, there's
a much larger backlog, which doesn't fully settle within the 30s observation window (or possibly does
not settle via `close()` the way it does via periodic auto-checkpoints during a long-lived run — untested
either way). **The `arc_queries.py` / `kuzu_client.py` batching change was reverted** (not committed) once
this was measured — it should not be reintroduced without first solving the checkpoint-cadence problem it
creates.

**What round 2 rules out / narrows:**
- Batching transactions, as a standalone mitigation, is off the table — it's counterproductive for this
  specific problem regardless of checkpoint_threshold pairing (tested both ways).
- `checkpoint_threshold` alone (unbatched) is not a simple "lower it and the spikes shrink" lever — the
  4MB test showed no improvement. Whether some *other* threshold value (larger, to match whatever Kuzu's
  internal auto-default actually resolves to, or a very different order of magnitude) would help is
  still untested — only one value was tried.
- No live confirmation against the real `brain_daemon.py` + ARC_AGI + Ollama stack was run this round —
  intentionally, since neither candidate mitigation earned that time investment. ARC_AGI (at
  `~/Desktop/GitProjects/ARC_AGI`) and a local Ollama server are both available for this if/when a
  mitigation is found worth confirming live.

**Next steps, revised:**
1. Investigate whether Kuzu exposes any way to force periodic checkpoints independent of commit count
   (e.g. a manual `CHECKPOINT` Cypher statement, called on a timer/counter from the daemon's background
   sweep task) — this would let campy keep low transaction counts (or not) while controlling checkpoint
   cadence directly, sidestepping the commit-boundary coupling round 2 found.
2. Try a broader sweep of `checkpoint_threshold` values (both smaller — e.g. 256KB — and larger — e.g.
   32-64MB) on the *unbatched* path to see if the relationship is non-monotonic or if 4MB was simply the
   wrong order of magnitude.
3. Only after 1 or 2 produces a genuinely better before/after profile in the isolated repro should a live
   `brain_daemon.py` + `make smoke` confirmation run be worth the time.

### Round 3/4: Manual Checkpoint Control, Implemented and Measured (2026-08-20)

Round 2 left three untried next steps; this round covers the first one end to end — build it (round
3, filed as its own backlog card, B337) and measure it (round 4, this section). B337 shipped
`KuzuClient.checkpoint()` (`campy/brain/hippocampus/graph/kuzu_client.py`) — a manual `CHECKPOINT`
call, and `BrainDaemon._periodic_checkpoint()` (`brain_daemon.py`), a background task that calls it on
a fixed interval (`[checkpoint] interval_seconds` in `campy.toml`, default 60s) independent of
transaction/commit count — exactly decoupling checkpoint cadence from commit boundaries, the mechanism
round 2's "next steps" identified. It merged via PR #61. (Note: B337's own card asked for this round's
results to land here as "Round 3" — that write-up was never produced when the code shipped; this
section covers both the implementation summary and the measurement in one pass, filed together as
round 4 rather than split further.)

**One real bug found and fixed before this could be measured honestly.** The first version of
`checkpoint()` was added without removing the original method of the same name later in the same
class — Python silently uses the *second* definition for method resolution, so the first (correctly
lock-wrapped) version was dead code, and the live method was the original, unlocked one. Manual
checkpoint could then run on a separate thread pool worker concurrently with an in-flight
`execute_write()` on the same shared `kuzu.Connection` — a real race, the same class of bug this file's
`_write_locks` mechanism (S3/S4/B316) exists to prevent. Fixed by removing the duplicate and adding the
lock to the one remaining method; verified by deliberately reverting the fix and confirming the
regression test (`tests/test_checkpoint_lock_serialization.py`) catches it.

**Measurement methodology, and how it differs from rounds 1-2 (stated up front, per this card's own
standard):** Same shape of isolated repro as rounds 1-2 — real `init_schema()` against a scratch
KuzuDB, then a write-heavy loop calling the real `arc_perceive_state`/`record_transition`/`record_rule`
handlers directly, no ARC_AGI process, no Ollama, no Claude Code capture connectors — but **600 steps,
not 2000**, and a **15s checkpoint interval, not B337's default 60s**, so several checkpoints would fire
within a run short enough to run multiple times in one sitting. Both the baseline and treatment runs
below use *identical* parameters except the one variable under test (checkpoint interval), so the A/B
comparison is fair on this machine at this scale — but the absolute numbers are not directly comparable
to round 1/2's 2000-step figures (1879.5MB peak, ~418MB settled). RSS sampled via `ps -o rss= -p <pid>`
every ~1s, same as rounds 1-2, on a subprocess with a fixed idle-before/idle-after window around the
workload.

| | baseline (no checkpoint) | treatment (checkpoint every 15s) |
|---|---|---|
| idle-baseline RSS | 82.4 MB | 98.3 MB |
| workload wall-clock | 95.4s | 92.2s (checkpointing did not meaningfully slow the workload) |
| **peak RSS** | **2057.4 MB** | **1445.2 MB (~30% lower)** |
| RSS after `close()` + 20s idle | 1751.9 MB, still declining | **1445.2 MB, completely flat across all 20 samples — zero decline** |
| RSS after `close()` + 90s idle (separate run, treatment only) | not measured | 755.6 MB, still declining |

**What this shows, stated plainly in both directions:**

- **Positive:** periodic checkpointing genuinely lowers peak RSS in this test — a ~30% reduction
  (2057MB → 1445MB), consistent across two treatment runs (1445.2MB and 1435.5MB peaks). This is the
  first mitigation across three rounds that has moved the peak-RSS number in the right direction at
  all — round 2's two candidates both made it worse.
- **Negative/confounding, reported with the same honesty round 2 held itself to:** post-close memory
  release is markedly *slower* under the treatment than the baseline. At the same 20s idle window, the
  baseline was still gently declining (1814.9 → 1751.9 MB) while the treatment was perfectly flat
  (1445.2 MB, unchanged across 20 consecutive 1s samples) — not a measurement artifact; a second
  treatment run with the idle window extended to 90s confirmed it does eventually decline further, to
  755.6MB, so it is *slow to release*, not *permanently stuck* — but even at 90s it is still roughly
  9-10x the ~80MB true-idle baseline, well short of round 1's 30s-to-settle result on the (larger,
  differently-shaped) original workload. No equivalent long-idle baseline-only run was taken this
  round, so whether the baseline *without* checkpointing would settle just as slowly given the same
  90s window, or faster, is not established — that's the natural next check, not yet done.
- **A plausible mechanism, not yet confirmed:** a manual `CHECKPOINT` forces Kuzu to flush and
  reorganize its buffer pool on a fixed cadence regardless of what the buffer pool's own eviction
  policy would otherwise have done — it's plausible this leaves more pages "live" in the pool
  immediately post-checkpoint (since the checkpoint just touched them) than an uncontrolled buffer pool
  would, and that this is what's slower to unwind after `close()`. Untested; would need Kuzu-internal
  buffer-pool instrumentation this round didn't attempt.

**Next steps, revised again:** (1) run a baseline-only long-idle (90s+) comparison to know whether slow
post-close release is specific to the checkpoint treatment or just how this workload behaves generally;
(2) if it's checkpoint-specific, sweep the interval (the current 60s default vs this round's 15s vs
something larger) to see whether a less-aggressive cadence keeps the peak-RSS win without the slower
release; (3) only after that, a live `brain_daemon.py` + ARC_AGI confirmation run is justified — this
round's result is promising enough to be worth confirming eventually, unlike round 2's two negative
candidates, but the post-close behavior needs to be understood first per this card's own standard of
not spending live-confirmation time on an unproven candidate.

### Outcome

Root cause narrowed (KuzuDB's checkpoint-at-commit-boundary behavior under write-heavy, un-batched
traffic). Round 1 ruled out embedding-model reload and concurrent journaling as *necessary* triggers.
Round 2 tested checkpoint_threshold tuning and transaction batching; both came back negative or
inconclusive, and batching was reverted rather than merged. Round 3 built manual/periodic checkpoint
control (B337, merged PR #61), fixing a real write-lock race along the way. Round 4 measured it: peak
RSS improved ~30% relative to an unbatched/no-checkpoint baseline — the first genuinely positive result
across four rounds — but post-close memory release is markedly slower under the treatment, a real
open question rather than a confirmed cost. This is a **partial win, not a fix**: the daemon still
spikes into the multi-hundred-MB-to-GB range, just to a lower ceiling than before. Card stays open.
No live `brain_daemon.py` + ARC_AGI confirmation run has been performed yet for this mitigation —
deliberately, pending the baseline-long-idle comparison and interval sweep described above.
