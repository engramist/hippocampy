### Problem

`tests/test_capability_queries.py::test_q5_verifies_requires_satisfiable` is flaky, confirmed unrelated
to any change in flight when found (B355's embedding backend migration). Found because the full test
suite run for B355 hit it once; re-running it in isolation showed it's genuinely non-deterministic
regardless of that change:

```
Against unmodified main, isolated repeated runs: 1 pass, then 5 consecutive fails.
Against B355's branch, isolated repeated runs: 2 passes, 1 fail (out of 3).
```

Failure: `assert by_id[CAP_REUSE_SATISFIABLE]["requires_satisfiable"] is True` — `AssertionError: assert
None is True` (`tests/test_capability_queries.py:432`). The field is `None`, not `False` — this isn't
"satisfiability was computed and came out wrong," it's "satisfiability was never computed/set" for that
row on the failing runs.

The test's own vectors (`_V_DUP`, `_V_SAT`) are hardcoded/synthetic, not real embeddings — the real
embedding backend (sentence-transformers vs. fastembed, pre- vs. post-B355) is very unlikely to be the
actual cause, consistent with the flakiness appearing identically on both sides of that change. The `gw`
fixture uses `tmp_path` (`tests/test_capability_queries.py:107`) for a KuzuDB instance — unlike B351's
AF_UNIX socket-path issue, KuzuDB is file-based, not socket-based, so that specific mechanism doesn't
directly apply here, but a related "test isolation depends on filesystem state that isn't as isolated as
it looks" class of bug hasn't been ruled out either.

### Root Cause and Fix (2026-08-23)

**Not a race condition, not test isolation, not embedding-backend-related — a genuine Kùzu 0.11.3 engine
bug in list-comprehension evaluation over a NULL aggregate**, present in two of this file's five customer
queries.

Both `capability.reuse_candidates` (Q5, this card's original test) and `capability.permitted_paths` (Q1,
the second flaky test found during B354's verification) used the same idiom: collect a nullable property
across an `OPTIONAL MATCH`, then test it with `size(collected) = 0 OR NOT ANY(x IN collected WHERE x IS
NOT NULL)`. Reproduced directly against raw Cypher (bypassing `GraphGateway` and the test harness
entirely — see scratchpad `b358_repro2.py`/`b358_repro3.py` for the isolation scripts) with debug columns
exposing every intermediate value:

```
'agent/reuse-satisfiable', dep_superseded=None, sz=None, sz_is_zero=None,
    any_not_null=True,  requires_satisfiable=None   <- wrong, this run
'agent/reuse-satisfiable', dep_superseded=None, sz=None, sz_is_zero=None,
    any_not_null=False, requires_satisfiable=True   <- correct, this run
```

**`collect(dep.superseded_by)` deterministically returns the scalar `NULL` (not `[]` or `[NULL]`) when
the single `OPTIONAL MATCH`-ed row's collected property is itself null** — confirmed reproducing the same
way on every run, not itself the nondeterministic part. The nondeterminism is downstream:
**`ANY(x IN <NULL> WHERE ...)` — iterating a list-comprehension over a `NULL` list value — returns `True`
on some runs and `False` on others**, instead of the spec-correct answer (`NULL`, since Cypher's 3-valued
logic says any predicate evaluated over an unknown/null collection is itself unknown). This reads as the
engine treating an absent/NULL list's backing storage as if it were real memory to iterate — undefined
behavior, not merely wrong logic. `NULL OR <garbage boolean>` then resolves to a real `True`/`False` only
when the garbage happens to be `True`; when it's `False`, the whole expression stays `NULL`, which is
exactly the intermittent `None` this card originally reported. The identical mechanism explains Q1's
independent flake: `capability.permitted_paths` used the same `collect(c.access_mode)` -> `size(...)=0 OR
NOT ANY(...)` idiom for its `blocking_modes` check, and a `WHERE` clause treats a `NULL` result as "filter
this row out" — so on unlucky runs it silently dropped rows (including ones the test asserted must be
present), rather than surfacing a visible `None` field the way Q5 did. Same bug, different symptom because
one use sits in a `RETURN` projection and the other in a `WHERE` filter.

**Fix: eliminate the `ANY()`-over-possibly-NULL-list pattern entirely**, rather than special-casing NULL
around it (patching the boundary would leave the same landmine for the next query written against this
idiom). Both queries now use `count(CASE WHEN <condition> THEN 1 END)`, which Cypher/Kùzu defines to
always return a real integer (0 for "no matching rows," never NULL, regardless of whether the underlying
property is null) — this never constructs or iterates a NULL-valued list at all:

- `capability.reuse_candidates`: `collect(dep.superseded_by)` + `size(...)=0 OR NOT ANY(...)` ->
  `count(CASE WHEN dep.superseded_by IS NOT NULL THEN 1 END)` -> `requires_satisfiable = (num_superseded_deps = 0)`.
- `capability.permitted_paths`: `collect(c.access_mode)` + `size(...)=0 OR NOT ANY(...)` ->
  `count(CASE WHEN c.access_mode IS NOT NULL AND c.access_mode <> trust_tier THEN 1 END)` ->
  filter `WHERE num_blocking_modes = 0`.

Checked the rest of `campy/brain/hippocampus/graph/queries/*.py` for the same idiom before considering
this closed: `collect()` is used only in `capability.py`, and grepping for `size(collect`/`OR NOT ANY(`/
`OR ANY(` across the whole query layer found no other instances — these were the only two.

**This was a real production correctness bug, not only a test-flakiness problem.** Both queries are
customer-facing (Q1 `permitted_paths`, Q5 `reuse_candidates`) — under the same condition (the sole
optionally-matched dependency/constraint having a null value on the property being checked), production
callers could have silently gotten a wrong `requires_satisfiable` value or a target wrongly excluded from
`permitted_paths`, not just flaky test output.

**Verification:** isolated soak test bypassing pytest entirely, 60 runs against the fixed queries, 0
mismatches (`b358_repro3.py`) — versus ~90% failure per run against the original queries measured the
same way beforehand. Full `tests/test_capability_queries.py` run 20 times after the fix: 440/440 passed
(22 tests x 20 runs), 0 flakes.
