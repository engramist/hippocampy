# B358 - Flaky test_q5_verifies_requires_satisfiable (requires_satisfiable Returns None, Not True/False)

State: ready
Priority: P3

Plan: none yet.

### Problem

`tests/test_capability_queries.py::test_q5_verifies_requires_satisfiable` is flaky, confirmed unrelated
to any change in flight when found (B355's embedding backend migration). Found because the full test
suite run for B355 hit it once; re-running it in isolation showed it's genuinely non-deterministic
regardless of that change:

```
Against unmodified main, isolated repeated runs: 1 pass, then 5 consecutive fails.
Against B355's branch, isolated repeated runs: 2 passes, 1 fail (out of 3).
```

Failure: `assert by_id[CAP_REUSE_SATISFIABLE]["requires_satisfiable"] is True` — `AssertionError: assert
None is True` (`tests/test_capability_queries.py:432`). The field is `None`, not `False` — this isn't
"satisfiability was computed and came out wrong," it's "satisfiability was never computed/set" for that
row on the failing runs.

The test's own vectors (`_V_DUP`, `_V_SAT`) are hardcoded/synthetic, not real embeddings — the real
embedding backend (sentence-transformers vs. fastembed, pre- vs. post-B355) is very unlikely to be the
actual cause, consistent with the flakiness appearing identically on both sides of that change. The `gw`
fixture uses `tmp_path` (`tests/test_capability_queries.py:107`) for a KuzuDB instance — unlike B351's
AF_UNIX socket-path issue, KuzuDB is file-based, not socket-based, so that specific mechanism doesn't
directly apply here, but a related "test isolation depends on filesystem state that isn't as isolated as
it looks" class of bug hasn't been ruled out either.

### What it does (scope)

1. Reproduce reliably (loop the isolated test 10-20 times, both alone and alongside the rest of
   `test_capability_queries.py`, to see if it's timing-dependent, order-dependent, or purely random).
2. Investigate why `requires_satisfiable` comes back `None` on failing runs — trace the
   `capability.supersede_fact_entity` call (which retires `MCP_UNSATISFIABLE_DEP` right before the
   query) and the `capability.reuse_candidates` query itself for a race between the supersede write
   actually being visible and the subsequent read, or a Cypher query path that leaves the field
   unset/NULL under some condition instead of computing `False`.
3. Fix at the root (a real race condition, a missing await, a query that doesn't handle a specific case)
   rather than adding a retry/sleep to paper over the symptom.

### Dependencies

None — confirmed independent of B355 (reproduces identically before and after that change). Found
incidentally while verifying B355's full test suite run.

### Files to create/modify

- `tests/test_capability_queries.py` and/or whatever production code implements
  `capability.reuse_candidates` / `capability.supersede_fact_entity` — narrow down which side (test
  race vs. production logic bug) once reproduced reliably.

### Acceptance Criteria

- [ ] Reproduced reliably enough to know it's fixed, not just "didn't happen to fail this time" (matches
      this project's own standard from B351/B352: verify with a real repeated-run loop, not a single
      pass).
- [ ] Root cause identified and documented (race condition, missing await, query logic gap — whichever
      it turns out to be).
- [ ] Fixed at the root, not worked around with a retry or sleep.
