# B438 - [campy-benchmarks] Mock Client's _mock_constraints Leaks Across Suites in a Combined run_all.py Run, Inflating MemBench's Token Estimate Past Raw Size

State: ready
Priority: P2
Branch: fix/b438-mock-client-state-isolation
PR Target: main (in the sibling `campy-benchmarks` repo, not this one)

### Note on repo location

Same as B436: this lives in the sibling `campy-benchmarks` repo
(`mcp_client.py`), which has no remote/issue tracker of its own — filed
here per B381's precedent.

### Problem

`CampyMCPClient._mock_constraints` (and `_mock_memory`) is instance
state shared across every suite that runs on the same client instance.
`run_all.py --suite all` constructs **one** `CampyMCPClient` and passes
it to `run_locomo`, `run_memory_gym`, `run_membench`, and
`run_arc_bridge` in sequence. LoCoMo's and MemoryGym's `notify_turn`
calls populate `_mock_constraints` with their own unrelated fake
constraint text (Postgres migrations, auth token rotation, etc.).

When MemBench later calls `compile_context`, the mock handler (fixed in
B436) builds its `total_token_estimate` from
`list(self._mock_constraints.values())` — which by that point contains
leftover entries from the OTHER suites, not just MemBench's own
persona data. This inflates the estimated bundle size well past the
persona's actual raw conversation size.

### Evidence

Discovered while verifying B436's fix. Isolated run:

```
python3 run_all.py --smoke --suite membench
# MemBench │ Contradiction: 0.0 | Savings: 85.15%
```

Combined run:

```
python3 run_all.py --smoke --suite all
# MemBench │ Contradiction: 0.0 | Savings: 0.0%
```

Direct reproduction confirmed the mechanism: after running LoCoMo +
MemoryGym on a shared client, `_mock_constraints` held 4 unrelated
entries (Postgres/analytics/auth constraint text), and the subsequent
MemBench run measured `bundle_tokens_avg=337.0` against
`raw_tokens_avg=178.5` — a bundle **larger** than the raw conversation,
which `token_savings_pct`'s `max(0.0, ...)` clamp floors to 0.0%.

This was invisible before B436 because the old hardcoded
`"token_count": 420` mock value never varied with `_mock_constraints`
content at all — B436's fix (correctly estimating from the actual
mocked content, matching how the real bundle reflects real content)
is what exposed it.

### Fix

`_mock_constraints`/`_mock_memory` need per-suite (or per-persona)
isolation rather than living on the long-lived `CampyMCPClient`
instance shared across `run_all.py`'s whole `--suite all` run. Options:
a fresh `CampyMCPClient` per suite in `run_all.py`'s `main()`, a
`reset_mock_state()` method called between suites, or scoping the mock
constraint/memory stores by a suite or session prefix. Exact mechanism
is an open design question, not prescribed here — whichever approach is
chosen should keep mock mode's job (fast, no live daemon needed) while
making each suite's mocked memory genuinely independent, matching how
production sessions don't bleed into each other.

### Acceptance Criteria

- [ ] `python3 run_all.py --smoke --suite all` produces the same
      MemBench `token_savings_pct` as running `--suite membench` alone
      (mock state no longer leaks across suites).
- [ ] A regression check (script or lightweight test) proves this by
      running suites in at least two different orders and confirming
      each suite's result is order-independent.
- [ ] Work executed in branch `fix/b438-mock-client-state-isolation`, PR to `main`.

### Outcome

`run_all.py --suite all`'s per-suite results are trustworthy on their
own, not artifacts of whichever other suites happened to run first on
the same mock client instance.
