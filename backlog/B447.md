# B447 - Gated Consolidation Loop Intermittently Stalls for 90+ Minutes on Unpredictable Messages

State: ready
Priority: P0
Branch: TBD (investigation card — see recommended next steps before assigning a fix branch)
PR Target: main

### Note on origin

Found live, by direct observation, while executing
[B446](B446.md)'s real (non-`--smoke`) external benchmark re-run
against a freshly restarted daemon on current `main` (2026-09-22). Not
inferred from a stack trace or a test — caught mid-reproduction on a
production-like daemon process, with hard log evidence, and refined
over several hours of continued observation of the same live process.
This card was revised twice the same day as more evidence came in;
both revisions are kept below rather than silently edited away, since
the first version was already merged to `main` (PR #242) and linked
from [B446](B446.md) and `docs/benchmarks/post-cutover-kpis.md`.

### What's confirmed, as of the last observation (2026-09-22, ~19:22 local)

The Gated Consolidation Loop worker (`campy/brain_daemon.py`'s
`_loop_worker`, `~line 926`) has now been observed getting stuck
**twice** on the same daemon process, on unrelated content, separated
by hundreds of fast, healthy completions in between:

| # | Dequeued | Content | Resolved | Duration |
|---|---|---|---|---|
| 1 | `14:07:48` | `'Our service uses PostgreSQL 14 hosted on AWS RDS. Constraint: all tables must use UUID primary keys.'` (LoCoMo turn) | `15:44:13` | **1h 36m 25s** |
| 2 | `16:54:23` | `'Observation at Step 0: MysteryPath navigation sequence is: (0, 0) -> (0, 1) -> ...'` (MemoryGym turn) | still unresolved after **2h 28m** at last check | **≥2h 28m** |

Between the two: **406** messages processed normally, at a healthy
~10s/message average (`15:44:13` → `16:54:23`).

**This rules out "one-time cold-start tax that clears and never
recurs"** (the first correction's theory, below) — the second stall
happened hours after the daemon was fully warm and had already proven
it could process hundreds of messages quickly. The real behavior is an
**intermittent, so-far-unpredictable stall**, not a fixed startup cost.

### Investigation history (kept for anyone picking this up)

**Original version (now superseded):** described the worker as
*permanently* stuck ("Zero Completions in 11 Days") after observing
zero `[Loop] msg=` completions in 11 days of `daemon.log` across
multiple restarts, and the then-current message stuck for 48+ minutes
with no resolution yet.

**Correction #1:** continued observation found message #1 above
*did* resolve, after 1h36m, then the worker caught up and processed
406 more messages fine — revised the framing to "one-time ~96-minute
cold-start tax that then self-resolves."

**Correction #2 (current):** continued observation further found
message #2 above got stuck too, hours later, on unrelated content —
invalidating "self-resolves and stays healthy." Current framing:
intermittent, recurring, multi-hour stalls, trigger unknown.

**Ruled out, based on direct checks:**
- **Connection/fd exhaustion**: `lsof -p <daemon_pid> | grep -c 11434`
  held flat at **25** established (never-closed) Ollama connections
  across both stalls — not growing over time — and total open FDs
  (`218`) is nowhere near this host's `ulimit -n` (`1048576`). The
  25-connection leak is real and worth its own fix, but isn't large
  enough to explain a stall via resource exhaustion on its own.
- **A one-time lazy-singleton warm-up** (e.g. an embedding model
  loaded on first use): doesn't explain the second stall, which
  happened hours after the daemon was already warm.
- **A simple content-based trigger** (e.g. `"Constraint:"` phrasing
  routing into an expensive conflict-check path): message #2 has no
  such phrasing, so if content matters at all, it isn't that
  specific pattern — not fully ruled out as *a* factor, just not
  *this* one.
- **Full event-loop freeze**: unrelated MCP tool calls (`ask`,
  `current_truth`) kept completing normally throughout both stalls —
  only the dedicated consolidation-queue-consumer task is affected,
  not the whole daemon.

**Additional evidence (2026-09-22, ~19:35 local), narrows the search
space:** `netstat -an -p tcp | grep 11434` on all 25 established
`localhost:11434` connections shows **Send-Q and Recv-Q both `0` on
every single one** — no connection has data in flight or a pending
unacked response. This means those 25 connections are idle leftovers
from *already-completed* calls that were never closed (the leak itself
is real, see next-steps), not evidence of the currently-stuck task
(#2, still stuck at time of this check) waiting on an in-flight Ollama
HTTP response. Combined with the process's own CPU profile during the
stall (~3-6% CPU, non-zero but low — measured via two `ps -o time`
samples 10s apart: `39:19.73` → `39:20.26`, i.e. ~0.5s CPU burned per
10s wall), the stuck task is most likely blocked on something other
than an Ollama call: a database query/lock, an internal `asyncio`
primitive (`Lock`/`Semaphore`/another `Queue`), or a periodic
sleep-based retry loop (the low-but-nonzero CPU pattern is consistent
with a loop that wakes briefly on a timer, does a little work, then
sleeps again, rather than either a tight busy-spin or a fully blocked
`await` with zero CPU use). Worth checking `run_loop()`'s DB/gateway
calls (`GraphGateway.run`/`run_sync`) and any `Lock`/`Semaphore`
acquisitions before assuming another Ollama round-trip is the culprit.

**Still open**: what the two stuck messages have in common, if
anything. Needs step-level instrumentation (see below), not further
log-reading — this investigation has extracted what it can from
external observation alone.

### Root cause found (2026-09-23), via step-level instrumentation

Step-level timing instrumentation ([PR #244](https://github.com/engramist/hippocampy/pull/244))
was added to `run_loop()` and the daemon restarted. The restarted
process (a different daemon lifetime than the two stalls above — see
caveat below) was fed real and synthetic `notify_turn` traffic and left
running. Checking back after several hours found the daemon had, at
some point, stopped logging entirely (last log line `22:17:05` local)
and by the time this was checked the *process itself* had been
restarted by launchd at `04:45:55` with no crash trace — consistent
with the host machine sleeping overnight, not a B447 crash. That means
the specific stuck task from this run is gone, but it left one precise,
final data point before it disappeared:

Both entities were stored as new concepts, so `concept_ids` has 2
entries and `len(concept_ids) > 1` is true — meaning Step 7
(`write_co_occurs_with`) **must** execute next. Its completion log
(`step=step7_co_occurs_with`) never appears. This narrows the stuck
call to exactly one line: the `await _gateway(db).run("pathways.
unwind_co_occurs_with", ...)` inside `write_co_occurs_with()`
(`campy/brain/temporal_lobe/loop/step7_pathway.py:245`).

**Tracing that call to its actual mechanism, in
`campy/brain/hippocampus/graph/oxigraph_client.py`:**

```python
# line 879
self._lock = asyncio.Lock()
...
# line 1076
async def execute_write(self, sparql, params=None):
    async with self._lock:
        return await asyncio.to_thread(self.execute, sparql, params)
```

**`self._lock` is a single, global `asyncio.Lock` shared by every
write anywhere in the daemon** — not scoped per-query, per-node-type,
or per-caller. It's held for the *entire* duration of
`asyncio.to_thread(self.execute, ...)`, which runs the real SPARQL
`UPDATE` (`self.store.update(bound_sparql)`, a direct call into
`pyoxigraph`'s Rust/RocksDB-backed store) in a background thread —
**with no timeout of any kind.** If that native call is slow for any
reason, the lock stays held for exactly as long as it takes, and
**every other write anywhere in the daemon queues up behind it** —
this is a materially bigger blast radius than this card originally
described: it's not "the Loop's own queue backs up," it's "no write of
any kind, from any code path, can proceed while one write is slow."

This also **retroactively explains the earlier netstat evidence**
(§"Additional evidence" above): the 25 idle, no-pending-data Ollama
connections were never going to show anything, because the stuck call
was never waiting on an LLM at all — it was waiting on a native
Oxigraph/RocksDB call running in a worker thread. `execute_read()`
(no lock) staying fast throughout both stalls, while `ask`/
`current_truth` kept completing, is also now fully explained: reads
never contend with this lock at all.

**Suspected (not yet proven) trigger for why the write itself is
slow**: `pathways.unwind_co_occurs_with`'s SPARQL (`campy/brain/
hippocampus/graph/queries/pathways.py:146`) upserts RDF-star quoted-
triple metadata per pair (`<< ?a campy:CO_OCCURS_WITH ?b >>
campy:count ...`) with an `OPTIONAL` match against each pair's
existing quoted triple to decide create-vs-increment. This is already
flagged in the query's own docstring as "an unbounded supernode
feeder" (B283) capped at 45 pairs/message — but the cap limits *pair
count*, not *per-pair cost*, and RDF-star quoted-triple lookups may
not be as well-indexed in `pyoxigraph` as plain triple patterns,
especially against a store this large (recall: ~650MB of uncompacted
RocksDB WAL observed during this same investigation's daemon-restart
timing). This is a hypothesis from one observed instance, not a
confirmed universal trigger — some other `execute_write` call site
could equally be the culprit in a different stall.

**Caveat on certainty**: the process holding this stuck task died
(likely host sleep, not a crash) before a live stack trace could
confirm it was still inside `self.store.update()` at that exact
moment, rather than having completed and moved on to something else
unlogged. This is the strongest, most parsimonious reading of all
evidence gathered across both investigation sessions — not
100%-certain proof — but it is now precise enough to act on directly
(add a timeout, then watch whether stalls stop) rather than needing
another blind multi-hour observation cycle.

### The mechanism (why one slow item matters so much)

`_loop_worker` is a strict FIFO `asyncio.Queue` consumer with **no
per-item timeout**:

```python
while True:
    message_id, text, role, session_id, precomputed = await self._loop_queue.get()
    try:
        summary = await run_loop(...)
        print(f"[Loop] msg={message_id[:8]} entities=... concepts=...")
        ...
    except Exception as e:
        print(f"[Loop] Error processing message {message_id}: {e}")
    finally:
        self._loop_queue.task_done()
```

Because it's strict FIFO with no timeout, **one slow item blocks every
item behind it for exactly as long as that item takes** — 96 minutes
for message #1, 2h28m and counting for message #2. Every `notify_turn`
call anywhere in the system queues up behind whichever item is
currently stuck, silently (no error, no warning, nothing surfaced to
the caller — `notify_turn` itself still returns success).

`~/.campy/daemon.log.pre-b423b` (the 72MB backup preserved exactly at
the B423 log-rotation cutover, `2026-09-11 12:44`) shows **16,456**
successful completions before that point — the loop clearly used to
run at normal, healthy speed. Whatever causes these stalls is either a
regression introduced sometime after `2026-09-11`, or a symptom of the
graph having grown large enough since then to expose a pre-existing
scaling problem that wasn't visible on a smaller graph.

### Why this matters

This is very likely the actual, dominant reason [B446](B446.md)'s
fresh external-benchmark run still scored near-zero on LoCoMo/
MemoryGym/MemBench: every one of that run's four suites finished (per
the harness's own reported per-suite timings) well before `15:44:13`
(message #1's resolution), meaning every probe in that run executed
before the very first consolidation event of the daemon's uptime had
completed. A 0% score is exactly what that predicts.

This also matters well beyond benchmarking: any real user whose
message happens to queue behind a stuck one — apparently an
unpredictable, recurring event, not just a first-message-after-restart
risk — silently waits 90+ minutes (or longer; message #2's true
duration isn't known yet) with no indication anything is wrong, while
every one of their subsequent messages queues up behind it too.

### Recommended next steps

Step-level instrumentation (items 1-2 below, from the prior revision
of this card) is done and paid off — it directly produced the root
cause above. What's left is fixing it and confirming the fix:

1. **Add a per-write timeout in `OxigraphClient.execute_write()`**
   (`campy/brain/hippocampus/graph/oxigraph_client.py:1076-1078`):
   wrap `asyncio.to_thread(self.execute, ...)` in
   `asyncio.wait_for(..., timeout=N)` so one pathologically slow
   `UPDATE` can no longer hold the single global write lock — and
   therefore block every other write in the daemon — indefinitely.
   This is the highest-leverage fix: it bounds the *blast radius*
   regardless of whether the underlying slowness itself ever gets
   fixed. Needs a real decision on: what timeout value (the fastest
   normal writes observed here are sub-second; even a generous 30-60s
   would have caught both stalls far earlier), and what happens to a
   write that times out (retry once? drop and log loudly? surface the
   failure to the caller?) — a dropped write is a real data-loss risk
   worth thinking through, not just adding the timeout blindly.
2. **Investigate whether `pathways.unwind_co_occurs_with` specifically
   is slow at current graph scale** (`campy/brain/hippocampus/graph/
   queries/pathways.py:146`) — try running it directly against a copy
   of the live store with a realistic pair count and see how long it
   actually takes. If it's the RDS-star quoted-triple `OPTIONAL` match
   that's slow, consider whether `pyoxigraph`'s quoted-triple indexing
   needs help (e.g., a different upsert strategy that doesn't need the
   `OPTIONAL` lookup, or batching writes differently), or whether B283's
   existing 45-pair cap needs to be lower for large graphs.
3. **Reconsider the single global write lock as a design**, once the
   above is fixed: today literally every write in the daemon serializes
   through one `asyncio.Lock`, so *any* slow write (not just this one
   query) can reproduce this exact class of bug from a different
   trigger. A per-write timeout (item 1) is the immediate safety net;
   whether finer-grained locking is worth the complexity is a separate,
   bigger discussion — flagged here, not resolved.
4. If a live stack trace would still help confirm the exact stuck line
   with certainty: `sudo py-spy dump --pid <daemon_pid>` once a message
   is confirmed stuck — this session could not do so without the
   user's password.
5. Separately, fix the 25-connection Ollama leak found during this
   investigation — real (confirmed via `lsof`), but now confirmed
   *unrelated* to the stalls (the stuck call was never using an Ollama
   connection). Look at whatever constructs the daemon's Ollama-backed
   LLM client(s) (`campy/brain/llm/provider.py` and callers) for a
   client/session created per-call without `async with`/explicit
   `.close()`/connection-pool reuse.
6. Once a timeout (item 1) lands, re-run [B446](B446.md)'s external
   benchmark suite again over a long enough window to have a real shot
   at a recurrence — this is very likely the actual precondition for
   that card's own numbers to mean anything, more so than
   [B448](B448.md)'s harness-side gap.

### Acceptance Criteria

- [ ] `OxigraphClient.execute_write()` has a per-call timeout; a write
      that exceeds it fails loudly (logged, surfaced) rather than
      holding the global write lock forever.
- [ ] `pathways.unwind_co_occurs_with`'s actual cost at current graph
      scale is measured directly, not assumed — confirms or refutes it
      as the (or a) real trigger.
- [ ] The 25-connection Ollama leak is fixed (confirmed unrelated to
      the stalls, but still worth fixing on its own).
- [ ] Verified against a real daemon over a long enough window (hours,
      matching how this bug was actually found) that a recurrence
      either doesn't happen or is caught and bounded by the timeout.
- [ ] [B446](B446.md)'s external benchmark suite re-run after this
      fix, to get the real "after" numbers this was masking.

### Outcome

The Gated Consolidation Loop processes messages at a consistent,
bounded pace, and a slow or pathological message can no longer
silently stall every other user's memory consolidation for an
unbounded, unpredictable amount of time.
