# B447 - Gated Consolidation Loop Intermittently Stalls for 90+ Minutes on Unpredictable Messages

State: ready
Priority: P0
Branch: TBD (investigation card — see recommended next steps before assigning a fix branch)
PR Target: main

### Note on origin

Found live, by direct observation, while executing
[B446](B446.md)'s real (non-`--smoke`) external benchmark re-run
against a freshly restarted daemon on current `main` (2026-09-22). Not
inferred from a stack trace or a test — caught mid-reproduction on a
production-like daemon process, with hard log evidence, and refined
over several hours of continued observation of the same live process.
This card was revised twice the same day as more evidence came in;
both revisions are kept below rather than silently edited away, since
the first version was already merged to `main` (PR #242) and linked
from [B446](B446.md) and `docs/benchmarks/post-cutover-kpis.md`.

### What's confirmed, as of the last observation (2026-09-22, ~19:22 local)

The Gated Consolidation Loop worker (`campy/brain_daemon.py`'s
`_loop_worker`, `~line 926`) has now been observed getting stuck
**twice** on the same daemon process, on unrelated content, separated
by hundreds of fast, healthy completions in between:

| # | Dequeued | Content | Resolved | Duration |
|---|---|---|---|---|
| 1 | `14:07:48` | `'Our service uses PostgreSQL 14 hosted on AWS RDS. Constraint: all tables must use UUID primary keys.'` (LoCoMo turn) | `15:44:13` | **1h 36m 25s** |
| 2 | `16:54:23` | `'Observation at Step 0: MysteryPath navigation sequence is: (0, 0) -> (0, 1) -> ...'` (MemoryGym turn) | still unresolved after **2h 28m** at last check | **≥2h 28m** |

Between the two: **406** messages processed normally, at a healthy
~10s/message average (`15:44:13` → `16:54:23`).

**This rules out "one-time cold-start tax that clears and never
recurs"** (the first correction's theory, below) — the second stall
happened hours after the daemon was fully warm and had already proven
it could process hundreds of messages quickly. The real behavior is an
**intermittent, so-far-unpredictable stall**, not a fixed startup cost.

### Investigation history (kept for anyone picking this up)

**Original version (now superseded):** described the worker as
*permanently* stuck ("Zero Completions in 11 Days") after observing
zero `[Loop] msg=` completions in 11 days of `daemon.log` across
multiple restarts, and the then-current message stuck for 48+ minutes
with no resolution yet.

**Correction #1:** continued observation found message #1 above
*did* resolve, after 1h36m, then the worker caught up and processed
406 more messages fine — revised the framing to "one-time ~96-minute
cold-start tax that then self-resolves."

**Correction #2 (current):** continued observation further found
message #2 above got stuck too, hours later, on unrelated content —
invalidating "self-resolves and stays healthy." Current framing:
intermittent, recurring, multi-hour stalls, trigger unknown.

**Ruled out, based on direct checks:**
- **Connection/fd exhaustion**: `lsof -p <daemon_pid> | grep -c 11434`
  held flat at **25** established (never-closed) Ollama connections
  across both stalls — not growing over time — and total open FDs
  (`218`) is nowhere near this host's `ulimit -n` (`1048576`). The
  25-connection leak is real and worth its own fix, but isn't large
  enough to explain a stall via resource exhaustion on its own.
- **A one-time lazy-singleton warm-up** (e.g. an embedding model
  loaded on first use): doesn't explain the second stall, which
  happened hours after the daemon was already warm.
- **A simple content-based trigger** (e.g. `"Constraint:"` phrasing
  routing into an expensive conflict-check path): message #2 has no
  such phrasing, so if content matters at all, it isn't that
  specific pattern — not fully ruled out as *a* factor, just not
  *this* one.
- **Full event-loop freeze**: unrelated MCP tool calls (`ask`,
  `current_truth`) kept completing normally throughout both stalls —
  only the dedicated consolidation-queue-consumer task is affected,
  not the whole daemon.

**Additional evidence (2026-09-22, ~19:35 local), narrows the search
space:** `netstat -an -p tcp | grep 11434` on all 25 established
`localhost:11434` connections shows **Send-Q and Recv-Q both `0` on
every single one** — no connection has data in flight or a pending
unacked response. This means those 25 connections are idle leftovers
from *already-completed* calls that were never closed (the leak itself
is real, see next-steps), not evidence of the currently-stuck task
(#2, still stuck at time of this check) waiting on an in-flight Ollama
HTTP response. Combined with the process's own CPU profile during the
stall (~3-6% CPU, non-zero but low — measured via two `ps -o time`
samples 10s apart: `39:19.73` → `39:20.26`, i.e. ~0.5s CPU burned per
10s wall), the stuck task is most likely blocked on something other
than an Ollama call: a database query/lock, an internal `asyncio`
primitive (`Lock`/`Semaphore`/another `Queue`), or a periodic
sleep-based retry loop (the low-but-nonzero CPU pattern is consistent
with a loop that wakes briefly on a timer, does a little work, then
sleeps again, rather than either a tight busy-spin or a fully blocked
`await` with zero CPU use). Worth checking `run_loop()`'s DB/gateway
calls (`GraphGateway.run`/`run_sync`) and any `Lock`/`Semaphore`
acquisitions before assuming another Ollama round-trip is the culprit.

**Still open**: what the two stuck messages have in common, if
anything. Needs step-level instrumentation (see below), not further
log-reading — this investigation has extracted what it can from
external observation alone.

### The mechanism (why one slow item matters so much)

`_loop_worker` is a strict FIFO `asyncio.Queue` consumer with **no
per-item timeout**:

```python
while True:
    message_id, text, role, session_id, precomputed = await self._loop_queue.get()
    try:
        summary = await run_loop(...)
        print(f"[Loop] msg={message_id[:8]} entities=... concepts=...")
        ...
    except Exception as e:
        print(f"[Loop] Error processing message {message_id}: {e}")
    finally:
        self._loop_queue.task_done()
```

Because it's strict FIFO with no timeout, **one slow item blocks every
item behind it for exactly as long as that item takes** — 96 minutes
for message #1, 2h28m and counting for message #2. Every `notify_turn`
call anywhere in the system queues up behind whichever item is
currently stuck, silently (no error, no warning, nothing surfaced to
the caller — `notify_turn` itself still returns success).

`~/.campy/daemon.log.pre-b423b` (the 72MB backup preserved exactly at
the B423 log-rotation cutover, `2026-09-11 12:44`) shows **16,456**
successful completions before that point — the loop clearly used to
run at normal, healthy speed. Whatever causes these stalls is either a
regression introduced sometime after `2026-09-11`, or a symptom of the
graph having grown large enough since then to expose a pre-existing
scaling problem that wasn't visible on a smaller graph.

### Why this matters

This is very likely the actual, dominant reason [B446](B446.md)'s
fresh external-benchmark run still scored near-zero on LoCoMo/
MemoryGym/MemBench: every one of that run's four suites finished (per
the harness's own reported per-suite timings) well before `15:44:13`
(message #1's resolution), meaning every probe in that run executed
before the very first consolidation event of the daemon's uptime had
completed. A 0% score is exactly what that predicts.

This also matters well beyond benchmarking: any real user whose
message happens to queue behind a stuck one — apparently an
unpredictable, recurring event, not just a first-message-after-restart
risk — silently waits 90+ minutes (or longer; message #2's true
duration isn't known yet) with no indication anything is wrong, while
every one of their subsequent messages queues up behind it too.

### Recommended next steps (this needs real investigation, not more log-reading)

1. **Step-level timing instrumentation is the priority.** Add a
   `time.perf_counter()` bracket around each of `run_loop()`'s 9
   documented steps (`campy/brain/temporal_lobe/loop/orchestrator.py`
   — NER, verb-pattern relations, gist classification, schema.org
   routing, Ollama relation extraction, pattern matching, dual-scope
   candidate retrieval, contradiction arbitration, pathway update) and
   log each step's duration, deployed before the next restart, so the
   *next* stall self-reports which step it's in via `daemon.log`
   without needing a live profiler.
2. If a live stack trace is wanted instead of/alongside
   instrumentation: `sudo py-spy dump --pid <daemon_pid>` (or an
   equivalent async-stack dump) once a message is confirmed stuck —
   this session could not do so without the user's password. The
   current stuck message (#2, dequeued `16:54:23`) may still be stuck
   by the time this is picked up — worth checking before restarting
   the daemon and losing the live repro.
3. Separately, fix the 25-connection Ollama leak regardless of whether
   it's implicated in the stalls — it's real (confirmed via `lsof`)
   and worth closing on its own. Look at whatever constructs the
   daemon's Ollama-backed LLM client(s) (`campy/brain/llm/provider.py`
   and callers) for a client/session created per-call without
   `async with`/explicit `.close()`/connection-pool reuse.
4. Regardless of root cause: add a per-item timeout
   (`asyncio.wait_for(run_loop(...), timeout=...)`) to `_loop_worker`
   as a belt-and-suspenders fix so one slow/pathological message can't
   silently block every message behind it indefinitely, even before
   the underlying slowness is fully understood.
5. Once fixed (or at least once stalls are surfaced/logged so they're
   no longer silent), re-run [B446](B446.md)'s external benchmark
   suite again — this is very likely the actual precondition for that
   card's own numbers to mean anything, more so than
   [B448](B448.md)'s harness-side gap.

### Acceptance Criteria

- [ ] Root cause of the intermittent multi-hour stalls identified via
      step-level instrumentation or a live stack trace — not just "it's
      slow sometimes."
- [ ] The 25-connection Ollama leak is fixed or confirmed unrelated
      and tracked separately.
- [ ] A fix and/or a watchdog timeout lands so a stuck message can no
      longer silently block the queue for 90+ minutes.
- [ ] Verified against a real daemon over a long enough window (hours,
      matching how this bug was actually found) that a recurrence
      would be caught, not just a quick first-message check.
- [ ] [B446](B446.md)'s external benchmark suite re-run after this
      fix, to get the real "after" numbers this was masking.

### Outcome

The Gated Consolidation Loop processes messages at a consistent,
bounded pace, and a slow or pathological message can no longer
silently stall every other user's memory consolidation for an
unbounded, unpredictable amount of time.
