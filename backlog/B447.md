# B447 - Gated Consolidation Loop Worker Stalls Permanently on Its First Real Message — Zero Completions in 11 Days

State: ready
Priority: P0
Branch: TBD (investigation card — see recommended next steps before assigning a fix branch)
PR Target: main

### Note on origin

Found live, by direct observation, while executing
[B446](B446.md)'s real (non-`--smoke`) external benchmark re-run
against a freshly restarted daemon on current `main` (2026-09-22). Not
inferred from a stack trace or a test — caught mid-reproduction on a
production-like daemon process, with hard log evidence, not a guess.

### The finding

`campy/brain_daemon.py`'s `_loop_worker` (the Gated Consolidation Loop
consumer, `~line 926`) is a strict FIFO `asyncio.Queue` consumer:

```python
while True:
    message_id, text, role, session_id, precomputed = await self._loop_queue.get()
    try:
        summary = await run_loop(...)
        print(f"[Loop] msg={message_id[:8]} entities=... concepts=...")
        ...
    except Exception as e:
        print(f"[Loop] Error processing message {message_id}: {e}")
    finally:
        self._loop_queue.task_done()
```

`notify_turn`'s handler (`campy/brain/thalamus/tools/capture.py:358-362`)
enqueues **every** turn onto this same queue. Because the worker is a
single strict consumer with no per-item timeout and no way to skip a
stuck item, **one message that never returns from `run_loop()` and
never raises permanently blocks every message behind it, forever** —
the queue only ever advances via `task_done()` in the `finally` block,
which only runs after `run_loop()` resolves one way or the other.

**Direct evidence, gathered today against a live daemon:**

- `~/.campy/daemon.log` (uninterrupted, unrotated, covering
  2026-09-11 12:44 → now, 2026-09-22 20:45 — 11 days, multiple daemon
  restarts in between per `~/.campy/activity.log`'s `daemon`/`status`
  events) contains **`grep -c "\[Loop\] msg=" daemon.log` → `0`**.
  Zero successful consolidation-loop completions, across every restart,
  in 11 days.
- `grep -c "\[Loop\] Processing" daemon.log` → **`1`** — only one
  message has ever even been dequeued in that whole window: the very
  first real `notify_turn` call of *today's* fresh restart (started
  cleanly at 13:57 to rule out stale-process artifacts), logged at
  `2026-09-22 14:07:48,513`:
  `[Loop] Processing (user): 'Our service uses PostgreSQL 14 hosted on
  AWS RDS. Constraint: all tables must use UUID primary keys.'`
  (a LoCoMo benchmark scenario turn — unremarkable content, not a
  pathological input).
- `grep -c "\[Loop\] Error" daemon.log` → **`0`**. It never raised
  either — this is a genuine stall/hang, not a crash-loop (that was
  B434's bug, already fixed; this is a different failure mode on the
  same subsystem).
- At time of filing, **48+ minutes** after that single dequeue, the
  daemon process (pid confirmed via `ps`) is still alive, still
  burning real CPU (~8-14%, RSS slowly climbing then flat around
  220-240MB) — not deadlocked/frozen, but never reaching `task_done()`
  either. `~/.campy/daemon.log.pre-b423b` (the 72MB backup preserved
  when B423 added the size-rotating log handler, exactly at
  2026-09-11 12:44 — i.e. precisely where the current `daemon.log`
  begins) shows **16,456** successful `[Loop] msg=` completions before
  that point. **The stall's onset lines up with the B423 boundary**,
  though this card does not claim B423 itself caused it — could equally
  be coincidental timing with something else that landed the same day;
  flagged as the first thing to check, not a conclusion.
- Meanwhile, concurrent MCP tool calls (`ask`, `current_truth`, etc.
  from the B446 benchmark run) **kept completing normally** throughout
  the same 48-minute window (visible in `daemon.log` as regular `ask`/
  httpx completions every ~30-45s) — so this is not a full event-loop
  freeze, only the one dedicated consolidation-queue consumer task is
  stuck.
- Could not get a live stack trace to pinpoint the exact stuck
  `await` inside `run_loop()` — `py-spy dump` requires `sudo` on this
  macOS host and this session does not have the user's password; left
  for whoever picks this up, ideally on a host/account where `py-spy`
  (or an equivalent async-stack dump) can run without a permission
  prompt.

### Why this matters (impact, not just a curiosity)

This is the **core mechanism** the entire memory system is built
around — raw `notify_turn` content is supposed to flow through the
Gated Consolidation Loop to become structured, queryable Concepts/
Entities/Relations. If the very first real message after a daemon
restart permanently wedges this pipeline, **no consolidation happens
at all for the rest of that daemon's uptime**, silently (no error
surfaced to any caller — `notify_turn` itself returns success; only
the background consequence is missing). This is very likely the
actual, dominant reason [B446](B446.md)'s fresh external-benchmark run
still scored near-zero on LoCoMo/MemoryGym/MemBench even with B434's
crash fix, B436's token-key fix, and B438's mock-isolation fix all
confirmed merged and present — none of those fixes address a worker
that dequeues fine but then never finishes its first real unit of
work.

### Recommended next steps (not prescribed as a full fix — this needs real investigation)

1. Reproduce cleanly and get a live stack trace: run with `sudo py-spy
   dump --pid <daemon_pid>` (or `py-spy` via a launchd context that
   already has the needed entitlement) once a message is confirmed
   stuck, to find the exact `await` line inside `run_loop()`
   (`campy/brain/temporal_lobe/loop/orchestrator.py`) or one of its
   step helpers (`_store_concept`, `_reify_concept`,
   `_ensure_concept_exists`, `_store_relation`, etc.) where it's
   parked.
2. Add step-level timing/instrumentation to `run_loop()` (even a
   `time.perf_counter()` around each of its documented Steps 1-7)
   deployed to the next restart, so the *next* stall self-reports
   which step it's stuck in via `daemon.log`, without needing a live
   profiler at all.
3. Once the stuck step is identified, consider whether the real fix is
   (a) a bug in that step, or (b) the loop worker needs a per-item
   timeout (`asyncio.wait_for(run_loop(...), timeout=...)`) so one
   pathological message can't starve the whole queue forever even if
   the underlying slowness/hang can't be eliminated outright — a
   watchdog is a reasonable belt-and-suspenders addition regardless of
   root cause.
4. Once fixed, re-run [B446](B446.md)'s external benchmark suite again
   — this card's fix is very likely the actual precondition for that
   card's own numbers to mean anything.

### Outcome

The Gated Consolidation Loop actually consolidates more than one
message per daemon lifetime, and a single bad/slow message can no
longer silently and permanently disable memory consolidation for
every other user of that daemon process.
