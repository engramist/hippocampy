# B354 - Footprint/Swap-Aware Memory Watchdog (vmmap-Based, Alongside PR #86)

State: shipped (PR #95), then caused a live restart-loop incident the same day — see "Incident: Live
Restart Loop Under Real Concurrent Traffic" below. Fixed by substantially widening the defaults
(300s/4000MB/6 breaches, from 90s/500MB/3); the design itself (relative-to-baseline, `vmmap`-based) was
not the problem, the calibration was. Implemented as designed: relative-to-startup-baseline growth
threshold (not absolute), `vmmap`-based (not RSS/psutil/`ru_maxrss`), debounced, degrades gracefully on

shared `_vmmap_parsed()` structured parser so there's one `vmmap`-parsing implementation, not two. Five
unit tests. Full test suite passed except two confirmed pre-existing, unrelated flakes in
`tests/test_capability_queries.py` (tracked in [B358](backlog/B358.md)). See PR #95 for the original diff
and the incident section below for the calibration fix.
Priority: P2

Plan: none yet — write one before starting. See "Design requirements" below for what it must satisfy;
this card intentionally does not prescribe exact code, since the threshold/debounce constants need to be

### Problem

[PR #86](https://github.com/engramist/hippocampy/pull/86) added a periodic self-restart (24h, +/-10%
jitter) as a safety net against B342's allocator-fragmentation growth. It's a reasonable, industry-
standard baseline (matches gunicorn/uWSGI's `max_requests` worker-recycling pattern) — but it's *time*-
based, not *footprint*-based, so it can't react faster than 24h if growth is ever unusually fast (e.g.
under heavier real usage than the synthetic harness tested), and it can't tell the difference between "a
totally normal 24h of uptime" and "something is actually wrong right now."

An external plan (reviewed in B353) proposed replacing PR #86 with a memory-threshold watchdog. The
underlying idea (react to actual memory state, not just a clock) is sound, but two of its concrete
proposals were wrong for reasons directly established by this project's own B342 investigation:

1. **It must not key off plain RSS (or `psutil`'s `uss`).** B342 spent five-plus PRs establishing that
   RSS is actively misleading on this platform — after an `asyncio.to_thread`-triggered macOS compression
   event, RSS can drop to looking completely healthy (attempt 3 saw it fall to 240K-590K KB) while the
   *real* footprint (resident + swapped) keeps climbing. A watchdog gated on RSS would systematically fail
   to trigger exactly when it's most needed. The correct signal is `vmmap -summary <own PID>`'s "Physical
   footprint" line — already proven correct and already used throughout B342 (see `_vmmap_swap_summary` in
   `brain_daemon.py`, added in [PR #84](https://github.com/engramist/hippocampy/pull/84) for the SIGUSR1
   diagnostic). Reuse that parsing logic directly rather than re-deriving it.
2. **A hardcoded absolute threshold is dangerous if it doesn't account for which baseline is currently in
   effect.** The externally-proposed 350MB threshold would trip almost immediately and constantly under
   the *current* (pre-B355) ~1.9-2.1GB baseline — creating exactly the kind of restart-loop failure mode
   the external plan's own round-1 (incorrectly) claimed already existed in PR #86. Any absolute threshold
   this card ships must either (a) be deployed only after B355 lands and be set relative to *that*
   baseline, or (b) be expressed relative to the daemon's own measured startup baseline (e.g., "footprint
   has grown by more than N MB since the fresh-start reading taken at startup") rather than a hardcoded
   absolute number — option (b) is more robust to either baseline and is the preferred design unless
   there's a good reason to choose (a) instead.

### What it does (scope)

1. Add a periodic watchdog task to `BrainDaemon` (same pattern as `_periodic_checkpoint` and
   `_periodic_restart`) that samples `vmmap -summary <own PID>`'s physical footprint on an interval (e.g.
   every 60-120s — cheap, ~50-200ms per call based on B342's own measurements, but not free, so don't
   sample every few seconds).
2. Compute growth relative to a startup baseline reading (taken once, early in `BrainDaemon.start()`),
   not an absolute hardcoded number — see design requirement 2 above.
3. Debounce: require multiple consecutive breaches (e.g. 3, spaced by the sample interval) before acting,
   not a single sample — a single `vmmap` reading during a real, transient write burst should not trigger
   a restart.
4. On confirmed breach: log clearly (what triggered it, the actual footprint value, how it compares to
   baseline) and call the same `self.shutdown()` path `_periodic_restart` already uses — clean db close,
   socket unlink, launchd `KeepAlive` brings up a fresh process. Do not invent a second shutdown path.
5. Runs **alongside** `_periodic_restart`, not replacing it — if this watchdog's `vmmap` call ever fails
   (tool unavailable, permission issue, unexpected output format), it should degrade to doing nothing
   (log and skip that check), not crash the daemon or disable the time-based backstop.
6. Config: add threshold/interval/debounce-count knobs under a new `[watchdog]` (or similar) `campy.toml`
   section, following the existing `[checkpoint]`/`[daemon]` section documentation style (see those
   sections for the expected level of comment detail — this project documents *why*, not just *what*, in
   config file comments).

### Design requirements (non-negotiable, given B342's findings)

- Must read physical footprint via `vmmap`, never `psutil` RSS/USS or `ru_maxrss`.
- Must not use a hardcoded absolute threshold incompatible with whichever baseline is currently live —
  prefer relative-to-startup-baseline growth.
- Must debounce, not act on a single sample.
- Must degrade gracefully if `vmmap` is unavailable, never crash the daemon over a failed diagnostic read.
- Must not replace or remove `_periodic_restart` — this is additive.

### Dependencies

Should land **after** B355 (embedding migration) if using an absolute threshold, to avoid tuning against
a baseline that's about to change. If using the relative-to-startup-baseline design (preferred), order
relative to B355 matters less, but testing this card's actual trigger behavior is easier and more
representative once B355 has landed and the "normal" baseline is small and stable.

### Files to create/modify

  `start()`, reusing `_vmmap_swap_summary`'s parsing logic (extend it to return a structured value rather
  than a formatted string, or add a small structured variant alongside it — don't parse `vmmap` output
  twice in two different ways in the same file).
- `campy.toml` — new config section, documented to the same standard as `[checkpoint]`/`[daemon]`.

### Incident: Live Restart Loop Under Real Concurrent Traffic (2026-08-22)

While restarting the live daemon to prepare for an ARC-side smoke test (unrelated to this incident
directly — the smoke test itself hadn't started yet), the ARC-side peer session reported the daemon's PID
had already changed twice within ~7 minutes and its fresh-restart baseline was already 2.3-2.4GB, far
above the ~1.2GB expected. Checking `~/.campy/daemon.log` confirmed the real problem: **the watchdog was
firing repeatedly, restarting the daemon roughly every 1-2 minutes in a tight loop**, each cycle logging
`Footprint growth confirmed over 3 consecutive checks (current ~2355-2457 MB, +1229-1331 MB above
~1126 MB baseline) -- initiating restart`.

**Root cause: the shipped defaults (90s check interval, 500MB growth threshold, 3 consecutive breaches)
were calibrated against B342's synthetic, single-session harness (~1MB/cycle growth over hours), never
validated against real concurrent multi-session load.** This daemon is shared — at the time of the
incident, both this session and an active ARC_AGI-side Claude Code session were hitting it simultaneously
with real embedding calls, KuzuDB writes, and journaling/capture traffic. Under that load, footprint grew
from baseline to +1.2GB within roughly 3 x 90-second checks (4.5-15 minutes depending on exact timing) —
trivially and immediately crossing a 500MB bar that was sized for a much slower, single-workload growth
rate. The watchdog's design (relative-to-baseline, `vmmap`-based, debounced) was not the problem — the
calibration was: a threshold meant to catch genuinely pathological growth was instead firing on normal,
if intense, real-world usage, and firing on a fresh baseline every single restart meant it could never
settle, only loop.

**This is worse than the problem it was meant to solve.** A restart loop interrupts in-flight requests
far more often than the original 24h time-based restart ever would, and risks recreating the exact
`Brain: OFFLINE` symptom (a request landing during a restart window) at a much higher frequency than
before this card shipped.

**Immediate fix, applied live before any code change:** disabled the watchdog (`[watchdog] enabled =
false`) via `campy.toml` and restarted once cleanly to stop the loop, confirmed stable, then substantially
widened the parameters and re-enabled:

```
check_interval_seconds:          90   -> 300   (5 min, not 90s)
growth_threshold_mb:             500  -> 4000  (4GB, not 500MB)
consecutive_breaches_required:    3   -> 6     (30 min of sustained breach, not 4.5 min)
```

These numbers are a conservative correction based on the one real data point this incident produced
(+1.2-1.3GB within a few minutes under heavy real dual-session load), not a rigorously re-derived
threshold — the goal was to move fast and stop active disruption, with a wide enough margin that normal
heavy usage (even by two concurrent sessions) shouldn't trip it, while still catching genuinely runaway,
sustained growth well before the original incident's multi-GB/multi-week-uptime scale. **This has not
been validated against another real incident of legitimate runaway growth — it is a safer default, not a
proven-correct one.** If it ever fires again, that itself is useful signal and should be investigated
before assuming the threshold needs raising further; if real usage patterns turn out to legitimately need
even more headroom, that's a sign the relative-to-baseline design may need a smarter baseline (e.g. a
rolling window rather than a single startup reading) rather than just a bigger number.

**Lesson for future watchdog-style thresholds in this codebase:** a threshold calibrated against an
isolated, single-workload synthetic harness is not validated for a shared, multi-session production
environment until it's actually been run under one. This project's own investigation discipline (B311,
B342) repeatedly found that isolated harnesses under-represent real-world behavior in surprising ways —
this incident is another instance of that pattern, just in a shipped mitigation rather than a diagnostic
finding.
