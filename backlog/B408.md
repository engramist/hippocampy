# B408 - Stale-Base Guard: Make Silent Reverts Unmergeable

State: ready
Priority: P0

### Problem

Five times in one day, a PR's diff proposed **deleting merged work** purely because
its branch predated a merge to `main`. Every instance was caught by a reviewer
diffing against current `main` — a check that is easy to skip, because **nothing in
the diff looks wrong**. The additions are all correct; the deletions are invisible
unless you go looking for them.

Recorded incidents:

| PR | Would have reverted |
|---|---|
| #167 (B400) | the entire `## Open Research Questions` section (57 lines), merged ~1 hour earlier |
| #174 (B396) | **5004 lines** across 7 modules — all of B392, B393, B394 (444 queries) |
| #163 (B387) | stale-base deletions of the design spec and B401 |
| #162 (B389) | stale base, caught before merge |
| #172-era rebases | repeated across the wave-2 batches |

The near-miss on #174 is the shape of the risk: 132 correct additions, and a silent
revert of three PRs merged the same day. A reviewer skimming for translation quality
would have approved it.

### Why this keeps happening

Agents branch from `main`, work for 20–40 minutes, and open a PR. `main` moves during
that window because other agents are merging concurrently. This is inherent to the
fan-out pattern — it is not carelessness, and telling agents to "remember to rebase"
has already failed five times.

The repo has branch protection, but it does **not** require branches to be current
before merge. `gh pr merge --admin` bypasses whatever is configured.

### Scope

1. **CI check** (`scripts/check_branch_current.py` or equivalent): fail a PR when its
   merge-base with `main` is not `main`'s HEAD. Message must say plainly: *"rebase
   onto main — your diff currently proposes deleting N lines of merged work"*, and
   compute that N so the cost is visible rather than abstract.
2. **Prefer the platform control if it is sufficient.** GitHub's "Require branches to
   be up to date before merging" does exactly this. Evaluate whether enabling it is
   simpler than a custom check — **but verify how it interacts with `--admin`**, which
   this project uses routinely and which may bypass it. If admin bypasses it, the CI
   check is required, because the bypass path is the one actually in use.
3. **Revert-detection as a backstop**: fail when a PR deletes lines from a file it does
   not declare as in-scope. This catches the general class, not just staleness.

### Explicitly NOT in scope

- Do not change the fan-out workflow itself. Concurrent branches are the point.
- Do not disable `--admin`. It is deliberately used for the review-count requirement
  when checks are green.

### Acceptance Criteria

- [ ] A PR whose base is not `main` HEAD fails CI with an actionable message naming the
      line count at risk.
- [ ] Demonstrated against a **reconstructed** stale-base scenario — ideally #174's
      exact one — proving it would have caught 5004 deletions.
- [ ] Interaction with `gh pr merge --admin` explicitly tested and documented. If admin
      bypasses the platform setting, say so and rely on the CI check.
- [ ] Wired in alongside `check_cypher_ratchet.py`.

### Related

Pairs with **B406** (schema conformance guard). Both convert a bug class that has
repeatedly reached review into one that cannot merge. B406 catches queries referencing
schema that does not exist; B408 catches PRs deleting work that does.

### Outcome

Silent reverts become impossible to merge, and the fan-out pattern stops depending on
a reviewer remembering to diff against current `main`.
