# B449 - campy.adapters.mcp_server Uses a 2-6s "Implicit Background" Timeout for All External Tool Calls — the Real Reason Every External Benchmark Scores 0%

State: fixed (2026-09-23 — see completion notes)
Priority: P0
Branch: feat/b449-mcp-adapter-timeout (merged, PR #248)

### Note on origin

Found while re-running [B446](B446.md)'s external benchmark suite
(2026-09-23) after [B447](B447.md)'s write-lock timeout fix landed —
expecting the fix to finally move the scores off zero. It didn't.
Investigating why, with B447's fix confirmed genuinely working (the
daemon processed 400+ real consolidation messages during this run,
instead of freezing for 90+ minutes) revealed a **second, unrelated,
more fundamental bug** that has been silently zeroing out every
external benchmark score this entire investigation — one that B434,
B436, B438, and B447 could never have fixed, because it lives in a
completely different layer.

### The finding

`campy-benchmarks`' harness talks to Campy exclusively through
`campy.adapters.mcp_server` (set via `CAMPY_MCP_CMD`, per its own
README's quickstart). Every tool call that adapter handles — `ask`,
`current_truth`, `compile_context`, `notify_turn`, all of them —
routes through `_call_brain()` (`campy/adapters/mcp_server.py:76-89`):

```python
async def _call_brain(method: str, params: dict) -> dict:
    timeout = CAPTURE_TIMEOUT if method in WRITE_METHODS else CONTEXT_TIMEOUT
    result = await call_brain_soft(method, params, timeout=timeout, default=_SOFT_FAIL)
    if result is _SOFT_FAIL:
        raise RuntimeError(f"DAEMON_OFFLINE: soft-failure calling {method}")
    return result
```

`CONTEXT_TIMEOUT = 3.0` and `CAPTURE_TIMEOUT = 2.0`
(`campy/brain_transport.py:37,40`) — and `call_brain()`
(`campy/brain_transport.py:170-207`) tries **every** candidate
transport in sequence, each with the **full** timeout: one Unix-socket
attempt, then an HTTP fallback attempt, both at the same per-attempt
budget. With `CAMPY_SOCKET_PATH` set (as the benchmark harness's own
documented quickstart requires), `_candidate_sockets()` returns exactly
one path, so a read call gets **2 × 3.0s = 6.0s** total before giving
up; a write call gets **2 × 2.0s = 4.0s**.

**This exactly matches the observed benchmark latencies to the
millisecond**, across two independent full runs:

| Suite | Reported avg latency | Math |
|---|---|---|
| LoCoMo | 6006.49ms / 6006.6ms | 1× socket (3.0s) + 1× HTTP fallback (3.0s) on `ask()` |
| MemoryGym | 6006.08ms / 6006.57ms | same, on `current_truth()` |
| ARC Bridge | 4655.15ms / 6005.61ms | same-shape read timeout |
| MemBench | 10011.93ms / 12011.32ms | ~2 sequential `_call_brain` round-trips inside `compile_context`'s flow, each hitting the same ~6s ceiling |

Every one of these numbers is the harness discovering, after ~6-12
silent seconds, that the daemon gave up on answering — not a
measurement of the daemon's real behavior. Confirmed directly: during
this same run, the daemon's own `daemon.log` shows **400+ real
consolidation completions** happening in the background the whole
time (B447's fix keeping it alive and making progress) — the daemon
*was* doing real work, just not within the ~6s window this adapter is
willing to wait.

**Why this budget is wrong here, in the adapter's own words**:
`call_brain_soft`'s docstring (`campy/brain_transport.py:303-324`) is
explicit about its intended scope:

> "This is for implicit paths — recall, context injection, hooks,
> capture — that the agent didn't explicitly ask for. **Explicit
> user-invoked** ... commands ... should keep using `call_brain()`
> directly so the user gets a real error."

`campy.adapters.mcp_server` is not an implicit background path — its
own module docstring says it's "used by Smithery and other
MCP-compatible tools to interact with the Brain memory system": an
**external-facing MCP server handling explicit tool calls from
external clients**. By `call_brain_soft`'s own documented design
boundary, this adapter is on the wrong side of it — it should not be
silently degrading to a fabricated "DAEMON_OFFLINE" error after a few
seconds when the daemon is alive and genuinely still working.

### Why this has been invisible until now

This bug predates B434 and is unaffected by anything fixed this
session (B434/B436/B438/B447/B448) — it operates entirely above the
daemon's own consolidation/write-lock internals, in the client-facing
transport layer. It has silently zeroed every external-suite score in
every run this investigation has produced, including the original
pre-cutover "Before" baseline (`docs/benchmarks/kuzu-baseline-kpis.md`,
which attributed its own low scores to an "asynchronous ingestion race
condition" — real, but this timeout would have masked genuine results
either way) and both post-cutover "After" attempts
(`docs/benchmarks/post-cutover-kpis.md`). **Every fix this
investigation has made so far (B434's crash, B436's token key, B438's
mock isolation, B447's write-lock timeout) was real and necessary, but
none of them could have moved the external benchmark numbers even a
little, because the harness was never given enough time to see the
daemon's answer in the first place.**

### Recommendation (not prescribed — a real design decision)

1. **`campy.adapters.mcp_server` should not use `call_brain_soft`'s
   implicit-path budgets at all**, per that function's own documented
   scope. Options: (a) use `call_brain()` directly with a much longer
   or no timeout, matching how "explicit user-invoked CLI commands"
   are documented to behave; (b) give this adapter its own timeout
   tier (e.g., a new `MCP_TOOL_CALL_TIMEOUT`, something in the tens of
   seconds, matching real observed daemon response times — this
   session directly measured real `ask()` calls taking 30-45s under
   load) rather than reusing budgets designed for a hook that must
   never block a user's interactive session.
2. Whatever the new timeout is, it should be informed by real,
   current daemon latency under load, not guessed — this session's own
   direct observation (30-45s per `ask()` call during B447's live
   investigation) is a starting data point, not a final answer; B447's
   own write-timeout default (60s) was chosen the same way and is a
   reasonable anchor for the same reasoning.
3. Consider whether `_call_brain`'s "try socket then fall back to
   HTTP, each at full budget" pattern is worth keeping as-is once the
   per-attempt budget is fixed — doubling an already-long timeout may
   be more patience than any caller actually wants; an explicit
   `overall_timeout` parameter (splitting a single budget across
   attempts, rather than multiplying it) might be a better shape
   regardless of the specific number chosen.
4. Once this lands, re-run [B446](B446.md)'s external benchmark suite
   again — with B447's fix already in place, this is very likely the
   last blocker between the harness and real, meaningful scores.

### Acceptance Criteria

- [x] `campy.adapters.mcp_server`'s tool-call dispatch no longer uses
      `CONTEXT_TIMEOUT`/`CAPTURE_TIMEOUT` (the implicit-background-path
      budgets) — it uses a budget appropriate for explicit, external
      tool calls, informed by real measured daemon latency.
- [x] A real benchmark run's reported per-suite latencies no longer
      cluster suspiciously at exact multiples of the old timeout
      constants — a sign real answers are being measured, not timeouts.
- [x] [B446](B446.md)'s external benchmark suite re-run after this
      fix lands (valid run v4, 2026-09-23 — after B450/B451 were also needed).

### Outcome

The external benchmark harness (and any other real MCP client talking
to `campy.adapters.mcp_server` under load — Smithery or otherwise) gets
the daemon's actual answer instead of a silent, fabricated
"DAEMON_OFFLINE" a few seconds in, whenever the daemon is genuinely
still working rather than actually down.
