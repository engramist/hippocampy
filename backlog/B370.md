# B370 - tests/test_schema.py Can Poison sys.modules["kuzu"] for the Rest of the Session

State: ready
Priority: P3

Plan: none yet.

### Problem

Found live 2026-08-29 while verifying B369 didn't regress anything: `pytest tests/test_schema.py
tests/test_arc_mechanic_memory.py -q` fails 4 of `test_arc_mechanic_memory.py`'s tests with
`AttributeError: 'NoneType' object has no attribute 'has_next'` inside `KuzuClient.execute_write`
(`campy/brain/hippocampus/graph/kuzu_client.py:164`) — but the exact same file passes clean (30/30)
run alone, and `test_arc_mechanic_memory.py` passes clean (10/10) run alone. Confirmed this is
**pre-existing on unmodified `main`** (reproduced via `git stash` back to a clean checkout, identical
failure) — not caused by B369's schema/tool changes.

Root cause: `tests/test_schema.py`'s own `_stub_kuzu()` (lines ~20-33):
```python
def _stub_kuzu():
    if "kuzu" not in sys.modules:
        _kuzu = types.ModuleType("kuzu")
        class _Conn:
            def execute(self, *a, **kw): return None
        _kuzu.Connection = _Conn
        sys.modules["kuzu"] = _kuzu
```
This only stubs `kuzu` if it's *not already imported* — a leftover accommodation from when kuzu (a
compiled C extension) wasn't installable in some test environment. In this environment kuzu **is**
installed, so the stub is normally skipped once something else imports the real module first. But if
`test_schema.py` happens to be the *first* file in a given pytest invocation to touch `kuzu` at all
(a subset run, `pytest -k`, a differently-ordered collection, an IDE "run this file" workflow), the
stub gets installed into `sys.modules["kuzu"]` — and nothing in this file ever removes it afterward.
Every subsequent test file's `import kuzu` (directly, or transitively via
`campy.brain.hippocampus.graph.kuzu_client`) then gets the fake, always-returns-`None` module instead
of the real compiled library, for the rest of that pytest process.

This didn't show up in this session's full `pytest tests/ -q` runs (2197 passed earlier today) because
alphabetically many other files touch the real `kuzu` before `test_schema.py` runs, so the stub
condition (`"kuzu" not in sys.modules`) is already false by the time `test_schema.py` imports. It's
latent, not fixed — a differently-ordered subset run (exactly what this session's own B369 verification
did) still triggers it.

### What it does (scope)

1. Give `_stub_kuzu()` a teardown: use `monkeypatch.setitem(sys.modules, ...)` (pytest's own
   auto-reverting mechanism) instead of a bare module-level `if "kuzu" not in sys.modules: ...` with no
   corresponding removal — or better, restructure so the stub is scoped to only the specific mock-DB
   tests in this file that actually need it (`_make_mock_db`-based tests), via a fixture with proper
   setup/teardown, rather than a bare module-level side effect that runs at import time and never
   reverts.
2. Verify the fix by reproducing the exact failing combination from this card (`pytest tests/test_schema.py
   tests/test_arc_mechanic_memory.py -q`) before and after, confirming it goes from failing to clean.
3. Check whether any other test file in this codebase does the same "stub a module at import time,
   conditionally, with no teardown" pattern — this class of bug (per this project's own history with
   B360's ambient-daemon-dependency and B316's sys.modules-eviction-without-restore pattern in
   test_web.py's own comments) has shown up more than once; worth a quick grep
   (`grep -rn "sys.modules\[" tests/`) rather than assuming this is the only instance.
