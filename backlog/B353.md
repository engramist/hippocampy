# B353 - PARENT: Campy Memory Footprint Reduction Initiative

State: both active child cards done (2026-08-22). B355 (embedding migration, PR #93) measured a
228.1MB fresh-start footprint, down from ~1.9-2.1GB (~8-9x reduction) — the highest-leverage change for
the stated "feels light" goal. B354 (footprint watchdog, PR #95) shipped as a relative-to-baseline safety
net alongside PR #86's existing time-based restart. B356 remains deliberately deferred (verified not
relevant at current data scale). This initiative's core work is complete; B356 stays open per its own
documented trigger condition, and B357/B358 (incidental findings from this work) are tracked separately.
Priority: P1

Plan: this is a parent/umbrella card. It has no implementation steps of its own — it exists to hold the
full context, decision history, and rationale that all child cards (B354, B355, B356) depend on, so
nobody re-derives or re-litigates any of this later. Read this card fully before touching any child card.

### Why this card exists

B311 and B342 (both still open, both linked below) investigated *why* `brain_daemon.py`'s memory behaves
the way it does — real, deep, multi-week technical work. But partway through, the user asked a sharper,
more important question than "what's the root cause": **"we need to solve the memory gain issue so that
campy stays 'light' — people hate memory hogging apps, and won't use them — we need campy to be 'light'
and usable."** (verbatim, 2026-08-22). That's a product/UX goal, not a debugging goal, and it reframes
what actually matters here. This card exists because B311/B342's own investigation-card format isn't the
right place to hold a cross-cutting strategic decision — those cards are about *root-causing a specific
observed anomaly*, not about *what to actually build in response to it*.

### The reframe: two different problems, only one of which matters for "feels light"

B311/B342's investigation was almost entirely about **growth over time and worst-case blowup** — the
daemon eventually degrading after days of continuous uptime, reaching the original incident's extreme
(5.4GB RSS, 99GB physical footprint, `Brain: OFFLINE`). That's real, and it's now mitigated: [PR
#86](https://github.com/engramist/hippocampy/pull/86) added a periodic self-restart (24h, +/-10%
jitter), which — per B342's own extrapolation (~a week of continuous uptime to reach the original
incident's scale, given the synthetic harness's aggressive load) — gives roughly a 7x safety margin.

But that mitigation does **not** touch the number that actually determines whether Campy *feels* light:
**steady-state baseline footprint, ~1.2-2GB, present from the moment the daemon starts, every single
time.** Most users will never run this daemon continuously for a week — normal sleep/reboot cycles
restart it far more often than 24h anyway. What they *will* see, constantly, is Activity Monitor (or
`top`, or a memory-usage complaint from a teammate) showing a background daemon sitting at over a
gigabyte. That's the thing that reads as "memory hogging app" and drives people to stop using a tool,
independent of whether it would ever actually blow up.

**This is the single most important framing decision in this card: the growth/blowup problem
(B311/B342, already mitigated) and the baseline-size problem (this initiative) are different problems,
and the baseline problem is the one that actually determines whether the stated goal is met.** B342's
own py-spy profiling and repeated `vmmap` sampling throughout the investigation confirmed the ~1.2-2GB
fresh-start baseline is dominated by the PyTorch/`sentence-transformers` embedding stack, not KuzuDB (see
the KuzuDB verification below) and not anything Python-level (gc counts stay flat throughout).

### External plan review — what happened, and why it matters for trusting the child cards

The user had Gemini review B342 and propose a solution. That review, and its correction, is directly
relevant to how the child cards below are scoped, so it's recorded here rather than lost in chat history.

**Round 1 (Gemini's original plan, `campy_memory_optimization_plan.md`)** proposed: migrate to
`fastembed`/ONNX, bound KuzuDB's buffer pool, replace PR #86 with an RSS-threshold watchdog
(`MemoryWatermarkGuard`), and some codebase-hygiene fixes. Reviewed against the actual codebase before
accepting any of it — **five confirmed factual errors**, not just style nitpicks:

1. **`torchvision` isn't a dependency at all** — checked `pyproject.toml`, nothing there. Fabricated.
2. **The claimed "PR #86 uses `ru_maxrss`, causing infinite restart loops" bug does not exist.**
   `_periodic_restart` (`brain_daemon.py`) is a pure `asyncio.sleep()` + `shutdown()` timer — it reads no
   memory metric at all. `ru_maxrss` only appears in the unrelated, on-demand SIGUSR1 diagnostic
   (B343/B344, extended for swap visibility in [PR #84](https://github.com/engramist/hippocampy/pull/84)),
   which never triggers a restart. The plan used a bug that isn't real to justify replacing working code.
3. **Port 7800 is not a broken link.** It's `[mission_control].base_url` — a genuinely separate,
   intentional panel service (B15). The daemon's own port (7799) was never wrong.
4. **The `brain_daemon.py` consolidation direction was backwards.** The plan said consolidate into
   `campy/brain_daemon.py`. [B345](backlog/B345.md) — this project's own card, based on checking the
   *live process's actual command line* — found the **top-level** file is the one running in production.
   Following the plan's direction would have made the daemon's real entry point the dead copy.
5. **Phase 2's KuzuDB code bypassed the actual `KuzuClient` wrapper entirely**, calling raw
   `kuzu.Database(...)` instead of the class every other line of this codebase actually uses.

**Round 2 (Gemini's corrected plan, after reviewing the above)** fixed all five and improved the
embedding-migration hardening (explicit same-model-parity option, or an explicit gated `campy reembed
--confirm` if actually upgrading models). But its "corrected" footprint-aware watchdog code had **its own
new bug**: the macOS branch of `get_physical_footprint_mb()` defines a `task_vm_info` ctypes struct for
the real `phys_footprint` field and then **never calls it** — it silently falls through to
`psutil...memory_info().uss`, which has the exact same blind spot as RSS (neither includes
compressed/swapped pages). The "fix" for the RSS-lies problem didn't actually fix it. Caught before any
of this shipped.

**Why this history is in the parent card, not just chat:** two independently-run passes of an
LLM-generated plan, reviewed against this specific codebase, produced five and then one more concrete,
checkable errors. That's not a knock on using external review — round 2 genuinely was much better than
round 1, and several of its ideas (same-model fastembed migration, KuzuDB bounding as future-proofing)
survived scrutiny and are implemented via the child cards below. But it's the reason every claim below is
marked as either "verified" (with the actual command/test that verified it) or "not yet verified" —
nothing in the child cards should be taken on the strength of an external plan's say-so alone.

### Verification work done before any implementation

**KuzuDB buffer pool default — verified, refutes bounding it as relevant to the current problem.**
`kuzu.Database.__init__`'s own docstring confirms `buffer_pool_size` "Defaults to ~80% of system memory"
when left at `0` — that part of both plan rounds was accurate. But an isolated test (bare
`kuzu.Database()`, no schema, no embedding model loaded at all) showed a footprint of **68.2MB right
after opening, 77.6MB after a trivial write+read** — nowhere near 80% of this machine's ~31GB RAM, and
nowhere near the ~1.9-2.1GB baseline seen throughout B342's testing. This confirms the "~80% of RAM"
figure is a **lazy ceiling, not an eager reservation** — for a small graph, it costs almost nothing. By
elimination, this further confirms the embedding stack, not KuzuDB, is the dominant baseline contributor.
See B356 for what this means for whether to still bound it.

**fastembed embedding parity — verified, clears the gating question for B355.** Ran a real parity test
(`b342_embedding_parity_test.py`, scratchpad) comparing the current production backend
(`sentence-transformers/all-MiniLM-L6-v2` via PyTorch) against `fastembed`'s ONNX conversion of the
*same* model (`qdrant/all-MiniLM-L6-v2-onnx`, confirmed present in fastembed's own model catalog under
the identical model name), against 200 real, diverse sentences pulled from this project's own
`campy/data/GistSeedExamples.md` (not generic filler text). Result: **per-sentence cosine similarity of
1.000000 (min=max=mean, std=0.0) across all 200 sentences**, and **100% top-10 retrieval overlap with
exact rank order match** across 15 randomly-chosen queries against the full corpus. This is a cleaner
result than expected (normal PyTorch-vs-ONNX-Runtime kernel differences were expected to show up as
~0.99-0.999 similarity, not a clean 1.0) — genuinely close to perfect parity, not merely "close enough."
Caveat, stated plainly: this tested real diverse short-to-medium prose, not extreme edge cases (near the
256-token truncation limit, code snippets, non-English text) — not directly tested, though the clean
result on diverse real text is a reasonable basis for confidence it generalizes.

### Decisions made (binding for child cards unless a child card explicitly revisits one with new evidence)

1. **Migrate the embedding backend to `fastembed`/ONNX, same model only** (`sentence-transformers/all-
   MiniLM-L6-v2` via its ONNX conversion) — approved, given verified parity. See B355. **Explicitly NOT**
   approved: upgrading to a different model (e.g., `bge-small-en-v1.5`) as part of this initiative — that
   is a separate, much bigger, deliberate decision requiring a real re-embedding migration
   (`campy reembed --confirm`), out of scope here.
2. **Add a footprint/swap-aware memory watchdog**, reusing the already-proven `vmmap`-based approach from
   PR #84 (not `psutil` RSS, not the broken ctypes stub from Gemini's round 2) — approved. See B354. Runs
   **alongside**, not instead of, PR #86's time-based restart — belt and suspenders, consistent with how
   cautiously this whole investigation has treated the live daemon.
3. **KuzuDB buffer pool bounding is deferred, not implemented now** — verified not to address the actual
   baseline problem at current data scale. See B356 for the future-proofing case and when to revisit it.
4. **`brain_daemon.py` duplicate consolidation is not re-litigated here** — B345 already investigated
   this and correctly identified the top-level file as canonical; that finding stands, this initiative
   does not touch it.
5. **Port 7800 is not a bug** — it's Mission Control's own intentional base URL. No action, anywhere.
