### Problem

The current bootstrap script works from a source checkout, but users still need to clone the repo first. The desired user experience is a single command that bootstraps Campy on a new machine, installs the package, starts the daemon, registers available clients, and tells the user what succeeded.

### What This Card Does

Creates a hosted/public bootstrap installer path suitable for:

```bash
curl -fsSL https://raw.githubusercontent.com/djs54/hippocampy/main/scripts/bootstrap.sh | bash
```

The script should be safe, idempotent, version-aware, and transparent. It should install from the package path created by B236, not from a mutable source checkout unless explicitly requested with a development flag.

### Dependencies

- B236 complete or at least a validated local package artifact
- B231 complete - existing source bootstrap, doctor, and repair behavior

### Acceptance Criteria

- [x] `scripts/bootstrap.sh` is shellcheck-clean where shellcheck is available, and `bash -n` clean everywhere. `bash -n` passes. `shellcheck` is not installed in the verification environment, so that half is unverified rather than confirmed passing.
- [x] Bootstrap rejects unsupported Python versions with an actionable message. Confirmed by reading Step 2: exits 1 with `"Python >= 3.12 not found. Install Python 3.12+ from https://python.org and try again."` when no candidate interpreter qualifies.
- [ ] Bootstrap creates or uses an isolated install location (`pipx`, `uv tool`, or managed venv) without writing into system Python. **REAL BUG** — see below. The pipx install itself *is* isolated, but the script's own verification step frequently can't find it, causing the whole run to fail or silently fall back to a stale/wrong install.
- [ ] Bootstrap is idempotent: running it twice does not duplicate Codex, Claude, VS Code, launchd, or skill config. **UNVERIFIED** — no automated test actually runs a real (non-dry-run) bootstrap twice and diffs client config state; only `--dry-run` idempotency is tested (`tests/test_installer_idempotency.py`).
- [x] Bootstrap never deletes `~/.campy/brain.db`, journals, logs, or user wiki/manual notes. Confirmed by reading the full script: no `rm -rf` touches `.campy` or `brain.db` anywhere.
- [ ] Bootstrap starts or repairs the daemon and then runs `campy doctor`. **ORDER IS REVERSED** from what's described: Step 6 runs `campy doctor --repair` and Step 7 (separately) runs `campy start` — doctor is run *before* the daemon start step, not after. Minor, but the card's own acceptance language doesn't match the implementation.
- [ ] Bootstrap registers Codex, Claude Code, Claude Desktop, and VS Code when present, and reports skipped clients clearly. Delegates entirely to `campy install` (Step 5); not independently re-verified here since B237's own bug (below) prevents even reaching a trustworthy Step 5 on a fresh machine via the pipx path.
- [x] Bootstrap can run in `--dry-run` mode and print planned actions without mutating the machine. Confirmed: `bash scripts/bootstrap.sh --dry-run` runs clean, prints `DRY RUN`, and (per `tests/test_bootstrap_clean_home.py::test_bootstrap_dry_run_does_not_create_files`) creates no files under a clean `HOME`.
- [x] Bootstrap supports `--dev-source PATH` for local development installs without making that the public default. Confirmed present and used for testing below; not the default path (pipx is default when present).
- [ ] README contains the final one-line command plus a safer inspect-first variant. **UNMET** — `grep -n "curl -fsSL|bootstrap.sh" README.md` finds nothing. README's Quickstart/Install sections only reference `pipx install hippocampy` and the old `scripts/install.sh` (source-checkout installer). `docs/homebrew-install.md` even claims *"see the main README Quickstart and `scripts/bootstrap.sh`"* — but that content was never actually added to the README, so that cross-reference itself is broken.

### Re-verification Notes (2026-08-03)

**Confirmed real bug: bootstrap.sh Step 4 fails on a genuinely fresh machine via its own preferred (pipx) path.**

Repro (`scripts/bootstrap.sh --dev-source dist/hippocampy-0.1.0-py3-none-any.whl --no-start --no-register`, run with `HOME` pointed at an empty temp dir and `PATH` stripped down to a plain system PATH with no pre-existing `campy`, simulating a real first-time machine):

```
==> Step 3: Installing HippoCampy package...
  installed package hippocampy 0.1.0, installed using Python 3.12.13
  These apps are now available
    - campy
    - campy-daemon
  ✓ Installed from local source
==> Step 4: Verifying campy CLI...
  ✗ campy CLI not found in PATH after install
  ✗ Try: export PATH="<temp-home>/.campy/venv/bin:$PATH"
EXIT CODE: 1
```

Root cause, read directly from `scripts/bootstrap.sh`:
- When pipx is present (the script's first-choice/preferred branch), the package installs correctly into an isolated pipx venv — confirmed by inspecting the temp `HOME`: `<temp-home>/.local/pipx/venvs/hippocampy/bin/campy` exists and reports `Python 3.12.13` (correct, isolated, in-spec).
- But pipx's bin dir (`~/.local/bin`) is not automatically on `PATH` — `pipx ensurepath` is never called, and the script's own pipx-install output literally warns *"is not on your PATH environment variable ... Run `pipx ensurepath`..."*.
- Step 4's verification logic is: `command -v campy` (fails — not on PATH) → else check `$CAMPY_VENV_DIR/bin/campy` where `CAMPY_VENV_DIR="$HOME/.campy/venv"`. That path is **only ever populated by the "no pipx/uv" managed-venv fallback branch**, never by the pipx branch. So after a pipx install, Step 4 has no correct path to check and hard-fails with `exit 1`, aborting before agent registration, daemon start, or `campy doctor` ever run.
- On *this* dev machine, the bug is normally masked: there's a pre-existing, unrelated real pipx install of `hippocampy` at `/Users/djshelton/.local/bin/campy` (built against Python 3.14.3, itself outside the supported 3.12–3.13 range) left over from earlier development. Because that stale entry is already on `PATH`, `command -v campy` in Step 4 finds it — so the script "succeeds," but it's silently verifying and then running `campy install` / `campy doctor --repair` / `campy start` against the **wrong, stale, unsupported-Python install**, not the fresh one it just performed in the isolated temp `HOME`. This was caught by running `scripts/validate_one_click_install.sh --use-temp-home --skip-daemon --package dist/hippocampy-0.1.0-py3-none-any.whl` for real, which reported `Python Version FAIL 3.14.5 (3.12-3.13 required)` and `Daemon FAIL` — genuinely confusing output that looks like a normal partial-install case but is actually this PATH-shadowing bug.
- Stripping the stale PATH entry to simulate a truly first-time machine (no `campy` ever on `PATH` before) reproduces the harder failure above: **immediate `exit 1` at Step 4**, before the script ever reaches agent registration or daemon start.

This means: on any machine that (a) has never had `campy` on `PATH` before and uses the pipx path (the script's own preference), OR (b) has a stale/older `campy` already on `PATH` from a previous attempt, the one-line bootstrap either aborts outright or silently operates on the wrong install. This directly undermines the "isolated install" and "idempotent" acceptance criteria, and it is exactly the class of problem this audit round was created to catch (cf. B278) — a script that looks complete from its own printed checkmarks but fails a real end-to-end run.

A real fix would need Step 4 to resolve the actual pipx bin directory (e.g. `pipx environment --value PIPX_BIN_DIR`, defaulting to `$HOME/.local/bin` when pipx was the branch taken) and check there directly, rather than relying solely on `command -v` / the venv-only fallback path — and probably also call `pipx ensurepath` or explicitly export the resolved bin dir onto `PATH` for the rest of the script's own run (`campy install`, `campy doctor --repair`, `campy start` all use bare `campy` later). This is a behavior change to the installer's core verification logic, not a mechanical one-liner, so it was documented here rather than fixed inline.

**Second, independent, unmet AC:** README never received the `curl -fsSL .../bootstrap.sh | bash` one-liner this card exists to ship. `docs/homebrew-install.md` already assumes it's there and links to it, so that doc is also quietly broken until this is fixed.

**What did hold up under real execution:**
- `bash -n scripts/bootstrap.sh` — clean.
- `bash scripts/bootstrap.sh --dry-run` and `--help` — both work, exit 0, correct output.
- `pytest -q tests/test_bootstrap_script.py tests/test_installer_idempotency.py tests/test_doctor_cli.py tests/test_setup_cli.py` — **39 passed**, real (non-mocked) execution. Note these tests only cover static/dry-run behavior — none of them execute a real, non-dry-run bootstrap install end to end, which is exactly the gap that let the Step 4 bug ship undetected.
- Never-deletes-brain.db guarantee — confirmed by direct code read, no dangerous `rm -rf` present.
