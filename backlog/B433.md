# B433 — `basal_ganglia.frustration_get_*` SPARQL Never Returns an Embedding, So Avoidance-Cluster Detection Always Finds Zero Clusters

**Status:** Open
**Found by:** B427 batch 2 (migrating `tests/test_basal_ganglia_real_kuzu.py` off `KuzuClient`
onto `OxigraphClient` — 2 of 7 tests failed: `detect_frustration_clusters()` found 0 clusters
even with 2 identical-embedding, high-salience `Concept`/`Decision` nodes seeded, well above
`min_cluster_size=2`).
**Severity:** High — `detect_frustration_clusters` (Basal Ganglia's avoidance-learning sweep,
`campy/brain/basal_ganglia/frustration_clusters.py`) is live-reachable from the sweep loop and
can never synthesize an avoidance Procedure against the shipped engine, silently (no error,
`errors == 0`).

## Root cause

`campy/brain/hippocampus/graph/queries/basal_ganglia.py`'s `basal_ganglia.frustration_get_concept`
/ `_decision` / `_constraint` NamedQueries each carry a `sparql=` body with:

```sparql
OPTIONAL { ?n campy:embedding ?emb }
```

This is dead code on Oxigraph: `OxigraphClient.write_node()` deliberately never asserts
`FLOAT[384]` columns as RDF triples (spec §5 — "FLOAT[384] embeddings are never written to RDF
... use `vector_store.VectorStore` instead"; enforced defensively in `literal_for()`, which
raises if ever called for `FLOAT[384]`). Embeddings live exclusively in the separate
sqlite-vec-backed `vector_store`, addressed by URI. The `OPTIONAL` clause above can therefore
never bind `?emb` — confirmed directly:

```python
rows = await gw.run("basal_ganglia.frustration_get_concept", floor=1.3)
# -> [{'id': 'fc-c1', 'name': 'x', 'description': 'x', 'emb': None, 'salience': 1.5}]
```

`frustration_clusters.py`'s `detect_frustration_clusters()` filters `if row.get("emb") and
node_id not in seen_ids:` — every row is silently dropped for lack of an embedding, so
`all_nodes` stays empty (or under `min_cluster`), and the function returns `(0, 0)` — zero
procedures synthesized, zero errors reported — for every real call, regardless of how much
genuinely high-salience, clusterable data exists.

## Why this went undetected

Same shape as B430/B431/B432: `tests/test_basal_ganglia.py` (the always-run suite) uses a
hand-rolled `MockDB` that never validates real query results, and
`tests/test_basal_ganglia_real_kuzu.py` (this bug's own regression suite, B277) only ever ran
against real `KuzuClient` — where `n.embedding` genuinely is a queryable node property — so
this defect had no way to surface until the B427 engine swap.

## Suggested approach

Embeddings need to be hydrated from `vector_store` after the SPARQL identifies candidate node
URIs, the same way `OxigraphClient.fts_search()` / `vector_search()` already do (`hydrate via
self.vector_store.get_vector(uri)`). Two shapes to choose between:

1. Drop `?emb` from the three `sparql=` bodies entirely and add a Python post-processing step
   in `gateway.py`'s Oxigraph dispatch (or in `frustration_clusters.py` itself, if it already
   has direct client access) that looks up each returned node's embedding via
   `db.vector_store.get_vector(uri)` and attaches it to the row before returning.
2. Replace `sparql=` with `sparql=None` and a dedicated Python handler (matching capability.py
   Q5's `reuse_candidates` pattern) that does the salience filter + embedding hydration in one
   pass directly against `store.quads_for_pattern()` / `vector_store`.

Given three near-identical queries share the exact same defect, prefer whichever shape lets the
fix be written once and reused across `_concept`/`_decision`/`_constraint`, rather than
triplicating it. This is a small, well-scoped, non-security-relevant fix (unlike B431/B432) —
likely does not need its own design checkpoint, but should still assert real cluster formation
end-to-end (not just that the query returns a non-null embedding) since that's the actual
regression this card exists for.

## Scope note

`tests/test_basal_ganglia_real_kuzu.py` was otherwise fully migrated to `OxigraphClient` as
part of B427 batch 2 (5 of 7 tests pass cleanly — the maturity-lifecycle and RPE-persistence
tests, which don't depend on `frustration_get_*`). The 2 failing tests
(`test_creates_procedure_with_salience_score_from_concept_cluster`,
`test_creates_distilled_from_edge_to_decision_source`) are left failing/xfail in that PR,
referencing this card, rather than blocking the whole file's migration — they'll pass once
