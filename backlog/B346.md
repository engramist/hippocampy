# B346 - Fix Dead Port 7800 in Campy MCP Tool Response Links

State: ready
Priority: P2

Plan: none yet.

### Problem

During B342's investigation (2026-08-21), calling `mcp__campy__current_truth` against a live daemon
returned results whose `memory_link` and `panel_url` fields pointed at
`http://127.0.0.1:7800/memory/...` — but `lsof -iTCP -sTCP:LISTEN -P` on that same machine at that
same time confirmed **only port 7799 was listening**, on the exact PID the MCP call was talking to.
Every link Campy's own tools hand back to a caller for "click through to see this in the dashboard" is
currently dead — a 404/connection-refused if anyone actually follows one.

**Root cause identified, not just the symptom:** `campy.toml` has two separate port-bearing config
keys — `[web] port = 7799` (the real, actually-bound Memory Control Panel port, confirmed via
`web/server.py`'s startup code) and `[mission_control] base_url = "http://127.0.0.1:7800"` (B15's
"Deep-Link Handoff (Chat → Memory Control Panel)" feature, with an explicit comment: `# Mission
Control — deep-link panel_url base (B15)`). The `memory_link`/`panel_url` generation code is reading
`[mission_control] base_url` instead of `[web] port` — and nothing in this environment actually listens
on 7800, so either B15's Mission Control panel was never fully stood up as its own service, or the
link-generation code should simply be pointing at `[web] port` instead (both are Memory Control
Panel links per the returned field names, not obviously two different UIs).

### What it does (scope)

1. Confirm which of the two config keys is *supposed* to govern `memory_link`/`panel_url`: read
   `backlog/B15.md` (Deep-Link Handoff) to understand whether Mission Control was meant to be a
   genuinely separate service/port from the Memory Control Panel, or the same UI referenced by two
   different config names for historical reasons. Check whether anything anywhere in the codebase
   actually starts a service bound to `[mission_control] base_url`'s port — if nothing does, Mission
   Control as a separate listener was likely never completed, and `[web] port` is the only real
   candidate today.
2. Fix the link-construction site (grep for `memory_link` and `panel_url` across
   `campy/brain/thalamus/` and `campy/brain/mcp_engine/`) to point at whichever config key is
   determined to be correct in step 1 — most likely `[web] port`, unless step 1 finds Mission Control
   is a real, intentionally-separate, just-not-yet-wired-up service, in which case the fix is to stand
   that service up (a larger scope — file as a follow-up rather than silently expanding this card if
   that's the finding).
3. Check whether this is a single occurrence or a systemic pattern — grep more broadly for the literal
   string `7800` across `campy/` to see if other hardcoded references to the wrong port exist elsewhere
   (config defaults, docs, other tool response formatters).
4. Add a regression test: call a tool that returns a `memory_link`/`panel_url` (e.g. `current_truth`)
   against a `create_app`-backed test instance configured with a non-default port, and assert the
   returned link's port matches the configured port, not a hardcoded value — this is the kind of thing
   that will silently drift again without a test pinning it.
