# B459 - Conversation Evidence Drops the Statements That Supersede the One It Found

State: fixed (2026-10-03; confirmed on the real model 2026-10-04, all criteria met)
Priority: P1

### Problem Statement

Found by campy-benchmarks' LoCoMo fixture (2026-10-02), `--repeat 3` with
all-MiniLM-L6-v2 and llama3.1:8b: `p_21_active`, "What is the current
required tool for tracing?", was answered "Jaeger standalone" in every run.
Jaeger was the first of three values (Jaeger, then Zipkin, then
OpenTelemetry), and the final message said "do NOT use Jaeger standalone or
Zipkin". The lexical scorer and the LLM judge both failed it.

`--trace-context` showed a 34-token bundle: "Constraint for tracing: we use
Jaeger standalone." and an unrelated monitoring line. Neither superseding
statement was in it. campy-benchmarks' `diag_conversation_stage.py` replayed
the conversation stage (`GraphGateway._bundle_conversation`, B454) on the
kept store and matched the traced bundle exactly:

| message | cosine | query words | result |
|---|---|---|---|
| Constraint for tracing: we use Jaeger standalone. | 0.511 | 1 | picked (vector hit) |
| Update: Jaeger standalone is deprecated; migrate tracing to Zipkin. | 0.265 | 1 | dropped |
| Final decision: ... strictly use OpenTelemetry OTel for tracing ... | 0.274 | 1 | dropped |

Root cause: both superseding statements sat just under the 0.30 similarity
floor, so they could only enter as lexical-only hits, and a lexical-only hit
needed two distinct query content words. But "tracing" was the only query
word any message contained: "current", "required" and "tool" occur nowhere
in the store, so two could never match. The rule exists so that one shared
common word is not evidence; it counted words without asking whether they
were specific.

The failure is systematic, not a near miss: a statement that replaces a value
names several values ("X has been replaced by Y; do NOT use X or Z"), so it
is longer and embeds further from a short question than the short original
statement does. The stage favoured the first thing said about a topic over
what replaced it. `p_20_active` (serialization) passed only because its
Update message scored 0.302, just over the floor.

### What It Does (Scope)

A lexical-only hit is also evidence when it contains the query's **anchor**
word: the rarest query content word that any stored message contains, when
the vector search also found that word in one of its top `limit` hits.

- **Rarest** (by Message document frequency, `VectorStore.document_frequencies`):
  the most specific word the question shares with memory. A common query word
  ("current") stays non-evidence on its own.
- **Corroborated by the vector search**: rarity alone is a property of the
  store, not of the topic. In the LoCoMo store "active" is as rare as
  "database", and without this check "Redis ... is now the active cache"
  would join a database bundle. Top vector hits of any role count here: they
  only decide which word is on topic; assistant text is still never evidence
  itself (ISSUE-024).

The two-word rule is unchanged. No threshold was tuned, and the 0.30 floor
is unchanged: lowering it would fit this fixture and admit noise everywhere
else.

Not changed, considered:

- **Following the supersession chain** (pull in newer user messages that
  share a picked message's distinctive words). No observed failure needs it
  after this fix, and "same topic" is better answered by the graph than by
  word overlap. Revisit if a superseding statement that shares no query word
  is missed.
- **`p1_current_db`** ("What is our active production database engine and
  version?" answered "Primary database"). Not fixed here and not this cause:
  no user message contains any of the question's words ("CRITICAL UPDATE:
  We have completely migrated from PostgreSQL 14 to PostgreSQL 16...", cosine
  0.253, no lexical match), and the only vector hits are assistant turns. The
  bundle's one item is the entity "Primary database", with no value attached.
  A vocabulary gap, to be looked at in the graph: separate card.

### Real-model confirmation (2026-10-04)

`--isolated --repeat 3` with all-MiniLM-L6-v2, llama3.1:8b and the gemma4:26b
judge, on main after #269, compared with the 2026-10-02 baseline:

- `p_21_active`: fail -> pass in all three runs, the only probe whose
  verdict changed. LoCoMo judge accuracy 0.9286 -> 0.9643 (27/28), identical
  in every run; the remaining failure is `p1_current_db` (out of scope above).
- MemoryGym 100%, MemBench 1.0, ARC 1.0: unchanged.
- `p5_hs256_rejection` failed the lexical scorer in one run of three
  (`negative_without_grounding`). Not a B459 regression: all three answers
  said no and cited the "do NOT accept HS256 tokens" constraint, and the
  judge passed all three. That answer used none of the probe's grounding
  words; the fixture now counts "not accept(ed)" (campy-benchmarks #9).
