# B308 - Archive-Move HNSW Rebuild Mechanism (B285 Path B)

State: not started — filed 2026-08-04 as a follow-up to B285's scope-alignment pass. Requires an architecture decision before implementation, not just a coding pass.
Priority: P3

Plan: none yet — needs a design pass before an implementation plan is written.

### Problem

B285 (Archived-Node HNSW Index Hygiene) shipped archived-ratio telemetry, adaptive fetch headroom, and a visibility warning log when a table's archived ratio crosses threshold — but the actual index rebuild trigger stays permanently disabled by design. `campy/brain/brainstem/sweep.py::_index_hygiene` computes the ratio and logs a warning, but never calls `db.rebuild_vector_index(...)`, because doing so wouldn't actually help.

B285's own Step 0 capability probe (`kuzu_client.py::rebuild_vector_index` docstring) confirmed against the real pinned kuzu==0.11.3 build:
- Deleting a row removes it from HNSW index query results.
- **Updating an indexed embedding property is not supported.**
- A drop/recreate rebuild re-indexes every row still present in the table, archived or not.

That rules out both cheap options: nulling the embedding on archive (blocked — can't update an indexed embedding property), and plain rebuild-in-place (rebuild doesn't exclude rows that are still in the table). The only mechanism that actually removes archived vectors from the index is physically moving archived rows into a parallel node table (e.g. `ConceptArchive`) that carries no vector index at all — B285's plan calls this "Path B" and explicitly says not to implement it unilaterally, since it touches several subsystems that currently assume archived nodes live in the same table as active ones:

- **Resurrection** (`_resurrect_archived` in `campy/brain/brainstem/sweep.py`) currently finds resurrection candidates via `vector_search` over the same table, filtered post-hoc by `archived = true`. Moving archived rows out means resurrection has to search a different (non-indexed) table — likely a numpy/brute-force cosine scan instead, since the archive table would have no HNSW index.
- **MergeEvent rollback** and any other code path that references an archived node by its original table + primary key would need to know to look in two places.
- **`explore_graph`** traversal and any other code that does `MATCH (n:{table})` unlabeled or with an archived filter would silently stop seeing archived nodes at all, or need a second query against the archive table.

### What This Card Should Do (once designed)

1. Design the archive-move mechanism: which tables get parallel `<Table>Archive` twins, what the move operation looks like (transactional? best-effort with a reconciliation sweep?), and how every consumer of archived rows (resurrection, rollback, any explicit `archived = true` query) is migrated to look in the right place.
2. Decide whether the archive-ratio threshold should trigger the move automatically (sweep-driven) or require an explicit operator action for the first implementation, given the blast radius.
3. Only after the design is settled: implement the move, migrate `_resurrect_archived` to a non-indexed scan of the archive table, wire the sweep's already-shipped `_index_hygiene` warning into an actual `rebuilt: True` action, and add real-Kuzu integration tests (insert N nodes, archive M, trigger the move, verify the index no longer returns archived rows and resurrection still works).
