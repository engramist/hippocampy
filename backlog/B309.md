### Problem

ARC_AGI's 2026-08-07 strategic review (A175-A179) shipped five client-side changes to how the ARC agent uses the graph as a world model — entity identity, transition persistence, causal rules, value-of-information experiment selection, and cross-game transfer. All five are implemented, unit-tested, and live-verified against the real MCP server from the ARC_AGI side. But **none of their behavioral improvements can reach live gameplay yet**, because every new/changed server-side piece they depend on is still missing:

- `arc_perceive_state` never writes a `MOVED_BY` edge (A175)
- `arc_record_transition` / `arc_get_entity_history` don't exist (A176)
- `arc_record_rule` / `arc_get_rules_for_action` don't exist (A177)
- `arc_get_transferred_rules` doesn't exist (A179)

Confirmed directly against the running daemon (not assumed): calls to `arc_record_rule` and `arc_get_transferred_rules` both return `{"error": {"code": -32000, "message": "Unknown method: ..."}}`. The ARC-side client code already degrades cleanly on every one of these (`capability_missing`/empty-list fallbacks, confirmed live) — so nothing is broken today, but the whole A175-A179 investment is inert until this card lands. A178 (VOI scoring) has no new server dependency of its own but consumes A177's rules, so it's gated transitively.

Four ARC_AGI hand-off docs already spec each ask in full detail (exact request/response JSON shapes, suggested Cypher, a live reproduction script for the entity-movement case). This card consolidates all four into one implementation pass since they're layered (A176 depends on A175's fix landing first for `entity_ref` to reliably map to a real `GridEntity`; A177 references A176's `Transition` nodes; A179 references A177's `Rule` nodes):

### What This Card Does

Implements, in `campy/brain/thalamus/tools/arc_queries.py` (same module B278 created), the server-side half of A175-A179:

#### 1. Fix `arc_perceive_state`'s `GridEntity` write to emit `MOVED_BY` (A175)

Currently the `MERGE`/`SET` on `GridEntity` only ever writes `color_id`, `centroid_row/col`, `pixel_count`, `inferred_role`, `last_updated_step` — never compares the incoming centroid against what the existing node already had. `entity_id` is now reliably stable across steps (ARC_AGI's A175 fixed the client to send real `color_id`/`region_index` instead of always-default `0`/`0`), so this comparison is now meaningful.

Change: when a `MERGE` finds an existing `GridEntity` node whose stored centroid differs from the incoming one, write a `MOVED_BY` edge (`GridEntity -> ActionEffect`, `delta_row`/`delta_col` = incoming minus existing centroid) in the same call. Read the existing centroid *before* overwriting it with `SET`.

#### 2. `arc_record_transition` (write) and `arc_get_entity_history` (read) — A176

```json
// arc_record_transition
{"task_id": "...", "step": 4, "action_id": "ACTION6", "changed_count": 3,
 "color_transitions": [{"from": 2, "to": 5, "count": 3}], "entity_ref": 1}
```

`entity_ref` may be `null` (legitimate — changed cells didn't fall inside a known entity's bbox). Persist as a `Transition` node (one per call, or `MERGE`d/updated per distinct `(action_id, entity_ref)` — whichever fits existing schema conventions better) with an edge to the `GridEntity` identified by `entity_ref` when non-null.

```json
// arc_get_entity_history
{"task_id": "...", "entity_ref": 1}
// ->
{"transitions": [{"action_id": "ACTION6", "step": 4, "color_transitions": [...]}], "changed_count_total": 3}
```

#### 3. `arc_record_rule` (write) and `arc_get_rules_for_action` (read) — A177

```json
// arc_record_rule
{"task_id": "...", "step": 4, "action_id": "ACTION6",
 "candidate_signatures": [{"action_family": "ACTION6", "from_color": 2, "to_color": 5}],
 "fingerprint": "ACTION6:small"}
```

Note the `fingerprint` field (added by A179, sent alongside A177's `candidate_signatures` — the hand-off doc for A177 predates it, but the live client already sends both; index `Rule` nodes by `fingerprint` too so B309's task 4 can query across games by it).

For each signature: find existing `Rule` nodes for this `task_id` + `action_family` + `from_color`. Same `to_color` → confirm (bump confidence, optionally `CONFIRMED_BY` edge to the `Transition` from task 2). Different `to_color` → falsify (`falsified: true`, `FALSIFIED_BY` edge). Neither → create a new `Rule` with a `PREDICTS` edge.

Suggested schema: `Rule {rule_id, task_id, action_family, from_color, to_color, fingerprint, confidence, falsified, created_step}`.

```json
// arc_get_rules_for_action
{"task_id": "...", "action_id": "ACTION6"}
// ->
{"rules": [{"rule_id": "...", "from_color": 2, "to_color": 5, "confidence": 0.6, "falsified": false}]}
```

Only live (unfalsified) rules.

#### 4. `arc_get_transferred_rules` (read) — A179

```json
{"task_id": "current-task-id", "fingerprint": "ACTION6:small"}
// ->
{"rules": [{"rule_id": "...", "confidence": 0.6, "source_game_id": "..."}]}
```

Rules from **other** `task_id`s (cross-game — this is the one query in this card that deliberately does *not* scope to the caller's own `task_id`) whose recorded `fingerprint` matches. Index off the `fingerprint` field written in task 3.

### Notes

- ARC tools use the same `(params, db, config)` signature as all other tool handlers, matching B278.
- Do NOT wrap any of these with `_with_phase()` — same rule as B278's existing 15 ARC tools.
- All tools should degrade gracefully on missing/empty data (empty list/zero counts, never an exception) — the ARC-side client already treats any error response as `capability_missing` and falls back cleanly, but the server side should still fail soft internally per this repo's existing pattern.
- Per `docs/ecosystem-rules.md`'s "No shadow stores" rule: all new state (`Transition`, `Rule` nodes, `MOVED_BY`/`CONFIRMED_BY`/`FALSIFIED_BY`/`PREDICTS` edges) must persist to KuzuDB, not Python-side caches.
- The `fingerprint` field on `Rule` (task 3/4) is a plain string (`"{action_family}:{magnitude}"`, e.g. `"ACTION6:small"`) computed client-side — no need to recompute or validate its internal structure server-side, just store and index it.

### Implementation (2026-08-08)

**Naming: shipped generic, not `arc_`-prefixed.** Mid-implementation the user flagged that these 5 tools shouldn't be ARC-specific by name — `Transition`/`Rule` tracking (state-change history, causal confirm/falsify bookkeeping) is a general world-model pattern any Campy client could use, not inherently tied to ARC grids. Renamed before merge: `arc_record_transition` → `record_transition`, `arc_get_entity_history` → `get_entity_history`, `arc_record_rule` → `record_rule`, `arc_get_rules_for_action` → `get_rules_for_action`, `arc_get_transferred_rules` → `get_transferred_rules`. The existing 14 B278 ARC tools (`arc_perceive_state` etc.) were left untouched — renaming those is a separate, larger, already-shipped-contract change out of this card's scope. **Cross-repo consequence handled:** ARC_AGI's client already calls these by name via a dedicated mapping table (`agents/arc4/graph_queries.py::ARC_V2_TOOL_NAMES`, one line per tool decoupling ARC's internal method name from the wire tool name) — updated the 5 affected values there plus 3 test assertions (`tests/test_a176_transition_persistence.py`, `tests/test_a177_rules_as_nodes.py`, `tests/test_a179_structural_transfer.py`) in the same session; ARC_AGI's suite re-run clean (475 passed, 1 skipped) after the change. That repo's commit is separate from hippocampy's and not yet pushed — flagged to the user.

**Task 1 (`arc_perceive_state` MOVED_BY fix):** the reproduction script in the hand-off doc has no `action_taken` on either call, so `MOVED_BY` needed an `ActionEffect` node to exist even without an explicit action — `arc_perceive_state` now always computes `effect_id`, reads each `GridEntity`'s stored centroid *before* overwriting it, and if it differs, ensures a (possibly minimal, action-less) `ActionEffect` node exists and writes `MOVED_BY` with `delta_row`/`delta_col` = incoming − existing. `effect_id` is only returned (non-null) when something was actually written this call, preserving existing callers' expectations when no action/movement occurred.

**Tasks 2-4 (Transition/Rule):** new `Transition` and `Rule` node tables plus a `TRANSITION_OF` (Transition → GridEntity) rel table added to `campy/brain/hippocampus/schema.py`. `Transition` is one node per `record_transition` call (keyed by `task_id+action_id+step+entity_ref`), deliberately not merged/updated per `(action_id, entity_ref)` — `get_entity_history`'s `changed_count_total` needs to sum the full per-step history, which a merge-and-overwrite design would lose. `entity_ref` (a bare int, A175's stable per-task correspondence id) resolves to a real `GridEntity` via `MATCH ... region_index: $eref` bounded with `WITH ... LIMIT 1`. `color_transitions` persists as a JSON string (`json.dumps`/`json.loads`), matching the established convention in `arc_artifacts.py`/`arc_mechanics.py` for list-of-dict fields. `record_rule` implements exactly the three-branch confirm/falsify/create logic from the hand-off doc's literal wording (no branch chains falsify-then-create) — the "existing Rule" lookup is scoped to unfalsified rules only, so a genuinely new signature after a prior falsification gets its own new `Rule` rather than resurrecting a dead one. **Scoped down from the suggested schema:** skipped the `PREDICTS`/`CONFIRMED_BY`/`FALSIFIED_BY` edges the hand-off doc listed as "if useful" — `record_rule`'s payload has no way to identify which specific `Transition` a signature came from (candidate_signatures carry no transition reference), so wiring those edges would require a guessed/ambiguous lookup; `Rule`'s own `confidence`/`falsified` fields carry the same information without that ambiguity. No AC or ARC-side consumer needs the edges today.

**Verification:** TDD throughout — `tests/test_arc_queries.py` gained a new module-scoped `b309_db` fixture (real `init_schema()`-backed Kuzu, same pattern as B277's `test_basal_ganglia_real_kuzu.py`, needed because this touches real column/rel-table definitions a hand-rolled `MockDB` can't validate) and 7 new tests, all watched to fail first (`KeyError`/empty-result assertions) before implementing. `pytest tests/test_arc_queries.py -q`: 18 passed. Broader check (`test_adapters.py`, `test_mcp_tool_surface.py`, `test_openclaw_*`, extension-surface tests): 236 passed, 6 skipped, 1 failure — `test_sse_exposes_all_tool_handlers`, which calls the REAL locally-running daemon process (started before this session) over HTTP; it fails only because that long-running daemon hasn't been restarted to load this session's code, not a code defect. Not restarted as part of this card since it's the user's live daemon (other things may depend on it staying up); noted here so it's not mistaken for a regression. Full suite run separately for final confirmation (see PR).

**Also filed:** B310, a real pre-existing bug found while adding these schemas — `scripts/generate_extension_tools.py` crashes (`TypeError: unhashable type: 'list'`) on any multi-type JSON-Schema field (`{"type": ["integer", "null"]}` etc.), previously unexercised because every existing multi-type field happened to belong to a tool already hand-written in `index.ts` (which the generator always skips). Worked around here by hand-writing all 5 new tools' extension entries directly, matching the existing 100%-hand-written pattern for the whole ARC tool surface.
