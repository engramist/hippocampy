# B310 - Fix `scripts/generate_extension_tools.py` Crash on Multi-Type JSON Schema Fields

State: complete -- 2026-08-08: fixed `_schema_to_typebox()` to handle list-typed `"type"` fields (`Type.Union([...])`, with `"null"` mapped to `Type.Null()`). See Implementation section below.
Priority: P3

Plan: (inline — small, self-contained bugfix in one script)

### Problem

`scripts/generate_extension_tools.py` (B293's "add a tool once" flow: define it in `tool_schemas.TOOLS` + `TOOL_HANDLERS`, then run this script to auto-generate the OpenClaw extension's TypeBox parameter definitions in `extensions/hippocampy/src/generated_tools.ts` for any tool not already hand-written in `extensions/hippocampy/src/index.ts`) crashes on any `inputSchema` property whose `"type"` is a JSON-Schema list rather than a single string — e.g. `{"type": ["integer", "string"]}` (used for several `step` fields) or `{"type": ["integer", "null"]}` (used for nullable fields like `entity_ref`).

Found 2026-08-08 while implementing B309: adding `entity_ref: {"type": ["integer", "null"]}` to a new tool's schema and running the generator produced:

```
TypeError: unhashable type: 'list'
  File "scripts/generate_extension_tools.py", line 63, in _schema_to_typebox
    if stype in {"integer", "number"}:
```

`_schema_to_typebox()` (`scripts/generate_extension_tools.py:~50-90`) assumes `schema["type"]` is always a single string and does `stype in {"integer", "number"}` — when `stype` is a `list`, Python's `in` on a set requires hashing the left operand, which raises `TypeError` for an unhashable list.

**Why this went undetected until now:** the script only calls `_schema_to_typebox()` for tools NOT already hand-written in `index.ts` (`_extract_handwritten_tool_names()` skips anything already present). Every existing tool schema in `tool_schemas.py` that already uses a multi-type `"type"` list (e.g. `arc_record_action_effect`'s `step`, `arc_get_entity_movement`'s `step`, `arc_record_reward_prediction_error`'s `step` — all pre-existing, predating B309) happens to already be hand-written in `index.ts`, so the generator never actually walked their schemas. B309 added the first NOT-yet-hand-written tools with a multi-type field, which is what finally triggered the crash. The bug has likely existed since multi-type fields were first added to `tool_schemas.py`, silently unexercised.

**Current workaround (B309):** all 5 of B309's new tools were hand-written directly into `extensions/hippocampy/src/index.ts`'s `arcQueryToolDefinitions`-equivalent array (matching the pattern already used by 100% of the ARC tool surface, all of which is hand-written, not generated) rather than relying on the generator. This is a real, sustainable pattern (nothing in the ARC tool surface has ever used the generated path), but it means the "define once in `tool_schemas.py`, run the script" flow documented at the top of `docs/tool-catalog.md` doesn't actually work today for any tool with a multi-type field, silently pushing everyone back to hand-writing `index.ts` entries.

### What This Card Does

Fixes `_schema_to_typebox()` in `scripts/generate_extension_tools.py` to handle `"type"` as either a string or a list:

- A list containing `"null"` alongside another type (e.g. `["integer", "null"]`) should map to `Type.Union([<mapped-type>, Type.Null()])` (or `Type.Optional(...)` if that fits the existing TypeBox-generation convention better).
- A list of multiple non-null types (e.g. `["integer", "string"]`) should map to `Type.Union([...])` over each mapped type, matching the hand-written pattern already used throughout `index.ts` (e.g. `Type.Union([Type.Number(), Type.String()])` for `step` fields).

### Implementation (2026-08-08)

**Fix:** `_schema_to_typebox()` (`scripts/generate_extension_tools.py`) now checks `isinstance(stype, list)` first. `"null"` maps directly to `Type.Null()` (it has no constraints of its own); every other member type re-enters `_schema_to_typebox()` with the full schema minus the list `"type"` swapped for that single member, so per-member constraints (`description`, `minimum`, etc.) still apply. The whole thing wraps in `Type.Union([...])`, matching the style already used by every hand-written multi-type field in `index.ts` (e.g. `Type.Union([Type.Number(), Type.String()])` for `step` fields).

**Verified against the real production impact, not just a synthetic schema:** this repo has a CI drift guard (`.github/workflows/tests.yml`, "Verify generated extension tools are up to date") that runs `python scripts/generate_extension_tools.py` then `git diff --exit-code` on the output — that exact sequence now passes locally. Before the fix, this step would have crashed CI outright the moment any tool with a multi-type field wasn't already hand-written in `index.ts` — which is precisely what B309's 5 new tools were, before that card chose to hand-write them as a workaround. Also directly confirmed the fix against the real field that originally crashed: `_schema_to_typebox(TOOLS["record_transition"]["inputSchema"])` now renders `entity_ref: Type.Optional(Type.Union([Type.Number({}), Type.Null()]))` correctly.

**Verification:** TDD. New `tests/test_generate_extension_tools.py` (5 tests: single-type baseline unaffected, `["integer","string"]` union, `["integer","null"]` → `Type.Null()`, per-member constraints preserved, full generator run against the real `TOOLS` list) — watched all 3 multi-type tests fail with the exact `TypeError: unhashable type: 'list'` before implementing. Full suite: see PR.

### Outcome

`scripts/generate_extension_tools.py` (and the CI drift guard that runs it) no longer crashes on any tool schema with a multi-type field. The "define once in `tool_schemas.py`, run the script" flow documented at the top of `docs/tool-catalog.md` now actually works for tools with nullable or union-typed fields, not just simple single-type ones.
