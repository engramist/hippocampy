# B466 - Step 1b Misses "Replace X with Y" and "X Is Deprecated ... Migrate to Y"

State: fixed in the sandbox (2026-10-04); real-model confirmation pending
Priority: P1

### Problem Statement

Found by campy-benchmarks after B460 (2026-10-04). B465's repair dry run on a
real-model (llama3.1:8b) LoCoMo store left 2 INVERTED supersession edges that
no re-extraction could fix, because Step 1b produced nothing for their source
messages and Step 3b's LLM guessed the direction again:

- "Security audit complete. Update constraint: symmetric HS256 is deprecated
  due to key distribution risks. We must migrate to RS256 asymmetric keys."
  -> "HS256 CHOSEN_OVER RS256 asymmetric keys"
- "Replace Memcached with Redis cluster on port 6379 ..." -> the Memcached /
  Redis pair, inverted.

### Root cause

Step 1b (`step1b_relations.extract_relations`, B460) knows three shapes:
active "A replaced B", passive "B was replaced by A" and "migrate from B to
A". Two common ways of stating a supersession fit none of them:

1. **"replace X with Y"** names the retired value as the object and the new
   one after a preposition. The active rule took the subject as the new value
   ("We replaced Memcached with Redis" -> "We REPLACES Memcached"); the
   imperative has no subject, so it gave nothing. "swap X for Y" and
   "substitute Y for X" (object = new value) likewise.
2. **"X is deprecated; migrate ... to Y"** splits the statement over two
   clauses (often two sentences): the retired value is the subject of
   "deprecated", the new one the "to" object of a move verb with no "from".
   B460 deliberately ignores a lone "migrate to Y" -- it names no retired
   value -- so nothing was produced and Step 3b ran.

### What It Does (Scope)

`step1b_relations.extract_relations`:

- **with**: replace (with/by), swap (for/with), exchange (for): the
  preposition's object REPLACES the verb's object (or passive subject);
  substitute Y for X: the object REPLACES the "for" object. Active,
  imperative and passive ("was replaced with Y"). When the verb has a passive
  "by" agent the passive rule keeps it: in "REST has been replaced by gRPC
  with Protobuf v3", "with Protobuf v3" describes gRPC.
- **retire + move**, only when the message has no other REPLACES: exactly one
  subject of deprecate/retire/sunset/decommission/discontinue (verb or the
  "is deprecated" adjective) and exactly one "to" object of a move verb
  without "from" (any part of speech: after a semicolon spaCy parses
  "migrate" in "migrate serialization to MessagePack" as a noun modifier).
  Both must name a value (a proper noun or number in the name span), so "the
  new wiki" or "the new one" produce nothing. More than one of either:
  nothing, rather than a guess at the pairing.

Measured offline on LoCoMo's 75 user messages (spaCy en_core_web_md), against
main's Step 1b: **16 relations added, 0 lost**, every one "current REPLACES
retired" (RS256 asymmetric keys / symmetric HS256, MessagePack / Pickle,
Nomad / Docker Swarm, Python 3.11 / Python 3.9, Travis CI / Jenkins, Graphite
/ Nagios, TLS 1.2 / TLS 1.1, Bazel / Makefiles, Route53 / BIND9, ...). The
patterns are general English; none of the wording is LoCoMo's own.

Changed test: B460's `test_step1b_needs_both_ends_of_a_move` asserted that
"Update: Pickle is deprecated; migrate serialization to MessagePack." gives
nothing. That message does name the retired value, so it is now B466's
positive case; the B460 test keeps its intent with "Update: migrate
serialization to MessagePack." (no retired value -> nothing).

Not changed:

- Step 3b and the orchestrator. Existing inverted edges are B465's repair
  (`campy graph repair-supersession-edges`), which re-runs extraction: with
  this card it can fix the last 2.
- Overlap with B464 (#274): B464 adds `_is_name` for the same "is this a
  named value" question `_names_something` answers here. Whichever merges
  second should use `_is_name(_span(tok, doc))` and drop `_names_something`.
  B466's relations go through `_relation`, so they get B464's `names` flag.
