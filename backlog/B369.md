# B369 - Implement `arc_start_or_resume_thread` Server-Side (ARC_AGI Client Calls It, Degrades Gracefully Today)

State: mostly complete — the one tool asked for is done; the other 3 tools from the full design spec are deliberately out of scope
Priority: P3

Plan: none yet.

### Problem

Found live 2026-08-29 during a joint cross-repo live smoke-test verification of ARC_AGI's A218/A219/A220
PRs, via `~/.campy/activity.log`: two `"Unknown method: arc_start_or_resume_thread"` error events, both
at the very start of a `run_single_puzzle.py --live-smoke` run, before any of the run's real ARC tool
calls. `grep -rn "arc_start_or_resume_thread" campy/` returns zero hits — this method has never existed
in `TOOL_HANDLERS`, `tool_schemas.TOOLS`, or anywhere else server-side.

Confirmed (via the ARC_AGI-side session, `arc-agi-9c`) that this is expected, not a bug on either side:
ARC_AGI's `agents/arc4/graph_queries.py:248` (`start_or_resume_thread`, wire method
`arc_start_or_resume_thread`) is a client capability for Annatar's investigation-thread resume feature
(see ARC_AGI's `docs/superpowers/specs/2026-08-23-trajectory-reasoner-design.md`), called from
`annatar_signals.py:324` and `arc_runtime/dispatch.py:57`. Both call sites already wrap the call in
try/except and degrade to a fresh-thread-shaped result when the server capability doesn't exist —
the method's own docstring states this explicitly. ARC_AGI's own README documents this as a known
"current rollout caveat": the client is wired to some hippocampy tools that don't exist server-side yet.

This card exists so that gap is tracked rather than silently degrading indefinitely — the ARC_AGI-side
session found nothing in this repo's backlog tracking it either, not even a stub.

### What it does (scope)

1. Read ARC_AGI's `docs/superpowers/specs/2026-08-23-trajectory-reasoner-design.md` and
   `agents/arc4/graph_queries.py`'s `start_or_resume_thread` client implementation to understand the
   exact expected request/response shape (what params it sends, what a "resumed" vs "fresh" thread
   result needs to contain) — this is the source of truth for the contract, not a guess from this side.
2. Design and implement `arc_start_or_resume_thread` as a real MCP tool: add to `TOOL_HANDLERS`,
   `tool_schemas.TOOLS`, and whatever test-adapter `EXPECTED_TOOLS` list exists (see this project's own
   "Adding MCP tool surfaces" convention — a new tool needs 3+ declaration sites, not just a handler).
3. Decide the actual persistence/resume semantics server-side (what makes a "thread" resumable — likely
   a graph node keyed by task_id/game_id plus some investigation-state fields, following this project's
   own KuzuDB-as-single-source-of-truth rule, no shadow stores).
4. Verify against a real live client call from the ARC_AGI side once implemented (coordinate with
   `arc-agi-9c` or whatever ARC_AGI-side session is current) — confirm the "Unknown method" errors stop
   appearing in `~/.campy/activity.log` and a real resumed/fresh-thread result comes back correctly.

### Outcome

Closed (for its own stated scope) 2026-08-29. Implemented `arc_start_or_resume_thread` exactly per the
handoff doc found at `docs/handoff/B278-investigation-thread-schema.md` in the local ARC_AGI checkout
(read directly rather than guessed) — that doc already specifies the exact request/response contract
and suggested schema, so no re-derivation was needed.

**What shipped:**
- `campy/brain/hippocampus/schema.py`: new `InvestigationThread` node table (`thread_id` PRIMARY KEY,
  a deterministic composite `f"{task_id}::{anchor_type}::{anchor_ref}"` — gives the handoff doc's
  required O(1) primary-key resume lookup with no separate index). Deliberately **not** added to
  `PROVENANCE_TABLES` — this is runtime/orchestration bookkeeping, not a learned/inferred fact, same
  category as `TaskGraph`/`TaskNode`. Two new rel tables, `ANCHORED_ON_ENTITY` (→ `GridEntity`) and
  `ANCHORED_ON_GOAL` (→ `Hypothesis`), instead of the doc's single polymorphic `ANCHORED_ON` — Kuzu
  requires a fixed FROM/TO type pair per rel table (the same constraint `ENTITY_HYPOTHESIS`/
  `ENTITY_RULE` already worked around in this file).
- `campy/brain/thalamus/tools/arc_queries.py`: the handler, plus `_link_thread_anchor()` (best-effort
  edge creation, silently no-ops if the anchor target doesn't exist yet — mirrors the existing
  `_link_entity_hypothesis` pattern).
- Registered in all required declaration sites: `arc_tools.py`'s re-export, `tools/__init__.py`'s
  import + `TOOL_HANDLERS`, `tool_schemas.py`'s `TOOLS`, and `tests/test_arc_queries.py`'s
  `EXPECTED_ARC_TOOLS` (the test-adapter `EXPECTED_TOOLS` in `tests/test_adapters.py` derives itself
  from `tool_schemas.TOOLS` automatically, no separate edit needed there).

**Deliberately out of scope, per this card's own title ("Implement `arc_start_or_resume_thread`",
singular) — not silently dropped, the full design spec (ARC_AGI's
`docs/superpowers/specs/2026-08-23-trajectory-reasoner-design.md`) names 4 tools and an `Attempt`/
`Cycle` node pair as one larger feature (its own §10 decomposes them into separate sequenced cards):**
`arc_write_thread_state`, `arc_write_cycle`, `arc_confirm_cycle` remain unimplemented (still
"Unknown method" if called — none of ARC_AGI's current wiring calls them yet per the handoff doc's own
"ARC-side status" section), and no `Attempt`/`Cycle` nodes or `HAS_THREAD` edge exist. A consequence
worth being explicit about: `last_cycle` in this tool's response is *always* `None`, even on a real
resume, since nothing yet writes a `Cycle`. A resumed thread's `state` field is similarly frozen at
whatever it was created with, since nothing yet calls `arc_write_thread_state`. These are not bugs in
what's implemented — they're the honest shape of implementing 1 of 4 tools from a larger spec, matching
this project's practice of documenting partial-scope work plainly rather than overclaiming.

One additional judgment call not spelled out by the spec: a thread found in a **terminal** state
(`satisfied`/`exhausted`) is *reopened* (reset to `exploring`, returned as a fresh non-resumed start)
rather than either resuming a dead thread or minting a new `thread_id` — the latter would break the
deterministic-key invariant for future lookups on the same anchor. Documented in the handler's own
docstring.

**Testing:** 7 new tests in `tests/test_arc_queries.py`, using the file's existing real-KuzuDB
`b309_db` fixture (production schema via `init_schema()`) per the design spec's own testing-strategy
recommendation ("fixture-graph tests against real Kuzu... for `arc_start_or_resume_thread`'s resume
lookup") — covering fresh creation, resume of a non-terminal thread, reopening a terminal thread,
invalid `anchor_type` rejection, and both `ANCHORED_ON_ENTITY`/`ANCHORED_ON_GOAL` edge creation
(including the best-effort no-op case when the anchor target doesn't exist yet). All passing, plus the
full `test_arc_queries.py`/`test_mcp_tool_surface.py`/`test_adapters.py` suites re-run clean (204
passed, 6 skipped).

**Live-verified against the real dev daemon** (restarted via the now-fixed `campy stop`/`campy start`
from B364, schema migration applied automatically via `init_schema()`'s idempotent `CREATE ... IF NOT
EXISTS`): two real socket calls with identical params returned `resumed: false` then `resumed: true`
as expected, and `~/.campy/activity.log` shows clean `"tool"/"ok"` events for `arc_start_or_resume_
thread` post-restart (the pre-fix "Unknown method" errors from the original 2026-08-29 smoke test
remain in the log's history, as expected — logs aren't rewritten).

the rest of a pytest session if it happens to run before anything else imports the real `kuzu`. Filed as
`backlog/B370.md`.
