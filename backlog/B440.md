# B440 - SessionEnd Hook Automation for generate_handoff (B383 v2)

State: fixed (2026-09-22, Claude Code only — see completion notes for Codex/Gemini)
Priority: P2
Branch: feat/b440-sessionend-hook-handoff
PR Target: main

### Note on origin

Deferred out of B383 (Automated Model Handoff Generator, merged via
[PR #237](https://github.com/engramist/hippocampy/pull/237)). B383's
own card described "Automated Hook Handoff: Claude Code / Codex
session-end and session-start hooks automatically sync the handoff
bundle through Unix domain socket IPC" as scope item 3. B383 shipped
v1 (the `generate_handoff` MCP tool + `campy handoff` CLI) and
deliberately deferred this item — see `backlog/B383.md`'s completion
notes for the full reasoning.

### Problem

Right now, getting a handoff artifact requires the developer to
remember to run `campy handoff` (or call `generate_handoff`) themselves
before switching models. The B383 card's original vision was for this
to happen automatically at session end, with zero manual action
required — matching the "zero-amnesia" framing of the parent feature.

### What's actually there today (verified 2026-09-21)

- `plugin/hooks/hooks.json` registers exactly three hook events:
  `SessionStart`, `PreToolUse`, `PostToolUse`. **No `SessionEnd` entry
  exists.**
- None of the three existing hook wrappers
  (`session_start_wrapper.py`, `pre_tool_use_wrapper.py`,
  `post_tool_use_wrapper.py`) touch `WorkSummary`/handoff data, or call
  the Unix socket transport (`campy/brain_transport.py`). They use a
  `campy` CLI subprocess (`session_start_wrapper.py`) or local file +
  regex matching against `~/.campy/triggers/manifest.json` (the two
  tool-use wrappers) — no daemon graph query at all in the latter two.
- **Open question, not yet resolved:** whether the Claude Code plugin
  host framework actually supports a `SessionEnd` hook event at all.
  A repo-wide grep found no reference to `SessionEnd` anywhere outside
  this card's own notes — meaning this hasn't been confirmed against
  the actual host framework's supported event list. This needs to be
  checked (Claude Code plugin/hook documentation, or empirically by
  registering a `SessionEnd` entry in a test plugin and observing
  whether it fires) before designing the rest of this card in detail.

### Scope

1. Confirm `SessionEnd` (or whatever the actual supported event name
   is — may differ from `SessionStart`'s naming convention) is a real,
   supported hook event in the Claude Code plugin framework.
2. If supported: add a `session_end_wrapper.py` (mirroring
   `session_start_wrapper.py`'s structure) that calls `campy handoff`
   (or `generate_handoff` directly over the Unix socket transport,
   consistent with how the daemon is otherwise reached) and writes the
   result somewhere durable — needs a design decision: a file next to
   `CONTEXT.md` (matching B290's `## Current Work` convention), a
   dedicated `HANDOFF.md`, or delivered via the socket to a waiting
   client. Not prescribed here.
3. Register the new event in `plugin/hooks/hooks.json` and (per the
   existing convention) the Gemini-equivalent `plugin/hooks/gemini-hooks.json`
   if that file also needs a matching entry.
4. Decide graceful degradation: what happens if the daemon isn't
   running, or the session has no active quest — must not block or
   error out the actual session-end/exit flow (matching every existing
   hook wrapper's fail-open convention).

### Acceptance Criteria

- [ ] Confirmed whether `SessionEnd` (or equivalent) is genuinely
      supported by the host hook framework, documented either way.
- [ ] If supported: a session ending automatically produces an
      up-to-date handoff artifact without any manual `campy handoff`
      call, verified end-to-end against a real Claude Code session.
- [ ] Fails open — a daemon-down or cold-start session must not block
      or error the actual session exit.
- [ ] Work executed in branch `feat/b440-sessionend-hook-handoff` and
      PR created targeting `main`.

### Outcome

Zero-amnesia handoff genuinely requires zero manual action, matching
B383's original framing, once (and only if) the underlying hook
framework supports it.

### Completion Notes (2026-09-22)

**Confirmed `SessionEnd` is real** — verified against Claude Code's
official Hooks Reference (code.claude.com/docs/en/hooks.md) via the
`claude-code-guide` agent: a documented event, stdin payload includes
`session_id`/`cwd`, fires on normal session close/exit (may not fire
on SIGKILL/VM preemption — documented limitation, not this
implementation's gap). Independently cross-checked the one load-bearing
structural claim (`plugin/.claude-plugin/plugin.json` really does
declare `"hooks": "./hooks/hooks.json"`) by reading the file directly
rather than trusting the agent's report alone.

Shipped: `plugin/hooks/session_end_wrapper.py` (mirrors
`session_start_wrapper.py`'s structure/fail-open convention exactly),
registered in `plugin/hooks/hooks.json`. Calls `campy handoff --out
<cwd>/HANDOFF.md --session-id <id>` as a bounded (10s) subprocess.
Writes a **separate `HANDOFF.md`** file rather than appending to
`CONTEXT.md`'s `## Current Work` section (B290) — different, richer
artifact, consistent with the CLI's own `--out HANDOFF.md` convention
from B383.

**Found and fixed a real, pre-existing, severity-blocking bug while
testing this end-to-end against the live daemon** (not just in-process
handler calls, which is what B382/B383's own tests used and which
never would have caught this): `campy/cli/recall.py`'s `_send()`
returned the raw MCP JSON-RPC envelope directly, but every command in
that file (`recall`/`bundle`/`timeline`/`diff`/`decide`/`dispatch`/
`context`, and now `handoff`) does `result.get("result", ...)`
expecting a flat tool-output dict — the real shape nests it as a
JSON-encoded string at `result.content[0].text`. Confirmed by hand:
`campy decide`/`campy dispatch` both printed `?`/`N/A` placeholders
for every field against the real daemon before this fix. **This bug
predates B440 and B382 entirely** (the `decide` command and this
response shape are both older than this session's work) — every
daemon-backed CLI command has been silently broken this whole time.
Fixed at the root (`_unwrap_tool_result()` in `_send()`), not per-command,
so all 8 affected commands are fixed by the one change. 7 new direct
unit tests (`tests/cli/test_recall_unwrap.py`), confirmed load-bearing
(the fix function doesn't exist without the change — `ImportError`,
not a silent pass).

**Three more findings filed as their own cards, not folded into this
one**, since each needs its own scoping/verification:
- **B441**: hook wrappers prefer the globally-resolved `campy` binary
  over the more-reliable in-process fallback, and silently produce
  zero diagnostic signal when that binary is broken — which it is, on
  this dev machine (`~/.local/pipx/venvs/hippocampy` resolves to
  Python 3.14.3, a version B428 already excluded via
  `requires-python`, missing `pyoxigraph` entirely). This silently
  degrades `SessionStart` too, not just this new `SessionEnd` hook —
  confirmed both independently before filing.
- **B442**: found while checking whether `adapters/claude_code/
  hooks/*.sh` (a second, older hook implementation) also needed a
  `session_end.sh`. Verified via the `claude-code-guide` agent (and
  independently cross-checked the `plugin.json` claim myself) that
  those `.sh` scripts are copied into `.claude/hooks/` by `setup.py`
  but never actually registered as `SessionStart`/`PreToolUse`/
  `PostToolUse` events anywhere — dead code, not a live alternate
  hook path. This B440 implementation correctly targets the one
  mechanism that's actually live (`plugin/hooks/hooks.json`).
- **B443**: B383's card named "Claude Code / Codex" explicitly; this
  card only implements the Claude Code side. Confirmed via web search
  (developers.openai.com/codex/hooks) that Codex does have a
  `SessionEnd` event, but it runs **synchronously with a ≤3-second
  cap** and doesn't support MCP tool hooks — far tighter than this
  wrapper's 10s internal budget (`check_daemon_health()` alone has a
  2s HTTP timeout, which could consume most of that budget on a slow
  daemon). Rather than ship an unreliable naive reuse, scoped as its
  own follow-up needing a leaner, Codex-specific timeout budget.
  Gemini was never named in either card's scope and has no verified
  `SessionEnd`-equivalent — not touched.

**One unverifiable acceptance-criterion caveat, stated honestly**:
"verified end-to-end against a real Claude Code session" wasn't
literally possible to test (no way to trigger a genuine host-level
`SessionEnd` event from within this session). Verified instead via:
(1) a simulated stdin payload matching the documented contract exactly,
run as a real subprocess against a real, running daemon, confirmed to
produce a real, non-empty `HANDOFF.md` (caught and fixed the
`_unwrap_tool_result` bug in the process); (2) the fail-open path
(daemon down) verified both via mocking and via a genuinely
unreachable daemon; (3) 11 direct/subprocess tests
(`tests/test_session_end_hook.py`). The daemon started for this
testing was stopped again afterward — confirmed via
`curl .../health` failing and the previously-daemon-sensitive test
suite passing cleanly again.

Full suite green aside from the pre-existing, unrelated
`test_packaging_installed_mode.py` trio; guard scripts unaffected (no
new MCP tool registered this round, so no principal-ratchet drift).
