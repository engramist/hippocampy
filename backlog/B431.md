# B431 — capability.py's Q1-Q4 SPARQL bodies are non-functional stubs

**Status:** Open
**Found by:** B427 batch 1 (migrating `tests/test_capability_queries.py` off `KuzuClient`
onto `OxigraphClient` surfaced this — all 22 tests pass against real Kùzu; 13 fail
against real Oxigraph).
**Severity:** High — one of the four gaps is a security control (trust-tier access
filtering) that silently passes through unfiltered on the Oxigraph path.

## What's broken

`campy/brain/hippocampus/graph/queries/capability.py`'s `_QUESTION_QUERIES` (Q1-Q5,
the customer's five capability-graph questions) each carry a `cypher=` (real, tested,
used to work against Kùzu) and a `sparql=` (untested against real data until now —
every prior capability test ran on Kùzu). The `sparql=` bodies for Q1-Q4 are
placeholders that don't implement the same logic as their `cypher=` counterparts:

1. **`capability.permitted_paths` (Q1)** — the SPARQL entirely omits the
   `CONSTRAINED_BY`/`trust_tier` filter. The Cypher version blocks any target
   reachable only through a node whose `CONSTRAINED_BY` `access_mode` doesn't match
   the caller's `trust_tier`; the SPARQL version has no such filter at all, so a
   `public`-tier caller sees guarded-branch targets a `public` caller should never see.
   This is a real access-control gap on the Oxigraph path, not just a test failure.
2. **`capability.permitted_paths` (Q1) / `capability.impact_of` (Q3) /
   `capability.lineage_of` (Q4)** — none of the three exclude superseded edges from
   the traversal (`incsup`/`include_superseded` is a no-op in SPARQL); none compute a
   real hop count (`BIND(1 AS ?hops)` hardcodes 1 instead of the traversed path
   length — SPARQL 1.1 property paths don't expose path length natively, so this
   needs either a length-tracking technique or a different traversal approach).
3. **`capability.explain_path` (Q2)** — structurally cannot bind its `$pairs`
   parameter (a list of `{from, to}` dicts). `OxigraphClient`'s `execute_read`
   substitution mechanism (see `tests/test_oxigraph_client.py`'s
   `test_execute_read_binds_params_via_substitutions_not_string_interpolation`) only
   supports scalar substitutions projected in the SELECT clause — there is no
   SPARQL-level equivalent of Cypher's `UNWIND $pairs AS pair`. The current SPARQL
   ignores `$pairs` entirely and returns every `FACT_INVOKES`/`FACT_REQUIRES` edge in
   the graph, not just the requested hops (confirmed: a 1-pair request returns 12 rows).

`capability.reuse_candidates` (Q5) is fine — deliberately `sparql=None` with a Python
vector-similarity handler in `gateway.py`, per its own docstring.

## What's NOT broken (already fixed, see B427 batch 1)

A related, smaller bug in the same file's write path was found and fixed alongside
this discovery: `gateway.py`'s `capability.create_edge_*` handler derived the target
rel table by blindly uppercasing the query-name suffix (`"invokes"` →
`"INVOKES"`), instead of mapping through `schema.FACT_PREDICATE_TABLES` (the real
table is `FACT_INVOKES`). Fixed in `gateway.py` by looking up
`FACT_PREDICATE_TABLES[predicate]` instead of literal `.upper()`.

## Suggested approach

Each of Q1/Q3/Q4 needs:
- Superseded-edge exclusion translated into the SPARQL body (likely via `FILTER` over
  an `OPTIONAL` on the reified occurrence's `superseded_by`, mirroring Q2's existing
  pattern for a single hop — extending it across a `+` property path is the new part).
- A real hop-count. SPARQL 1.1 has no built-in path-length binding for `+`/`*`
  property paths. Options: (a) bound-depth `UNION` of fixed-length paths up to the
  same max (5/4/6 hops respectively) with a `BIND` per branch, since the bound is
  small and static; (b) a Python-side handler that walks the graph the way
  `gateway.py`'s existing star/occurrence handlers do, bypassing SPARQL property
  paths altogether for these three queries specifically.

Q1 additionally needs the `CONSTRAINED_BY`/`trust_tier` filter re-implemented in
whichever of the above forms is chosen.

Q2 needs `$pairs` handled either via a Python handler (loop the pairs, run one
single-hop pattern per pair, same shape as the existing single-hop pattern already in
the SPARQL body) or by reformulating the query to accept pairs some other
substitutable way.

Given the security-relevant nature of Q1's gap and the design decisions involved
(bound-depth UNION vs. Python handler, once for all three queries or per-query), this
needs the same explicit design checkpoint B430 got before implementation — do not
guess at the traversal-length strategy silently.
