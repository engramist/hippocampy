# B454 - Retrieval/Consolidation Quality: Benchmark Facts Are Stored But Not Retrievable via ask/compile_context

State: fixed (2026-09-24 — see completion notes)
Priority: P1

First valid benchmark run (B446 v4) shows LoCoMo F1 0.011 / deprecation 0.074,
MemoryGym 0%, MemBench 0.0 (with an empty-bundle "100% token savings"
artifact). Direct probes (2026-09-23) show why, in order of leverage:

1. **Consolidation drops these statements as noise.** `Constraint for
   storage_tier: we use S3 Standard.` / `Update: S3 Standard is deprecated;
   migrate ...` log `entities=1-2 concepts=0 noise=1-2` — no Concept/Constraint/
   Decision is created, so `compile_context` has nothing to surface. Check
   Step 4 (`classify_artifact` signals + NOISE_FLOOR gating) against short
   declarative "Constraint ... / Decision ..." turns; B283/ask-eval fixtures
   pass because they seed structured nodes via tool handlers, not via
   `notify_turn` prose.
2. **`ask`/`compile_context` return empty bundles** (`sections: []`,
   "No relevant context was found in memory") even though the raw turns exist
   as `Message` nodes (confidence 0.0, `confidence_low: true`) that
   `current_truth` finds lexically. Decide whether low-confidence Messages
   should ever back an answer, and whether the bundle compiler's relevance
   floor (B305-B307) is too strict for this input.
3. **`system`-role messages are never returned** by `current_truth`
   (user-role ones are) — MemoryGym's observations were written as `system`
   and were unrecallable by construction (harness now writes `user`).
4. **Id-token / multi-word queries miss a just-written, settled Message**
   (`current_truth("memgym_mysterypath_dbg1")` -> 0 results while a single
   alnum token like `quixnar9` hits): underscore/punctuation tokenization in
   the lexical branch is worth checking.
5. MemBench `token_savings_pct` reads 100% because bundles are empty (0
   tokens) — meaningless until bundles have content; consider reporting N/A
   when `bundle_tokens_avg == 0`.


## Completion notes (2026-09-24)

The card's original premise ("consolidation drops these turns as noise") was
real but was NOT the main reason facts were unreachable. Measured root causes,
in order of impact (all on the same path: write -> index -> retrieve):

1. **Nodes were never indexed.** Since the SPARQL cutover, `sparql=` node-creates
   bypass `OxigraphClient.write_node()` (the only place that populates the
   sqlite-vec vector store and FTS5 index); only `lessons.create_lesson` re-attached
   indexing (B418). Live: 5/400 Concepts, 0/82 Decisions, 1,546 Messages had no
   embedding; gist-example embeddings (centroid learning) never stored. Fix:
   `queries/vector_indexing.py` (one spec table for all 28 embedding-carrying
   creates, attached to the registry) + a conformance test; `scripts/backfill_vector_index.py`
   healed the live store (31 s).
2. **FTS was unusable for questions.** `VectorStore.search_text` passed free text
   as FTS5 syntax: any `?` raised `syntax error` (swallowed by every caller) and
   bare words were ANDed. Now an OR of quoted content words, bm25-ranked.
3. **Typed vector lookups were starved.** `search_vectors(k=limit*5)` takes the
   *global* top-k then filters by node type; ~20k Messages crowd out hundreds of
   Concepts/Decisions. k is now generous (sqlite-vec scans flat anyway; capped at 4096).
4. **No conversation evidence.** Consolidation keeps entity labels ("PostgreSQL"),
   not statements, so raw user turns are the only place a fact lives and the bundle
   never looked at them. New `conversation` bundle stage (`thalamus.bundle_conversation`):
   vector+FTS fusion over user-role, non-question, de-duplicated messages, near-duplicates
   of the query dropped before truncation (dozens of `ask` echoes filled the window),
   FTS-only hits need >=2 query words, returned oldest-first so later statements
   visibly supersede earlier ones; `[retrieval] conversation_limit` (0 disables).
5. **The sweep archived every Message.** 20 sweep queries (`unwind_archive_*`,
   `resurrect_node_*`, `unwind_delete_session_*`) took an id list whose SPARQL had no
   `VALUES ?ids { }`, so `?ids` never bound and the UPDATE hit every node of the type
   (proven: archiving one message archived all three). Live: all 19,764 Messages were
   archived. Fixed + conformance test that every list param actually binds; repaired
   with `scripts/repair_wrongly_archived.py`.
6. **Decay wiped strength-0 nodes** (`DELETE {old} INSERT {new}` with an identical
   triple deletes it — Oxigraph applies inserts first): fixed in all 9 decay queries.
7. **Messages had no retention grace.** Created at strength 0.0 < the 0.10 archive
   threshold, contradicting the config's own ~23-day half-life / 14-day episodic
   window. `[pruning] message_grace_days` (default 30).
8. **`ask` captures its own question/answer** into memory (closed loop) — fine for
   product use but it polluted evaluation (echoes, "no info" answers, garbage
   graph relations derived from questions). `capture` is now a documented `ask`
   parameter and the harness probes with `capture=false`.

**Result (strict 4-suite smoke slice, same live store):** LoCoMo deprecation
accuracy 0.07 -> 0.80, EM 0 -> 0.17; MemoryGym 0% -> 100%; MemBench precision
0.0 -> 1.0 (contradiction 1.0); ARC 1.0/1.0. Full-run numbers in
`docs/benchmarks/post-cutover-kpis.md`.

**Still open (not fixed here):**
- Consolidation itself still yields entity labels, not statements (Step 2 noise
  floor vs message-level text; Step 4 per-entity artifacts). The conversation stage
  compensates but structured Decision/Constraint memory from prose is weak.
- The conversation stage can surface loosely related old messages (min cosine 0.30);
  rank quality is the next tuning lever.
- `capability.explain_path` (read) has an unbound `pairs` param and returns all paths.
- ~18 other `sparql=` queries insert `<< >>` annotations (B451 follow-up).
- LoCoMo F1 is token-overlap against short gold answers, so verbose LLM answers
  score low even when correct; consider an answer-contains/LLM-judge metric.
