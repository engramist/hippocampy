# B321 - Cross-Session Continuity for an App

State: done
Priority: P1

Plan: (inline — self-contained, sized for a Sonnet-level implementer)

Depends on: **B312** (provenance). Composes with **B316** (workspace isolation) and
**B318** (fail-open).

**Supersedes the original B321 ("Advisory Co-Activity"), which was written against a
misdiagnosis.** See "Why this card was rewritten" below — the correction matters, because the
original card would have built a warning system for a hazard that does not exist.

### Positioning — read before the rest (platform evaluation, 2026-08-15)

The evaluating platform's architecture review flagged this card under their capability-reuse
rule: a git-native workspace design is *already assigned* as the mechanism for the
"disconnected islands" problem (real git branches per session, cloned with a genuine
merge-base). Proposing a parallel graph-based visibility layer read to them as "a second,
un-reconciled answer to a problem this repo has already assigned an owner and a mechanism
for."

That objection is fair as the card was framed, and their review names the resolution:
"unless explicitly scoped as observability on top of the git-workspace model rather than an
alternative to it."

**So, stated first and unambiguously: this card is additive to that git-workspace design and
never a substitute for it.** The distinction is substantive, not cosmetic:

- **Their git-workspace design gives shared ancestry** — real branches, a merge base,
  divergence reads, a rebase affordance. It answers "what changed in the files, and how do I
  reconcile it."
- **This card gives decision continuity** — what an earlier session on the same App decided,
  what it tried that failed, what it learned. A diff does not carry a decision or its reason.

If their design ships, this card still adds value and does not conflict with it. If it never
ships, this card does not substitute for it — sessions still lack shared ancestry. Any
implementation, PR description, or platform-facing text must lead with that framing.

### Why this card was rewritten

The original B321 assumed an evaluating platform's build agents were overwriting each other in
a shared working tree, and proposed surfacing "another agent touched this file N minutes ago."

A factual audit of the target platform (2026-08-15, answers cited against the platform's own
repository and live deployment) established that **that hazard does not exist in their
system**:

- Each session gets its own workspace directory (`root / session_id`). **Two sessions never
  share a directory**, so two agents cannot write the same file.
- The shared root's read bit is stripped (`ROOT_MODE = 0o300`) and an OS-level sandbox
  confines each build subprocess to its own workspace — **enabled in production**, verified live.
- Their complete incident record contains **no case of two agents writing conflicting content
  into the same file.** The real incidents were a cross-session *read/copy*, a duplicate-session
  re-mint, and deploy-pipeline races.

The actual problem is the **opposite of collision — it is isolation.** Their own design docs
describe the current model as "disconnected islands" with "no visibility between concurrent
sessions on the same app," and the follow-on work (real git seeding, shared ancestry,
divergence reads, rebase affordance) is **unbuilt; status Proposed**.

That gap is memory-shaped, and Campy can close the visibility half without touching workspace
seeding or git ancestry. This card does that.

### What This Card Is NOT

- **Not collision prevention.** There is no collision to prevent. Anything framed as "warning"
  or "conflict" is wrong for this system.
- **Not a replacement for their git-workspace design.** It gives sessions *knowledge* of each
  other, not shared filesystem ancestry, and it merges nothing. The two are complementary; if
  that design lands later, this still adds value and does not conflict with it.
- **Not locking.** Campy stays advisory and fail-open (B318).

### The join key, and its one weakness

The unit of continuity is the **App**, not the session and not the file.

- App id is an opaque platform-supplied `<prefix>_<kebab-name>` string (e.g.
  `APP_notes-service`), and `app_id == slug`. Deterministic and in use.
- **Iteration has no identity of its own** — production sets `iteration_id = str(session.id)`.
  So "iteration" and "session" are the same thing today, and this card must not assume
  otherwise. Model continuity as **App → many sessions**, ordered in time.
- App slug rename-stability is **explicitly deferred** upstream. A pre-lock rename produces a
  different `app_id` for what a human considers the same App, and nothing reconciles it. Treat
  `app_id` as stable-in-practice, and record it as a known hazard rather than designing around
  a fix that does not exist.

### What This Card Does

**Task 1 — Record the App association on captured facts.**

Campy already has `Workspace` (`workspace_id`, `path`, `os`, `hostname`) and `Session`, joined
by `IN_WORKSPACE`. What is missing is the **external App identity**.

Add via `_MIGRATIONS` (`campy/brain/hippocampus/schema.py:1116`) — extend, never redefine:

| Table | Column | Meaning |
|---|---|---|
| `Session` | `external_app_id` | the platform's App id, e.g. `APP_notes-service` |
| `Session` | `external_session_id` | the platform's session id, for correlation |

Populate from the capture path when the client supplies them. **Both are nullable** — local
Campy has no App concept and must be unaffected.

**Task 2 — The continuity query.**

```python
async def app_continuity(
    db, *, external_app_id: str, exclude_session: str,
    limit_sessions: int = 5, since_days: int = 30,
) -> dict:
    """What earlier sessions of this App decided, tried, and learned."""
```

Return, per prior session, newest first: decisions, constraints, lessons, and plan outcomes
attributable to it, each with B312 provenance and its `authority` (B313).

Rules:
- `exclude_session` is **required** — a session seeing its own work reported back as
  "previous work" is noise that teaches agents to skip the section.
- Bound it: at most `limit_sessions` prior sessions, and a `since_days` window. This is a
  briefing, not an archive dump.
- **Prefer lessons and decisions over raw concepts.** The value is "we already decided X" and
  "we tried Y and it failed," not a term dump.

**Task 3 — Surface it, in the right register.**

Add a bundle section in `campy/brain/thalamus/bundle_compiler.py`, following the existing
`_stage_*` conventions (read the file first; the `0.70` similarity floor does **not** apply
here — this is an exact-id join, not a similarity match).

Wording is retrospective, never imperative:

> **Earlier work on this app**
> Session 3 days ago (`agent:build-worker`) — decided Postgres over Mongo for the task store;
> lesson: the Stripe webhook needs an idempotency key, first attempt double-charged in test.

Do **not** emit "do not", "already claimed", "in progress", "owned by". The same denylist test
from the original card applies, for the same reason: an advisory section that reads like a
guarantee will be relied on as one.

**Task 4 — Omit when empty, and fail open.**

Absent section when there is no prior work — not present-and-empty (the B305 convention).
Query failure or timeout drops the section and never fails the recall (B318).

**Task 5 — Verify the capture side actually populates.**

The original card's Task 5 asked whether `WorkArtifact` rows are written during ordinary agent
edits. **That question is now less central** — this card joins on `Session.external_app_id`,
not on file paths — but the capture path still has to receive and store the App id.

Determine how a client passes it. Options, in order of preference:

1. The platform's agent passes it in the capture call as ordinary tool input (an App id is not
   a security boundary — unlike `workspace_id`, which B315 forbids from request params).
2. Derived from `Workspace.path` if the workspace root encodes the App.
3. Not available → say so in the PR; the card cannot complete and needs a platform-side change.

State which applies. This is the one genuine unknown.

### Acceptance Criteria

- [ ] Two sessions carrying the same `external_app_id` — the second's recall surfaces the
      first's decisions and lessons, and never its own
- [ ] `exclude_session` is required; omitting it raises `TypeError`
- [ ] A session with a **different** `external_app_id` sees nothing
- [ ] A session with `external_app_id` NULL (local Campy) behaves exactly as today — the
      section is absent and nothing errors
- [ ] `limit_sessions` and `since_days` both bound the result
- [ ] Section is **absent** when there is no prior work — assert the key is missing
- [ ] Section text passes the imperative denylist (`do not`, `locked`, `claimed`,
      `in progress`, `owned by`)
- [ ] Each item carries provenance and `authority`
- [ ] Query failure produces a bundle without the section and does not raise
- [ ] Cross-workspace isolation holds (trivially true under B316; assert anyway)
- [ ] `pytest tests/ -q` failure set identical to pre-change baseline

### What This Card Does NOT Do

- Does not warn about, detect, or prevent file collisions
- Does not lock, lease, claim, or gate anything
- Does not implement the platform's own git-native workspaces, seeding, or merge
- Does not model Iteration separately from Session — upstream does not either
- Does not solve App-slug rename instability; it records it as a known hazard
- Does not push or notify — pull-only, surfaced on the next recall

### Outcome

A session starting work on an App inherits what earlier sessions of that App decided, tried and
learned, instead of starting from nothing. That is the "no visibility between concurrent
sessions" gap the platform's own design docs name — closed from the memory side, while their
git-native workspace work remains Proposed.
