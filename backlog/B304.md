### Problem

The `ask` demo question ("what did agent X do on B292?") now fails only at the final
synthesis step: retrieval and prompt assembly deliver the right bundle (verified live
2026-07-15 post-B303), but the default local model (`llama3.1:8b`) can't reliably read a
plan whose goal literally starts with "Implement B293…" and connect it to a question about
B293. We need to (a) pick a better default small model and (b) prove that harness
techniques compensate for small-model weakness — with numbers, not vibes.

**Hard constraint:** the default model must run on an "average" user machine — assume
16 GB RAM, so quantized model files ≤ ~10 GB (7B–9B class). The dev machine (M2 Max,
32 GB) can additionally test one larger tier, but the *default* recommendation must fit
16 GB.

**Hypothesis to test:** harness variant H1 (identifier fast-path) on the CURRENT
llama3.1:8b beats a naive (H0) run of a better model. If true, harnessing > horsepower
is validated with data.

### Design

Three parts: a deterministic fixture graph, a scored question set, and a matrix runner
that varies (model × harness variant).

#### Part 1 — Fixture graph (`benchmarks/ask_eval/fixtures.py`)

A function `async def seed_fixture_graph(db, config) -> None` that writes known content
through the REAL tool handlers (import from `campy.brain.thalamus.tools`) — never raw
Cypher — so the eval exercises genuine pipeline output:

1. Three plans via `register_plan` + step/final `report_outcome` (valence +0.9,
   `valence_source` explicitly `"explicit"` if B303's sweep-fix landed, else omit):
   - goal `"Implement B292 by splitting campy/brain/thalamus/tools/__init__.py into
     focused domain modules while preserving behavior and exports"`, steps:
     `["Create shared utility module", "Create domain modules with mechanical moves",
     "Rewrite __init__ as thin aggregator", "Run parity checks and tests"]`
   - goal `"Implement B293 so the MCP tool surface is schema-first with generated
     extension definitions and CI drift protection"`, steps:
     `["Derive EXPECTED_TOOLS from tool_schemas", "Add generator script",
     "Wire generated definitions into index.ts", "Add CI drift check"]`
   - goal `"Implement B298 Claude auto-memory piggyback capture into Campy via
     notify_turn with non-blocking hooks"`, steps:
     `["Parse memory frontmatter", "Wire PostToolUse hook", "Add idempotency key",
     "Add tests"]`
   Report each step succeeded, then a final plan-level outcome ("all steps complete,
   tests green", valence 0.9).
2. Two lessons via `upsert_lesson`:
   - `"When adding a new MCP tool, register it in tool_schemas.TOOLS and TOOL_HANDLERS,
     then regenerate extension entries with scripts/generate_extension_tools.py"`,
     domain `"tooling"`, lesson_type `"architecture-principle"`
   - `"Kuzu is single-writer: stop the daemon before any direct-DB maintenance command
     or it fails with a lock error"`, domain `"operations"`, lesson_type `"edge-case"`
3. Four messages via `notify_turn` (role user/assistant alternating,
   session_id `"eval-seed-session"`) describing ordinary work chatter, e.g. user:
   `"let's use Apache-2.0 for the license"`, assistant confirmation, user:
   `"the daemon port stays 7799"`, assistant confirmation. (No daemon loop runs in the
   eval process, so these stay raw Messages — that is fine and realistic.)

DB creation: mirror `tests/test_b64_integration.py` — `KuzuClient` at a temp path +
`init_schema(db, "campy/data/GistSeedExamples.md", embedding_model)`. Config: load the
real defaults (`campy/data/config/campy.toml`) then override `llm.model` per run.

#### Part 2 — Question set (`benchmarks/ask_eval/questions.py`)

A list of dicts: `{id, family, question, must_match: [regex], must_not_match: [regex]}`.
Regexes are case-insensitive. Full set (16 questions):

Identifier recall (4):
- I1 `"What work was done on B292?"` — must: `[r"split", r"__init__|module"]`; must-not: `[r"no (information|memory)|memory is empty"]`
- I2 `"What happened with B293?"` — must: `[r"schema|tool_schemas", r"generat"]`; must-not: `[r"memory is empty"]`
- I3 `"What did the work on B298 accomplish?"` — must: `[r"auto.?memory|memory file|piggyback", r"notify_turn|hook"]`; must-not: `[r"memory is empty"]`
- I4 `"Was B292 completed successfully?"` — must: `[r"complete|succeed|success|done"]`; must-not: `[r"fail|memory is empty"]`

Paraphrase recall, no identifiers (4):
- P1 `"Who or what split the big tools module into smaller files?"` — must: `[r"B292|__init__|domain modules"]`; must-not: `[r"memory is empty"]`
- P2 `"How do I add a new MCP tool the right way?"` — must: `[r"tool_schemas", r"TOOL_HANDLERS|generate_extension_tools"]`; must-not: `[r"memory is empty"]`
- P3 `"Why did a maintenance command fail with a database lock error?"` — must: `[r"single.?writer|daemon"]`; must-not: `[r"memory is empty"]`
- P4 `"What license did we pick?"` — must: `[r"Apache"]`; must-not: `[r"MIT|GPL|memory is empty"]`

Cross-lane (2):
- X1 `"What lessons came out of the tooling work?"` — must: `[r"tool_schemas|regenerate"]`; must-not: `[r"memory is empty"]`
- X2 `"Summarize everything we know about the extension tool surface."` — must: `[r"schema|generat"]`; must-not: `[r"memory is empty"]`

Continuation (2):
- C1 `"What was the plan for the module split and did every step finish?"` — must: `[r"aggregator|parity|steps"]`, must: `[r"complete|succeed|finish"]`; must-not: `[r"memory is empty"]`
- C2 `"What port does the daemon use?"` — must: `[r"7799"]`; must-not: `[r"memory is empty"]`

Negative controls — the anti-hallucination gate (4):
- N1 `"What did we decide about Kubernetes deployment?"` — must: `[r"no (information|record|memory)|not (found|mentioned)|don'?t have|empty"]`; must-not: `[r"kubernetes.*(cluster|helm|deploy(ed|ment) (is|was|uses))"]`
- N2 `"Who is the database administrator?"` — must: `[r"no (information|record)|not (found|mentioned)|don'?t have|empty"]`; must-not: `[]`
- N3 `"What did we conclude about the React frontend rewrite?"` — must: `[r"no (information|record)|not (found|mentioned)|don'?t have|empty"]`; must-not: `[r"react.*(chose|decided|rewrote)"]`
- N4 `"When is the production launch date?"` — must: `[r"no (information|record|date)|not (found|mentioned)|don'?t have|empty"]`; must-not: `[r"\b20\d\d-\d\d-\d\d\b"]`

Scoring per question: `covered = all must_match hit`; `hallucinated = any must_not_match
hit`. Question score: 1.0 if covered and not hallucinated; 0 if not covered; **-1.0 if
hallucinated** (fabrication is worse than ignorance). Also record latency per question.
Run score = mean. Negative-control family additionally reported as its own
pass-rate column.

#### Part 3 — Matrix runner (`benchmarks/ask_eval/runner.py` + CLI)

- New typer sub-app `eval_app` registered in `campy/cli/main.py` as
  `app.add_typer(eval_app, name="eval")` (mirror how `graph_app` is wired at line ~33 /
  ~463).
- `campy eval ask --model llama3.1:8b --model gemma4:e4b --variant H0 --variant H1
  --variant H2` — each (model, variant) combination: fresh temp DB → seed fixtures →
  for each question call `run_ask(query, session_id="ask-eval", db=db, config=cfg,
  capture=False)` (capture=False so eval questions never pollute the fixture graph) →
  score → next.
- Model override: deep-copy the loaded config and set `config["llm"]["model"] = <model>`
  (provider stays ollama). Precondition check: `ollama list` contains the model; if not,
  print a pull hint and skip that model (do NOT auto-pull).
- Output: a rich table (rows = model × variant; columns = overall score, per-family
  scores, negative-control pass rate, median latency) AND a JSON file written to
  `~/.campy/eval_results/ask-eval-<UTC timestamp>.json` (runtime dir — never write
  results into the repo).

#### Harness variants (implemented in `campy/brain/thalamus/ask.py`, toggled via
`config["ask"]["harness_variant"]`, default `"H0"`)

- **H0 — baseline**: current behavior, no changes.
- **H1 — identifier fast-path**: before prompt assembly, extract `\bB\d+\b` tokens from
  the query; if any bundle plan/lesson item's text contains one of those tokens, prepend
  to the prompt: `"DIRECT MATCHES for <tokens>: "` followed by those items' full
  goal/step text, and instruct: `"These items directly answer the question — base your
  answer on them."`
- **H2 — empty-claim guard**: after the LLM answers, if the bundle was non-empty AND the
  answer matches `r"(memory|context) is empty|no information"`, retry ONCE with the
  original prompt plus: `"The context above is NOT empty. List what the plans section
  contains, then answer the question from it."` Return the retry answer (record
  `retried: true` in eval JSON).
- Variants are additive flags in the eval CLI: `H1+H2` runs both. Keep each variant's
  code path small and clearly commented; both must be no-ops when not enabled so
  production behavior is unchanged by default (`H0`).

### Eval matrix to run (and report in the PR description)

Models (all ≤ 10 GB, 16 GB-safe): `llama3.1:8b` (baseline), `gemma4:e4b` (installed),
`gemma4:e2b` (low-RAM tier), `qwen3:8b` (pull first). Variants: H0, H1, H1+H2.
That's 12 runs × 16 questions. Include the table in the PR. The PR must state whether
the hypothesis (llama3.1:8b + H1 ≥ best model + H0) held.

### What This Card Does NOT Do

- No model auto-pulling, no model files in the repo
- No LLM-as-judge scoring (deterministic regexes only — rerunnable, free)
- No select-then-synthesize variant (H3) — follow-up card if H1/H2 don't close the gap
- No changing the shipped default model — that decision is made BY the maintainer FROM
  the eval table, in a follow-up one-line config change

### Outcome

A rerunnable instrument that turns "which small model + which harness tricks" into a
table, validates (or kills) the harness-over-horsepower strategy with data, and gives
every future ask/retrieval change a regression score.
