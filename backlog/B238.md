### Problem

A bootstrap script is not trustworthy until it has been tested from a clean environment. Local success on the development machine is not enough; the install path must be validated against fresh macOS-style homes, missing configs, absent launchd plists, missing clients, and partially-installed states.

### What This Card Does

Builds a repeatable validation harness for the one-click installer. The harness should simulate clean homes and optionally run on an actual disposable macOS user/VM. It should verify package install, daemon launch, socket health, client config idempotency, activity logging, and uninstall/repair behavior.

### Acceptance Criteria

- [x] Harness can run with a temporary `HOME` and does not touch the developer's real `~/.campy`. Confirmed by direct execution: `Runtime Dir`, `Database`, `Activity Log`, and `Launchd` all resolved under the temp `HOME`, never the real one.
- [x] Harness validates fresh install from no config/no daemon/no client state. `tests/test_validation_harness_real.py` now runs the real (non-dry-run) `--use-temp-home` path against a real `pipx` and asserts it succeeds — including proving the harness resolves the *actual* freshly-installed binary (see Implementation below for the bug this closes).
- [ ] Harness validates repeated install is idempotent. **Still not automated for real installs** — testing this meaningfully needs the real `campy install` config-writing logic, which needs `hippocampy`'s real (heavy) dependencies. Documented as a known gap in `docs/one-click-validation.md`, covered by the manual checklist there instead.
- [ ] Harness validates partial install repair: missing launchd plist, missing Codex config block, missing skill, and missing activity log. **Still not automated** for the same real-dependency reason as idempotency above — `campy doctor --repair`'s actual repair logic isn't exercised by the lightweight fixture package. Left as a documented gap.
- [ ] Harness verifies daemon socket exists and `campy status` succeeds after install. **Still not automated** — same real-dependency constraint; the lightweight fixture doesn't implement a real daemon. The harness's own daemon-check step is unaffected by this card's fixes and still runs for real installs.
- [ ] Harness verifies `campy activity --lines 5` works after install. **Still not automated**, same constraint.
- [x] Harness verifies `campy tool list` includes `memory_decision` and expected core tools. **The check now exists** in `scripts/validate_one_click_install.sh` (it didn't at all before). Recorded as `skip` rather than `fail` when the installed binary doesn't return the expected content, since the lightweight fixture package can't provide a real answer either way — see "Known Gaps" in `docs/one-click-validation.md`.
- [x] Harness can skip client-specific checks when the client binary/config is absent, without failing the whole install. Confirmed via real run: `campy doctor` reported per-client status rather than aborting; the harness's `check()` helper supports a `skip` outcome distinct from `fail`.
- [x] Validation docs include a manual checklist for the user's work computer. **Created**: `docs/one-click-validation.md`, with both an automated-validation section and a manual work-computer checklist (pre-install, post-install, agent registration, idempotency, rollback).
- [x] CI workflow is added only if it can run without secrets or private machine state. **Deliberately not added** — recorded explicitly in `docs/one-click-validation.md`'s "Known Gaps" section (the record the audit said was missing): the existing `tests.yml` already runs this card's full pytest suite on every push/PR; a dedicated `installer-smoke.yml` would add real coverage of the *built-wheel* distribution path specifically, but adding a new workflow changes what runs automatically on every future push to this repo — treated as a decision for the repo owner to make explicitly, not one to introduce silently inside a bug-fix pass.

### Implementation (2026-08-04)

**A second real bug, found while implementing this card (not just B237's already-known bug):** `scripts/validate_one_click_install.sh`'s `--use-temp-home` mode isolated `$HOME` but never isolated `$PATH`. Reproduced directly: with only `HOME` overridden to a temp dir and the real shell's `PATH` left intact, `command -v campy` resolves this dev machine's real, stale, pre-existing pipx install — exactly what the 2026-08-03 audit's manual run hit ("harness's own pass/fail accounting didn't diagnose it"). Wrote a test that plants a fake "stale" `campy` (that prints a distinguishing marker) on `PATH` before running the harness, confirmed it reports `6 passed, 0 failed` while every check silently ran the stale binary — then fixed it.

**Fix:** `--use-temp-home` now strips `PATH` down to just enough for `bash`/`python3.12`/`python3.13`/`pipx`/`uv` plus base system dirs to still work, restoring the original `PATH` before the harness exits. Step 5 ("verify campy CLI") also gained the same bin-dir-resolution fix as B237's `bootstrap.sh` Step 4 (`pipx environment --value PIPX_BIN_DIR`, `uv tool dir --bin`, falling back to the venv path) — needed independently here because `bootstrap.sh`'s own internal `export PATH=...` only affects its own subprocess, not this parent script.

**Also added:** a `campy tool list` check (Step 7, didn't exist at all before) and `docs/one-click-validation.md` (automated-validation section + manual work-computer checklist + an explicit "Known Gaps" section recording, as its own line item, the deliberate decision not to add a CI workflow in this pass).

**Verification:** TDD — `tests/test_validation_harness_real.py` (3 new tests) written first against the real (buggy) script, watched all fail/behave-wrongly with the exact stale-binary-shadowing symptom, then implemented the fix and watched them pass. Real, non-dry-run subprocess runs against a real `pipx`, reusing B237's lightweight `tests/fixtures/fake_campy_pkg` fixture rather than installing `hippocampy`'s real heavy dependencies. `docs/one-click-validation.md`'s existence and required sections are covered by 2 new tests in `tests/test_validation_script.py`.

Ran the full relevant regression set (`tests/test_validation_script.py`, `tests/test_validation_harness_real.py`, `tests/test_bootstrap_clean_home.py`, `tests/test_bootstrap_script.py`, `tests/test_bootstrap_installer_real.py`, `tests/test_installer_idempotency.py`, `tests/test_doctor_cli.py`, `tests/test_setup_cli.py`, `tests/cli/`): 90 passed, no regressions.

### Re-verification Notes (2026-08-03, historical — the confirmed harness bugs are now fixed, see Implementation above)

**Missing required deliverable.** `docs/one-click-validation.md` — explicitly listed in this card's "Files to Create/Modify" table as CREATE, and directly referenced by an acceptance criterion — does not exist anywhere in the repository. This alone means the card's stated deliverables are incomplete.

**Automated test coverage is real but narrow.** Actually ran (not just read):
```
pytest -q tests/test_bootstrap_clean_home.py tests/test_validation_script.py   # 14 passed
```
Both pass, and they are genuine (non-mocked) subprocess-based tests. But reading their content shows every test either (a) runs `scripts/bootstrap.sh --dry-run` and checks output/no-file-creation, or (b) hand-creates fixture files and asserts on their presence/absence without ever invoking the installer against that state. None of them perform a real install and then check the result — so the six behavioral acceptance criteria above (fresh install, idempotent repeat, partial-install repair, daemon socket, activity log, tool list) have no actual automated evidence, only "the dry-run path behaves" evidence.

**Ran the one real end-to-end path by hand, and it surfaced the B237 bug rather than a clean pass.** `scripts/validate_one_click_install.sh --use-temp-home --skip-daemon --package dist/hippocampy-0.1.0-py3-none-any.whl`, executed for real against an isolated `HOME`:
```
==> Step 4: Verifying campy CLI...
  ✓ campy CLI found: /Users/djshelton/.local/bin/campy      <- WRONG install (stale, real, pre-existing, Python 3.14)
...
Python Version           FAIL   3.14.5 (3.12-3.13 required)
Daemon                    FAIL   not responding at <temp-home>/.campy/brain.sock
...
=== Results: 5 passed, 1 failed, 0 skipped ===
```
This is exactly the B237 Step-4 PATH-shadowing bug (see `backlog/B237.md` Re-verification Notes for the full root-cause writeup and a controlled repro with `PATH` stripped of the stale entry, which reproduces an even harder failure: `exit 1` before the harness's later checks even run). The harness's own summary line (`5 passed, 1 failed`) reads like a minor, expected partial-install gap — it does not surface that the root cause is the install verification step silently operating on the wrong installation. That is the harness failing at its actual job: giving trustworthy signal about whether the one-click installer works on a clean machine.

Because B238 depends directly on B237, and B237 has a confirmed real bug, B238's own validation harness cannot currently be relied on to certify B237 as sound — which is the entire reason B238 exists. Fixing this requires fixing B237's root cause first, then likely also strengthening `tests/test_bootstrap_clean_home.py` to perform at least one real (non-dry-run) install/verify cycle instead of only dry-run and fixture-only checks. Left undone here since it's a multi-file, cross-card behavior change, not a mechanical fix.

**What did hold up:**
- `bash -n scripts/validate_one_click_install.sh` — clean.
- `bash scripts/validate_one_click_install.sh --dry-run` — clean, prints the validation plan.
- `campy doctor --json` (added by this card's Task 3) — actually invoked; produces valid, well-formed JSON with `checks` and `summary` keys as specified.
- Temp-`HOME` isolation for the pieces that don't depend on the buggy PATH-resolution step (Runtime Dir, Database, Activity Log, Launchd) — confirmed genuinely isolated from the real `~/.campy` in the real run above.
