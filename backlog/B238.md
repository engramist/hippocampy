### Problem

A bootstrap script is not trustworthy until it has been tested from a clean environment. Local success on the development machine is not enough; the install path must be validated against fresh macOS-style homes, missing configs, absent launchd plists, missing clients, and partially-installed states.

### What This Card Does

Builds a repeatable validation harness for the one-click installer. The harness should simulate clean homes and optionally run on an actual disposable macOS user/VM. It should verify package install, daemon launch, socket health, client config idempotency, activity logging, and uninstall/repair behavior.

### Acceptance Criteria

- [x] Harness can run with a temporary `HOME` and does not touch the developer's real `~/.campy`. Confirmed by direct execution: `Runtime Dir`, `Database`, `Activity Log`, and `Launchd` all resolved under the temp `HOME`, never the real one.
- [ ] Harness validates fresh install from no config/no daemon/no client state. **NOT AUTOMATED.** `tests/test_bootstrap_clean_home.py` only runs `--dry-run` against a clean `HOME`, or hand-constructs files and asserts they exist — it never invokes a real, non-dry-run `bootstrap.sh` and checks the resulting install state. The only thing that does a real fresh install is `scripts/validate_one_click_install.sh --use-temp-home`, which is not wired into any test suite or CI and must be run by hand. When run by hand for this audit it hit the B237 bug (below).
- [ ] Harness validates repeated install is idempotent. **NOT AUTOMATED for real installs** — only `--dry-run` run twice is tested (`test_dry_run_twice_same_output`, `test_bootstrap_dry_run_twice`); no test performs two real installs and diffs client/daemon/skill config state.
- [ ] Harness validates partial install repair: missing launchd plist, missing Codex config block, missing skill, and missing activity log. **NOT REALLY VALIDATED** — the corresponding tests (`test_partial_install_missing_brain_db`, `test_partial_install_missing_launchd_plist`) only assert that hand-created fixture files are absent; they never run `campy doctor --repair` against that state and check it actually gets repaired.
- [ ] Harness verifies daemon socket exists and `campy status` succeeds after install. **NOT AUTOMATED**; only exercised via the manual bash harness, and that run showed `Daemon FAIL not responding` (see below — confounded by the B237 bug, not independently isolated).
- [ ] Harness verifies `campy activity --lines 5` works after install. **NOT AUTOMATED** — no test (pytest or bash) calls this after a real install; `scripts/validate_one_click_install.sh` only checks `campy activity --lines 1` and only inside the `--use-temp-home` (not `--skip-daemon`) branch, which was never run to completion in this audit because the B237 bug and real-daemon-start risk made a full run unsafe to attempt against a temp environment repeatedly.
- [ ] Harness verifies `campy tool list` includes `memory_decision` and expected core tools. **NOT AUTOMATED anywhere** — no pytest test and no line in `scripts/validate_one_click_install.sh` checks this at all, despite being an explicit acceptance criterion. Confirmed by grepping both files for `tool list` / `memory_decision`: no matches.
- [x] Harness can skip client-specific checks when the client binary/config is absent, without failing the whole install. Confirmed via real run: `campy doctor` reported per-client status (`Plugin Status: installed: VS Code..., not installed: Claude Code, Codex`) rather than aborting; the harness script's own `check()` helper also supports a `skip` outcome distinct from `fail`.
- [ ] Validation docs include a manual checklist for the user's work computer. **UNMET — file does not exist.** `docs/one-click-validation.md` is listed as a required "CREATE" deliverable in this card's own Files table and is directly named in this acceptance criterion; it is not present anywhere in the repo.
- [ ] CI workflow is added only if it can run without secrets or private machine state. **Ambiguous, not documented either way.** `.github/workflows/installer-smoke.yml` does not exist. The criterion technically permits omitting it, but nothing records that this was a deliberate decision (that record would naturally live in the missing `docs/one-click-validation.md`) versus simply never having been done.

### Re-verification Notes (2026-08-03)

**Missing required deliverable.** `docs/one-click-validation.md` — explicitly listed in this card's "Files to Create/Modify" table as CREATE, and directly referenced by an acceptance criterion — does not exist anywhere in the repository. This alone means the card's stated deliverables are incomplete.

**Automated test coverage is real but narrow.** Actually ran (not just read):
```
pytest -q tests/test_bootstrap_clean_home.py tests/test_validation_script.py   # 14 passed
```
Both pass, and they are genuine (non-mocked) subprocess-based tests. But reading their content shows every test either (a) runs `scripts/bootstrap.sh --dry-run` and checks output/no-file-creation, or (b) hand-creates fixture files and asserts on their presence/absence without ever invoking the installer against that state. None of them perform a real install and then check the result — so the six behavioral acceptance criteria above (fresh install, idempotent repeat, partial-install repair, daemon socket, activity log, tool list) have no actual automated evidence, only "the dry-run path behaves" evidence.

**Ran the one real end-to-end path by hand, and it surfaced the B237 bug rather than a clean pass.** `scripts/validate_one_click_install.sh --use-temp-home --skip-daemon --package dist/hippocampy-0.1.0-py3-none-any.whl`, executed for real against an isolated `HOME`:
```
==> Step 4: Verifying campy CLI...
  ✓ campy CLI found: /Users/djshelton/.local/bin/campy      <- WRONG install (stale, real, pre-existing, Python 3.14)
...
Python Version           FAIL   3.14.5 (3.12-3.13 required)
Daemon                    FAIL   not responding at <temp-home>/.campy/brain.sock
...
=== Results: 5 passed, 1 failed, 0 skipped ===
```
This is exactly the B237 Step-4 PATH-shadowing bug (see `backlog/B237.md` Re-verification Notes for the full root-cause writeup and a controlled repro with `PATH` stripped of the stale entry, which reproduces an even harder failure: `exit 1` before the harness's later checks even run). The harness's own summary line (`5 passed, 1 failed`) reads like a minor, expected partial-install gap — it does not surface that the root cause is the install verification step silently operating on the wrong installation. That is the harness failing at its actual job: giving trustworthy signal about whether the one-click installer works on a clean machine.

Because B238 depends directly on B237, and B237 has a confirmed real bug, B238's own validation harness cannot currently be relied on to certify B237 as sound — which is the entire reason B238 exists. Fixing this requires fixing B237's root cause first, then likely also strengthening `tests/test_bootstrap_clean_home.py` to perform at least one real (non-dry-run) install/verify cycle instead of only dry-run and fixture-only checks. Left undone here since it's a multi-file, cross-card behavior change, not a mechanical fix.

**What did hold up:**
- `bash -n scripts/validate_one_click_install.sh` — clean.
- `bash scripts/validate_one_click_install.sh --dry-run` — clean, prints the validation plan.
- `campy doctor --json` (added by this card's Task 3) — actually invoked; produces valid, well-formed JSON with `checks` and `summary` keys as specified.
- Temp-`HOME` isolation for the pieces that don't depend on the buggy PATH-resolution step (Runtime Dir, Database, Activity Log, Launchd) — confirmed genuinely isolated from the real `~/.campy` in the real run above.
