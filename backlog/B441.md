# B441 - Hook Wrappers Silently Degrade With Zero Diagnostics When the Resolved `campy` Binary Is Broken/Stale

State: ready
Priority: P2
Branch: fix/b441-hook-wrapper-diagnostics
PR Target: main

### Note on origin

Found while implementing and end-to-end testing B440's `SessionEnd`
hook (`plugin/hooks/session_end_wrapper.py`). This machine's globally
installed `campy` (`/Users/djshelton/.local/bin/campy`, a pipx entry
point) resolves to a pipx venv running **Python 3.14.3**
(`~/.local/pipx/venvs/hippocampy`) — but this project's own
`requires-python` was narrowed to 3.12-only by B428 ("3.13 was a false
advertised claim"). Running that binary directly raises
`ModuleNotFoundError: No module named 'pyoxigraph'` immediately on
import.

B237/B238 already found and partially addressed this exact class of
problem — but only inside `validate_one_click_install.sh`'s own PATH
isolation (so the install *validator* no longer falsely certifies
against a stale binary in a fresh test run). Both cards' own
re-verification notes explicitly name "this dev machine's own stale
pipx `campy` entry" as the known confound being isolated away — i.e.
this machine's actual broken pipx install was never remediated, only
worked around for that one test harness's own correctness.

### Problem

`plugin/hooks/session_start_wrapper.py` and (as of B440)
`plugin/hooks/session_end_wrapper.py` both do:

```python
campy_cmd = shutil.which("campy")
command = [campy_cmd, ...] if campy_cmd else [sys.executable, "-m", "campy.cli.main", ...]
```

`shutil.which("campy")` finds the broken pipx entry point and *prefers*
it over the working fallback — and when that subprocess then crashes
(non-zero exit, or raises before producing output), both wrappers
degrade *completely silently*, per each hook's own fail-open design (a
hook must never block a session, confirmed intentional and correct
behavior). The problem isn't the fail-open behavior itself — it's that
there is **zero diagnostic signal anywhere** that this happened. On
this machine right now:

- `SessionStart` silently falls back to the generic
  `DEFAULT_SESSION_MESSAGE` instead of a real, personalized
  recommendation from `campy decide`.
- `SessionEnd` (B440) silently produces no `HANDOFF.md` at all.

A developer would have no way to discover their session automation is
non-functional short of manually running `campy <anything>` themselves
and noticing the traceback.

### Scope

1. Some form of one-time, low-noise diagnostic when the resolved
   `campy` binary fails — not a hard failure (hooks must stay
   fail-open), but something a developer could actually find. Options,
   not prescribed: log to `~/.campy/daemon.log` or a dedicated hook-log
   file; a `campy doctor`-surfaced check; a one-line stderr note (some
   hook frameworks show stderr to the user, some don't — verify before
   relying on this).
2. Consider whether `shutil.which("campy")` should still be preferred
   over `sys.executable -m campy.cli.main` at all, given the fallback
   is provably more reliable when both are available — or whether the
   preference order should flip (try the in-process-equivalent fallback
   first, only use the resolved binary as a secondary option).
3. Separately (may be a different, smaller card): whatever produces
   `~/.local/pipx/venvs/hippocampy` should not silently succeed when
   installing into a Python version this project's own
   `requires-python` excludes. Investigate `campy install`'s pipx
   invocation (or whatever wraps it) for why 3.14 was selected despite
   B428's constraint.

### Acceptance Criteria

- [ ] A broken/stale resolved `campy` binary produces *some* discoverable
      signal (log line, `campy doctor` finding, etc.) without blocking
      the hook or requiring the user to manually reproduce the failure.
- [ ] Decision made (and documented) on whether to keep preferring the
      resolved `campy` binary over the in-process fallback, given the
      fallback's proven higher reliability.
- [ ] Work executed in branch `fix/b441-hook-wrapper-diagnostics` and
      PR created targeting `main`.

### Outcome

A stale/broken global `campy` install degrades visibly instead of
silently, so a developer can actually notice and fix it (or the
installer itself refuses to create the broken state in the first
place).

### Related, minor observation (2026-09-22, not its own card)

While testing B440, `tests/adapters/test_claude_code_hooks.py::
test_session_start_hook_graceful_when_daemon_down` failed when a real
daemon happened to be running locally (started for B440's own manual
verification) — resolved once the daemon was stopped again. The test's
own isolation trick (`CAMPY_BRAIN_SOCKET` pointed at a nonexistent
path) doesn't actually apply to `adapters/claude_code/hooks/
session_start.sh`, which checks daemon health via a hardcoded
`curl http://127.0.0.1:7799/health` HTTP call, not the socket path the
env var overrides — so the test has only ever "passed" because CI
(and most local runs) don't have a live daemon on that port, not
because the isolation actually works. Same broader theme as this card
(a real daemon's presence/absence changing test/hook behavior in ways
that are easy to miss) — worth folding into this card's fix rather
than opening a fifth tangential card from one B440 session, but not
re-scoped into the acceptance criteria above since it's CI-safe
(no live daemon there) and only bites local dev runs.
