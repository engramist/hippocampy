# B366 - Flaky test_research_sim_detects_memory_benefit (Narrow-Margin Statistical Assertion)

State: complete
Priority: P3

Plan: none yet.

### Problem

`tests/test_research_sim.py::test_research_sim_detects_memory_benefit` failed in CI on PR #130 (a
docs-unrelated daemon change — `campy/brain_daemon.py`/`tests/test_auth_context.py` only, no
relation to `benchmarks/research_sim/` whatsoever):

```
assert baseline["regression_rate"] > sidequests["regression_rate"]
E   assert 0.6363636363636364 > 0.65
```

The test uses a fixed seed (`{"seed": 98765}`) and asserts `baseline["regression_rate"] >= 0.1` and
`baseline["regression_rate"] > sidequests["regression_rate"]` — a narrow-margin comparison (the
observed failure was off by only ~0.014) that depends on `ResearchSimHarness`'s internal
random-number draws. If the harness reseeds Python's *global* `random` module rather than using an
isolated `random.Random(seed)` instance, then whatever else runs earlier in the same pytest process
(and consumes global `random` state before this test's `setup()`/`run()`) could shift this test's
actual draws despite the "fixed" seed — consistent with this being a collection-order-sensitive
flake, the same general class as B360/B361, not a real regression. A full local suite run
immediately prior to this failure (after merging PR #125) came back completely clean (2180 passed,
0 failures), and PR #130's diff has no plausible connection to this test's subsystem.

### What was NOT established

- Whether the harness actually reseeds global `random` vs. using an isolated instance — not yet
  read. This is the first thing to check; if confirmed, it's the direct root cause and the fix is
  mechanical (use `random.Random(seed)` internally instead of `random.seed(seed)`).
- Whether this is genuinely order-dependent (reproduces when run after specific other tests) or a
  one-off CI environment quirk — not reproduced locally yet.

### What it does (scope)

1. Reproduce with a repeated-run loop, and specifically with `test_research_sim.py` run after
   `tests/test_auth_context.py`/`tests/test_daemon.py` (the two files most likely to consume
   `random` this session, given `_periodic_restart`'s `random.uniform()` jitter — B342/B365) to
   check for the exact cross-test interaction pattern.
2. Read `benchmarks/research_sim/`'s harness to confirm whether it reseeds the global `random`
   module or uses its own isolated `Random` instance.
3. Fix at the root: isolate the harness's RNG (a local `random.Random(seed)` instance, not global
   `random.seed()`) so this test's outcome is deterministic regardless of what ran before it in the
   same process — preferred over widening the assertion's margin, matching this project's existing
   preference (see B361) for eliminating the flake class over tolerating it.

### Outcome

Closed 2026-08-28. Item 2's premise turned out to be wrong when actually checked: the harness
already uses an isolated `random.Random(self.seed + variant_offset)` instance
(`benchmarks/research_sim/__init__.py::_simulate_variant`), not global `random.seed()` — this is not
a cross-test-order flake at all, and the "run after test_auth_context.py" reproduction plan in item 1
would never have found anything.

The actual root cause, found by reading `HypothesisTracker` (`benchmarks/research_sim/hypothesis_tracker.py`)
next: `_failed_hypotheses` was a `Set[str]`, and `_select_hypothesis`'s baseline branch does
`rng.choice(list(self._failed_hypotheses))`. A seeded `Random.choice()` deterministically picks an
*index* — but which hypothesis string sits at that index depends on `set`'s iteration order, which
for strings depends on Python's **per-process hash randomization** (`PYTHONHASHSEED`, random by
default on every interpreter start, unrelated to this test's own "fixed" RNG seed or to test
execution order within one process). That's the actual flake mechanism: stable within any single
`pytest` invocation (one hash seed for the whole process), but genuinely different across separate
invocations (fresh hash seed each time) — matching "passed 2180/2180 immediately before, failed on
the very next unrelated PR's CI run" far better than a same-process ordering theory would.

**Reproduced directly and precisely**, closing this card's first acceptance criterion with actual
evidence rather than a plausible-sounding theory: ran the harness under 200 different
`PYTHONHASHSEED` values (0-200) with the exact same `{"seed": 98765}` config. 5 of them
(`PYTHONHASHSEED=12, 33, 147, 150, 167`) reproduced the *exact* CI failure values —
`baseline["regression_rate"] == 0.6363636363636364` vs `sidequests["regression_rate"] == 0.65` — not
just a similar-looking failure, the identical floats PR #130's CI log showed.

**Fixed at the root**, per this card's own stated preference for eliminating the flake class over
widening a margin: changed `_failed_hypotheses` from a `Set[str]` to a `Dict[str, None]` (keys only,
insertion-ordered since Python 3.7+), so `failed_hypotheses()`'s return order is now a pure function
of the seeded RNG's actual sequence of decisions, with no incidental dependency on the interpreter's
hash seed. Re-ran the same 200-value `PYTHONHASHSEED` scan after the fix: **all 201 runs (0-200)
produce the bit-identical result** (`baseline=0.7777777777777778, sidequests=0.65`), including all 5
seeds that previously reproduced the real failure. `tests/test_research_sim.py` passes (3 passed).
