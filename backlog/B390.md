### Problem

Kùzu currently holds both the graph and the 384-dim fastembed vectors
(`FLOAT[384]` columns, `QUERY_VECTOR_INDEX`), plus full-text search via
`QUERY_FTS_INDEX`. Per `docs/rdf-schema-mapping.md` §5, **neither has a SPARQL
equivalent** — RDF has no ANN index and Oxigraph has no full-text search. Both must
move to a separate embedded store before the graph engine can be swapped.

Doing this first, against the *existing* Kùzu graph, de-risks the migration: the
vector/FTS plane is proven standalone while the graph is still known-good.

### Scope

Build `campy/brain/hippocampus/graph/vector_store.py` over
`~/.campy/vectors.db` (SQLite + `sqlite-vec` + FTS5).

1. **Vector plane:** `sqlite-vec` index over 384-dim fastembed embeddings.
   - Keyed by **full instance URI string** (`https://campy.dev/id/Concept/c_01H8XK`)
     per `docs/rdf-schema-mapping.md` §2, so it joins to Oxigraph with no
     translation table. During this card the URI is minted from
     `(table, primary_key)` using the spec's function even though Kùzu is still the
     graph — the key format must be final now.
   - Cosine distance, top-k with a distance threshold.
2. **Lexical plane:** SQLite FTS5 table, same URI keying, replacing
   `QUERY_FTS_INDEX`.
3. **Handler contract:** expose the two-stage shape the spec requires —
   ANN/FTS returns `[(uri, score)]`; graph hydration is the caller's job. The store
   must not know about Kùzu or Oxigraph.
4. **Calibration parity:** retrieval results must match the B279 calibration
   thresholds. Existing calibration tests are the acceptance check.
5. Add `sqlite-vec` to `pyproject.toml`. Confirm it is MIT/Apache-2.0.

### Explicitly NOT in scope

- Do **not** modify `kuzu_client.py`, `gateway.py`, or any named query.
- Do **not** cut retrieval over to this store. This card builds and proves the
  component; B397 wires it in. Cutting over here would break retrieval on `main`.
