# B422 - Whole `arc.link_mechanic_*` Handler Cluster Targets Wrong Edge Names + Non-Existent Node Tables — `publish_mechanic_summary` Would Raise on Every Link (Latent)

State: guard + 5 handler fixes implemented (this PR)
Priority: P2
Branch: docs/b422-mechanic-link-handler-cluster

### Problem

Found by auditing the entire `gateway.py` `_handle_oxigraph_handler` `write_edge` cluster
after B420/B421 (three instances of the same class made a full sweep worthwhile). Five
handlers — the mechanic/failure family — reference edge labels and node tables that do not
exist under those names, so every `write_edge` in them would **raise** (`write_edge` raises
for any edge not in `EDGE_REIFICATION`). They are wired to the live `publish_mechanic_summary`
MCP tool (`campy/brain/thalamus/tools/arc_mechanics.py:149-238`, schema
`tool_schemas.py:631`), but **no run has ever called that path** (0 occurrences in the
activity log), so this is latent, not actively firing — hence P2, unlike B421.

| Handler (gateway.py) | Writes edge | Uses node tables | Reality |
|---|---|---|---|
| `arc.link_mechanic_action_pattern` | `HAS_ACTION_PATTERN` | `Mechanic`, `Pattern` | edge unclassified; tables don't exist |
| `arc.link_mechanic_effect_pattern` | `HAS_EFFECT_PATTERN` | `Mechanic`, `Pattern` | " |
| `arc.link_mechanic_precondition` | `HAS_PRECONDITION` | `Mechanic`, `Precondition` | " |
| `arc.link_mechanic_failure_mode` | `HAS_FAILURE_MODE` | `Mechanic`, `FailureMode` | " |
| `arc.link_failure_recovery_policy` | `HAS_RECOVERY_POLICY` | `FailureMode`, `RecoveryPolicy` | " |

The schema actually declares these as **Arc-prefixed** node tables (`ArcMechanic`,
`ArcActionPattern`, `ArcEffectPattern`, `ArcPrecondition`, `ArcFailureMode`,
`ArcRecoveryPolicy`) and **differently-named** rel tables, e.g. `schema.py:1499-1500`:
`ARC_MECHANIC_HAS_ACTION_PATTERN (FROM ArcMechanic TO ArcActionPattern, confidence, evidence_count)`,
`ARC_MECHANIC_CAUSES_EFFECT_PATTERN (…)`. So each handler needs the correct rel-table name
+ Arc-prefixed `mint_uri` tables (and the declared props: `confidence` + `evidence_count`).
Same class as B420 (`ANCHORED_TO` vs `ENTITY_RULE`) and B421 (`Entity` vs `GridEntity`).

### Fix

For each handler, use the schema's real names, e.g.:

```python
if name == "arc.link_mechanic_action_pattern":
    self._client.write_edge(
        "ARC_MECHANIC_HAS_ACTION_PATTERN",
        mint_uri("ArcMechanic", params["mechanic_id"]),
        mint_uri("ArcActionPattern", params["pattern_id"]),
        {"confidence": params.get("confidence")})  # + evidence_count if the caller has it
    return []
```

Map each of the five to its real `ARC_MECHANIC_*` / `ARC_*` rel table and Arc-prefixed
endpoints (confirm each rel name in `schema.py`; only `HAS_ACTION_PATTERN` →
`ARC_MECHANIC_HAS_ACTION_PATTERN` and the effect one are shown above — the precondition /
failure-mode / recovery-policy rel names need to be read off the schema, and if any is
genuinely absent, that rel table must be added or the handler gated). Prove with a
`publish_mechanic_summary` round-trip test that asserts the edges exist and
`recall_mechanic_priors` reads them back.

### Systemic recommendation (do this regardless)

This is the **8th instance** of the class across B413/B420(×2)/B421/B422(×5): a gateway
handler or `sparql=` template hand-writes an edge label / node table / property set that
must match the schema, with nothing checking it until a live run raises. Add the guard
B420 proposed, as a unit test over the registry + handlers:

- every `write_edge(label, mint_uri(T1,…), mint_uri(T2,…), props)` reachable from a handler
  must have `label` in `EDGE_REIFICATION`, `T1`/`T2` in `NODE_PRIMARY_KEYS`, and (for
  star/occurrence edges) every prop key in `REL_COLUMNS[label]` — else fail at test time.

The audit script that found this (17 handler calls scanned, 6 clean, 5 broken here + the 2
already fixed) can seed that test directly.
