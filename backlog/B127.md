# B127 - DAG Task Graph Schema (First-Class Execution DAG in SideQuests)

State: complete ✅ DONE (2026-04-01)
Priority: P1

Plan: backlog/plans/B-127-dag-task-graph-schema.md

### Problem

When an orchestrator or coordinator agent builds a multi-task execution plan, there is no durable, auditable place to store the plan's dependency structure. The agent holds this in-context — it's lost between calls and invisible to any outside observer. `Plan`/`PlanStep` (B66) captures *strategic memory for recall*, but it's a linear chain optimized for embedding-based retrieval. What's needed is a **first-class execution DAG**: task nodes with explicit multi-parent dependency edges, topological ordering, live status, and a stable "ready frontier" query. This is the Task Board from the Task-Graph Orchestration pattern — versioned, auditable, durable.

### What it does

Adds `TaskGraph` and `TaskNode` node tables to the Kùzu schema with `DEPENDS_ON` edges forming a Directed Acyclic Graph (DAG). Implements cycle detection on insert and a topological-frontier query helper.

### New Node Tables

**`TaskGraph`**
- `graph_id STRING PRIMARY KEY`
- `label TEXT` — human-readable name (e.g., "solve puzzle 3f7fe0f6 run 2")
- `version INT64` — incremented on structural changes
- `session_id STRING`
- `owner STRING` — which agent/coordinator created it
- `status STRING` — "active" | "completed" | "abandoned"
- `created_at TIMESTAMP`
- `completed_at TIMESTAMP`

**`TaskNode`**
- `task_id STRING PRIMARY KEY`
- `graph_id STRING` — FK reference to TaskGraph
- `label TEXT` — short description of the task
- `description TEXT` — full intent (what success looks like)
- `status STRING` — "pending" | "active" | "complete" | "failed" | "skipped"
- `owner STRING` — which sub-agent or module owns this task
- `result TEXT` — filled on complete/failed (summary of outcome)
- `created_at TIMESTAMP`
- `started_at TIMESTAMP`
- `completed_at TIMESTAMP`

### New Relationship Tables

- `TASK_OF` — `TaskNode → TaskGraph` (membership)
- `DEPENDS_ON` — `TaskNode → TaskNode` (DAG dependency edge; a task is ready when all upstream deps are `complete` or `skipped`)

### Cycle Detection

On every `DEPENDS_ON` insert, run a bounded DFS from the new target node back toward the source node. If a path exists, reject the insert and return an error. This must be done in the `register_task_graph` handler before committing any edges.

### Topological Frontier Query

`get_ready_tasks` returns all TaskNode rows in a given graph where:
- `status = 'pending'`
- All nodes with a `DEPENDS_ON` edge pointing to this node have `status IN ('complete', 'skipped')`

This is a pure Kùzu Cypher query — no LLM involved.

### HNSW Vector Index

Do NOT add embedding columns to TaskNode. This schema is for execution coordination, not semantic recall. Recall is handled by `Plan`/`PlanStep` (B66/B67). Keep concerns separate.

### Acceptance Criteria

- `mcp_engine/schema.py` defines `TaskGraph` and `TaskNode` node tables with all listed properties
- `TASK_OF` and `DEPENDS_ON` relationship tables created with correct FROM/TO typing
- A `_dag_has_cycle(graph_id, from_task_id, to_task_id)` helper in `mcp_engine/tools/task_graph.py` that returns `True` if adding the edge would create a cycle
- A `_get_ready_tasks_query(graph_id)` Cypher helper that returns the topological frontier
- Unit tests in `tests/test_b127_dag_schema.py` covering: node creation, edge creation, cycle detection (rejects cyclic edge), frontier query (returns correct pending nodes)
