# B439 - test_traversal_speedup_measurement Is a Flaky Hard Timing Gate (plain <= OPTIONAL * 1.05) That Fails Intermittently on Shared CI Runners

State: fixed — this PR (2026-09-21)
Priority: P2
Branch: fix/b439-flaky-traversal-speedup-test
PR Target: main

### Problem

`tests/test_b410_status_parity.py::test_traversal_speedup_measurement`
(added in B410, `fa48e37`) asserted `t_plain <= t_opt * 1.05` — i.e. that a
plain-BGP `campy:archived false` query is no more than 5% slower than the
equivalent `OPTIONAL` + `FILTER(!BOUND(..) || ..)` query — timed as 10
back-to-back iterations of one arm followed by 10 of the other.

It failed on CI for PR #232 (run 35565191950, attempt 1, 2026-09-21):

```
E   assert 0.026415709299999434 <= (0.02407083259998899 * 1.05)   # ratio 1.097
1 failed, 2717 passed, 92 skipped, 2 xfailed in 864.44s
```

### Investigation

**Confirmed flaky, not a regression.**

- Attempt 2 of the *same run on the same commit* passed. Nothing in #232
  touches this query family (`gateway.py` / `bundle_compiler.py` only).
- Since B410 landed (2026-09-08): 108 completed `Tests` runs on main + PRs
  (69 success, 25 failure, 14 cancelled). Log-grepping all 25 failed runs
  (logs confirmed retrievable) for this test: 0 hits; the one known failure is only
  visible via attempt 1 of run 35565191950. So roughly 1 observed failure
  in ~100 runs — rare, but a hard merge gate.

**Reproduced locally, but only under load.**

- Idle machine (60 trials of the test's exact protocol, on-disk store, same
  fixture): plain/OPTIONAL ratio median 0.70, worst 0.87, **0 failures**.
  The genuine speedup is ~1.4x.
- With a full `pytest tests/` running concurrently as background load, real
  single-test runs printed speedups of 1.04x–1.24x and **2 of 12 failed**
  (0.85x and 0.91x). Under contention the advantage compresses toward 1.0x,
  so a 5% margin sits inside the noise band.
- Contributing factor: both arms pay an identical fixed cost —
  `_execute_and_collect` materialises 1000 rows into `RowDict`s — which
  dilutes the query-shape difference being measured.
- Unverified hypothesis: the fixture is a `tmp_path` **on-disk** store (not
  in-memory, as the original report assumed), so background RocksDB
  flush/compaction after the 24k-triple bulk insert may compete with the
  timed queries. I did not measure this.
- Contributing factor: the protocol timed all of arm A then all of arm B, so
  a load spike or drift lands on one arm only.

**What I could not establish.** I could not reproduce the failure with a
synthetic CPU-oversubscription harness (24 busy processes on 12 cores; old
protocol 0/40, worst ratio 0.94), and sample sizes (40–60) are too small to
distinguish a ~1% failure rate from 0%. I therefore did not claim a specific
mechanism for the single CI stall, and I could not show that a cleverer
estimator (interleaved median, interleaved min) beats the original at
tight thresholds — the min-based variant produced a 1.24 outlier in one
sample. That is why the fix loosens the assertion rather than only changing
how it is measured.

### Fix

- Interleave the two arms (A,B,A,B,…) so drift affects both, 15 iterations,
  compare per-arm **medians**.
- Replace the 1.05 gate with a coarse **1.5x regression ceiling** with an
  explanatory failure message, and always print the measured ratio. Worst
  ratios observed in any condition were ~1.10 (CI) and ~1.18 (local, loaded),
  so 1.5x has ample headroom while still catching a real planner regression
  (plain query becoming dramatically slower than the OPTIONAL form).
- The test no longer asserts "plain is faster"; that claim is now only
  logged. Result-count parity (`len(res_opt) == len(res_plain)`) remains a
  hard assertion.

### Follow-up (not done here)

If B410's "plain BGP is cheaper" property should be a hard guarantee, guard
it structurally (e.g. assert the generated SPARQL for the status filter
contains no `OPTIONAL`) rather than by wall-clock, or move timing checks to a
non-gating benchmark job.
