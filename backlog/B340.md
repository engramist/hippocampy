# B340 - `pip install hippocampy` Doesn't Get the Reviewed/Pinned Dependency Versions

State: complete — merged via PR #59 (2026-08-20)
Priority: P2

Plan: none yet.

### Problem

`requirements.txt` is meticulously pinned with extensive per-package rationale comments — e.g.
`sentence-transformers==3.3.1` (with a documented, deliberate decision not to bump past a known-CVE
transformers range, see the file's own comment block), `fastapi==0.133.0` + `starlette==1.6.0` (bumped
specifically to clear several HIGH starlette CVEs, per the comment), `pytest==9.1.1` (bumped to clear a
HIGH pytest CVE). This is the dependency set that's actually been security-reviewed and tested.

But `pyproject.toml`'s `[project] dependencies` — the set that governs what `pip install hippocampy`
(the real, now-published PyPI package, per B327) actually resolves — uses **floating `>=` bounds**:
`sentence-transformers>=2.2.0`, `fastapi>=0.115.0`, `openai>=1.50.0`, `spacy>=3.7.0`,
`uvicorn>=0.32.0`, and no direct `starlette` pin at all. An external audit flagged this: someone running
`pip install hippocampy` today does not necessarily get the versions that were actually reviewed and
tested — pip's resolver could legally satisfy `fastapi>=0.115.0` with something older than the
CVE-fixed `0.133.0`, or a `sentence-transformers` version whose transitive `transformers` range differs
from the one `requirements.txt`'s comment reasoned carefully about.

### What it does (scope)

1. Compare every dependency listed in both `pyproject.toml`'s `[project] dependencies` and
   `requirements.txt`, and identify every case where `requirements.txt` pins a specific version that
   `pyproject.toml`'s floating bound would not guarantee (i.e. pip could legally resolve something
   older or a different major/minor than what's actually been reviewed).
2. Tighten `pyproject.toml`'s bounds to match the reviewed floor from `requirements.txt` — at minimum,
   change each floating `>=X` to `>=Y` where `Y` is the actual reviewed/pinned version in
   `requirements.txt` (e.g. `fastapi>=0.133.0` not `>=0.115.0`), so `pip install hippocampy` can no
   longer resolve to a version below what's been security-reviewed. Do not necessarily convert to exact
   `==` pins in `pyproject.toml` (that's a stricter policy than most published libraries use and could
   cause its own resolution conflicts for downstream consumers) — raising the floor to match the
   reviewed version is the required minimum; discuss in the card outcome if exact pinning was chosen
   instead and why.
3. Carry forward the *reasoning*, not just the number — for dependencies where `requirements.txt` has a
   deliberate comment explaining why a version was chosen (the `sentence-transformers`/`transformers`
   CVE tradeoff is the clearest example), add a short inline comment in `pyproject.toml` too, or a
   pointer comment ("see requirements.txt for full rationale") so the constraint doesn't look arbitrary
   to a future maintainer editing `pyproject.toml` in isolation.
4. Add a CI check (or extend an existing one) that fails if `pyproject.toml`'s floor for any dependency
   also present in `requirements.txt` drops below `requirements.txt`'s pinned version — so this drift
   can't silently reoccur after the next dependency bump. A simple Python script comparing the two
   files' version specs is sufficient; it doesn't need to be a general-purpose tool.

### Dependencies

None.

### Files to create/modify

- `pyproject.toml`
- A new drift-check script (e.g. `scripts/check_dependency_pin_drift.py`) plus wiring it into whatever
  CI workflow already runs other repo-hygiene checks (check `.github/workflows/` for the right place).

### Acceptance Criteria

- [ ] Every dependency present in both files has a `pyproject.toml` floor at or above
      `requirements.txt`'s pinned version — verified by the new drift-check script, not by manual
      inspection alone.
- [ ] `pip install .` (or building the wheel and installing it fresh) in a clean venv resolves each
      shared dependency to a version at or above the `requirements.txt` floor — spot-check at least
      `fastapi`, `sentence-transformers`, and `openai`.
- [ ] The new drift-check script runs in CI and is proven to fail on a deliberately-introduced
      regression (test it locally by temporarily lowering a `pyproject.toml` bound and confirming the
      script catches it, then revert the deliberate regression).
- [ ] Existing packaging/install tests (`bash scripts/audit_public_release.sh` per B327's precedent, or
      whatever the current packaging validation entrypoint is) still pass.
