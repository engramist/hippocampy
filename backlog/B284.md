# B284 - Bound the Lexical Fallback and Property Scans

State: complete -- 2026-08-03. Fixed the real gap: the FTS branch of the lexical fallback now applies the same recency window and archived filter as the CONTAINS branch. See Implementation section below; original Audit Findings preserved further down for history.
Priority: P2

Plan: backlog/plans/B-284-lexical-scan-hygiene.md

### Problem

Kuzu 0.11.3 provides only primary-key hash indexes and HNSW vector indexes — no secondary property indexes, no built-in full-text search at our pin. Several hot queries are full table scans:

1. `current_truth`'s lexical fallback: `MATCH (m:Message) WHERE lower(m.text_raw) CONTAINS lower($query)` — scans every Message ever captured, on every recall. Message is the fastest-growing table (every turn writes one). This degrades linearly and runs inside the recall hot path.
2. `WHERE n.archived = false` filters in sweeps and retrieval scan whole tables (acceptable for sweeps, hot-path concern for retrieval).
3. `{gist_class: $domain}` lookups in knowledge-gap detection scan Concept.

### What This Card Does

1. Bounds the lexical Message scan with a recency window: only scan Messages from the last N days (default 14) and/or the current session+quest, with a hard `LIMIT` — recency is the actual intent of the episodic fallback ("what did we just say about X?").
2. Probes whether the pinned Kuzu build ships the FTS extension; if yes, adds an FTS index on `Message.text_raw` behind a feature flag and uses it instead of CONTAINS.
3. Adds a scan-budget regression test asserting the lexical query includes both the recency predicate and LIMIT.
4. Documents which remaining scans are accepted (sweep-time scans are fine — they're background) in a comment block.

### Implementation (2026-08-03)

**Fix:** `KuzuClient.fts_search()` gained an optional `cutoff: str | None` parameter. When provided, the Cypher becomes `CALL QUERY_FTS_INDEX(...) YIELD node, score WITH node, score WHERE node.created_at > timestamp($cutoff) AND node.archived = false RETURN node, score ORDER BY score DESC LIMIT {limit}` — the same window/archived semantics the CONTAINS branch already had. `retrieval.py`'s `current_truth()` now passes the already-computed `cutoff` variable into `fts_search(...)`.

**Why `WITH...WHERE` and not `WHERE` directly after `YIELD`:** confirmed empirically that Kuzu 0.11.3's parser rejects `YIELD node, score WHERE ...` (`Parser exception: expected rule oC_SingleQuery`). A `WITH node, score` continuation before the `WHERE` is required.

**Why filter before `LIMIT`, not after:** the alternative (fetch top-N FTS-scored rows, then filter old ones out in Python) has a real correctness gap — a `limit` of high-scoring-but-old rows could crowd out a matching recent row instead of surfacing it. Pushing the filter into the query itself, before `LIMIT`, avoids this entirely and is covered by a dedicated regression test (`test_fts_search_cutoff_does_not_truncate_before_filtering`).

**Also fixed (from the plan, not the audit — a related, low-risk gap the plan explicitly flagged):** `reconstruct_timeline`'s two `CONTAINS` scans over `Message` had no `LIMIT` at all — a genuinely unbounded full-table scan on every call, on the same fastest-growing table the audit's Problem section is about. Timeline reconstruction is deliberately "all history" (no recency window belongs there), so this adds a generous config-driven cap (`retrieval.timeline_limit`, default 200) rather than a window — bounds worst-case cost without changing behavior for any topic with a reasonable hit count.

**Verification:** TDD, real Kuzu DB (not mocked) in `tests/test_lexical_fallback_fts_real_kuzu.py` (6 new tests) — reproduces the exact audit scenario end-to-end through the real `current_truth()` tool (old message correctly excluded, recent message still surfaces), plus focused unit tests of `fts_search()`'s cutoff/archived filtering and the before-vs-after-LIMIT correctness guard. One more test (`test_reconstruct_timeline_queries_are_bounded_by_limit`) covers the `reconstruct_timeline` LIMIT addition. Existing `tests/test_lexical_fallback.py` (mocked) passes unchanged — its `LexicalCaptureDB` mock still has no `has_fts`, so it continues to only exercise the CONTAINS branch, same as before. `pytest tests/test_lexical_fallback.py tests/test_web.py -q` → 48 passed, 1 xfailed (identical count to the audit's own baseline — this card's specified validation command was already green before the fix, since the mock structurally cannot see the FTS bug; the real regression is proven by the new real-Kuzu file instead). Full suite: 1688 passed, 31 skipped, 2 xfailed (was 1681 after B250; +7 new tests, no regressions — the full unfiltered suite run is clean; an apparent 2-test failure seen only in one ad hoc combined-file invocation earlier was confirmed to be a pre-existing test-isolation artifact between unrelated files, not caused by this change).
