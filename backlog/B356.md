# B356 - KuzuDB Buffer Pool Bounding (Deferred, Future-Proofing Only)

State: deferred — not blocking, not scheduled. Revisit only per the trigger condition below.
Priority: P4

Plan: none — this card intentionally records a decision *not* to act now, plus the condition under which
that decision should be revisited. Do not pick this up without checking whether the trigger condition
has actually occurred.

Parent: [B353](backlog/B353.md) — read that card first for full context.

### Problem (as originally proposed, and why it doesn't apply right now)

Both rounds of the externally-reviewed plan (see B353's "External plan review" section) proposed bounding
KuzuDB's buffer pool (`kuzu.Database(buffer_pool_size=256MB, max_num_threads=2, ...)`), on the correct
factual basis that `kuzu.Database`'s own docstring states `buffer_pool_size` "Defaults to ~80% of system
memory" when left at its default of `0`.

That fact is real (verified directly against the installed `kuzu` package's docstring). But **whether it
matters for Campy's actual observed problem is a separate question, and it was checked, not assumed.**

An isolated test — bare `kuzu.Database()`, default `buffer_pool_size=0`, no schema, no embedding model
loaded at all — showed a physical footprint of **68.2MB immediately after opening, 77.6MB after a
trivial write+read**. This machine has ~31GB RAM; 80% would be ~25GB. The observed footprint is nowhere
close to that ceiling, and nowhere close to the ~1.2-2GB baseline observed throughout B342's testing with
the full daemon (schema + embedding model) running.

**Conclusion: KuzuDB's "~80% of RAM" default is a lazy ceiling, not an eager reservation.** For a small
graph (this project's own test data: 5 concepts, 8 messages, per B342's original incident report), it
costs almost nothing regardless of what the ceiling is nominally set to. Bounding it would not change
Campy's current baseline footprint or address any part of B311/B342's growth findings — both of those are
about the embedding stack and `asyncio.to_thread`-routed executor activity, not KuzuDB's buffer pool.

### Why this card exists anyway, instead of just dropping the idea

Per this project's own standing practice (see `feedback_incidental-issues-get-cards.md` in memory —
"always file a backlog card immediately for unrelated issues found in passing, don't just mention and
move on"): a verified-but-not-currently-actionable finding still gets a card, not a footnote lost in
chat. This also protects against the idea being re-proposed later by someone (human or agent) who
rediscovers the "80% of RAM" default without checking whether it's actually consumed — the answer is
already here, verified, with the actual numbers.

### What it does (scope) — if and when revisited

Bound `buffer_pool_size` and `max_num_threads` via new `KuzuClient.__init__` parameters (the current
signature, `__init__(self, db_path, read_only=False, auto_checkpoint=True, checkpoint_threshold=-1)`,
does not expose either — they'd need to be added and threaded through to the underlying
`kuzu.Database(...)` call inside `KuzuClient`, not bypassed via a raw `kuzu.Database()` call the way both
external plan drafts wrote it). A reasonable starting point if this is ever picked up: `buffer_pool_size`
in the low hundreds of MB (256MB was the externally-proposed figure — not independently verified as the
right number, just a reasonable starting guess), `max_num_threads` around 2-4 depending on what's
actually needed for query latency at whatever data scale triggered the revisit.

### Trigger condition — when to actually revisit this

Not on a schedule. Revisit if either becomes true:
1. The graph's real data volume grows large enough that KuzuDB's own footprint (checked the same way this
   card checked it — an isolated `vmmap` reading of a `KuzuClient`-only process, no embedding model
   loaded) becomes a meaningfully large fraction of the daemon's total footprint (a rough starting
   threshold: if KuzuDB alone ever measures above ~500MB-1GB in such an isolated check, it's worth
   bounding as a precaution even before it becomes a majority contributor).
2. Someone observes memory pressure specifically correlated with heavy query/traversal load (not just
   idle baseline) — this card's own test didn't exercise anything beyond a trivial single-row write/read,
   so it says nothing about KuzuDB's behavior under a genuinely large, actively-queried graph.
