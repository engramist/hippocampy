### Problem

ARC_AGI's planner never asks the graph "what do we already know about this specific object" before
deciding whether to act on it — only action-family-level evidence (`fetch_per_action_evidence`,
`fetch_rules_for_action`) and coordinate-level attempt/falsification counts exist today. The one
entity-scoped query already exposed, `get_entity_history`, is used once client-side for a flat +0.08
goal-confidence bump, not for hypothesis generation. ARC's own A175 already gives every entity a stable
`entity_ref` across frames; it just never reaches a query that returns "what hypotheses/mechanics touch
this entity."

### What it does (scope)

Add one new read tool: `arc_get_entity_neighborhood`.

Request: `{"task_id": "...", "entity_ref": 3}`

Response: `{"hypotheses": [{"hypothesis_id": "...", "claim": "...", "confidence": 0.6, "falsified":
false}], "mechanics": [{"name": "...", "confidence": 0.5}]}` — live (unfalsified) hypotheses and
mechanics already associated with the given entity.

Schema options (implementer's call, whichever is cheaper against the current schema — evaluate both
before picking):

1. A new direct edge from `GridEntity` to the `Hypothesis`/`Rule` nodes derived from effects observed on
   that entity (a natural extension of the existing `Transition` nodes, which `Rule` nodes already
   reference via `CONFIRMED_BY`/`FALSIFIED_BY`).
2. Traversal through existing nodes: `GridEntity` already has `MOVED_BY` edges to `ActionEffect` (per
   `arc_get_entity_movement`'s existing pattern) — traverse from there out to whatever `Rule`/`Hypothesis`
   nodes reference those same effects, no new edge type needed.

### Implementation Notes (2026-08-23)

**Scope was expanded beyond a read-only tool before writing any code**, per an explicit user decision:
tracing the actual write paths in this repo before implementing found that neither association this
tool needs to read actually gets written anywhere. `ENTITY_HYPOTHESIS (GridEntity -> Hypothesis)` exists
in `schema.py` but nothing ever wrote to it; more strikingly, **no tool in this repo ever creates a
`Hypothesis` node at all** — `arc_confirm_hypothesis`/`arc_contradict_hypothesis` only ever `MATCH` by
`id`, assuming one already exists. `ArcMechanic` has no entity-level edge either (only task-level, via
`source_task_ids`) — `GridEntity` appears in exactly one file in this whole codebase (`arc_queries.py`).
Given this, "build the read tool as literally scoped" would have shipped a tool that always returns
empty results. Presented this to the user with three options (ship the hollow read tool, expand scope to
also build the write-path, or check back with arc-agi-45 first); the user chose to expand scope.

**Concrete realization of "expand scope," scoped narrowly to what's actually reachable today:**
Hypothesis *creation* is a separate, much larger, pre-existing gap (nothing creates them at all) and was
explicitly left out — wiring that up is not this card's problem to solve. What *is* reachable: both
`arc_confirm_hypothesis` and `arc_contradict_hypothesis` already get called against hypotheses that
exist by some means outside this repo's own write paths, so both gained an optional `entity_ref` (+
`step`) param. When present, they now `MERGE` the `ENTITY_HYPOTHESIS` edge with the hypothesis's current
confidence as `weight` — real, incremental progress from an already-reachable write point, not a
fabrication. `entity_ref`/`step` are optional; omitting them is a no-op, not an error (test:
`test_b359_confirm_hypothesis_without_entity_ref_does_not_link`).

**"Mechanics" in the response is task-scoped, not per-entity**, and this is documented in the function's
own docstring rather than silently overclaiming precision the schema doesn't model: `ArcMechanic` has no
per-entity edge anywhere, so `arc_get_entity_neighborhood` returns live mechanics for the entity's
`task_id` (via the same `source_task_ids CONTAINS` pattern `recall_mechanic_priors` already uses), which
is real, populated data (`publish_mechanic_summary` does write it) rather than an empty stub.

**A real, separate, pre-existing bug was found and fixed while building this**, not something this
card's own new code introduced: `arc_perceive_state` builds each `GridEntity`'s `entity_id` from
`region_index` but never actually persisted `region_index` as its own field on the node. This meant
`record_transition`'s existing `TRANSITION_OF` edge (A176, already shipped, joins on
`GridEntity {region_index: $eref}`) has **silently never been created, ever** — nothing caught it because
`get_entity_history` reads `Transition.entity_ref` directly and never needed the edge. My own new
`ENTITY_HYPOTHESIS` write hit the identical join and returned zero rows, which is how this surfaced.
Fixed at the root (`arc_perceive_state` now sets `e.region_index`), with a new explicit regression test
(`test_a176_record_transition_and_get_entity_history`'s new assertion) locking in that the
`TRANSITION_OF` edge actually gets created — previously nothing verified that, only that
`get_entity_history` returned right despite the edge being absent.

**Declaration sites touched** (5, not the 3 the general MCP-tool-addition lesson names, since
`arc_tools.py` re-exports from `arc_queries.py` before `tools/__init__.py` imports from `arc_tools.py`):
`campy/brain/thalamus/tools/arc_queries.py` (handler + `__all__`), `arc_tools.py` (re-export),
`tools/__init__.py` (`TOOL_HANDLERS`), `tool_schemas.py` (`TOOLS`), `extensions/hippocampy/src/index.ts`,
plus `tests/test_arc_queries.py`'s `EXPECTED_ARC_TOOLS` set.
