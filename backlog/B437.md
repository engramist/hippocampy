# B437 - bundle_compiler.py's Schema-Introspection Helpers Always Return False Against the Real Oxigraph Engine — Flagged/Archived/Superseded Content Leaks Into ask()/compile_context()

State: ready
Priority: P0
Branch: fix/b437-bundle-compiler-schema-introspection
PR Target: main

### Problem

`campy/brain/thalamus/bundle_compiler.py` has three schema-introspection
helpers — `_table_has_authority`, `_table_has_flagged_for_review`,
`_table_has_column` — used by `_stage_exact_facts`,
`_stage_semantic_context`, and `_stage_graph_structure` to decide
whether to append `_flagged` / `_archived` / `_superseded` / `_auth`
suffixes onto the `thalamus.bundle_*` NamedQuery name they call (each
suffix adds the corresponding exclusion filter to that query's
WHERE clause).

All three helpers detect the column by running:

```python
r = db.execute(f"CALL table_info('{table}') RETURN *")
```

`CALL table_info(...)` is **Kùzu-only Cypher syntax**. Since the
Kùzu -> Oxigraph cutover (B389/B397), the real `db` in production is
`OxigraphClient`, whose `execute()` passes the string straight to
pyoxigraph's real SPARQL parser (`self.store.query(...)`). This is not
valid SPARQL, so it raises, is caught by the helper's own bare
`except Exception: pass`, and the helper **always returns `False`** —
even when the column genuinely exists.

Verified directly against a real `OxigraphClient` instance
(2026-09-20): `_table_has_authority`, `_table_has_flagged_for_review`,
and `_table_has_column(..., "archived")` all returned `False` for
`Concept`, even though `Concept`'s DDL in `schema.py` declares all
three columns (`archived`, `flagged_for_review`, `authority`).

### Impact

Because these helpers always report "column absent" in production,
every one of `bundle_compiler.py`'s three affected stages always picks
the **base** NamedQuery variant (no exclusion suffix) — the one with no
`flagged_for_review` / `archived` / `superseded_by` WHERE clause at all.
Concretely, in production right now:

- `_stage_exact_facts` (GlobalConstraint/GlobalPreference)
- `_stage_semantic_context` (Concept/Decision/Constraint/Requirement)
- `_stage_graph_structure` (Concept)

can all surface **flagged-for-review, archived, or superseded** content
into the context bundle handed to `ask()` / `compile_context()` — the
exact anomaly-flagged or stale/contradicted facts these exclusions
exist to keep out of LLM-facing recall. This is the same failure shape
as B432 (`explore_graph` structurally broken against the shipped
Oxigraph engine): code that looks correct and is covered by tests that
run against a **real Kùzu client** (`tests/kuzu_test_client.py`'s
`KuzuClient`, which genuinely supports `CALL table_info`), never
exercised against the actual production engine.

### Fix

Replace the runtime `db.execute("CALL table_info...")` introspection
with a static schema lookup — `NODE_COLUMNS` (from
`campy/brain/hippocampus/graph/oxigraph_client.py`, parsed once from
`schema.py`'s DDL, engine-independent) already has exactly this
information:

```python
from campy.brain.hippocampus.graph.oxigraph_client import NODE_COLUMNS

def _table_has_column(db, table: str, column: str) -> bool:
    return column in NODE_COLUMNS.get(table, {})
```

`_table_has_authority` / `_table_has_flagged_for_review` become thin
wrappers over the same check (or are deleted in favor of direct
`_table_has_column(db, table, "authority")` calls at each call site).
Verified this returns the correct `True` for `Concept`/`archived`,
`flagged_for_review`, `authority` in a quick manual check.

### Completion Notes (2026-09-20)

Found while implementing B435, which touches the same function: fixing
`_table_has_column` alone (switched to the static `NODE_COLUMNS` schema
lookup, as this card originally proposed) was NOT sufficient — the real
bug went deeper. The Oxigraph Python handlers in `gateway.py`'s
`_handle_thalamus_bundle` for all three affected query families
(`thalamus.bundle_exact*`, `thalamus.bundle_semantic_*`,
`thalamus.bundle_graph_anchors*`) completely ignored their own qname
suffix — they never even fetched `flagged_for_review` / `archived` /
`superseded_by` from the graph, regardless of which NamedQuery variant
was requested. Even with `_table_has_column` correctly returning `True`
and the correct suffixed qname being requested, these handlers would
still leak flagged/archived/superseded content, because the suffix
never reached the actual SPARQL hydration query or its Python-side
filtering.

Fixed all three handlers: each now parses its own suffix
(`_flagged`/`_archived`/`_superseded`), adds the corresponding
`OPTIONAL` triple patterns to hydrate those fields, and filters
accordingly before appending to the result rows (with the `limit` cut
correctly moved to *after* filtering, so excluded candidates don't
starve the result of otherwise-available matches).

Verified against a real `OxigraphClient` (6 new tests in
`tests/test_b437_bundle_compiler_schema_introspection.py`, covering all
three affected stages plus the helper functions directly). Confirmed
all three stage-level tests fail without the `gateway.py` fix and pass
with it. Full test suite green; guard scripts clean.
