# B445 - Real Cloud Dispatch: Let Campy Actually Call the Model route_task Recommends

State: ready
Priority: P2
Branch: feat/b445-real-cloud-dispatch
PR Target: main

### Note on origin

`route_task` (B382, merged via
[PR #236](https://github.com/engramist/hippocampy/pull/236)) is
advisory-only by design — it returns `{tier, recommended_model,
context_bundle, rationale}` and never calls a cloud model itself, "the
caller decides whether/how to actually call a frontier model." This
was a deliberate scope boundary matching the card's own stated MCP
interface, not an oversight. This card is for if/when that boundary
should actually move — Campy itself making the real API call, not
just recommending one.

**This is a genuine architecture and product decision, not a
mechanical follow-up** — read the whole card before starting, and
confirm the scope/safety approach with the user before implementing
anything that can spend real money.

### What already exists (verified 2026-09-22)

The hard infrastructure part is mostly already built and directly
reusable — this is not starting from zero:

- **`campy/brain/llm/provider.py`**: `create_llm_client(config)` /
  `create_llm_client_for_step(config, step_name)` already support
  `ollama`/`openai`/`anthropic`/`google`/`bedrock`, resolve API keys
  from env vars (`OPENAI_API_KEY`/`ANTHROPIC_API_KEY`/
  `GOOGLE_API_KEY`, or boto3's default credential chain for Bedrock —
  no key needed), and return `None` gracefully if a provider is
  unavailable/misconfigured (already-established fail-open
  convention). This is the *exact same shape* `route_task`'s tier
  config (`provider`/`model` per tier) already carries — the plumbing
  match is direct, not coincidental.
- **`LLMClientProtocol`**: `chat()`/`chat_with_usage()`/`achat()`/
  `achat_with_usage()`, with `last_usage: dict | None` (B180) already
  tracking token usage per call. This is real, working cost-visibility
  infrastructure to build on, not something to invent.
- **What's genuinely missing** (confirmed by grep, not assumed): zero
  hits anywhere in the codebase for a spend cap, budget cap, rate
  limit, or any kind of pre-call confirmation gate. Nothing today
  stops a misconfigured or malicious caller from burning arbitrary
  API spend through `create_llm_client`. This has been fine so far
  because every existing caller (`step2_gist`, `step6_arbitration`,
  `ask()`, etc.) is Campy's *own* internal pipeline, gated by
  `campy.toml`'s own config that the user directly controls — B445
  would be the first path where an *external agent/caller* could
  trigger real spend through a tool call, which is a different trust
  boundary.

### Recommendation

**1. A new, separate tool — don't change `route_task`'s contract.**
`route_task` is documented and tested (30 tests in
`tests/test_model_router.py`) as advisory-only; every existing caller
relies on it never having a side effect. Silently teaching it to
sometimes spend money would violate its own documented behavior and
risk surprising an existing integration. Add a new tool instead
(name TBD — `execute_task`/`dispatch_and_run` — not prescribed here)
that:
   - Calls `route_task`'s existing logic internally to get the
     routing decision (reuse `model_router.route_task()` directly,
     don't duplicate the phase-detection logic).
   - If (and only if) the caller explicitly opts in (see safety gate
     below), constructs a client via `create_llm_client()` using the
     recommended tier's `provider`/`model` (small adapter needed:
     `route_task`'s tier config lives at `config["routing"]["tiers"]
     [tier]`, not `config["llm"]`, which is what `create_llm_client`
     reads — build a temporary `{"llm": {...}}` dict from the tier
     config, or add an explicit provider/model override parameter to
     `create_llm_client` itself, whichever is less invasive once you're
     looking at the real call sites).
   - Sends the task description + `context_bundle` (already built by
     `route_task`) as the prompt, returns the model's real response.

**2. Safety gate — default to confirmation, not silent execution.**
Real financial/external-system actions get explicit user permission by
default in every other context this session operates under — the same
principle should apply to a feature that spends the user's own API
budget on their behalf. Concretely:
   - The new tool should require an explicit `confirm: true` (or
     equivalent) parameter — calling it without confirmation should
     return the routing recommendation only (same shape as
     `route_task`) plus an estimated cost/token count, *not* execute.
   - A configurable spend cap (`[routing].max_spend_per_call` or
     similar, following B375/B382's established `_DEFAULT_CONFIG`
     merge convention) that refuses to execute above a threshold,
     defaulting to something conservative or requiring the user to set
     it explicitly before any real dispatch is possible at all.
   - Log every real dispatch (provider, model, tokens, estimated cost)
     somewhere durable and inspectable — `~/.campy/activity.log`
     (already exists, mentioned in this repo's own CLAUDE.md as the
     place for "recall queries, status" — extending it to cover real
     spend events fits its existing purpose) is a reasonable
     candidate, not prescribed.

**3. Scope the provider list down for v1.** Local (`ollama`) obviously
needs no safety gate at all (no real-world cost) — consider whether v1
should even support cloud providers immediately, or ship the mechanism
gated behind the safety controls above with `ollama`/local models
first (where the risk is near-zero) and cloud providers as an explicit
opt-in config flag, rather than shipping full frontier-model dispatch
capability on day one.

### Open questions for the user (resolve before implementing)

- Is this feature actually wanted at all, given Campy's current
  local-only usage pattern (confirmed earlier in this session: no
  cloud provider is configured for this installation)? Building this
  now would be speculative infrastructure for a workflow not currently
  in use.
- If wanted: what's an acceptable default spend cap, and should
  cloud-provider dispatch require an explicit `campy.toml` opt-in
  flag separate from local dispatch?
- Tool naming and exact parameter shape (not prescribed above).

### Files to create/modify (indicative, not exhaustive — scope will
shift based on the open questions above)

- Create: the new dispatch tool (module + MCP wrapper, same 5-site
  registration pattern as B382/B383/B440: `TOOL_HANDLERS`,
  `tool_schemas.TOOLS`, `scripts/generate_extension_tools.py`
  regeneration, `docs/tool-catalog.md`, `scripts/
  check_principal_ratchet.py --update`)
- Modify: `campy/brain/brainstem/config.py` / `campy.toml` (spend cap
  + cloud-dispatch opt-in config)
- Modify: `campy/brain/llm/provider.py` (if an explicit override
  parameter is the chosen approach over building a temp config dict)
- Create: tests proving the confirmation gate and spend cap are both
  genuinely load-bearing (not just present) — same rigor this session
  applied throughout (revert the gate, confirm the test fails).

### Acceptance Criteria

- [ ] Confirmed with the user whether/how this should actually ship
      before writing implementation code.
- [ ] `route_task`'s existing advisory-only contract and all 30 of its
      existing tests remain unchanged and passing.
- [ ] Real dispatch requires explicit confirmation — verified by a
      test that calling without it never results in an API call.
- [ ] A configured spend cap genuinely blocks dispatch above it —
      verified by a test proving this, not just documented.
- [ ] Every real dispatch is logged somewhere durable and inspectable.
- [ ] Work executed in branch `feat/b445-real-cloud-dispatch` and PR
      created targeting `main`.

### Outcome

A developer can go from "Campy recommends a frontier model" to
"Campy actually asked it, safely and with cost visibility" in one
opt-in step — without touching `route_task`'s existing, tested,
advisory-only contract.
