# B351 - AF_UNIX Path-Too-Long Failures in Socket-Stub Tests (Environmental, Pre-Existing)

State: ready
Priority: P3

Plan: none yet.

### Problem

While verifying B342's periodic-restart change (PR #86) didn't introduce regressions, running the test
suite with a `-k` filter surfaced 3 failing tests, all with the identical error:

```
OSError: AF_UNIX path too long
```

```
tests/adapters/test_claude_code_hooks.py::test_session_start_hook_graceful_when_daemon_down
tests/test_fail_open.py::TestCallBrainSoftFailureModes::test_stalled_daemon_times_out_and_returns_default
tests/test_fail_open.py::test_claude_code_post_tool_use_hook_exits_zero_and_stays_under_budget_against_stalled_daemon
```

All three go through the same helper, `unix_stub_server()` in `tests/test_fail_open.py`, which binds a
real `AF_UNIX` socket at a path built from pytest's per-test tmp directory
(`socket.socket(socket.AF_UNIX, ...).bind(str(sock_path))`). macOS (and BSD generally) caps `AF_UNIX`
socket paths at roughly 104 bytes. Pytest's tmp directory path on this machine — of the form
`/private/var/folders/<hash>/.../pytest-of-djshelton/pytest-<N>/<test_name>0/brain.sock` — is long
enough, especially for tests with long names (`test_claude_code_post_tool_use_hook_exits_zero_and_stays_
under_budget_against_stalled_daemon` is itself over 90 characters), to blow past that limit.

**Confirmed pre-existing, not caused by any in-flight change:** reproduced identically against
unmodified `main` via `git stash` + re-run (see B342/PR #86's verification notes). This is a standing,
environment-dependent flakiness in the test suite itself — likely worse on machines/CI runners with
longer base tmp-dir paths (username length, `TMPDIR` configuration, etc.), and probably passes silently
on shorter-tmpdir setups, which is presumably why it hasn't been caught/fixed already.

### What it does (scope)

1. Fix `unix_stub_server()` (and any other test helper following the same pattern) to use a
   short, collision-safe socket path instead of one derived from pytest's full tmp directory — e.g.
   a path under `/tmp` directly (still bounded, but much shorter than pytest's nested per-test
   tmpdir), or a short random suffix in a fixed short-prefix directory.
2. Audit for other test helpers that bind `AF_UNIX` sockets against pytest tmp paths and could hit the
   same limit under sufficiently long test names or deeply nested tmpdirs.
3. Confirm the fix by running the 3 currently-failing tests directly and confirming they pass, plus a
   full suite run to catch any other test relying on the specific (long) path this changes.

### Dependencies

None — fully independent of B342/B311's memory investigation; the socket path length has nothing to do
with daemon memory behavior. Found incidentally while verifying an unrelated change.

### Files to create/modify

- `tests/test_fail_open.py` — `unix_stub_server()` helper, and any call sites relying on its current
  path construction.
- Possibly other test files if the audit in scope item 2 finds more instances.

### Acceptance Criteria

- [ ] The 3 tests listed above pass reliably (not just "shorter path happens to fit this run").
- [ ] Root cause (socket path length) is fixed at the helper level, not worked around per-test.
- [ ] A brief note on why the old path length was unsafe (104-byte `AF_UNIX` limit) so this doesn't
      regress if someone changes the helper again later.
