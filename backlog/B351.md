# B351 - AF_UNIX Path-Too-Long Failures in Socket-Stub Tests (Environmental, Pre-Existing)

State: closed — fixed, PR pending. Two of the three originally-listed failures were genuinely the
AF_UNIX path-length issue described below, fixed by routing all socket paths in `tests/test_fail_open.py`
through a new `short_sock_path` fixture instead of pytest's nested `tmp_path`. **The third
(`test_session_start_hook_graceful_when_daemon_down`) turned out to be a different, unrelated bug** —
caught and corrected mid-fix rather than left as a wrong diagnosis: its actual failure was a
`subprocess.TimeoutExpired`, not an `AF_UNIX` error. The test never isolated `CAMPY_BRAIN_SOCKET`, so on
this dev machine (where a real daemon is normally running) it was silently testing against the *real*
daemon instead of a down one, and occasionally timed out when that live daemon was slow to respond —
itself tied to B342's memory-pressure findings, not a bug in the hook script. Fixed by pointing it at a
guaranteed-nonexistent short socket path. Verified: 20 consecutive runs of the original failing
combination, zero failures (was ~15-20% flaky before the fix); full `test_fail_open.py` +
`test_claude_code_hooks.py` suite passes (38/38).
Priority: P3

Plan: none yet.

### Problem

While verifying B342's periodic-restart change (PR #86) didn't introduce regressions, running the test
suite with a `-k` filter surfaced 3 failing tests, all with the identical error:

```
OSError: AF_UNIX path too long
```

```
tests/adapters/test_claude_code_hooks.py::test_session_start_hook_graceful_when_daemon_down
tests/test_fail_open.py::TestCallBrainSoftFailureModes::test_stalled_daemon_times_out_and_returns_default
tests/test_fail_open.py::test_claude_code_post_tool_use_hook_exits_zero_and_stays_under_budget_against_stalled_daemon
```

**Correction, same investigation:** the paragraph above (and this section's original framing) assumed
all three shared the identical root cause based on the pytest summary line alone, without checking each
traceback individually — wrong for one of the three, caught while implementing the fix rather than left
standing. `test_stalled_daemon_times_out_and_returns_default` and
`test_claude_code_post_tool_use_hook_exits_zero_and_stays_under_budget_against_stalled_daemon` genuinely
share the AF_UNIX cause: both go through `unix_stub_server()` in `tests/test_fail_open.py`, which binds a
real `AF_UNIX` socket at a path built from pytest's per-test tmp directory
(`socket.socket(socket.AF_UNIX, ...).bind(str(sock_path))`). macOS (and BSD generally) caps `AF_UNIX`
socket paths at roughly 104 bytes. Pytest's tmp directory path on this machine — of the form
`/private/var/folders/<hash>/.../pytest-of-djshelton/pytest-<N>/<test_name>0/brain.sock` — is long
enough, especially for tests with long names (`test_claude_code_post_tool_use_hook_exits_zero_and_stays_
under_budget_against_stalled_daemon` is itself over 90 characters), to blow past that limit.

**`test_session_start_hook_graceful_when_daemon_down` (the third test) does not use
`unix_stub_server()` at all** and its actual failure, captured directly once reproduced with a full
traceback, was `subprocess.TimeoutExpired` — not `AF_UNIX path too long`. It runs the real
`session_start.sh` hook via `subprocess.run(env=dict(os.environ))` with no override for
`CAMPY_BRAIN_SOCKET`, so despite its name ("graceful when daemon down") it was silently exercising
whatever daemon actually happened to be running on the machine executing the tests — normally true on
this dev machine, where a real Campy daemon runs continuously. It flaked when that real daemon was slow
enough to respond that the hook's subprocess call blew past its 10s test timeout, which happened to be
occurring during this same session because of B342's memory-pressure findings (a live daemon under
memory pressure responds slower). Fixed separately: point `CAMPY_BRAIN_SOCKET` at a guaranteed-
nonexistent short path so the test actually exercises "daemon is down," independent of the real machine
state — this also needed a short path rather than pytest's `tmp_path`, since the hook's own connect
attempt is subject to the identical AF_UNIX length limit as the first two tests, just via a different
code path (the `campy` CLI's own socket client, not `unix_stub_server`).

**Confirmed pre-existing, not caused by any in-flight change:** the two genuine AF_UNIX-length failures
were reproduced identically against unmodified `main` via `git stash` + re-run (see B342/PR #86's
verification notes) before this fix. This was a standing, environment-dependent flakiness in the test
suite itself — likely worse on machines/CI runners with longer base tmp-dir paths (username length,
`TMPDIR` configuration, etc.), and probably passing silently on shorter-tmpdir setups, which is
presumably why it hadn't been caught/fixed already. The third test's daemon-isolation gap was a
separate, coincidentally co-occurring bug, not evidence the pytest-tmp-dir-length theory applied to it.

### What it does (scope) — done

1. ~~Fix `unix_stub_server()`~~ Added a `short_sock_path` pytest fixture in `tests/test_fail_open.py` —
   a factory building short paths directly under `tempfile.gettempdir()` (a short, fixed prefix) with a
   short unique suffix per call, instead of pytest's nested `tmp_path`. Cleans up created files after
   each test. Every socket-path call site in the file (11 total across both failing tests plus others
   using the same vulnerable pattern, found while fixing) now routes through it.
2. Audited: no other test files bind/connect `AF_UNIX` sockets against pytest tmp paths except
   `tests/adapters/test_claude_code_hooks.py`'s `test_session_start_hook_graceful_when_daemon_down`,
   fixed separately (see Problem section's correction) with the same short-path approach, inlined
   locally rather than importing the fixture cross-file (kept the two files' test isolation independent).
3. Confirmed: 20 consecutive runs of the original failing combination (`pytest -k "daemon or checkpoint
   or config"`), zero failures. Full `test_fail_open.py` + `test_claude_code_hooks.py` suite passes
   (38/38). Full repo test suite run separately to catch unrelated regressions from either file's edits.

### Dependencies

None — fully independent of B342/B311's memory investigation; the socket path length has nothing to do

bug turned out to be indirectly related to B342 — a live daemon slowed by memory pressure caused its
flakiness — but the fix itself, proper test isolation, is unrelated to anything in B342's own changes.)

### Files to create/modify

  environment unmodified.
