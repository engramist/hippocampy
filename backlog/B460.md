# B460 - Relation Extraction Names the Retired Value as the Winner

State: fixed (2026-10-04; real-model confirmation pending -- see the last criterion)
Priority: P1

### Problem Statement

Found by campy-benchmarks while investigating LoCoMo `p1_current_db`
(2026-10-04). In a LoCoMo store built with llama3.1:8b (kept with
`--isolated --keep-store`), `diag_supersession_edges.py` classified the edges
between each deprecation probe's current and retired values:

- 11 edges said which value won (CHOSEN_OVER); **8 pointed the wrong way**:
  "PostgreSQL 14 CHOSEN_OVER PostgreSQL 16", "Zipkin CHOSEN_OVER OpenTelemetry
  OTel", "HS256 CHOSEN_OVER RS256", "ActiveMQ CHOSEN_OVER Apache Kafka",
  "TLS 1.2 CHOSEN_OVER Strict TLS 1.3", "Bazel CHOSEN_OVER Hatch / UV",
  "JSON REST CHOSEN_OVER GraphQL", "HS256 CHOSEN_OVER RS256 asymmetric".
- 3 were right; the rest of the probes had only CO_OCCURS_WITH, no edge, or
  no concept for one of the values.

An inverted edge is worse than none: whatever reads it (bundle graph
structure, traversal) learns that the retired value won. LoCoMo still scores
well because `ask` mostly answers from raw user statements (B454, B459), but
the edges do reach bundles ("serialization CHOSEN_OVER Pickle" appeared in a
`--trace-context` trace), and in a real store they are a standing source of
confidently wrong context.

### Root cause

The edges are written during consolidation (`temporal_lobe/loop`). Hebbian
promotion in the sweep could not have written them: it needs 10
co-occurrences and these pairs co-occur in 2-4 messages.

1. **Step 1b (spaCy verb patterns) handled active voice only.** "OpenTelemetry
   replaced Zipkin" -> REPLACES, but supersessions are usually stated as
   "X has been replaced by Y" (the passive subject was even taken as the
   head when a tail was found) or "we migrated from X to Y" (no pattern).
   Both produced nothing, so Step 3b ran.
2. **Step 3b (LLM) offered no REPLACES and never stated direction.** Its type
   list was CHOSEN_OVER / IMPLEMENTS / EXTENDS / ALTERNATIVE_TO, with no
   definitions; the sweep's promotion prompt defines "A CHOSEN_OVER B" (A was
   selected), this one did not. The model took the first-named entity as the
   head -- the retired one.

### What It Does (Scope)

- `step1b_relations.extract_relations`:
  - passive: the agent ("by Y") is the head, the passive subject the tail;
    a passive without an agent produces nothing (never the subject as head);
  - move verbs (migrate, switch, move, transition, upgrade, change) with both
    "from X" and "to Y": Y REPLACES X; only one of them: nothing;
  - the subject nearest the verb ("Final decision: X has been replaced by
    Y" parses both "decision" and X as subjects);
  - endpoint text is the name, not the noun chunk: the contiguous run of the
    token's name modifiers (compound, nummod, appos, ...) widened to whole
    written words, so versions and hyphenated names survive ("PostgreSQL 14",
    "Vue 2", "Debian 12 Bookworm slim", "eu-central-1"). Determiners are no
    longer part of a span ("a valid token" -> "valid token").
- `step3b_relations`: REPLACES added; every type defined with its direction
  (same definitions as the sweep); for REPLACES / CHOSEN_OVER the head is the
  value now in use whatever the sentence order, with the two supersession
  phrasings as an example.
- `orchestrator`:
  - a Step 1b relation is kept when an endpoint equals OR contains (whole
    words) a surviving entity: "PostgreSQL 16" names the entity "postgresql";
  - a Step 3b relation on a pair Step 1b already related is dropped in
    either direction (`_llm_relation_is_new`): grammar beats the LLM's guess.

Measured offline on LoCoMo's 75 user messages (spaCy en_core_web_md, real
Step 1 NER): Step 1b now yields 23 REPLACES relations, all 23 with the right
direction and the full names; 20 survived the old exact-match filter, all 23
survive the new one.

Not changed:

- **Edges already in existing stores stay inverted.** Repairing them means
  re-running relation extraction on their source messages: separate card.
- **`p1_current_db` retrieval.** The current value's concept ("PostgreSQL 16")
  is never reached from the question; expanding along edges only helps once
  they point the right way. Next card, after this one is confirmed.
- No deterministic override of Step 3b beyond the reversed-pair rule: the
  prompt fix is measured first (last criterion).
