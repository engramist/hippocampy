### Problem

Campy installs artifacts across 10+ locations on the user's machine. There's no way to cleanly uninstall — users must manually hunt down launchd plists, config file entries, skill directories, hook files, MCP registrations, and the Python package. We need this both for users AND for testing the new installer (B272).

### What This Card Does

1. Creates a `campy uninstall` CLI command that removes all Campy artifacts
2. Creates a standalone `scripts/uninstall.sh` for users who can't run `campy` (e.g., broken install)

### Dependencies

- None (can be implemented immediately)

### Complete Inventory of Campy Artifacts

Based on audit of a real install, Campy touches ALL of these locations:

**1. Daemon (must stop first)**
- Process: `brain_daemon.py` (kill via `pkill -f brain_daemon`)
- Launchd plists:
  - `~/Library/LaunchAgents/ai.hippocampy.brain.plist`
  - `~/Library/LaunchAgents/ai.sidequests.mission-control.plist` (legacy)
  - `~/Library/LaunchAgents/dev.hippocampy.indicator.plist`

**2. Campy data directory**
- `~/.campy/` — contains daemon.log, activity.log, triggers/, KuzuDB graph data, offline queue
- This is where ALL user memory lives. Uninstall should WARN before deleting this.

**3. Claude Code**
- MCP registration: entry in `~/.claude/settings.json` under `mcpServers`
- Hook entries: `hooks.UserPromptSubmit` entries containing `hook_user_turn.py`
- Project hooks: `.claude/hooks/` in any project where `campy setup` was run
- Plugin (if native install): `~/.claude/plugins/hippocampy/` or plugin cache

**4. Claude Desktop**
- MCP entry in `~/Library/Application Support/Claude/claude_desktop_config.json`

**5. Codex**
- Skills: `~/.codex/skills/` — Campy skill directories (recall, brief, learn, campy-grill, etc.)
- Hooks: `~/.codex/hooks/campy/` directory
- Hook config: entries in `~/.codex/hooks.json` containing "campy"
- MCP config: `[mcp_servers.campy]` block in `~/.codex/config.toml`
- Archived skills: `~/.codex/skills/_archived_by_campy/`
- Plugin (if native install): `~/.codex/plugins/hippocampy/` or plugin cache

**6. Gemini CLI**
- Skills: `~/.gemini/skills/` — Campy skill directories
- Hooks: `~/.gemini/hooks/campy/` directory
- Hook config: entries in `~/.gemini/settings.json` hooks section containing "campy"
- MCP config: entries in `~/.gemini/settings.json` mcpServers section
- Context file: `GEMINI.md` in installed package or project
- Extension (if native install): linked or cached extension

**7. VS Code**
- MCP entry in `~/Library/Application Support/Code/User/mcp.json`

**8. OpenClaw**
- Config entries (check `~/.openclaw/` or equivalent)

**9. Python package**
- pipx: `pipx uninstall hippocampy`
- pip: `pip uninstall hippocampy`
- Console scripts: `campy`, `campy-daemon`, `sidequests`, `sidequests-daemon`

def _stop_daemon():
    """Stop the brain daemon."""
    console.print("[yellow]Stopping daemon...[/yellow]")
    for label in LAUNCHD_LABELS:
        subprocess.run(["launchctl", "unload",

def _remove_claude_code():
    """Remove Campy from Claude Code settings."""
    settings = Path.home() / ".claude" / "settings.json"

            changed = False

### Implementation (2026-08-04)

Fixed the confirmed bug plus one more of the same class the audit explicitly flagged as worth checking, and added a general safety net for any future case:

1. **`_deregister_openclaw()`**: wrapped both `subprocess.run` calls (`plugins remove`, `gateway restart`) in `try/except (subprocess.TimeoutExpired, OSError)`. The plugin-removal call's failure no longer blocks the gateway-restart attempt (best-effort, since config patches from step 1 are already saved regardless); either failure now degrades to a reported `_R("OpenClaw", done=<config-patch-applied>, "<specific reason>")` instead of raising.
2. **`_deregister_claude_code()`**: same fix for its `claude mcp remove` call — the audit's own note ("worth auditing the other unguarded external-CLI subprocess.run calls... though it did not manifest as a crash in this test run") flagged this exact call site. Fixed the same way.
3. **Orchestration-level safety net**: added `_safe_call(name, fn)` in `run_uninstall()`, wrapping every per-integration step (`_stop_daemon`, all five `_deregister_*` calls, `_remove_campy_home`, `_remove_ollama_model`). Any *future* integration with a similar unguarded external call now degrades to a reported failure for that one step and the uninstall continues through Steps 3 and 4, rather than crashing wherever the gap happens to be. This directly targets the actual harm described in this card's title: an uninstall that crashes partway through leaves things half-removed.

**Real bug found by actually running the code:**
`_deregister_openclaw()` (campy/cli/uninstall.py, lines 533–590) has **no exception handling** around either of its two `subprocess.run(..., timeout=15)` calls (`openclaw plugins remove hippocampy` at line 575, `openclaw gateway restart` at line 583) — unlike other file-removal helpers in the same module, which wrap risky operations in `try/except OSError`. During the sandboxed run above, this machine has a real `openclaw` binary on PATH; `openclaw gateway restart` hung and raised `subprocess.TimeoutExpired` after 15s, which propagated uncaught all the way out of `run_uninstall()`, aborting the process with a raw Python traceback **after Step 2 of 4** — Step 3 (data removal) and Step 4 (Ollama model removal / final package removal) never ran. Exact repro:

```
Step 2/4: Removing adapter registrations...
Traceback (most recent call last):
  ...
  File ".../campy/cli/uninstall.py", line 694, in run_uninstall
    results.append(_deregister_openclaw())
  File ".../campy/cli/uninstall.py", line 583, in _deregister_openclaw
    subprocess.run([openclaw_bin, "gateway", "restart"], capture_output=True, text=True, timeout=15)
subprocess.TimeoutExpired: Command '['/opt/homebrew/bin/openclaw', 'gateway', 'restart']' timed out after 15 seconds
```

**Impact:** any machine with `openclaw` installed on PATH but whose gateway is slow, unresponsive, or not running will cause `campy uninstall` (and `scripts/uninstall.sh`, which delegates to it) to crash ungracefully partway through, leaving the runtime data dir, Ollama model, and Python package uninstalled — the opposite of the acceptance criterion "Uninstaller handles missing artifacts gracefully (no errors if already removed)" and the general expectation that an uninstaller completes or fails cleanly rather than crashing mid-run.

**What a fix would need to touch:** wrap both `subprocess.run` calls in `_deregister_openclaw()` (campy/cli/uninstall.py ~574–586) in `try/except (subprocess.TimeoutExpired, OSError)`, converting a failure into `_R("OpenClaw", False, "<reason>")` the same way other helpers degrade gracefully, so a hung/missing gateway doesn't abort the rest of the uninstall. Worth auditing the other unguarded external-CLI `subprocess.run` calls in this file for the same gap (e.g. `_deregister_claude_code`'s `claude mcp remove` call at line ~400 has the same missing try/except, though it did not manifest as a crash in this test run).

**Caveat on test methodology:** because `_deregister_openclaw()`'s external-binary subprocess calls are not scoped by the `$HOME` override the way the JSON/file operations are (only its config-file path, not the `openclaw` binary invocation itself, is `Path.home()`-relative), running the sandboxed end-to-end test caused a real, unplanned interaction with this machine's actual `openclaw` installation (the `gateway restart` call ran for real and hung for 15s before timing out). No evidence was found that this left the system in a broken state, but this could not be fully ruled out, and it is itself part of why this bug matters — the same unsandboxable subprocess call is exactly what a real end user's uninstall would hit.
