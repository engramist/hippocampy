# B322 - Learned Change Coupling and Conflict Forecast

State: deferred
Priority: —

**Deferred 2026-08-16. Do not implement. Both of this card's inputs were established not to
exist in the target system.** The design is retained because the reasoning is reusable if a
different customer's system turns out to have the preconditions; the original card text follows
the deferral note.

### Why this is deferred

The card proposed learning file-coupling from observed co-change, then forecasting assignment-
time collisions for an orchestrator. A factual audit of the target platform (2026-08-15,
cited against the platform's own repository and live deployment) removed both foundations:

**1. There are no collisions to forecast.** Each build session gets its own workspace directory
(`root / session_id`); two sessions never share a directory. The shared root's read bit is
stripped (`0o300`) and an OS-level sandbox confines each build subprocess to its own workspace,
enabled in production. Their complete incident record contains **no case of two agents writing
conflicting content into the same file** — the recorded incidents were a cross-session
read/copy, a duplicate-session re-mint, and deploy-pipeline races.

**2. There is no co-change signal to learn from, and no dependency graph either.** The card
depended on `WorkArtifact` history accumulating file-level touch events across sessions that
work on shared files — which the per-session directory model prevents. And there is no bundler
step at all: the "build" is a headless coding agent authoring the app, which may run
`npm run build` as a self-check, but the platform never parses or persists the output. A repo
search for `--metafile`, webpack stats, `tsc --listFiles`, and Vite manifests returned **zero
matches**, and no retention location exists.

So the forecast has nothing to forecast, and the coupling has nothing to learn from.

### What replaced it

**B321** was rewritten from the same audit. The real problem is the inverse of collision: the
platform's own design doc describes their workspaces as "disconnected islands" with no
visibility between concurrent sessions on the same app, and the shared-ancestry work that would
fix that is unbuilt. B321 now closes the visibility half — App-scoped cross-session continuity
— instead of warning about a hazard that does not occur.

### What would revive this card

All three would need to hold:

1. Agents share a working tree, or otherwise write the same files concurrently.
2. Enough cross-session touch history accumulates on shared files for co-change to be
   measurable — a per-session-directory model will never produce it.
3. Either a retained module dependency graph exists, or exact-file overlap alone proves
   insufficient in measurement.

If a future deployment meets those, the design below is sound and the supernode handling in
particular is the part worth keeping — without it, ambient files (`package.json`, `tsconfig`,
root `index`) couple to everything and the forecast reports universal conflict, which is worse
than no signal.

### Lesson worth carrying forward

This card was written from a verbal description of the problem ("agents stepping on each
other's changes in the working tree"). The audit showed the described mechanism was not what
was happening. **Two cards were designed against a misdiagnosis before anyone checked the
target system's actual isolation model** — and the check, when finally requested, took one
prompt and returned file-and-line evidence.

Ask for the evidence before designing against a symptom description.

## Original card text (retained for reference — not for implementation)

The original design covered: a `FilePath` node plus a symmetric `CO_CHANGES` rel table with
`co_count` / `support` / `confidence` / `last_seen_at`, computed from `WorkArtifact` history
scoped by session or `linked_card`; recompute on the existing background sweep with
`authority='projected'` and `source='campy:cochange'` so `drop_projections` could rebuild it;
ambient-file classification by touch-frequency percentile with those files excluded from
pairwise coupling and reported instead as serialize-only hotspots; a bounded
`conflict_forecast()` returning `direct`/`coupled`/`indirect` risk tiers over `[:CO_CHANGES*..2]`;
and MCP tool registration for orchestrator consumption.

Full original text is in git history at the commit that added this file.
