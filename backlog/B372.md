# B372 - Persist Disappeared Entities in `arc_perceive_state` (ARC_AGI Now Sends `disappeared_entities`)

State: complete
Priority: P3

Plan: none yet.

### Problem

ARC_AGI's `A221` Finding 2 (2026-08-31) promoted its A219 disappearance-detection feature from
telemetry-only to a real graph write. `agents/arc4/graph_queries.py::ingest_perception` (wire method
`arc_perceive_state`, handled here at `campy/brain/thalamus/tools/arc_queries.py:85`) now sends an
additional payload field, `disappeared_entities` — a list with the exact same shape as the existing
`entities` field (`color_id`, `region_index`, `centroid_row`, `centroid_col`, `pixel_count`,
`attributes`), just populated with entities that were present in the *previous* frame and are absent
this frame (A175's stable `entity_ref`/`region_index` no longer appears among the current frame's
entities).

Confirmed this degrades gracefully today: `arc_perceive_state`'s handler reads `params.get("entities")`
directly with no strict schema validation on unknown keys, so the new field is currently silently
ignored, not rejected — same non-strict pattern as every other ARC_AGI graph consumer. Confirmed via
direct code reading, not assumed.

This is deliberately scoped narrower than "graph-promote all of A219's entity_effects" — ARC_AGI's own
design conversation concluded disappearance is the one genuinely new causal fact (A175's correspondence
tracking had zero disappearance detection before A219 existed at all) worth a graph write now; the other
five effect-type classifications (translation/growth/shrink/appearance/unchanged) stay ARC_AGI-side
local process state until a concrete consumer (the still-undesigned diversity-scoring follow-up to A220)
specifies what it actually needs. Don't read this card as an invitation to design schema for those too.

### What it does (scope)

Not yet decided — this card records the client contract that now exists, not a chosen implementation.
Whoever picks this up should:

1. Read `arc_perceive_state`'s existing entity-handling loop (`arc_queries.py:114-152`) first — it
   already tracks per-entity state via `GridEntity {entity_id}` nodes and detects movement by comparing
   stored vs. incoming centroids, writing a `MOVED_BY` relationship when a real move is detected. Disappearance
   is naturally the same shape of fact: decide whether it's a `GridEntity` property (`disappeared_at_step`),
   a dedicated event node (mirroring `ActionEffect`'s own pattern just below the entity loop), or a new edge
   type — whichever fits this project's own schema conventions, not a guess imported from ARC_AGI's side.
2. Decide whether/how a disappearance should ever get "undone" — if the same `entity_ref` reappears in a
   later frame (should that happen for this game genre, worth checking against real ARC-AGI-3 mechanics
   before assuming it can't), does the disappearance record get corrected, superseded, or left as a
   historical fact alongside a new appearance? Don't presuppose either answer here.
3. Verify against a real live client call from the ARC_AGI side once implemented (coordinate cross-repo,
   same pattern as B369's own verification).
4. `disappeared_entities` will often be an empty list (most steps have no disappearance) — confirm the
   handler doesn't do unnecessary write work when it's empty (mirrors how `action_taken` already gates
   the `ActionEffect` write above).

### Outcome

Implemented 2026-08-31, per explicit instruction to design for real rather than guess.

**Schema decision (scope item 1): a dedicated event node, `EntityDisappearance`, not a `GridEntity`
property.** Read the existing entity-handling loop first as instructed
(`arc_queries.py::arc_perceive_state`, the `GridEntity`/`MOVED_BY` pattern) — `GridEntity` is a mutable
per-entity *current-state* record (`MERGE` + `SET`, overwritten every frame the entity is observed), the
same shape `Transition` and `ActionEffect` deliberately reject for anything that needs full history
("deliberately not merged/updated... since get_entity_history needs the full per-step history" — A176's
own comment on `Transition`). Disappearance is squarely in that second category: one node per
*observation* of disappearance (`task_id`, entity, `step`), keyed the same way `Transition` is, so it
can never be silently overwritten by a later event. New `EntityDisappearance` node table, plus a
`DISAPPEARED` rel (`GridEntity -> EntityDisappearance`, matching `MOVED_BY`'s `GridEntity -> ActionEffect`
shape). Added to `PROVENANCE_TABLES` (same category as `ActionEffect`/`Transition` — an observed game
fact, not orchestration bookkeeping like B369's `InvestigationThread` was) — though, matching this
file's own existing practice, `record_transition`/`record_rule` never actually call
`provenance.provenance_fields()` either, so `EntityDisappearance`'s provenance columns stay unpopulated
too; not a gap introduced here, a pre-existing pattern this card doesn't change.

**Design decision (scope item 2): reappearance never corrects, supersedes, or touches an earlier
disappearance record.** Didn't presuppose this — reasoned it through: `superseded_by`/`supersession_reason`
(available via `PROVENANCE_TABLES` membership) exist for facts *later found to be wrong* (a
`supersession_reason` of `"contradicted"` is for a claim proven false). "This entity was absent at step
N" and "this entity is present again at step M" are not in tension — both can be true, in sequence, for
the same physical object across a game with toggled/blinking mechanics (a real ARC-AGI-3 pattern this
session directly observed live — an unrelated countdown/counter-style effect surfaced during B369's own
cross-repo verification runs). Treating a reappearance as needing to "undo" the disappearance would be
answering a question that was never asked: nothing about the disappearance observation was wrong, the
game state genuinely changed twice. Each disappearance is therefore its own permanent historical
record — an entity that disappears, reappears, and disappears again gets **two** distinct
`EntityDisappearance` rows, not one. Proven directly by
`test_perceive_state_repeated_disappearance_keeps_full_history`, not just asserted.

**Verification:** 4 new tests in `tests/test_arc_queries.py`, real KuzuDB via the file's existing
`b309_db` production-schema fixture (matching this card's own item 3 emphasis on live/real
verification over mocks) — covering the write path, the empty-list no-op case (existing
`test_arc_perceive_state_handles_empty_state`'s `MockDB` assertion of exactly 1 write also still holds
unchanged, confirming no regression), the reappearance-doesn't-touch-history case, and the
repeated-disappearance-keeps-full-history case. All existing `arc_perceive_state` tests pass unchanged
(the new `disappeared_count` field in the response is additive, nothing asserts exact dict equality
against it). New Cypher written as `NamedQuery` entries from the start
(`campy/brain/hippocampus/graph/queries/arc.py`), following B369's own established practice, to stay
under the Cypher ratchet (`scripts/check_cypher_ratchet.py`, confirmed clean:
"Cypher line count unchanged: 592").

Live-verified against the real dev daemon (restarted to pick up the schema migration, applied
idempotently via `init_schema()`): a direct socket call reproducing ARC_AGI's exact
`disappeared_entities` payload shape returned `disappeared_count: 1` correctly. A real call from the
ARC_AGI client itself hasn't happened yet — that's the one item still open, to be confirmed once
`arc-agi-38` (or whichever session is current) runs a live episode against this.
