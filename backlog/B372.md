# B372 - Persist Disappeared Entities in `arc_perceive_state` (ARC_AGI Now Sends `disappeared_entities`)

State: not started -- client contract shipped, server implementation not yet designed here
Priority: P3

Plan: none yet.

### Problem

ARC_AGI's `A221` Finding 2 (2026-08-31) promoted its A219 disappearance-detection feature from
telemetry-only to a real graph write. `agents/arc4/graph_queries.py::ingest_perception` (wire method
`arc_perceive_state`, handled here at `campy/brain/thalamus/tools/arc_queries.py:85`) now sends an
additional payload field, `disappeared_entities` — a list with the exact same shape as the existing
`entities` field (`color_id`, `region_index`, `centroid_row`, `centroid_col`, `pixel_count`,
`attributes`), just populated with entities that were present in the *previous* frame and are absent
this frame (A175's stable `entity_ref`/`region_index` no longer appears among the current frame's
entities).

Confirmed this degrades gracefully today: `arc_perceive_state`'s handler reads `params.get("entities")`
directly with no strict schema validation on unknown keys, so the new field is currently silently
ignored, not rejected — same non-strict pattern as every other ARC_AGI graph consumer. Confirmed via
direct code reading, not assumed.

This is deliberately scoped narrower than "graph-promote all of A219's entity_effects" — ARC_AGI's own
design conversation concluded disappearance is the one genuinely new causal fact (A175's correspondence
tracking had zero disappearance detection before A219 existed at all) worth a graph write now; the other
five effect-type classifications (translation/growth/shrink/appearance/unchanged) stay ARC_AGI-side
local process state until a concrete consumer (the still-undesigned diversity-scoring follow-up to A220)
specifies what it actually needs. Don't read this card as an invitation to design schema for those too.

### What it does (scope)

Not yet decided — this card records the client contract that now exists, not a chosen implementation.
Whoever picks this up should:

1. Read `arc_perceive_state`'s existing entity-handling loop (`arc_queries.py:114-152`) first — it
   already tracks per-entity state via `GridEntity {entity_id}` nodes and detects movement by comparing
   stored vs. incoming centroids, writing a `MOVED_BY` relationship when a real move is detected. Disappearance
   is naturally the same shape of fact: decide whether it's a `GridEntity` property (`disappeared_at_step`),
   a dedicated event node (mirroring `ActionEffect`'s own pattern just below the entity loop), or a new edge
   type — whichever fits this project's own schema conventions, not a guess imported from ARC_AGI's side.
2. Decide whether/how a disappearance should ever get "undone" — if the same `entity_ref` reappears in a
   later frame (should that happen for this game genre, worth checking against real ARC-AGI-3 mechanics
   before assuming it can't), does the disappearance record get corrected, superseded, or left as a
   historical fact alongside a new appearance? Don't presuppose either answer here.
3. Verify against a real live client call from the ARC_AGI side once implemented (coordinate cross-repo,
   same pattern as B369's own verification).
4. `disappeared_entities` will often be an empty list (most steps have no disappearance) — confirm the
   handler doesn't do unnecessary write work when it's empty (mirrors how `action_taken` already gates
   the `ActionEffect` write above).

### Dependencies

None on this repo's side. Depends on ARC_AGI's A221 Finding 2 (already shipped, client-side only).
