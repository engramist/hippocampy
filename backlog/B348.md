# B348 - Local Memory-Pressure Watchdog/Alarm for brain_daemon.py

State: mostly complete — one real gap remains, tracked in B367
Priority: P2

Plan: none yet.

### Problem

B342's 99GB-physical-footprint finding was discovered by accident, during an unrelated investigation
(B311's checkpoint mitigation measurement) — not because anything alerted anyone to it. The
VibeGuide build-worker OOM disclosure note (referenced in project history) describes the same gap in
its own original incident: "we'd originally found the incident by hand-sampling RSS," and its fix
included a CloudWatch alarm at 85% sustained specifically because of that gap. Campy has no local
equivalent — a background daemon meant to run persistently and invisibly on a user's machine has no
mechanism to surface "this is using way more memory than it should" until something actually breaks
(as it did here — `ask` went offline) or someone happens to look.

### What it does (scope)

1. Decide the detection mechanism: a lightweight periodic check is more appropriate here than a cloud
   alarm (no CloudWatch equivalent locally) — options include (a) a check built into
   `brain_daemon.py`'s own background sweep loop (reuse B344's instrumentation if that card lands
   first — check its Outcome), or (b) a fully separate lightweight watchdog script invoked by
   cron/launchd on its own schedule, independent of the daemon's own health (preferable if the concern
   is the daemon becoming too degraded to reliably report on itself — an external watchdog survives a
   daemon that's too swap-thrashed to run its own checks promptly).
2. Pick a threshold and signal: given B342's `ps`-vs-`vmmap` discrepancy (RSS drastically undercounts
   real footprint on macOS due to swap/compression), make sure whatever the watchdog measures is the
   metric that actually matters — `vmmap`'s "physical footprint" or platform equivalent, not raw RSS,
   or at minimum document clearly which one is being used and why if RSS is chosen for simplicity.
   A sustained-over-time threshold (mirroring VibeGuide's "85% sustained," not a single-sample spike) is
   likely more useful than an instant trigger, to avoid false alarms during B311-class transient spikes
   that are expected to self-resolve.
3. On trigger, at minimum: log a clear, visible warning to `~/.campy/daemon.log` and/or
   `~/.campy/activity.log` (per this project's existing activity-indicator convention — check
   `CLAUDE.md`'s "Campy Activity Indicator" section for the established pattern before inventing a new
   one). A desktop notification or other more visible alert is a reasonable stretch goal but not
   required for this card's baseline scope.
4. Make sure the watchdog itself is cheap and can't become part of the problem — it should not hold
   long-lived state, accumulate history unboundedly, or require attaching a heavy profiler (that's
   B343/B344's job, not this card's) — this is a simple threshold check, not a diagnostic tool.
5. Document how to check current status and how to adjust the threshold, consistent with this project's
   existing `campy activity --follow` operator-facing convention.

### Dependencies

Loosely related to B344 (continuous instrumentation) and B347 (bounded restart) — if B347's restart
policy lands first, this watchdog is still valuable (catches abnormal growth *within* one restart
interval, which B347 alone wouldn't), but coordinate on not building three independent, overlapping
"check the daemon's memory" mechanisms. Read B344 and B347's outcomes before starting if they've landed.

### Files to create/modify

- A new watchdog script (e.g. `scripts/memory_watchdog.sh` or a small Python module under
  `campy/brain/brainstem/`, consistent with where other operational/monitoring code lives in this
  codebase).
- Supervisor config (cron/launchd) if run as an independent scheduled check rather than baked into the
  daemon's own loop.
- `docs/` — document the alarm, its threshold, and what to do when it fires.

### Acceptance Criteria

- [ ] A working threshold check exists, using a footprint metric that's actually meaningful (not raw
      RSS alone, unless explicitly justified as sufficient for the chosen approach).
- [ ] Triggering it (test by lowering the threshold temporarily against a real or simulated large
      process) produces a visible, discoverable alert — verified manually, not just code-reviewed.
- [ ] The watchdog's own resource usage is negligible and doesn't accumulate state unboundedly.
- [ ] Documented: what the alarm means, where to look when it fires, and how to adjust the threshold.

### Outcome

Reviewed 2026-08-26 as part of an audit of B342-era cards. `_periodic_footprint_watchdog` (B354,
now in `campy/brain_daemon.py` since B365's port) satisfies most of this card:
- Meaningful metric, not raw RSS: yes — `vmmap` physical footprint via `_vmmap_parsed()`, explicitly
  chosen over RSS per the same B342 finding this card cites.
- Sustained-over-time threshold, not instant trigger: yes — `consecutive_breaches_required` (default
  3) debounces exactly as asked.
- Negligible, non-accumulating resource use: yes — tracks one int and one float, no history buffer.
- Documented (what it means, how to adjust): yes — `[watchdog]` section in `campy.toml` has detailed
  comments; `docs/ARCHITECTURE.md` explains the design rationale.
- "Visible, discoverable alert... verified manually, not just code-reviewed": partially. Five unit
  tests (monkeypatched `vmmap` sequences) thoroughly cover the trigger logic — no-breach,
  single-breach-reset, consecutive-trigger, baseline-failure, transient-failure — but a real live
  trigger (temporarily lowering the threshold against the actual daemon and watching it fire) was not
  done; the unit coverage is treated as a reasonable substitute given the cost of forcing a real
  footprint breach.
- "Log a clear, visible warning... per this project's existing activity-indicator convention": **not
  satisfied**. The watchdog logs via `_logger.warning()`, which reaches `~/.campy/daemon.log` — but
  not `~/.campy/activity.log` (the `emit_activity()`-backed feed `CLAUDE.md` specifically names as
  the recommended way to check daemon status "instead of the noisy daemon log"). Investigating this
  found something bigger: `campy/brain_daemon.py` has **zero** `emit_activity()` calls anywhere,
  including for basic daemon start/stop — a gap that predates this card and B365, now universal since
  B365 made this module the only implementation. Filed as `backlog/B367.md` rather than fixed inline
  here (real fix, deserves its own verified PR, not a rushed addition mid-audit). This card stays
  "mostly complete" rather than "complete" until B367 lands.
