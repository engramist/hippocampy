# B461 - Measure Save-Gate Changes on LoCoMo; Opt-In Jev Provider Trial (Conditional)

State: in-progress (Part A done 2026-10-01: measurement tooling in campy-benchmarks; the runs need a machine with the models; Jev decision not yet possible)
Priority: P3

### Problem Statement

B462, B459 and B460 are judged on a small author-labeled set. That shows whether the
gate classifies statements correctly; it doesn't show whether better save
decisions improve recall at question time. LoCoMo is already wired in
`campy-benchmarks` (`check_locomo10.py`), and it's the benchmark the Jev-Mem
paper (arXiv 2609.23986) reports on (0.777 LLM-judge overall, 6.6× faster
memory construction than the fastest baseline), so it gives a like-for-like
comparison.

Jev itself (TypeSafe AI, launched 2026-09-15) returns typed answers with
calibrated probabilities, ~70–500 ms, $0.042 per million input tokens. It is
**hosted-only** (no weights, no on-prem, early-access waitlist). Campy is
local-first and the Loop sees every user and assistant turn, so a Jev
provider would send the full conversation to a third party. That is why it
is last, conditional, and opt-in.

### What It Does (Scope)

1. **LoCoMo before/after:** run `campy-benchmarks` LoCoMo against the
   pre-B462 baseline commit and after each of B459 and B460. Record overall
   and per-category scores, memory construction time, and nodes created
   (fewer, better-typed nodes is a result in itself).
2. **Decision gate for the Jev trial:** only proceed if B460's local
   calibrated gate misses its acceptance targets, or LoCoMo shows the save
   gate is still the bottleneck. Record the decision here either way.
3. **If proceeding:** add a `jev` decision provider behind the existing
   per-step LLM client selection (`create_llm_client_for_step`), off by
   default, requiring explicit config and an API key from env. Map Steps 2,
   3b, 4, 6 onto Jev typed questions using the B462 spec as the decision
   criteria. Document the data-egress implication in `campy.toml` comments
   and the README.
4. Compare local vs. Jev on the B462 set and LoCoMo: accuracy, calibration,
   latency, cost.

### Out of Scope

- Making any hosted model the default.

### Dependencies

- B460 (and B459 if landed). `engramist/campy-benchmarks` LoCoMo harness.

### Part A (done 2026-10-01): measurement tooling

The LoCoMo-10 runs can't be done in the sandbox that built this (no
embedding-model download, no Ollama). What was missing for them is now in
`campy-benchmarks` (branch `claude/brave-fermat-uz4gpe`):

- **Nodes created.** `store_stats.py`: after an `--isolated` run, the
  daemon's Python counts what the store holds before it is deleted:
  - nodes per type;
  - Concepts split into confirmed/tentative and by `origin_role`;
  - artifact nodes (Decision, Constraint, Requirement, ActionItem).

  The counts are recorded as `provenance.store.graph_stats`, one entry per
  run under `--repeat`. The probe uses only pyoxigraph and the
  `https://campy.dev/ns#` IRIs, so it also works on the pre-B462 baseline
  commit (there, origin shows as `unset`).
- **Per-category scores and construction time in comparisons.** The
  comparison table (`run_all.py --compare` and the new
  `compare_results.py A.json B.json` for two saved files) now includes:
  - LoCoMo-10 per-category scores;
  - `ingest_seconds` (memory construction time);
  - the graph counts.
- Already there: overall/per-category judge accuracy, F1, evidence recall,
  `--repeat N` for run-to-run spread.
- Tests: `check_store_stats.py`. It runs the probe against an Oxigraph
  store when a Python with pyoxigraph is available. The probe was also
  checked against a store written by hippocampy's own `create_concept`. The
  existing `check_*.py` scripts still pass.

**What this benchmark can and can't show:**
- LoCoMo-10 writes every turn as role `user` (harness protocol), so B459's
  assistant-provenance rules are never exercised. Only the evidence rescue
  and the dedup threshold change can show up.
- LoCoMo questions are about personal facts and events, not decisions or
  constraints. Typed-artifact changes (B460 item 6, the artifact statement)
  will barely move recall. The graph counts are where save-gate changes
  should be visible.
- B460 Part A changes Steps 2 and 6 only if the configured LLM endpoint
  returns log-probabilities. With `--keep-store`, `grep "Gate:NearTie"` in
  the isolated `daemon.log` shows near ties. No lines is ambiguous: either
  no near ties, or no logprobs. Steps 2 and 6 only call the LLM for
  gray-zone cases, so the count may be small either way.

### Item 2: Jev go/no-go — not decidable yet; default no-go

The gate has two conditions, and neither can be evaluated today:
- "B460's local calibrated gate misses its acceptance targets": the
  calibrated Step 4 classifier (B460 item 1) isn't built. It waits on the
  B462 full-mode baseline and labels, so there is nothing to miss targets
  yet.
- "LoCoMo shows the save gate is still the bottleneck": needs the item 1
  runs above, plus a way to attribute misses to the gate rather than to
  retrieval or the answering LLM. `evidence_recall` gives the first cut: a
  question whose evidence turns were never retrieved is a gate miss only if
  those turns' entities are also absent from the graph. That second check is
  manual today (`--keep-store`, then query the store). Entities present but
  not retrieved point at retrieval.

Until both are known, the decision is **no-go**, and item 3 (the `jev`
provider) is not started. Reasons beyond the gate:
- it would send every turn to a hosted, early-access API;
- the Jev claims in this card come from TypeSafe's launch material and one
  LinkedIn post, none of it reproduced here.

Revisit after the B460 item 1 classifier lands and the three LoCoMo-10
runs are recorded here.
