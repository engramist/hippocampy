# B298 - Piggyback Claude Code's Auto-Memory Writes into Campy

State: ready — design decisions confirmed 2026-07-13, unblocked for implementation
Priority: P2

Plan: (inline — this card is self-contained)

### Problem

Claude Code has its own persistent auto-memory system (`~/.claude/projects/<project-slug>/memory/*.md`
+ a `MEMORY.md` index), separate from and invisible to Campy. Claude writes to it constantly —
this very session produced 7 memory files (`project_b290-cws.md` through `project_b297-readme-install.md`)
containing real decisions, root causes, and gotchas discovered while working the codebase.

None of that is visible to Campy, and therefore none of it is visible to any OTHER agent
(Codex, Gemini CLI, VS Code Copilot) working the same repo — directly undermining B290's own
premise (cross-agent continuity via a shared graph). If a user hits a token limit in Claude Code
and switches to Codex, Codex's `[Campy] Working on...` resume line has zero awareness of
anything Claude decided to remember, even though Claude explicitly judged that content durable
and important enough to persist.

The auto-memory system is not a special internal call — Claude writes to it using ordinary
`Write`/`Edit` tool calls targeting a specific directory. This means the existing PostToolUse
hook infrastructure can observe it, the same way B290's `register_artifact` capture already
observes `*.md` writes for document provenance.

### Why `register_artifact` (B290) Cannot Be Reused As-Is

`adapters/claude_code/hooks/post_tool_use.sh`'s existing `*.md` detection block (confirmed at
the end of the file) computes a **repo-relative path** via
`os.path.relpath(file_path, repo_root)` before calling `register_artifact`. A memory file lives
at `~/.claude/projects/<slug>/memory/*.md` — outside any project repo — so `relpath()` against
`repo_root` produces a nonsensical `../../../../.claude/projects/.../memory/foo.md` value.
`register_artifact`'s schema (`file_path`, `document_type`, `linked_card`) also models "a
document that exists in this project," not "a discrete fact the agent decided to remember" —
the wrong shape for this data. This card needs its own detection branch and its own Campy-side
handling, not a tweak to the existing WorkArtifact path.

### Design Decisions — CONFIRMED 2026-07-13 (maintainer review)

**1. Entry point: `notify_turn`.** Confirmed. Hook reads the memory file's frontmatter + body,
wraps it as a synthetic system-role message, calls `notify_turn`. Content flows through the
normal Gated Consolidation Loop — NER (Step 1) → gist classification (Step 2) → schema.org
routing (Step 3) → pattern matching (Step 4) → arbitration (Step 6) → pathway update — the same
pipeline every other captured turn goes through (`docs/ARCHITECTURE.md` Loop Steps section).

**2. Memory-type scope: capture all four types — no filtering at the hook.** Reversed from the
original recommendation (`project`+`feedback` only) after maintainer review. The original
reasoning — that `user`/`reference` memories are cross-project or point outside the repo, so
they'd pollute this repo's graph — solved the wrong problem. Dropping data at the capture
boundary throws away information Claude already judged worth keeping; a "data swamp" risk is a
structure problem, not a volume problem, and this graph already has the structure to solve it
without exclusion.

Concretely: `docs/ARCHITECTURE.md:655` — when Step 4 classifies a `Concept` at >90% confidence,
Campy creates a typed artifact node (`Decision`, `Constraint`, etc.) linked via
`(Concept)-[REIFIED_AS]->(...)`. The gist→schema.org ontology (`docs/ARCHITECTURE.md:391-413`,
`696-746`) already exists specifically so heterogeneous captured content gets typed and routed
rather than dumped flat. Claude's `metadata.type` (`user`/`feedback`/`project`/`reference`)
should ride along as a property on the captured node (e.g. `source_memory_class`) — not as a
pre-ingestion filter. That makes it a first-class, queryable dimension: `compile_context` or a
repo-scoped `ask` can filter `WHERE source_memory_class IN ('project','feedback')` for
"what happened in this repo" questions, while a `user`-class fact remains in the graph,
retrievable by anything that legitimately wants cross-project facts about the person. Nothing
observed is discarded at write time; scoping happens at query time, where the caller actually
knows what they need.

**3. Idempotency + real reification (not just a raw capture).** Upsert keyed on the memory
file's `name:` frontmatter field (stable identifier — mirrors `register_artifact`'s
upsert-by-`file_path` pattern), not the free-text body, so repeated edits to the same memory
file (`MEMORY.md` rewrites trigger edits to individual memory files as facts accrue) update one
node instead of appending duplicates.

Separately and just as important: `notify_turn` alone does not guarantee the content becomes a
proper graph node. This session's own compile_context work surfaced exactly this failure mode —
content sitting as an undistilled raw `notify_turn` capture that Step 4 never promoted to an
artifact node, invisible to `compile_context`/`ask` even though it was technically "in the
graph." A memory file's frontmatter is already structured (`name`, `description`,
`metadata.type`) plus a body written to the rule/fact + **Why:** + **How to apply:** convention
(`CLAUDE.md`'s memory-writing instructions) — the hook should preserve that structure in the
synthetic message (not flatten it to prose) specifically so Step 2/3/4 classification has a
clean shape to work from and reliably clears the reification confidence gate. This needs
verifying, not assuming — see updated acceptance criteria below.

### What This Card Does (once decisions are confirmed)

1. Add a new detection branch to `adapters/claude_code/hooks/post_tool_use.sh`, alongside the
   existing `*.md` WorkArtifact block: if `CLAUDE_TOOL_NAME` is `Write`/`Edit` AND the resolved
   file path matches `~/.claude/projects/*/memory/*.md` (auto-memory files, not `MEMORY.md`
   itself — see step 2), read the file, parse its YAML frontmatter (`name`, `description`,
   `metadata.type`) and body.
2. Do NOT filter by `metadata.type` — capture all four types (decision #2). Skip `MEMORY.md`
   itself only (it's an index of pointers, not a memory — parsing it would either double-capture
   every entry or capture nothing useful; the per-memory files are the source of real content).
3. Call `notify_turn` with a synthetic system-role message that preserves the memory's
   structure — `name`, `description`, `metadata.type`, and body (rule/fact + Why + How to apply)
   kept as distinct, labeled fields in the message rather than flattened into one paragraph — so
   Step 2/3/4 classification has a clean shape to route and reify (decision #3). Pass
   `metadata.type` through as `source_memory_class` so it lands as a queryable property on
   whatever node Step 4 reifies the content into. Key the call on the memory's `name:` field for
   upsert idempotency.
4. Tag the captured content clearly as originating from Claude's auto-memory (e.g. a
   `source: "claude_auto_memory"` param or a prefix in the synthesized message) so it's
   distinguishable in `current_truth`/`ask` results from content Campy classified from raw
   conversation — a future debugging aid, not optional polish.
5. Never block the agent: same `try/except: pass` discipline as every other hook integration
   this session (`register_artifact`'s block is the reference pattern).
6. Add a companion Campy-side test with a fixture memory file (frontmatter + body) asserting
   the parsed params reach `notify_turn` correctly AND that the resulting content actually
   reifies to an artifact node (not just accepted without erroring), matching this session's
   B290 `register_artifact` test pattern (`tests/test_register_artifact.py`).

### Acceptance Criteria

- [ ] Writing a NEW memory file (e.g. `project_test-example.md`), of ANY `metadata.type`
      (`user`, `feedback`, `project`, `reference`), triggers exactly one Campy capture via
      `notify_turn` — verified via a real (not mocked) daemon/DB round-trip or a unit test at
      the hook-script parsing boundary
- [ ] Editing the SAME memory file twice does not produce two separate Campy facts — upsert
      confirmed by `name:` frontmatter key, not append
- [ ] Writing to `MEMORY.md` itself does not trigger a capture (it's the index, not content)
- [ ] Hook failure (Campy daemon down, malformed frontmatter, etc.) never blocks or errors the
      agent's response — matches the `try/except: pass` discipline throughout this codebase's
      hook integrations
- [ ] A piggybacked memory actually reifies to a typed artifact node — verified via
      `explore_graph` or a direct Kuzu query for a `(Concept)-[REIFIED_AS]->(...)` edge on the
      captured content, not merely that `current_truth`/`ask` can retrieve *something* (a
      low-confidence, un-reified `Concept` is retrievable too and would be a false pass)
- [ ] The reified node (or its backing `Concept`) carries `source_memory_class` matching the
      originating memory's `metadata.type`, and a repo-scoped `compile_context`/`ask` query can
      filter on it (e.g. include only `project`+`feedback` for "what happened in this repo,"
      while a `user`-class fact remains present in the graph and retrievable by a query that
      asks for it)

### Outcome

Whatever Claude Code decides is worth remembering about a project becomes visible to Codex,
Gemini CLI, and every other agent working the same repo — without the person needing to
manually re-explain it, and without Claude needing to remember to call a Campy tool by hand on
top of its own native memory system.
