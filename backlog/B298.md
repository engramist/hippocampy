# B298 - Piggyback Claude Code's Auto-Memory Writes into Campy

State: ready — DESIGN DECISIONS NEEDED before implementation (see below)
Priority: P2

Plan: (inline — this card is self-contained)

### Problem

Claude Code has its own persistent auto-memory system (`~/.claude/projects/<project-slug>/memory/*.md`
+ a `MEMORY.md` index), separate from and invisible to Campy. Claude writes to it constantly —
this very session produced 7 memory files (`project_b290-cws.md` through `project_b297-readme-install.md`)
containing real decisions, root causes, and gotchas discovered while working the codebase.

None of that is visible to Campy, and therefore none of it is visible to any OTHER agent
(Codex, Gemini CLI, VS Code Copilot) working the same repo — directly undermining B290's own
premise (cross-agent continuity via a shared graph). If a user hits a token limit in Claude Code
and switches to Codex, Codex's `[Campy] Working on...` resume line has zero awareness of
anything Claude decided to remember, even though Claude explicitly judged that content durable
and important enough to persist.

The auto-memory system is not a special internal call — Claude writes to it using ordinary
`Write`/`Edit` tool calls targeting a specific directory. This means the existing PostToolUse
hook infrastructure can observe it, the same way B290's `register_artifact` capture already
observes `*.md` writes for document provenance.

### Why `register_artifact` (B290) Cannot Be Reused As-Is

`adapters/claude_code/hooks/post_tool_use.sh`'s existing `*.md` detection block (confirmed at
the end of the file) computes a **repo-relative path** via
`os.path.relpath(file_path, repo_root)` before calling `register_artifact`. A memory file lives
at `~/.claude/projects/<slug>/memory/*.md` — outside any project repo — so `relpath()` against
`repo_root` produces a nonsensical `../../../../.claude/projects/.../memory/foo.md` value.
`register_artifact`'s schema (`file_path`, `document_type`, `linked_card`) also models "a
document that exists in this project," not "a discrete fact the agent decided to remember" —
the wrong shape for this data. This card needs its own detection branch and its own Campy-side
handling, not a tweak to the existing WorkArtifact path.

### Design Decisions Needed (resolve before implementation starts)

**1. Which Campy entry point should receive the piggybacked content?**

| Option | How it works | Tradeoff |
|---|---|---|
| **`notify_turn` as a synthetic system message (recommended)** | Hook reads the memory file's frontmatter + body, wraps it as `{"role": "system", "content": "<memory type>: <body>", ...}`, calls `notify_turn`. Content flows through the normal Gated Consolidation Loop (NER, gist classification, relation extraction) like any other captured turn. | Reuses existing capture pipeline and classification intelligence; Campy decides Decision vs Lesson vs Constraint itself instead of the hook guessing. Slight risk: GCL is tuned for conversational turns, not memory-file prose — worth a quick eval before committing. |
| `upsert_lesson` direct call | Hook parses `metadata.type` and hand-maps it to a Lesson `lesson_type` (mistake/edge-case/optimization/architecture-principle). | Simple, deterministic — but `project`/`reference` memory types don't map cleanly onto Lesson's four-way taxonomy; would force awkward categorization. |
| New dedicated tool (e.g. `upsert_external_memory`) | New node type mirroring Claude's own memory schema (name, description, type, body). | Most semantically honest, but adds a 5th "how do I get context into the graph" path alongside notify_turn/upsert_lesson/ingest_document/register_artifact — more surface area than this feature's value obviously justifies right now. |

**2. Which memory types should piggyback?** Claude's memory system has four types:
`user` (cross-project facts about the person), `feedback` (how to work with them — often but
not always project-specific), `project` (facts about this codebase's work), `reference`
(pointers to external systems). Recommendation: piggyback `project` and `feedback` only.
`user` and `reference` memories are more often cross-project or point at systems outside this
repo (e.g. "bugs tracked in Linear project X") — pushing them into one repo's graph is likely
wrong scope. This needs a maintainer decision, not a default silently picked by the implementer.

**3. Idempotency.** Memory files get edited repeatedly — `MEMORY.md` in particular is rewritten
on nearly every new fact. Without upsert-by-filename (mirroring `register_artifact`'s
upsert-by-`file_path` pattern), every edit to `MEMORY.md` would fire a fresh capture, producing
duplicate/noisy Decision nodes over time. The hook must key on a stable identifier (the memory
file's `name:` frontmatter field, not the free-text body) and the Campy-side handler must
upsert, not blindly append.

**Recommended defaults if no objection:** notify_turn (option 1) + `project`+`feedback` types
only + upsert-by-`name:` frontmatter field. Do not start implementation until these are
confirmed — this is explicitly the same "STOP and ask" pattern used for B296's InvertorsDocs
decision.

### What This Card Does (once decisions are confirmed)

1. Add a new detection branch to `adapters/claude_code/hooks/post_tool_use.sh`, alongside the
   existing `*.md` WorkArtifact block: if `CLAUDE_TOOL_NAME` is `Write`/`Edit` AND the resolved
   file path matches `~/.claude/projects/*/memory/*.md` (auto-memory files, not `MEMORY.md`
   itself — see step 2), read the file, parse its YAML frontmatter (`name`, `description`,
   `metadata.type`) and body.
2. Filter by `metadata.type` per decision #2 above. Skip if the type isn't in the allowed set.
   Skip `MEMORY.md` itself (it's an index of pointers, not a memory — parsing it would either
   double-capture every entry or capture nothing useful; the per-memory files are the source of
   real content).
3. Call the chosen Campy entry point (per decision #1) with the parsed content, keyed by the
   memory's `name:` field for idempotency (per decision #3).
4. Tag the captured content clearly as originating from Claude's auto-memory (e.g. a
   `source: "claude_auto_memory"` param or a prefix in the synthesized message) so it's
   distinguishable in `current_truth`/`ask` results from content Campy classified from raw
   conversation — a future debugging aid, not optional polish.
5. Never block the agent: same `try/except: pass` discipline as every other hook integration
   this session (`register_artifact`'s block is the reference pattern).
6. Add a companion Campy-side test with a fixture memory file (frontmatter + body) asserting
   the parsed params reach the chosen entry point correctly, matching this session's B290
   `register_artifact` test pattern (`tests/test_register_artifact.py`).

### Acceptance Criteria

- [ ] Design decisions #1–#3 above have an explicit recorded answer (not a silently-applied
      default) before any code is written
- [ ] Writing a NEW memory file (e.g. `project_test-example.md`) with an allowed `metadata.type`
      triggers exactly one Campy capture, verified via a real (not mocked) daemon/DB round-trip
      or a unit test at the hook-script parsing boundary
- [ ] Writing a memory file with a disallowed type (per decision #2) triggers zero captures
- [ ] Editing the SAME memory file twice does not produce two separate Campy facts — upsert
      confirmed, not append
- [ ] Writing to `MEMORY.md` itself does not trigger a capture (it's the index, not content)
- [ ] Hook failure (Campy daemon down, malformed frontmatter, etc.) never blocks or errors the
      agent's response — matches the `try/except: pass` discipline throughout this codebase's
      hook integrations
- [ ] `current_truth` or `ask` can retrieve a piggybacked memory's content after capture,
      proving it's genuinely recallable, not just written and orphaned

### Outcome

Whatever Claude Code decides is worth remembering about a project becomes visible to Codex,
Gemini CLI, and every other agent working the same repo — without the person needing to
manually re-explain it, and without Claude needing to remember to call a Campy tool by hand on
top of its own native memory system.
