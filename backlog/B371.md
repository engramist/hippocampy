# B371 - Brain Daemon Briefly Unresponsive During IndexHygiene Warning Loop (B285 Follow-Up)

State: found, not yet investigated/fixed
Priority: P2

Plan: none yet.

### Problem

Found live 2026-08-30 during a joint cross-repo live-smoke verification of ARC_AGI's A221 Finding 1
change (`arc-agi-38` session, coordinating on this repo). A `run_single_puzzle.py --live-smoke
--max-steps 50` run failed its startup readiness probe with:

```
sidequest_mcp_client.readiness.ReadinessError: HippoCampy MCP upsert_lesson returned no lesson id
during readiness probe (payload={'text': '[Campy | Brain: OFFLINE - memory unavailable]'}).
```

Investigated before touching the process (per user instruction, not a blind restart):

1. `ps -p <daemon_pid> -o pid,pcpu,pmem,etime,stat` showed the daemon (PID alive since 04:25, ~16h
   uptime at the time) at **~125% CPU sustained, STAT=R (running)**, not idle.
2. A direct raw-socket `tools/list` JSON-RPC call to `~/.campy/brain.sock` (6s timeout, from a plain
   Python script, no MCP client wrapper) **timed out** — confirmed genuinely unresponsive, not just
   slow.
3. `~/.campy/daemon.log` (tail, at the time of the failure) showed **4,884 identical, unrate-limited
   repeats** of:
   ```
   [IndexHygiene] Message archived_ratio=1.00 >= threshold=0.50 — rebuild is disabled by design
   (Path B archive-move not yet implemented, see backlog/B285.md); index staleness for this table is
   accumulating
   ```
   immediately preceded by many repeats of `[Sweep] decayed=12 archived=0 resurrected=0 promoted=0
   centroids=0 patterns=0 errors=25`, also unrate-limited.
4. **This contradicts B285's own design intent.** B285's Implementation section explicitly says the
   warning "now logs a `WARNING` when a table crosses threshold" — a single log event per crossing, not
   a tight, repeated loop. 4,884 identical repeats of the same message, with no timestamps separating
   them in this daemon.log format, strongly suggests something is calling the sweep/hygiene check (or
   just its warning-emission path) in a busy loop rather than on its normal interval — the CPU spike and
   socket unresponsiveness are consistent with the event loop being starved by this.
5. **It self-resolved without intervention.** ~1 minute after the failed readiness probe: re-checked
   `ps` — CPU back to 0.1%, STAT=S (sleeping/idle). Re-ran the same raw-socket `tools/list` call —
   responded in 0.00s with a valid 2010-byte payload. `daemon.log` had stopped growing (checked twice,
   5s apart, static file size) before the recovery was confirmed, meaning the loop had already ended by
   the time it was caught, not something actively still running.
6. `py-spy dump --pid <pid>` was attempted for a live stack trace but requires `sudo` on macOS with an
   interactive password prompt, which wasn't available in this session — worth having a passwordless
   path to this (or documenting `sample <pid> <duration>`, the macOS built-in that worked without sudo
   for a same-user process, as the fallback) for whoever investigates this next. The `sample` output
   *after* recovery showed the main thread idle in `kevent` (normal asyncio idle) and Kuzu's worker
   threads idle in `pthread_cond_wait` (normal thread-pool idle) — consistent with "already recovered,"
   not diagnostic of the stuck state itself. No stack trace was captured *during* the actual hang — that's
   the real gap for a future investigation.

Related but distinct from B308 (the actual archive-move rebuild mechanism B285 deferred to): this card
is specifically about the **warning-logging path itself misbehaving** (looping without rate-limiting,
apparently starving the event loop), independent of whether B308's real fix ever lands.

### What it does (scope)

Not yet decided — this card records the symptom and evidence, not a fix. Whoever picks this up should:

1. Find where `_index_hygiene`'s warning log call sits relative to the sweep's own scheduling loop —
   confirm whether it's genuinely being invoked in a tight loop (a scheduling bug: sweep interval not
   respected, or a retry path re-entering it) or whether daemon.log's lack of timestamps is misleading
   about the actual time window (i.e. 4,884 repeats could span minutes, not seconds — worth checking
   sweep's own configured interval against how long 4,884 iterations would take at that interval, before
   assuming it's a true busy-loop).
2. If it is a real busy-loop: add rate-limiting/backoff to the warning emission itself (log once per
   sweep pass, or once per N minutes, not once per check) — the simplest fix, independent of whatever
   is causing repeated invocation.
3. Separately worth checking: does anything in the sweep/hygiene path hold a lock or block the main
   asyncio event loop synchronously (explaining the socket unresponsiveness, not just high CPU)? A
   pure background-thread CPU spike shouldn't itself block a `kevent`-based event loop from accepting a
   new connection — the observed *socket* timeout (not just slow CPU) suggests something more specific
   than "the CPU was busy."
4. Get a real stack trace *during* a live occurrence next time (schedule a `py-spy dump` with
   passwordless sudo pre-authorized, or `sample <pid> 5` at the first sign of elevated CPU) rather than
   only being able to diagnose after the fact.

### Dependencies

- B285 (closed) — this is a regression/gap in that card's own delivered behavior, not new scope.
- B308 (archive-move rebuild) — unrelated fix, but closing it would stop the underlying condition
  (`archived_ratio >= threshold`) from recurring, which would incidentally stop this warning from firing
  at all. Not a substitute for fixing the loop/rate-limiting itself.

### Acceptance Criteria

- [ ] Root cause identified: confirmed busy-loop vs. misread timestamps vs. some other explanation
- [ ] If busy-loop confirmed: warning emission is rate-limited (once per sweep pass, not once per check)
- [ ] Confirmed whether the hang blocks the event loop directly (socket-level) or is purely a CPU/
      scheduling side effect
- [ ] A repeatable way to capture a live stack trace during a future occurrence is documented (even if
      just "run `sample <pid> 5` the moment you see elevated CPU in `ps`")
