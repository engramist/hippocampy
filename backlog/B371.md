# B371 - Brain Daemon Briefly Unresponsive During IndexHygiene Warning Loop (B285 Follow-Up)

State: investigated — the leading hypothesis (busy loop) is disproven; real fixes landed for what was actually found; the original CPU/socket-timeout symptom's exact cause remains unconfirmed
Priority: P2

Plan: none yet.

### Problem

Found live 2026-08-30 during a joint cross-repo live-smoke verification of ARC_AGI's A221 Finding 1
change (`arc-agi-38` session, coordinating on this repo). A `run_single_puzzle.py --live-smoke
--max-steps 50` run failed its startup readiness probe with:

```
sidequest_mcp_client.readiness.ReadinessError: HippoCampy MCP upsert_lesson returned no lesson id
during readiness probe (payload={'text': '[Campy | Brain: OFFLINE - memory unavailable]'}).
```

Investigated before touching the process (per user instruction, not a blind restart):

1. `ps -p <daemon_pid> -o pid,pcpu,pmem,etime,stat` showed the daemon (PID alive since 04:25, ~16h
   uptime at the time) at **~125% CPU sustained, STAT=R (running)**, not idle.
2. A direct raw-socket `tools/list` JSON-RPC call to `~/.campy/brain.sock` (6s timeout, from a plain
   Python script, no MCP client wrapper) **timed out** — confirmed genuinely unresponsive, not just
   slow.
3. `~/.campy/daemon.log` (tail, at the time of the failure) showed **4,884 identical, unrate-limited
   repeats** of:
   ```
   [IndexHygiene] Message archived_ratio=1.00 >= threshold=0.50 — rebuild is disabled by design
   (Path B archive-move not yet implemented, see backlog/B285.md); index staleness for this table is
   accumulating
   ```
   immediately preceded by many repeats of `[Sweep] decayed=12 archived=0 resurrected=0 promoted=0
   centroids=0 patterns=0 errors=25`, also unrate-limited.
4. **This contradicts B285's own design intent.** B285's Implementation section explicitly says the
   warning "now logs a `WARNING` when a table crosses threshold" — a single log event per crossing, not
   a tight, repeated loop. 4,884 identical repeats of the same message, with no timestamps separating
   them in this daemon.log format, strongly suggests something is calling the sweep/hygiene check (or
   just its warning-emission path) in a busy loop rather than on its normal interval — the CPU spike and
   socket unresponsiveness are consistent with the event loop being starved by this.
5. **It self-resolved without intervention.** ~1 minute after the failed readiness probe: re-checked
   `ps` — CPU back to 0.1%, STAT=S (sleeping/idle). Re-ran the same raw-socket `tools/list` call —
   responded in 0.00s with a valid 2010-byte payload. `daemon.log` had stopped growing (checked twice,
   5s apart, static file size) before the recovery was confirmed, meaning the loop had already ended by
   the time it was caught, not something actively still running.
6. `py-spy dump --pid <pid>` was attempted for a live stack trace but requires `sudo` on macOS with an
   interactive password prompt, which wasn't available in this session — worth having a passwordless
   path to this (or documenting `sample <pid> <duration>`, the macOS built-in that worked without sudo
   for a same-user process, as the fallback) for whoever investigates this next. The `sample` output
   *after* recovery showed the main thread idle in `kevent` (normal asyncio idle) and Kuzu's worker
   threads idle in `pthread_cond_wait` (normal thread-pool idle) — consistent with "already recovered,"
   not diagnostic of the stuck state itself. No stack trace was captured *during* the actual hang — that's
   the real gap for a future investigation.

Related but distinct from B308 (the actual archive-move rebuild mechanism B285 deferred to): this card
is specifically about the **warning-logging path itself misbehaving** (looping without rate-limiting,
apparently starving the event loop), independent of whether B308's real fix ever lands.

### What it does (scope)

Not yet decided — this card records the symptom and evidence, not a fix. Whoever picks this up should:

1. Find where `_index_hygiene`'s warning log call sits relative to the sweep's own scheduling loop —
   confirm whether it's genuinely being invoked in a tight loop (a scheduling bug: sweep interval not
   respected, or a retry path re-entering it) or whether daemon.log's lack of timestamps is misleading
   about the actual time window (i.e. 4,884 repeats could span minutes, not seconds — worth checking
   sweep's own configured interval against how long 4,884 iterations would take at that interval, before
   assuming it's a true busy-loop).
2. If it is a real busy-loop: add rate-limiting/backoff to the warning emission itself (log once per
   sweep pass, or once per N minutes, not once per check) — the simplest fix, independent of whatever
   is causing repeated invocation.
3. Separately worth checking: does anything in the sweep/hygiene path hold a lock or block the main
   asyncio event loop synchronously (explaining the socket unresponsiveness, not just high CPU)? A
   pure background-thread CPU spike shouldn't itself block a `kevent`-based event loop from accepting a
   new connection — the observed *socket* timeout (not just slow CPU) suggests something more specific
   than "the CPU was busy."
4. Get a real stack trace *during* a live occurrence next time (schedule a `py-spy dump` with
   passwordless sudo pre-authorized, or `sample <pid> 5` at the first sign of elevated CPU) rather than
   only being able to diagnose after the fact.

### Outcome

Investigated 2026-08-30, per explicit instruction to investigate for real rather than guess at a fix.
The leading hypothesis in this card's own "What it does" section — a genuine busy-loop re-invoking
`_index_hygiene` far faster than the configured sweep interval — is **disproven** by direct
measurement. What actually happened, and what's fixed:

**1. "4,884 identical repeats" is not a burst — it's ~3.5 months of cumulative, correctly-paced
history, misread because `daemon.log` is never rotated and has no timestamps.**

`~/.campy/daemon.log` (checked directly): created **May 15, 2026**, currently 857,146 lines / 62MB,
never rotated or truncated since. `grep -c` for the exact warning across the *entire* file: **4,888**
— essentially the same number the original investigation found in a "tail" snapshot, which strongly
suggests that snapshot was not a tight recent burst but a large fraction of the file's entire history.
Corroborating math: the file also contains **12,230** total `[Sweep] decayed=...` lines (one per
completed sweep cycle, ever). At the shipped 300s interval, that's ~42.5 cumulative days of
sweep-active daemon uptime spread across many restarts over a 3.5-month wall-clock span — and 4,888 of
those 12,230 cycles (~40%) logged the Message-table warning, consistent with Message's `archived_ratio`
having been pinned at (or near) 1.0 for a long-standing, expected reason (see next point), not a new
or accelerating condition. **This directly answers this card's own open question 1: it is the "misread
timestamps" explanation, not a busy loop — verified by counting the actual file, not assumed.**

**2. Directly measured: `_index_hygiene`'s own queries are far too fast to be the hang's cause.**

Stopped the (idle) dev daemon, ran `_index_hygiene`'s exact query pattern against the real production
KuzuDB for all 9 sweepable tables: **13.5ms total**, with the Message table itself (18,125 rows,
confirmed `archived_ratio=1.000` right now — a real, current, permanent condition, not historical) at
**0.7ms**. This rules out `_index_hygiene`'s synchronous `db.execute()` calls (flagged in this card's
own open question 3 as a plausible event-loop-blocking mechanism) as the cause of any multi-second
hang — the numbers are two to three orders of magnitude too small.

**3. Found and fixed two real (but likely not the cause of this specific incident) event-loop-blocking
bugs while tracing the LLM-calling steps in `run_sweep()`'s pipeline for other candidate blockers.**

`_hebbian_promote` and `_dream_consolidation` each independently reimplemented an
"if the LLM client has `achat`, await it; else call `.chat()` directly" branch. The `else` branches
were broken: `_hebbian_promote`'s called `.chat()` synchronously with no `await` and no thread
offload — a genuine event-loop block for the duration of the LLM call, for any client lacking `achat`.
`_dream_consolidation`'s was worse — `await llm_client.chat(...)` on a method that returns a plain
`str`, which would raise `TypeError: object str can't be used in 'await' expression` outright. Both
are almost certainly **dead code in this deployment** — the real `LLMClient` (Ollama-backed, per
`campy/brain/llm/provider.py`) always has `achat`, so the `else` branch is unreachable today — but
real, latent bugs regardless, and a correctly-implemented version of this exact branching
(`_call_llm()`, defined later in the same file) already existed and was already used elsewhere. Fixed
both call sites to reuse `_call_llm()` instead of a third, buggy copy of the same logic. Verified via
the existing test suite: `test_hebbian_promote_writes_named_edge` (and siblings) already exercise the
achat-less mock-LLM path and pass unchanged post-fix, since `_call_llm()`'s branching is behaviorally
identical to the (correct) `if hasattr` branch these tests were already hitting.

**4. Fixed the actual, concrete reason this investigation was hard: `brain_daemon.py` never configures
logging, so every `_logger.*` line in `daemon.log` had no timestamp at all.**

Confirmed via grep: no `logging.basicConfig`/`Formatter`/handler setup anywhere in `campy/brain_daemon.py`
or anything it imports at daemon-process scope (`campy/cli/main.py` has one, but that's a separate CLI
process, not the daemon). Python's logging module was falling back to its last-resort handler —
`%(levelname)s:%(name)s:%(message)s`, no time field — which is exactly why the original investigation
couldn't tell "4,884 repeats over minutes" from "4,884 repeats over months" without the file-level
forensics done above. Added a real `logging.basicConfig(..., format="%(asctime)s %(levelname)s
%(name)s: %(message)s")` call at the top of `main()`. This does **not** timestamp the separate
`print()`-based lines (`[Sweep] decayed=...`, `[Loop] ...`, etc.) — a smaller, known residual gap, not
fixed here since it would mean touching many call sites for comparatively less benefit than the
`_logger.warning` lines that actually caused this confusion.

**What's still genuinely unresolved, honestly:** the original incident's real symptom — ~125% CPU and
a raw-socket `tools/list` call actually timing out — was real and is not explained by any of the above
(IndexHygiene itself is proven fast; the LLM-fallback bugs are proven unreachable in this deployment).
The self-resolution within ~1 minute, during a period of real concurrent write traffic from an
active live-smoke run, is consistent with the *already-documented* class of transient CPU/write-pressure
spike this project spent six rounds investigating in `backlog/B311.md` (culminating in B337's periodic
checkpoint) and `backlog/B342.md` (culminating in B354's footprint watchdog + B342's periodic
restart) — both of which already exist as mitigations for exactly this shape of event, but neither
was confirmed as *this specific* incident's cause; that would need a live stack trace captured
*during* a future occurrence, which did not happen here either (none occurred while investigating).

**Repeatable live-capture method for next time (this card's open question 4), documented since a
passwordless `sudo` path for `py-spy` isn't something this session can configure (would need the
account owner's password):**
```bash
# The moment `ps -p <daemon_pid> -o pid,pcpu,stat` shows elevated CPU / STAT=R sustained:
sample <daemon_pid> 5 -f /tmp/daemon_hang_sample.txt
```
`sample` is a macOS built-in, needs no `sudo` for a same-user process (confirmed working by the
original investigation, just captured too late). The key correction to how it was used last time:
run it **immediately** on the first elevated-CPU observation, not after confirming the daemon is
"still" unresponsive — by the time a second `ps` check confirms sustained CPU, several seconds have
already passed and the window may close (this incident self-resolved in about a minute). If watching
for a real occurrence, a tight polling loop (`while true; ps -p <pid> -o pcpu= ; sleep 1; done`)
piped to trigger `sample` past a CPU threshold would catch it far more reliably than manual checking.
