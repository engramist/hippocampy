# B319 - Backup and Restore for Earned Memory

State: done
Priority: P1

Plan: (inline — self-contained, sized for a Sonnet-level implementer)

Depends on: **B313** (the `authority` split defines what actually needs backing up).
Composes with **B316** (per-workspace databases) but does not require it — write the
backup layer workspace-aware from the start and it works either way.

### Why

B313 establishes that Campy holds two kinds of fact. `projected` facts are mirrors of an
external authority and can be regenerated by re-running a harvest. **`earned` facts cannot
be regenerated by anything.** A lesson an agent learned, a decision recorded mid-session, a
hypothesis that got falsified — if the database is lost, that knowledge is simply gone.

Campy currently has **no backup or restore command**. Verified: `campy/cli/` contains 23
modules and none of them is a backup. The closest thing is `campy/cli/graph_io.py`
(`export_graph_cmd` line 25, `import_graph_cmd` line 48), which is a manual JSONL dump —
useful, but it is a developer tool, not a backup story: no scheduling, no retention, no
restore verification, no per-workspace awareness.

The evidence that this matters is in the repo's own history: `backlog/masterBacklogTracker.md`
records B302 taking a manual one-off backup (`~/.campy/brain.db.pre-b302-backup-202607142244`)
before a destructive sweep. Someone already knew a backup was needed and did it by hand.

The moment Campy holds anything authoritative for an external customer, "what is your DR
story?" is the first question their platform review asks, and "we have an export script"
is not an answer.

### What This Card Does

**Task 1 — `campy backup` / `campy restore`.**

New module `campy/cli/backup.py`, registered in `campy/cli/main.py` following the existing
subcommand pattern (read how `graph_io` is wired and match it).

```
campy backup create   [--workspace ID|--all] [--out DIR] [--include-projected]
campy backup list     [--workspace ID]
campy backup verify   SNAPSHOT
campy backup prune    [--keep-daily N --keep-weekly N]
campy restore         SNAPSHOT [--workspace ID] [--force]
```

Design decisions to make explicitly rather than by default:

- **Default excludes projected facts** — B313 already added `include_projected=False` to
  `export_graph_dump`/`export_graph`. Reuse it; do not reimplement the filter.
- **Snapshot format**: reuse the existing JSONL dump from `graph_io`/`export.py` rather than
  copying the Kùzu database directory. A file copy is faster but is opaque, version-locked to
  Kùzu 0.11.3, and cannot be restored into a different engine — which defeats the portability
  B314 is buying. If dump/restore turns out to be unacceptably slow on a large graph,
  say so in the PR with numbers rather than silently switching to a file copy.
- **Every snapshot carries a manifest**: schema version, Campy version, embedding model +
  dimension, workspace id, node/edge counts per table, creation time, and a checksum of the
  payload. Without the embedding model recorded, a restore can silently produce a graph whose
  vectors do not match the running model — retrieval then degrades with no error anywhere.

**Task 2 — Restore must be verified, not hoped for.**

An unverified backup is not a backup. `campy backup verify SNAPSHOT` must:

1. check the payload checksum against the manifest
2. restore into a **temporary throwaway database**, never the live one
3. assert the restored node/edge counts match the manifest
4. run one real recall query against the restored graph and assert it returns results
5. report embedding-model mismatch against the currently configured model as a **warning,
   not a failure** — restoring onto a different model is legitimate (you may be migrating),
   it just means vectors need rebuilding

Step 2 is the part people skip. Verify must never touch the live database.

**Task 3 — `restore` is the dangerous one.**

- Refuse to overwrite a non-empty database without `--force`
- With `--force`, **take an automatic pre-restore snapshot first** and print its path before
  doing anything. The most common way to lose data during a restore is restoring the wrong
  snapshot over good data.
- Refuse outright if the manifest's schema version is *newer* than the running code — a
  forward restore can silently drop columns the current code does not know to write back.
  Older is fine: run `init_schema()` after restore so `_MIGRATIONS` brings it up to date.
- Print a summary and require confirmation on an interactive terminal; `--yes` for scripts.

**Task 4 — Scheduling, minimal.**

Do not build a scheduler. Campy already installs platform services — see
`campy/cli/launchd.py` (macOS) and whatever the Linux equivalent is in `campy/cli/install.py`.
Add a daily `campy backup create --all` to that existing mechanism, defaulting to
`~/.campy/backups/`, with `--keep-daily 7 --keep-weekly 4` retention via `backup prune`.

If a workspace has not changed since its last snapshot, skip it and hard-link or record a
pointer instead of writing a duplicate dump. Cheap, and it keeps retention honest.

**Task 5 — Workspace awareness.**

Write this layer against a workspace id from the start, even before B316 lands: with one
database, `--all` iterates a single `local` workspace. When B316 arrives, the same code walks
the router's workspace root with no rewrite. Snapshot paths must include the workspace id so
a restore cannot land in the wrong one.

### Acceptance Criteria

- [ ] Round-trip: seed a graph with earned facts, `backup create`, wipe the DB, `restore`,
      and assert every earned node and edge is present with identical properties — not just
      matching counts
- [ ] Projected facts are excluded by default and included with `--include-projected`
- [ ] Manifest records schema version, Campy version, embedding model + dim, workspace id,
      per-table counts, and a payload checksum
- [ ] `backup verify` detects a corrupted payload (flip a byte in the dump, assert failure)
- [ ] **`backup verify` does not touch the live database** — assert the live DB's mtime and
      contents are unchanged after a verify run
- [ ] `restore` into a non-empty DB without `--force` refuses and changes nothing
- [ ] `restore --force` writes a pre-restore snapshot first and prints its path
- [ ] `restore` refuses a snapshot whose schema version is newer than the running code
- [ ] `restore` of an *older*-schema snapshot succeeds and `init_schema()` migrates it —
      assert a post-B312 column exists afterward
- [ ] Embedding-model mismatch warns and still restores
- [ ] `backup prune` honors retention and never deletes the most recent snapshot
- [ ] `pytest tests/ -q` failure set identical to pre-change baseline

### What This Card Does NOT Do

- Does not implement continuous point-in-time recovery — this is snapshot-based. Real PITR
  needs a write-ahead log Campy does not have, and is a much larger card.
- Does not implement remote/offsite backup targets (S3 et al.). Local directory only; the
  output is a plain directory a customer's existing backup tooling can pick up.
- Does not encrypt snapshots at rest
- Does not back up `~/.campy/` config, triggers, or the activity log — graph only

### Outcome

Earned memory stops being one disk failure away from gone, restore is verified rather than
assumed, and "what happens if this is lost" has an answer with a command attached. This is
the obligation that comes with B313's claim that some of Campy's data is authoritative.
