### Problem

`membench/runner.py` reads:

```python
ctx_res = client.compile_context(probe.question, token_budget=4000)
bundle_tokens = ctx_res.get("token_count", 380)
```

but `compile_context`'s real MCP response (see
`campy/brain/thalamus/tools/context_tools.py:139` and `:651` in the
`hippocampy` repo) nests the estimate at
`ctx_res["bundle"]["total_token_estimate"]` — there is no top-level
`token_count` key at all. Every call silently falls through to the
hardcoded default of `380`, so `membench`'s `token_savings_pct`
calculation is computed from a constant rather than the real bundle
size, always reporting **0.0%** token savings regardless of actual
compression.

### Evidence

Documented in the orphaned pre-cutover benchmark report
(`docs/benchmarks/kuzu-baseline-kpis.md`, committed via PR #229 in
`hippocampy`), Section 5.2 item 4 ("Harness Token Calculation Key
Mismatch"). Confirmed still present by reading
`campy-benchmarks/membench/runner.py:56` directly on 2026-09-20 — not
just re-reading the old report's claim.

### Fix

```python
bundle_tokens = ctx_res.get("bundle", {}).get("total_token_estimate", 380)
```

(or equivalent) — and re-run MemBench to get a real, non-zero baseline
`token_savings_pct` measurement.

### Acceptance Criteria

- [ ] `membench/runner.py` reads the real nested key.
- [ ] A re-run of MemBench (`python run_all.py` or the membench suite
      alone) produces a non-constant, non-zero `token_savings_pct` when
      bundles are genuinely compressed relative to raw conversation size.
- [ ] `docs/benchmarks/kuzu-baseline-kpis.md` (in `hippocampy`) gets a
      follow-up note or superseding report once a corrected number
      exists, so the `0.0%` figure isn't mistaken for a real measurement
      going forward.

### Outcome

MemBench's token-savings metric reflects Campy's actual context
compression instead of an always-0% artifact of a harness bug.

### Completion Notes (2026-09-21)

Fixed `membench/runner.py` to read the real nested key. Also fixed
`mcp_client.py`'s mock `compile_context` handler, which had the exact
same wrong-shape bug baked into its fake response (`"token_count": 420`
top-level instead of `bundle.total_token_estimate`) — this had been
silently masking `runner.py`'s bug in smoke/mock mode too, so fixing
only `runner.py` wouldn't have been verifiable without a live daemon.
The mock now estimates tokens from its own actual mocked content
(~4 chars/token, matching `runner.py`'s own heuristic) instead of a
hardcoded literal.

Verified: `python3 run_all.py --smoke --suite membench` went from a
hardcoded `Savings: 0.0%` to `Savings: 85.15%`. Confirmed load-bearing
by reverting and reproducing the original 0.0% output, then restoring.

While verifying against a combined `--suite all` run, found a second,
separate bug: `_mock_constraints` is shared mutable state across every
suite on the same `CampyMCPClient` instance, so LoCoMo/MemoryGym's fake
data leaks into MemBench's mocked bundle in a combined run, inflating
its token estimate past the raw conversation size and flooring
`token_savings_pct` back to 0.0% — order-dependent and unrelated to
this card's fix. Filed as B438 rather than expanding this card's scope.

A real, live-daemon end-to-end re-run (this card's third acceptance
item, and the corrected-baseline follow-up to
`docs/benchmarks/kuzu-baseline-kpis.md`) was not performed — that needs
a running Campy daemon + Ollama, a heavier verification step than
confirming the fix itself. The smoke/mock verification above proves the
mechanism works; a live number is separate follow-up work.
