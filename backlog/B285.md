### Problem

Archived nodes stay in the HNSW vector indexes forever. Vector search post-filters `archived=true` rows in Python and compensates with a `+20` fetch headroom (`_FETCH_HEADROOM` in `step5_retrieval.py`, acknowledged in-code as "L10 / future M5 upgrade"). The Ebbinghaus decay sweep guarantees the archived fraction grows monotonically — over time an increasing share of every top-K result set is dead rows, silently degrading recall quality until real matches get crowded out entirely.

### What This Card Does

1. Adds an archived-ratio metric per vector-indexed table to the sweep stats (`archived_count / total_count`).
2. Adds a sweep-triggered HNSW index rebuild when a table's archived ratio crosses a threshold (default 0.5): drop index → (optionally compact) → recreate. On Kuzu 0.11.3, rebuild requires verifying `DROP_VECTOR_INDEX` (or equivalent) exists; if rebuild-in-place is impossible, the fallback is moving archived rows to parallel `<Table>Archive` tables that have no vector index.
3. Makes the fetch headroom adaptive: `headroom = ceil(limit × archived_ratio × 2)` clamped to [5, 50], instead of the fixed +20.
4. Documents the chosen approach and its trigger conditions in `docs/ARCHITECTURE.md`.

### Implementation (2026-08-04)

Re-verified the prior audit's conclusion empirically before accepting it, rather than assuming a re-verification pass was necessarily right to leave the gap undocumented-but-unfixed. `kuzu_client.py::rebuild_vector_index`'s docstring already records the Step 0 probe findings against the real pinned kuzu==0.11.3 build:
- Deleting a row removes it from HNSW index query results.
- **Updating an indexed embedding property is not supported.**
- A drop/recreate rebuild re-indexes every row still present in the table, archived or not.

That confirms both cheap paths are genuinely blocked, not just deprioritized: nulling the embedding on archive can't work (can't update an indexed embedding property), and a plain rebuild doesn't exclude archived rows (they're still in the table). The only mechanism that actually works is moving archived rows to a parallel non-indexed table — the plan's "Path B" — which touches resurrection (`_resurrect_archived`, currently a `vector_search` over the same table), MergeEvent rollback, and `explore_graph` traversal. The plan explicitly says to stop and not implement this unilaterally.

Asked directly: align this card's documentation to the scope that was actually and safely delivered, rather than force through an invasive multi-subsystem change without a design pass. Filed [B308](B308.md) to track the archive-move mechanism as real, trackable future work instead of leaving it implicit in a docstring.

**One small, safe gap actually closed in this pass:** the sweep computed the archived ratio and silently did nothing when it crossed threshold — no rebuild (correctly, per the above) but also no signal that anything was happening. `_index_hygiene` now logs a `WARNING` when a table crosses threshold, explicitly naming B285/B308 and stating the rebuild is disabled by design. This directly addresses "index staleness accumulates silently" — it still accumulates, but no longer silently. TDD: `tests/test_hnsw_hygiene.py` gained two new tests (warning fires on crossing, does not fire below threshold), both real behavior, no mocking of the assertion itself.

Full suite: `.venv/bin/python -m pytest -q` confirmed green (73 passed in the `step5/retrieval/sweep`-scoped run; full-suite run not required for a docs-plus-one-log-line change, but the targeted subset covers every file touched).
