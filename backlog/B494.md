# B494: LLM calls have no output-length cap; a runaway generation hangs ask for ~12 minutes

**Status:** in review · **Found:** 2026-10-19 during benchmark replays

`run_ask` on one LoCoMo conversation repeatedly hung. The Ollama log showed `/v1/chat/completions` requests from the 8b answer model each running exactly 3m0s (the client's 180 s timeout, `_resolve_timeout_seconds`), retried 3 more times (`_resolve_max_retries`): about 12 minutes per question, then `openai.APITimeoutError` aborted the replay. Every other request took 2-5 s.

## Cause
`LLMClient.chat/achat/chat_with_usage/achat_with_usage` called `chat.completions.create(...)` with no `max_tokens`, so a degenerate repetition generated until the timeout. A real user's `ask` can hang the same way.

## Fix
- New `[llm] max_tokens` (default 2048; `0` = no cap) in `_DEFAULT_CONFIG`, documented in `campy.toml`, env override `CAMPY_LLM_MAX_TOKENS`.
- `LLMClient` sends `max_tokens` on every request; a per-call `max_tokens=` wins. All four methods now accept kwargs. `BedrockLLMClient` maps it to `inferenceConfig.maxTokens` and honours the per-call value (previously silently dropped).
- A response that stops on the cap (`finish_reason == "length"`, Bedrock `stopReason == "max_tokens"`) logs a WARNING naming provider/model, the cap and the first 120 chars of the last user message. It does not raise.
- `LLMProseCompressor` raises its per-call cap to 1.5x its target when that exceeds 2048. Other callers (answers, summaries, key facts, extraction, arbitration, lessons, quest purpose) produce short outputs and already pass small explicit caps where they matter (B468).

## Done when
Unit tests in `tests/test_provider.py` (B494 block) and `tests/test_cloud_deployment_readiness.py` pass; a runaway generation ends at the cap and logs the offending question.
