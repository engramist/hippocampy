# B332 - Retract or Reproduce the ARC3 Benchmark Result (No Harness Exists for It)

State: complete, with a correction — see "Correction (2026-08-20)" below before reading the rest of
this card. The original problem statement is factually incomplete in a way that changes the right
framing for the retraction; it's left as-written for the historical record, not because it's accurate.
Priority: P1

Plan: none yet.

### Problem

`benchmarks/results/arc3.json` claims a flagship result:

```json
{
  "benchmark_name": "arc3",
  "success": true,
  "duration": 3600,
  "metrics": { "solve_rate_improvement": 0.08, "p_value": 0.042 },
  "error": null,
  "timestamp": 1774716222.9183722
}
```

An external audit found this result cannot be reproduced with any documented command, and re-verified
here for this card: there is no ARC3 benchmark harness class anywhere in the tree, no call to
`BenchmarkRunner.register_benchmark(...)` for anything named "arc3" (`register_benchmark` is defined
once at `benchmarks/runner.py:21` but never called with an arc3 harness), and no reference to "arc3" in
git history outside this one static results file. `duration: 3600` is exactly what a configured timeout
would produce, which is consistent with this being a placeholder rather than a real run's output.

This is currently presented as a genuine benchmark result (e.g. cited in whatever report/README
surfaces benchmark numbers) with no caveat that it's unverifiable. That's a credibility risk — if a
skeptical outside reviewer checks this the way the external audit did, it reads as a fabricated number,
regardless of intent.

### What it does (scope)

This card is a data-integrity fix, not a feature build. Two acceptable outcomes — pick whichever
matches reality once investigated:

**Path A — the result is real but the harness was lost/never committed.** If there's evidence (in
private notes, another branch, an old commit, or team memory) that this run genuinely happened against
a real ARC3 task set, then build (or recover) the actual harness, register it via
`BenchmarkRunner.register_benchmark(...)` following the pattern of the other benchmark harnesses under
`benchmarks/` (e.g. `benchmarks/causal/`, `benchmarks/longcontext/`), and re-run it to produce a
reproducible result. Document the exact command in `benchmarks/benchmark_sources.md` the way other
benchmarks are documented there.

**Path B — the result cannot be substantiated.** Delete or clearly mark `benchmarks/results/arc3.json`
as retracted (e.g. rename to `arc3.json.retracted` or add a top-level `"status": "retracted, unable to
reproduce — see backlog/B332.md"` field), and remove or caveat every place that cites the 0.08 /
p=0.042 numbers as a real result (grep the repo for `"0.08"` near "arc3" or "solve_rate_improvement" to
find citing docs — check README.md and any benchmark summary/report doc).

Default to Path B unless investigation turns up real evidence for Path A — do not fabricate a harness
retroactively just to make the old number reproducible.

### Correction (2026-08-20)

The Problem statement above, and the retraction it produced, are **incomplete, not wrong about the
narrow technical fact** — but the framing overstated what that fact means. Verified directly against
the sibling `ARC_AGI` repo (`~/Desktop/GitProjects/ARC_AGI`, a real, separate project this one is
architecturally split from — Campy is the memory engine, ARC_AGI is the game-playing agent that calls
it over MCP):

`ARC_AGI/benchmarks/arc3/harness.py` is real, substantial code, literally titled *"ARC-AGI-3 A/B Harness
(Baseline vs SideQuests-Augmented) — Implements the A/B evaluation for ARC puzzles, measuring memory
impact on solve rate, step count, and token efficiency."* Its adapter (`benchmarks/arc3/adapter.py`)
imports `sidequest_mcp_client` and talks to Campy over MCP — exactly the shape of harness that could
produce a `solve_rate_improvement`/`p_value` result. The `benchmarks/arc3/` directory also contains
real competition scaffolding (`KaggleSiteInfo.md`, `TermsAndConditions.md`, `tasks_manifest.json`,
`model_eval.py`, `trajectory_eval.py`, `world_model_eval.py`, `regression_monitor.py`) — not a stub.

So **"there is no ARC3 harness anywhere in the tree" was true only about this repo's own tree**, and
this repo's architecture intentionally puts that harness in a sibling repo, not here. The original
framing — "no harness exists," leading to a full retraction — implied the result was fabricated. That
implication isn't supported: a real, working mechanism to produce this class of result exists, just not
where the original check (or the external audit it followed) looked.

**What's still genuinely unresolved, even accounting for that:** the *specific* numbers in the retracted
`arc3.json` (`solve_rate_improvement: 0.08`, `p_value: 0.042`) do not appear anywhere in
`ARC_AGI/benchmarks/results/regression_history.jsonl` — that file uses a different metric shape entirely
(raw `solve_rate` per run, no `p_value` field), and no entry matches. So a real harness exists, but this
particular result still isn't traceable to a specific run in it. That could mean it came from an
aggregation script not yet located, or from a run that's aged out of the history file — genuinely
unknown, not evidence of fabrication.

**Corrected status:** the retraction language has been softened from "retracted, unable to reproduce" to
"unverified" — deliberately not re-asserting the number as real, but no longer implying it was invented.
See `benchmarks/results/arc3.json`, `benchmarks/RESULTS.md`, and `benchmarks/benchmark_sources.md` for
the updated text. Cross-repo reconciliation (finding the actual source of this number in ARC_AGI, if it
exists, or establishing conclusively that it doesn't) remains open work — filed as a note here rather
than a new numbered card, since it would require coordinated changes across two repos.
