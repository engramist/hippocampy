# B417 - Oxigraph Cutover Strands a Legacy Kùzu `brain.db`: Daemon Crash-Loops on a Cryptic `FileExistsError`, No In-Place Migration or Guard

State: ready
Priority: P0
Branch: docs/b417-kuzu-brain-db-startup-crash

### Problem

Any existing user whose `~/.campy/brain.db` predates the Oxigraph cutover cannot start
the daemon. Discovered live on 2026-09-09 while bringing the daemon up for a smoke test:
`~/.campy/brain.db` was a **415 MB Kùzu single-file database**, but the Oxigraph backend
opens that path as a **directory-backed (RocksDB) store**. Startup crash-loops:

```
File ".../campy/brain/hippocampus/graph/oxigraph_client.py", line 821, in __init__
    Path(db_path).mkdir(parents=True, exist_ok=True, mode=0o700)
FileExistsError: [Errno 17] File exists: '/Users/djshelton/.campy/brain.db'
```

`mkdir(exist_ok=True)` suppresses the error only when the existing path is a *directory*;
against a regular file it still raises `FileExistsError`. So `campy start` reports
"started via launchd", the socket never appears, and `campy status` shows `offline` with
no actionable reason. The real cause is only visible by reading `~/.campy/daemon.log`.

This is not a data-corruption edge case — it is the **default state of every installed
user** carrying a pre-cutover `brain.db`. The code at `oxigraph_client.py:821` is correct
(Oxigraph stores are directories); the gap is that the cutover has **no handling for a
legacy on-disk Kùzu file at the store path**.

### Why B384 Phase 2C does not cover this

B384 Phase 2C says: *"Update `campy export-graph` and `campy import-graph` (B281) to
migrate legacy Kùzu JSONL dumps into the Oxigraph + sqlite-vec store."* That path assumes
the user **exported to JSONL while still running Kùzu**. It does not help the actual
population in the field:

- Upgrading the code flips the client to Oxigraph. `export-graph` now runs **through
  `OxigraphClient`**, which crashes on the same `mkdir` before it can read anything — so
  you cannot export the Kùzu data *after* upgrading.
- There is no offline Kùzu-reader migrator in the CLI (`campy --help` shows only
  `export-graph` / `import-graph` / `restore`, all Oxigraph-side).

Result: the legacy 415 MB graph is **stranded** — unreadable by current code — the moment
the user upgrades, and the daemon won't even boot.

### Verified (2026-09-09)

- `get_database_path()` → `runtime_dir()/"brain.db"` (`campy/paths.py:77`); the crash names
  exactly this path.
- `~/.campy/brain.db` was a 415 MB regular file (`file` → `data`), dated pre-cutover;
  `~/.campy/tables/` (887 `*.sqlite`) is B250 tabular datasets, unrelated to the graph.
- Non-destructive workaround that unblocked the daemon: rename the file aside
  (`brain.db` → `brain.db.kuzu-bak-<ts>`) and let Oxigraph create a fresh directory store.
  After that: `campy smoke` all-pass, `notify_turn` write lane `ok`, RocksDB store
  materialized (`CURRENT`/`MANIFEST`/`.sst`), `current_truth` executes live (no
  `DAEMON_OFFLINE` fallback). Fresh store only — the legacy graph is preserved in the
  backup but **not migrated**.

### Scope

1. **Fail loud, not cryptic (min-viable, ship first).** Before `OxigraphClient` calls
   `mkdir`, detect a non-directory at `db_path` and raise a clear, actionable error:
   what was found (a legacy Kùzu file), why it blocks startup, and the exact remediation
   (back it up / run the migrator). Surface it through `campy status` / `campy doctor`,
   not only `daemon.log`. This belongs to the B415/B416 environment-drift family.
2. **Automatic, non-destructive handling on startup.** When `db_path` is a legacy Kùzu
   file: move it aside to a timestamped backup and create the fresh store (what was done
   by hand here), emitting a one-line WARN and a pointer to migration — so a plain upgrade
   never hard-crashes. Guard must be idempotent and must never delete.
3. **Real Kùzu→Oxigraph data migrator (the actual fix for stranded data).** A path that
   reads a legacy Kùzu `brain.db` **without** the Oxigraph client and writes the
   engine-neutral JSONL that `import-graph` consumes (or writes the Oxigraph store
   directly). Decide whether this ships in-tree or as a one-shot upgrade script. Without
   it, B384 Phase 2C's promise is unmet for anyone who didn't pre-export.
4. **`doctor` check + upgrade note.** `campy doctor` should flag a legacy `brain.db`
   file and print the migration command; the release/upgrade notes must call it out.
5. **Cosmetic:** `campy smoke`'s check is still labelled "Kùzu Health" though it now
   exercises Oxigraph — rename to avoid masking exactly this class of confusion.

### Severity / ordering

P0 for item 1 (every upgrading user hits a cryptic hard-crash today) and item 2 (so an
upgrade self-heals). Item 3 is the substantive data-continuity fix and may be larger —
split into its own card if it grows, but it must not be dropped: "renamed aside" is a
smoke-test unblock, not data migration.
