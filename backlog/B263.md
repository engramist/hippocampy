# B263 - OpenClaw Adapter Activation

State: complete -- re-verified 2026-08-03: found and FIXED a real bug -- register_openclaw() registered an MCP server command (`python -m campy.cli.main mcp`) that does not exist (confirmed live: "No such command 'mcp'."), which would make OpenClaw's Campy connection fail at first real use; fixed to point at the actual working entrypoint (campy.adapters.mcp_server, same one every other adapter uses), added a regression test, also added a missing `campy doctor` OpenClaw check (AC3 was previously unimplemented) -- see Verification Findings
Priority: P2

Plan: backlog/plans/B-263-openclaw-adapter.md

### Problem

The OpenClaw plugin config exists at `extensions/hippocampy/openclaw.plugin.json` with `autoCapture: true` and `autoRecall: true`, but the adapter integration is incomplete. OpenClaw detection exists in `detect.py` but there's no `register_openclaw()` in `register.py`. The plugin config references a `brainUrl` but the actual MCP client connection isn't wired.

### What This Card Does

Completes the OpenClaw integration by:
1. Adding `register_openclaw()` to `register.py`
2. Implementing the `autoCapture` and `autoRecall` behavior based on plugin config
3. Wiring the OpenClaw plugin to connect to the Campy daemon

### Dependencies

- B255 complete (plugin installation path)
- B262 recommended (REST API simplifies OpenClaw integration)

### Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Connection method | REST API (`/api/v1/`) or MCP SSE | REST is simpler for OpenClaw's plugin system |
| autoCapture | POST each turn to `/api/v1/notify` | Same as notify_turn MCP tool |
| autoRecall | GET `/api/v1/recall` at session start | Returns recall context for prompt injection |
| Registration | Copy plugin config to OpenClaw's extensions dir | Standard OpenClaw plugin installation |

### Verification Findings (2026-08-03) — REAL BUG FOUND AND FIXED

**The bug:** `campy/cli/register_openclaw.py` registered this MCP server entry into `~/.openclaw/openclaw.json`:
```json
"campy-memory": {"command": "python", "args": ["-m", "campy.cli.main", "mcp"], ...}
```
But `campy.cli.main` has no `mcp` subcommand. Confirmed live:
```
$ PYTHONPATH=<worktree> .venv/bin/python -m campy.cli.main mcp
Error: No such command 'mcp'.
```
Had OpenClaw actually tried to spawn this command to talk to Campy, it would fail immediately — the entire OpenClaw integration was non-functional at the point of use, despite `register_openclaw()` "succeeding" and writing well-formed JSON (which is exactly why the existing test, which only checked `config["mcpServers"]["campy-memory"]["command"] == "python"`, never caught it).

**Corroborating evidence this isn't just theoretical:** running the (now-patched) `campy doctor` check against this actual machine's real `~/.openclaw/openclaw.json` showed OpenClaw already has a `campy-memory` entry registered from a prior real run — meaning this bug likely affected a real, previously-completed registration on the operator's own machine, not just a hypothetical.

**The fix (`campy/cli/register_openclaw.py`):** changed `args` to `["-m", "campy.adapters.mcp_server"]` — the real stdio MCP entrypoint, confirmed importable (`python -c "import campy.adapters.mcp_server"` succeeds) and used identically by every other working adapter (`campy/cli/register.py`: Claude Code line 151, VS Code line 335). Added a regression test, `test_register_openclaw_points_at_real_mcp_entrypoint` in `tests/cli/test_openclaw_adapter.py`, that registers into a temp config and asserts the resulting module path is actually importable — this would have caught the bug. Full suite re-run: `PYTHONPATH=<worktree> .venv/bin/python -m pytest tests/cli/test_openclaw_adapter.py -v` → **6/6 passed**.

**AC3 gap found and fixed:** `campy/cli/doctor.py`'s `_check_plugin_status()` had zero references to OpenClaw anywhere (verified via `grep -in openclaw campy/cli/doctor.py` → no matches) despite AC3 explicitly requiring it and despite Claude Code/Codex/VS Code/Gemini all already having their own branches in the exact same function. Added an OpenClaw branch following the established pattern (checks `~/.openclaw/openclaw.json` for a `campy-memory` entry in `mcpServers`). Verified live: `DoctorChecker._check_plugin_status()` now reports `"...OpenClaw; not installed: Claude Code"` correctly reflecting this machine's real state. `tests/cli/test_doctor_plugin.py` still passes (1/1) after the change.

**AC4/AC5 — not independently verifiable from this repo:** grepped the entire codebase for `autoCapture`/`autoRecall` usage — the only occurrences are the config schema defaults in `extensions/hippocampy/openclaw.plugin.json` itself and this card's own test file. Nothing in this repo *implements* auto-capture/auto-recall triggering logic; per the shipped MCP-server-registration design, that responsibility lives in OpenClaw's own runtime (an external, third-party host application not part of this codebase) — analogous to how B259's hooks depend on Claude Code's own hook-firing behavior. Cannot be verified without a real OpenClaw installation. Not treating this as a gap in Campy's own code, since the plugin.json config schema (which OpenClaw is expected to read) is present and correct (`autoCapture: true`, `autoRecall: true` defaults, confirmed by `tests/cli/test_recall_config.py::test_openclaw_plugin_config_valid` passing).
