# B102 — Local Graph Visibility UI Using Kuzu Explorer as the Base

- **State:** complete
- **Priority:** P2
- **Plan:** backlog/plans/B-102-local-graph-visibility-ui.md
- **Dependencies:** B92, B93, B94

## Problem Statement

We can now export richer ARC traces, but it is still hard to directly inspect what SideQuests is
actually writing into the graph during a run. Debugging graph-backed behavior from JSON alone is too
indirect. We need a local web UI that makes the live graph inspectable so we can verify concepts,
plans, lessons, action facts, path hypotheses, and their relationships directly.

This must remain an optional debugging install/workflow. It should not become part of the main
SideQuests runtime, default install path, or core product surface.

The user specifically wants this effort based on the official Kùzu Explorer project:
- [kuzudb/explorer](https://github.com/kuzudb/explorer)

## What It Does

Create a local graph-visibility workflow for SideQuests, using Kùzu Explorer as the starting point:

- launch a local browser UI against the active SideQuests Kùzu database
- prefer read-only access by default for debugging safety
- keep the entire workflow optional and isolated from the main SideQuests install/runtime
- document how to mount/open the SideQuests database locally
- provide a SideQuests-focused query starter pack for common inspections:
  - recent writes
  - plans and plan steps
  - lessons
  - hypotheses
  - ARC action facts and path hypotheses
- make it easy to inspect "what was written this step" during live ARC runs

## Acceptance Criteria

1. Add a documented local workflow that opens the SideQuests Kùzu database in Kùzu Explorer.
2. Default the debugging workflow to read-only mode unless explicitly overridden.
3. Add a SideQuests-specific query guide or starter queries for inspecting plans, lessons,
   hypotheses, and ARC-related artifacts.
4. Document the exact database path(s) and launch command(s) needed for this repo.
5. Include a verification step showing the explorer can open a real local SideQuests database from
   this project.
6. The card must stay at the app/tooling layer only; it should not require changing SideQuests core
   memory semantics just to visualize the graph.
7. The workflow must be documented as optional. It must not be wired into the default setup flow,
   package install, daemon startup, or core app UX.

## Outcome

We gain a practical optional local UI for inspecting the graph directly, so debugging stops
depending only on logs and exported JSON without expanding the main product surface.
