# B344 - Add Lightweight Continuous Memory Instrumentation to brain_daemon.py

State: ready
Priority: P1

Plan: none yet.

### Problem

B342's investigation into a live `brain_daemon.py` process's 99GB physical footprint required ad-hoc
forensics after the fact — `vmmap`, `lsof`, and log-reading — because the daemon has no built-in memory
instrumentation. This meant reconstructing what happened over 10+ hours of uptime from OS-level tools
that can describe the symptom (a big number) but not the cause (which Python objects are actually
accumulating). B343 is doing a one-off deep profiling pass to find the current root cause; this card is
about making the *next* occurrence — of this or any other memory issue — diagnosable in minutes instead
of requiring another ad-hoc investigation.

### What it does (scope)

1. Add a lightweight periodic memory-instrumentation log line, emitted alongside the existing
   `[Sweep] decayed=... errors=...` line in `brain_daemon.py`'s `_background_sweep()` (or on its own
   timer if that's cleaner — check whether reusing the sweep interval, default 300s per `campy.toml`'s
   `sweep_interval_seconds`, is a reasonable cadence, or whether memory logging should be more frequent
   given B342 showed multi-GB growth can happen well within a sweep interval).
2. At minimum, log: `len(gc.get_objects())` (cheap, always available, a good leak-trend indicator even
   without knowing *what* the objects are), and the process's RSS via `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss`
   (cheap, no subprocess needed, though note `ru_maxrss` is a *high-water mark* not current RSS on some
   platforms — check macOS/Linux semantics and document which one this actually reports in the log
   line's own text so a future reader isn't misled).
3. Gate a heavier, opt-in tier behind an env var (e.g. `CAMPY_MEMORY_DEBUG=1`) that additionally starts
   `tracemalloc` at daemon startup and periodically logs
   `tracemalloc.take_snapshot().statistics('lineno')[:10]` — this is the exact capability B343 needed
   and had to improvise; make it a standing, always-available opt-in instead of something reinvented
   per-investigation. Keep it opt-in (not default-on) since `tracemalloc` has real overhead.
4. Make sure whatever's added doesn't itself become a source of growth — e.g. don't accumulate a
   growing list of historical snapshots in memory; log and discard, or cap at a small fixed history if
   trend-over-time is valuable.
5. Add a test verifying the log line's format/presence (e.g. run a short-lived sweep cycle in a test
   harness and assert the memory log line appears with the expected fields) — doesn't need to assert on
   actual memory values, just that the instrumentation fires and doesn't crash the sweep loop if e.g.
   `tracemalloc` isn't started.

### Dependencies

Coordinate with B343 if that investigation is still in progress or already added temporary
instrumentation — don't duplicate; either B343's temporary hook becomes this card's permanent one
(preferred, avoids double work), or this card supersedes whatever B343 added temporarily. Check
`backlog/B343.md`'s Outcome section before starting.

### Files to create/modify

- `brain_daemon.py` (top-level — confirmed the one actually running; see B345 for the
  two-files ambiguity, don't silently instrument the wrong copy).
- `campy.toml` — new config keys if the interval/toggle should be configurable rather than hardcoded
  (e.g. `[memory_debug] enabled`, `[memory_debug] interval_seconds`).
- A test file covering the new logging (check `tests/` for where `brain_daemon.py`-level behavior is
  currently tested, if anywhere — this may be new test coverage).

### Acceptance Criteria

- [ ] A memory-stats log line (object count + RSS/footprint proxy) is emitted periodically without
      requiring any external tooling to be attached.
- [ ] An opt-in `tracemalloc`-based deeper tier exists, gated behind an explicit env var or config flag,
      default off.
- [ ] The instrumentation itself is verified not to grow unboundedly over a long-running test (or a
      documented cap exists).
- [ ] A test proves the logging fires and the sweep loop survives even if the opt-in tier is disabled.
- [ ] No regression to existing sweep-loop behavior/tests.
