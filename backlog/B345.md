# B345 - Resolve the Two brain_daemon.py Files (Top-Level vs campy/brain_daemon.py)

State: ready
Priority: P1

Plan: none yet.

### Problem

B342's investigation confirmed two different `brain_daemon.py` files exist in this repo:

- The **top-level** `brain_daemon.py` (repo root) — confirmed, via the live process's own command
  line (`ps aux`), to be **the one actually running in production** on the investigating machine.
- `campy/brain_daemon.py` — a **different file**: different size (32,844 bytes vs 22,954 bytes as of
  2026-08-21), different module docstring ("HippoCampy Daemon" vs "HippoCampy Brain Daemon" — confirm
  current exact wording, may have changed).

This is a real hygiene risk, independent of the B311/B342 memory investigations: B337's checkpoint fix
this session touched the **top-level** file specifically (confirmed via that PR's diffstat). If anyone
edits `campy/brain_daemon.py` believing it's the live daemon — a reasonable assumption given this
project's `campy/` package structure and the in-progress "anatomy refactor" migration
(`docs/codebase-anatomy-refactor-plan.md`) — those changes would silently not affect what's actually
running, or vice versa: someone editing the top-level file for a "temporary/legacy" reason might not
realize it's the one in production.

### What it does (scope)

1. Diff the two files in full (`diff brain_daemon.py campy/brain_daemon.py`) to understand the actual
   scope of divergence — is `campy/brain_daemon.py` a superset (in-progress migration target with more
   features not yet cut over), a subset (older/pared-down), or genuinely parallel/forked
   implementations that have drifted independently?
2. Check git history for both files (`git log --follow -- brain_daemon.py` and
   `git log --follow -- campy/brain_daemon.py`) to understand which one is the "original" and which was
   introduced later, and why — check for any backlog card or commit message explaining the intended
   relationship (search for "anatomy" or "migration" in commit messages touching either file).
3. Check whether anything in the codebase actually imports/uses `campy/brain_daemon.py` (grep for
   `from campy.brain_daemon import` or `import campy.brain_daemon` across the repo, including
   `pyproject.toml`'s entry points, any `__main__`-style invocation, tests, and CI workflows) — if
   nothing references it, it's very likely genuinely dead code from an incomplete migration.
4. Based on findings, do ONE of:
   - **If `campy/brain_daemon.py` is dead/unused:** delete it, and add a brief note to
     `docs/codebase-anatomy-refactor-plan.md` (or wherever the migration is tracked) recording that this
     particular file was never actually cut over and has been removed rather than left as silent drift.
   - **If `campy/brain_daemon.py` is the intended future/migration target but genuinely incomplete:**
     do not delete it, but add a prominent module-level comment/docstring making unambiguous which file
     is currently live (the top-level one) so a future editor doesn't get confused, and file a follow-up
     card for completing the migration if one doesn't already exist (check first — this may already be
     tracked under the broader anatomy-refactor cards).
   - **If both are genuinely live in different deployment contexts** (e.g. one is used by the pip
     package's entry point, the other by a local dev/launchd setup) — document that explicitly, since
     it's a legitimate but easily-forgotten fact that needs to be discoverable, not just correct.
5. Whichever outcome: make sure the actually-live file has an accurate, non-misleading module docstring
   and that this investigation's finding is recorded somewhere durable (this card's Outcome section at
   minimum).

### Dependencies

None, but coordinate loosely with B343/B344 if they're in flight — both of those cards need to know

should become canonical going forward), flag that back to whoever's working B343/B344.

      (`pytest tests/ -k brain_daemon` or equivalent — check for existing coverage first).
- [ ] The live/canonical file's own docstring accurately reflects its status after this card lands.
