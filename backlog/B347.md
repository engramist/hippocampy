# B347 - Bounded Restart Policy for brain_daemon.py (Interim Mitigation for Unbounded Footprint Growth)

State: complete
Priority: P2

Plan: none yet.

### Problem

B342 found a live `brain_daemon.py` process at a 99GB physical footprint after roughly 10 hours of
uptime, degrading a core feature (`ask`). B343 is investigating the actual root cause, but root-causing
and fixing a real leak can take multiple rounds (see B311's own 6-round history for a comparable
investigation). In the meantime, this daemon is meant to run persistently on a user's machine — there is
currently no bound on how large it's allowed to grow before something goes wrong.

This mirrors a pattern already solved once in this exact codebase's own ecosystem: the disclosure note
exchanged with a prospective integrator (see project history/memory around the VibeGuide build-worker
OOM) describes fixing an analogous problem primarily by *bounding the work* — not by finding and fixing
every possible leak source first, but by making sure no single failure mode could grow unbounded while
the real fix was still in progress. A scheduled/bounded restart is the daemon-level equivalent: cheap,
immediately effective, and orthogonal to whatever B343 eventually finds.

### What it does (scope)

This is explicitly an interim mitigation, not a substitute for B343's root-cause work — say so in the
outcome, don't let this card get treated as "solved" once merged.

1. Determine how `brain_daemon.py` is currently supervised on the reference deployment (B342's
   diagnostic found it's `launchd`-managed on macOS — check for a `.plist` file, likely under
   `~/Library/LaunchAgents/` or similar, and check `docs/` for any Linux/systemd equivalent for other
   platforms this project supports).
2. Add a bounded-lifetime mechanism appropriate to the supervisor in use:
   - For `launchd`: investigate `StartInterval` (periodic restart) or a `KeepAlive` +
     resource-limit-triggered-exit approach. A clean, graceful self-restart (the daemon exits itself on
     a schedule and lets the supervisor relaunch it) is preferable to an external force-kill, since it
     lets in-flight requests drain first — check whether `brain_daemon.py` already has a graceful
     shutdown path (SIGTERM handling) to hook into; if not, that itself may need a small addition.
   - For systemd (if applicable): `RuntimeMaxSec` in the unit file achieves the same thing more directly.
3. Make the interval configurable (e.g. `campy.toml`'s `[server]` section, or wherever daemon-level
   config already lives) rather than hardcoded, with a sane default — consider daily (low disruption,
   bounds worst-case growth to well under what B342 observed) as a starting point, not a rigorously
   tuned value; note in the outcome that the specific interval is a judgment call, not derived from
   measurement, and can be revisited.
4. Make sure a scheduled restart doesn't silently drop in-flight work: check whether pending writes,
   the background sweep, or active MCP connections need graceful-shutdown handling before this is safe
   to enable by default. If graceful shutdown isn't already robust, that's a prerequisite, not optional
   — a restart policy that corrupts in-flight state is worse than the problem it's solving.
5. Document the restart policy clearly (in `docs/` and/or `campy.toml`'s own comments) so it's not a
   silent surprise to anyone debugging "why did the daemon restart" later — this is exactly the kind of
   thing that becomes a confusing mystery without a comment pointing back to this card.

### Dependencies

None blocking, but this is explicitly a stopgap — B343 (root cause) is the real fix and should not be
deprioritized just because this interim mitigation exists. If B343 lands a real fix first, this card's
restart interval can likely be relaxed or removed; note that possibility in the outcome either way.

### Files to create/modify

- Supervisor config (launchd `.plist` or systemd unit file — locate via `docs/` install instructions or
  `scripts/install.sh`).
- `campy.toml` — new config key for the interval if made configurable at the app level rather than
  purely at the supervisor level.
- `brain_daemon.py` — only if graceful-shutdown handling needs strengthening as a prerequisite (item 4).
- `docs/` — document the policy.

### Acceptance Criteria

- [ ] A bounded-restart mechanism is in place and verified to actually trigger (test with a short
      interval first, e.g. restart every 5 minutes in a throwaway local test, confirm the daemon
      actually cycles and comes back healthy, before setting the real default interval).
- [ ] Graceful shutdown is confirmed not to drop in-flight writes or corrupt state — verified by
      triggering a restart mid-write in a test and confirming data integrity after.
- [ ] The restart interval is documented, both in code/config comments and in user-facing docs.
- [ ] This card's outcome explicitly states it's an interim mitigation, references B343, and notes
      whether/how the policy should change once root cause is known.

### Outcome

Closed 2026-08-26 as part of an audit of B342-era cards. `_periodic_restart` (B342, now in
`campy/brain_daemon.py` since B365's port) is exactly this card's ask: a graceful, self-triggered
restart (`self.shutdown()`, which lets launchd's `KeepAlive` relaunch), configurable via
`[daemon] restart_interval_hours` in `campy.toml` (default 24h, ±10% jitter), documented both in
`campy.toml`'s own comments and `docs/ARCHITECTURE.md`.

Checked against each acceptance criterion:
- Mechanism exists and triggers: yes, tested (`test_periodic_restart_calls_shutdown_after_interval`,
  `test_periodic_restart_applies_jitter`).
- Interval documented in code/config and user-facing docs: yes, both.
- Outcome states this is an interim mitigation referencing the root-cause card: B342 (not B343 as
  this card names — B343 never independently root-caused anything; B342 itself found the answer) —
  the restart policy remains valuable regardless: B342 concluded the growth is real OS-level
  behavior under memory pressure, not something a code fix eliminates, so the bounded-restart safety
  net stays warranted rather than becoming obsolete once "root cause" landed.
- Graceful shutdown confirmed not to drop committed data: partially gapped until today — no test
  verified this. Added `test_committed_write_survives_close_without_explicit_checkpoint` in
  `tests/test_manual_checkpoint.py`: a literal "mid-write" (started-but-uncommitted) scenario doesn't
  exist in this architecture to test (every `execute_write()` call is already a fully-committed,
  independent transaction by the time it returns — see `backlog/B311.md`), so the test proves the
  narrower, actually-relevant claim instead: a write committed before `KuzuClient.close()` (which
  does `del self.conn; del self.db`, no explicit `CHECKPOINT`) is still visible to a freshly-opened
  client on the same path afterward. Passes.
