Campy Activity Indicator — Architecture Approaches

A lightweight status API with three presentation surfaces: menu bar, CLI, web widget

A

SSE Event Stream (Recommended)

Add a GET /api/v1/activity/stream SSE endpoint to the existing daemon. Emits phase transitions as real-time events. All consumers (menu bar, CLI, web widget) subscribe to the same stream.

Pros

  • Real-time — phase changes push instantly
  • Single source of truth — daemon already knows its own state
  • SSE infrastructure already exists (MCP transport uses it)
  • Multiple consumers can subscribe simultaneously
  • No polling, no file watching, no extra processes

Cons

  • SSE connection per consumer (trivial overhead)
  • Consumers need reconnect logic if daemon restarts
B

Polling Status Endpoint

Add a GET /api/v1/heartbeat that returns current phase + last activity timestamp. Consumers poll every 1-2 seconds.

Pros

  • Simpler to implement — just a JSON endpoint
  • Stateless — no connection management
  • Easy to test with curl

Cons

  • 1-2s latency on phase changes
  • Constant polling even when idle
  • N consumers × 1 req/sec = unnecessary load
C

File-Based Status (activity.log watch)

Consumers tail ~/.campy/activity.log directly. No new API needed — just parse the existing log stream.

Pros

  • Zero daemon changes — data already exists
  • Works even if HTTP server is down (file persists)

Cons

  • Log parsing is fragile (format changes break consumers)
  • No structured phase state — must infer from events
  • File I/O + inotify/kqueue per consumer
  • Can't determine "idle" — only "last event was N seconds ago"
